# Typed site rules escape nine servers' traps

The proposal is right on the points that matter most, and the evidence for them is unusually consistent. Every major server that applied headers only to successful answers, let a nested block silently drop inherited fields, or appended its value next to the application's has since added an opt-in fix. nginx added `always` in 2014 and `add_header_inherit merge` in October 2025, Apache has its `always` table, HAProxy its `http-after-response`, Caddy its deferred `>`. Administrators still pay for the old defaults, in questions with hundreds of thousands of views. The evidence points to one typed rule set that reaches every answer and has three verbs: `set` replaces the application's field, `default` fills the field only when it is absent (only Apache, Caddy and h2o offer this), and `remove` deletes it. Rules match exact paths or whole-segment prefixes, with no regex and no variables. The redirect status is mandatory, because the servers' defaults disagree: 302, 301, 307/308, or chosen by method. Five things need to change before the feature ships:

1. Resolve each field by the longest matching rule that names it, instead of running the rules in sequence. Otherwise a deeper `default` does nothing under a shallower `set`.
2. Give rules a success-only scope for cache lifetimes. "Every answer" otherwise stamps a year-long `immutable` on 404s, an outcome reported on Caddy.
3. Send a bounded `Cache-Control` on 301 and 308 by default, because Chromium still caches them forever.
4. Write every byte of `Location` with agensio's own encoder and check the result. Joins that produced `//host` or `/\host` caused open redirects in Django, Tomcat, fastify-static, Astro and the MCP Registry.
5. Rename `[[site.redirect]]`, which collides with the existing `redirect = "https"` site key.

A test of the alpha.72 binary, with a reading of its code, shows why the feature is needed now. Today's `add_headers` repeats nginx's two worst traps, so a managed site's `hsts: true` reaches neither the answers its front controller produces nor its error pages.

## Nine servers lose headers in the same three ways

Response header handling fails in three ways that recur from server to server:

- **Fields vanish** when a more specific block defines fields of its own.
- **Fields are missing from error answers.**
- **Fields duplicate the application's** when the server appends instead of replacing.

Each server's design is a different mix of the three. The fixes they shipped later all point toward the same model.

**nginx** is the reference case for the first two. `add_header` directives "are inherited from the previous configuration level if and only if there are no `add_header` directives defined on the current level". Without `always`, a field is added only on 200, 201, 204, 206, 301, 302, 303, 304, 307 and 308 ([ngx_http_headers_module](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header)). `always` arrived in 1.7.5 in 2014. Mainline 1.29.3, released on 28 October 2025, added `add_header_inherit on | off | merge`, with the old behaviour still the default ([nginx CHANGES](https://nginx.org/en/CHANGES)). The fork Angie declined that directive as "poor design" ([Angie](https://en.angie.software/angie/docs/configuration/nginx-unsupported-directives/)). The generic handler always appends, even when the upstream sent the same field. Only Cache-Control and Link are chained as lists, and only ETag and Last-Modified are replaced ([source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)). So replacing an application's field takes two directives, `proxy_hide_header` or `fastcgi_hide_header` followed by `add_header`. There is no "only if absent" primitive at all. Stock nginx also cannot remove its own `Server` field: `server_tokens off` still sends `Server: nginx`, and an empty value is a commercial-subscription feature ([core module](https://nginx.org/en/docs/http/ngx_http_core_module.html#server_tokens)). Header rules are read from the location the request is in when headers are sent. After `error_page` or `try_files` has moved the request, that is a different location from the one the administrator configured. The third-party **headers-more** module fixes most of this. `more_set_headers` "replaces (if any) or adds", applies "to all the status codes" by default, merges parent commands before child ones, and `more_clear_headers` accepts `*` wildcards ([README](https://github.com/openresty/headers-more-nginx-module)). It is not in the nginx source, and its README was last tested against 1.29.2.

**Apache httpd** offers the widest vocabulary: `set`, `append`, `merge`, `add`, `setifempty`, `unset`, `edit`, `echo` and `note`. It undermines that vocabulary by storing headers in two tables. Plain `Header` works on the `onsuccess` table. CGI and `mod_proxy_fcgi`, which means PHP-FPM, put the application's fields in the `always` table, and locally generated errors and redirects send only that table. The manual's own example: a PHP backend sends `X-Foo: bar`, and `Header set X-Foo baz` ends up "having the header duplicated with both values". The documented fix is `Header onsuccess unset X-Foo` followed by `Header always set X-Foo "baz"` ([mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)). The same PHP code behaves differently under mod_php, which writes to the other table. Section merging also differs by type. `<Directory>` sections apply shortest path first, so the child wins, but `<Location>` sections apply in file order, so a `<Location "/">` placed after `<Location "/admin">` overrides it ([sections](https://httpd.apache.org/docs/2.4/sections.html#merging)). `Server` cannot be removed at all: `ServerTokens Prod` still sends `Server: Apache`, and the setting is server-wide ([core](https://httpd.apache.org/docs/2.4/mod/core.html#servertokens)). Two security bugs come from header values derived from requests. CVE-2024-43204 is an SSRF through a request-derived Content-Type, fixed in 2.4.64. CVE-2026-43951 is an out-of-bounds read in `merge_response_headers` ([CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)).

**Caddy** has the right operations under confusing timing rules:

- The verbs are set, `+` add, `-` delete with wildcards, `?` default, `>` deferred set, and regex replace.
- A plain set runs before the response exists, and `reverse_proxy` then *adds* the upstream's values. A Caddy setting plus an upstream setting therefore yields duplicate `Server` or `Cache-Control` fields ([Caddy community](https://caddy.community/t/repeated-server-header/24830), [thread 8146](https://caddy.community/t/header-directive-is-not-mutually-exclusive/8146)).
- Deferred operations do replace the upstream's values, but they are lost when a later handler returns an error. Issue #6689 showed a deleted field reappearing on a `file_server` 404. It was closed as working as intended, with a pointer to `handle_errors` ([caddy #6689](https://github.com/caddyserver/caddy/issues/6689)).
- Directives are sorted most specific first, so with immediate sets the *general* rule runs last and wins. The maintainers reversed this for `vars` because "the most specific matcher should be evaluated last", but not for `header` ([sorting algorithm](https://caddyserver.com/docs/caddyfile/directives#sorting-algorithm)).

**Traefik** and **HAProxy** each fixed one axis and left another. Traefik's `customResponseHeaders` run after the backend answers and overwrite its fields, and an empty value deletes. There is no add and no default, though HSTS, frame options and CORS exist as typed fields ([headers middleware](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/headers/)). But the middleware on the outer entry point has the last word. A router-level CSP cannot override an entry-point one, which a maintainer confirmed in 2025 ([traefik #12195](https://github.com/traefik/traefik/issues/12195)). HAProxy's `set-header` removes the field and then adds it. `http-response` rules see only server responses, and `http-after-response`, added in 2.2, sees all of them, HAProxy's own redirects and errors included. Errors from the early multiplexer stage are the exception ([manual](https://docs.haproxy.org/3.4/configuration.html#4.2-http-after-response)). Backend rules run before frontend rules, so again the broader rule wins.

**OpenLiteSpeed, h2o and IIS** complete the picture:

- **OpenLiteSpeed** uses Apache's syntax (`set`, `append`, `merge`, `add`, `unset`) per context. Contexts inherit down the URI tree unless the child says `NONE`. There is no only-if-absent verb. `Header` lines in `.htaccess` are ignored, because OpenLiteSpeed reads only rewrite rules there ([OLS manual](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/Static_Context.html), [docs](https://docs.openlitespeed.org/config/rewriterules/)). A server-level "Server Signature" setting can hide the whole `Server` field ([Server General](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/ServGeneral_Help.html)). **LiteSpeed Enterprise** instead reads Apache's configuration and `.htaccess`, mod_headers included, except `Header edit`; its own `ForceSecureCookie` replaces the usual `Header edit Set-Cookie` recipe ([LiteSpeed docs](https://docs.litespeedtech.com/lsws/configuration/)).
- **h2o** is the closest existing match to agensio's proposal. Its verbs include `header.set`, `header.setifempty` and `header.unset`. They run as an output filter on every answer, proxied, FastCGI and h2o's own errors alike, but not on broken requests. The configurator refuses `Connection`, `Content-Length`, `Transfer-Encoding`, `Date` and `Server` with "the named header cannot be rewritten" ([docs](https://h2o.examp1e.net/configure/headers_directives.html), [headers.c](https://github.com/h2o/h2o/blob/master/lib/handler/headers.c)). Its one weakness here is that only the single longest `paths:` entry applies, so sibling prefixes never combine ([config.c](https://github.com/h2o/h2o/blob/master/lib/core/config.c)).
- **IIS** spreads the job over three mechanisms. `customHeaders` only adds, "in every response", and cannot replace or remove the application's field. Removing `Server` needs `removeServerHeader`, which exists only from Windows 1709. Everything else needs URL Rewrite outbound rules ([customHeaders](https://learn.microsoft.com/en-us/iis/configuration/system.webserver/httpprotocol/customheaders/), [requestFiltering](https://learn.microsoft.com/en-us/iis/configuration/system.webserver/security/requestfiltering/)).

| Server | Replaces the application's field | Only if absent | Reaches error answers | Nested levels combine | Server field |
|---|---|---|---|---|---|
| nginx | Only with `*_hide_header` + `add_header` | No (map idiom on upstream fields) | Only with `always` | Child replaces parent; `merge` opt-in since 1.29.3 | Name cannot be removed |
| nginx + headers-more | Yes | No | Yes by default | Parent then child | Clearable (README ambiguous) |
| Apache | Only in the right table (`always` for PHP-FPM) | `setifempty` (Content-Type caveat) | `always` table only | Directory shortest-first, Location in file order | Cannot be removed |
| Caddy | Only deferred `>` or `header_down` | `?` | Deferred operations lost on errors | Immediate sets: general wins | Upstream's passes, Caddy adds Via |
| Traefik | Yes | No | Downstream of the middleware only | Entry point wins | n/a |
| HAProxy | `set-header` | Condition idiom | `http-after-response` only | Frontend after backend | `set-header` |
| OpenLiteSpeed | `set` | No | Likely (shared send path, untested) | Context tree, `NONE` opt-out | Server-level switch |
| h2o | Yes | `setifempty` | Yes, except broken requests | Longest path only, plus global and host | Refused |
| IIS | No (`customHeaders` adds) | No | "Every response" (errors unverified) | Collection add/remove/clear | `removeServerHeader` (IIS 10) |

The designs that hold up best (h2o, headers-more, OpenLiteSpeed's context tree, Apache's `<Directory>` order) share three traits. They apply rules at one point, as the answer leaves. They replace rather than append. They let the more specific rule decide. agensio's proposal has all three, and it combines sibling prefixes, which h2o does not.

## Redirect defaults disagree on every axis that matters

No two products agree on what a redirect does when the administrator does not say. That is the strongest argument for a required status and for stating the remainder and query rules once.

| Server or platform | Default status | Prefix remainder | Query | Runs before access and auth |
|---|---|---|---|---|
| nginx `return` / `rewrite` | 302; `permanent` 301 | Needs regex captures | `rewrite` appends; `return` only with `$request_uri` | Yes (rewrite phase precedes ACCESS) |
| Apache `Redirect` | 302 | Yes, whole segments, re-escaped | Kept unless the target has `?` | Server/vhost: yes; `.htaccess`/`<Directory>`: no |
| Caddy `redir` | 302 | No (`{uri}` is the whole path) | Dropped unless `{uri}` | Yes (before `basic_auth`) |
| Traefik redirectRegex | 302/307 by method; `permanent` 301/308 | Through regex | Inside the matched text | Chain order decides |
| HAProxy `redirect` | 302 | `prefix` prepends the whole URI | `location` keeps it only with `keep-query` (3.1+) | Legacy `redirect` runs after `http-request auth` |
| OpenLiteSpeed Redirect context | 302 for an absolute target; internal for `/` | Yes | Kept unless the target has `?` | Yes (source reading) |
| h2o `redirect` | 302 scalar; required in mapping form | Always (normalised, re-escaped) | Always | Probably not (unverified) |
| IIS httpRedirect / URL Rewrite | 302 / 301 (secondary source) | Yes unless `exactDestination` / back-references | Unstated / appended | After auth / before auth |
| Netlify, Cloudflare bulk, WP Engine | 301 | Splat / subpath flag / regex | Passed / dropped by default / appended | Platform-defined |
| Vercel | 307/308 | Patterns | Config passes; bulk drops by default | Platform-defined |

Sources: [nginx rewrite](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html), [Apache mod_alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect), [Caddy redir](https://caddyserver.com/docs/caddyfile/directives/redir), [Traefik redirect.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/redirect/redirect.go), [HAProxy redirect](https://docs.haproxy.org/3.4/configuration.html#4.2-redirect), [OLS httpreq.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpreq.cpp), [h2o redirect.c](https://github.com/h2o/h2o/blob/master/lib/handler/configurator/redirect.c), [IIS httpRedirect](https://learn.microsoft.com/en-us/iis/configuration/system.webserver/httpredirect/), [URL Rewrite reference](https://learn.microsoft.com/en-us/iis/extensions/url-rewrite-module/url-rewrite-module-configuration-reference), [SecureAuth KB](https://support.secureauth.com/hc/en-us/articles/360035997852), [Netlify](https://docs.netlify.com/routing/redirects/), [Cloudflare bulk parameters](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/parameters/), [WP Engine](https://wpengine.com/support/redirect/), [Vercel bulk](https://vercel.com/docs/routing/redirects/bulk-redirects).

**The typed prefix redirects are the ones vendors themselves recommend.** Apache calls mod_rewrite "a last resort" and points to `Redirect` because it "preserves path information" ([avoid mod_rewrite](https://httpd.apache.org/docs/2.4/rewrite/avoid.html)). NGINX's blog tells users to prefer `return` over `rewrite` ([NGINX blog](https://blog.nginx.org/blog/creating-nginx-rewrite-rules)). OpenLiteSpeed's Redirect context, h2o's `redirect` and Cloudflare's bulk rows with `subpath_matching` and `preserve_path_suffix` all express "prefix plus kept remainder" as data rather than as a pattern. These typed forms still have sharp edges:

- Apache concatenates the remainder blindly. Its source builds the target plus the re-escaped remainder, so `Redirect /one/ http://x/two` sends `/one/a` to `http://x/twoa` ([mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c)). h2o, by contrast, inserts or drops a slash at the join ([util.c](https://github.com/h2o/h2o/blob/master/lib/core/util.c)).
- Within one Apache context the first match in file order wins, so "you must list the most specific path first".
- Traefik's `PathPrefix(`/products`)` matches `/products-for-sale` ([rules](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/rules-and-priority/)).
- IIS's `httpRedirect` is inherited by every child folder. A site-wide redirect therefore loops inside its own target unless `childOnly` is set, and Microsoft's description of that switch contradicts the IIS team's own explanation of it ([IIS team blog](https://blogs.iis.net/ksingla/client-side-redirection-using-httpredirection-module)).

**Order against authentication splits the field.** nginx runs `return` and `rewrite` before the access phase, and the mailing list explains that "the order of directives as written in nginx conf is not important": a `return` inside an `auth_basic` location never asks for a password ([nginx list, 2016](https://mailman.nginx.org/pipermail/nginx/2016-November/052313.html)). Caddy sorts `redir` before `basic_auth`. OpenLiteSpeed returns a Redirect context's answer before its `HSPS_CHECK_AUTH_ACCESS` state, even though the same context offers Realm and Require settings ([httpsession.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpsession.cpp)). Apache does both, depending on where the line is written. A vhost `Redirect` runs in translate_name, before authentication. The same line in `.htaccess` runs in fixups, after it ([request.c](https://github.com/apache/httpd/blob/2.4.x/server/request.c)). By a reading of the source, Apache's documentation and its code even disagree on how `.htaccess` Redirect and RewriteRule are ordered against each other ([rewrite tech](https://httpd.apache.org/docs/2.4/rewrite/tech.html), [mod_rewrite.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_rewrite.c)). agensio's choice to check redirects before access and auth matches the majority and Apache's recommended placement. The cost is that a moved path discloses its target without authentication.

**Regex is where the redirect security bugs live.** In 2026, nginx shipped three heap-overflow fixes in this area. CVE-2026-42945 (1.31.0) concerns a crafted request in the rewrite module, CVE-2026-9256 (1.31.1) overlapping rewrite captures, and CVE-2026-42533 (1.31.3) map regex captures ([CHANGES](https://nginx.org/en/CHANGES)). Apache's mod_rewrite produced CVE-2019-10098 (encoded newlines in self-referential redirects) and CVE-2020-1927 (open redirect). In 2024, CVE-2024-38474 changed what existing rules do ([Apache vulnerabilities](https://httpd.apache.org/security/vulnerabilities_24.html)). Building `Location` from nginx's decoded `$uri` allows CRLF injection. Gixy and Acunetix flag it, and Detectify found the pattern common in about 50,000 nginx configurations from GitHub ([Detectify](https://blog.detectify.com/2020/11/10/common-nginx-misconfigurations/), [Acunetix](https://www.acunetix.com/vulnerabilities/web/nginx-redirect-header-injection/)).

**Scale favours exact tables, not rule lists.** nginx's exact-key `map` is a hash with at most two memory accesses when a bucket fits a cache line ([hash docs](https://nginx.org/en/docs/hash.html)). HAProxy stores exact map keys in a tree and, in current source, prefix keys in a longest-prefix tree ([pattern.c](https://github.com/haproxy/haproxy/blob/master/src/pattern.c)). A user measured "negligible" difference between 0, 10,000 and 100,000 redirect entries, and the maintainer answered "that is the use-case for map files" ([HAProxy discourse](https://discourse.haproxy.org/t/any-issues-with-large-map-files/7279)). The opposite patterns are Caddy's `map`, which scans its entries linearly ([map.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/map/map.go)), Traefik's regex evaluated per middleware, and Apache's `.htaccess`, which costs extra filesystem lookups on every request "whether or not you actually even use them" ([.htaccess howto](https://httpd.apache.org/docs/2.4/howto/htaccess.html)).

## Administrators lose hours to silent defaults and praise predictable tools

The complaint record is large and points one way. A caveat on reading it: Stack Exchange votes accumulate over time, so the most-voted questions date from 2009 to 2017. Newer reports repeat the same problems at smaller counts.

**Headers that vanish.** "nginx add_header not working" has 90 votes and 176,126 views. The top answer says "nginx only processes the last add_header it spots down a tree". The poster's headers in `location /` were also lost because `try_files` moved the request into the `\.php$` location ([SO 18450310](https://stackoverflow.com/questions/18450310/nginx-add-header-not-working)). Arch Linux's infrastructure carries a merge request titled "Fix missing HSTS header for some URLs due to nginx 'directive inheritance'" ([Arch MR 859](https://gitlab.archlinux.org/archlinux/infrastructure/-/merge_requests/859)). Gixy, the nginx configuration linter, has a check for this trap alone ([gixy](https://gixy.getpagespeed.com/checks/add-header-redefinition/)).

**Headers missing on errors.** "Nginx add_header for a 50* page" has 18,351 views. Its most-voted answer (73 votes) is simply "Since Nginx 1.7.5 you can use always" ([SF 418709](https://serverfault.com/questions/418709/nginx-add-header-for-a-50-page)). CORS headers vanished when `try_files` fell through ([SF 785251](https://serverfault.com/questions/785251/nginx-location-block-add-header-not-working-when-try-files-exists)). nginx closed a Drupal user's ticket about missing headers on 404s as invalid, with the remark that `add_header` "is not expected to add headers to such responses" ([trac #1122](https://trac.nginx.org/nginx/ticket/1122)).

**Duplicates.** The headline example is "How do I remove a server-added header from proxied location?" (160,154 views). Its fix: `add_header` "will stack the values", so use `proxy_hide_header` and then `add_header ... always` ([SF 928912](https://serverfault.com/questions/928912/how-do-i-remove-a-server-added-header-from-proxied-location)). Further reports:

- **Browser errors from two ACAO values.** "The 'Access-Control-Allow-Origin' header contains multiple values" has 474,030 views ([SO 22343384](https://stackoverflow.com/questions/22343384/the-access-control-allow-origin-header-contains-multiple-values)). A Plesk KB article reportedly lists three places in one Plesk site that can set the field (search summary) ([Plesk KB](https://support.plesk.com/hc/en-us/articles/12377315860631-Error-in-browser-console-on-website-that-requests-content-from-another-website-hosted-on-Plesk-for-Linux-server-The-Access-Control-Allow-Origin-header-contains-multiple-values-but-only-one-is-allowed)).
- **Two HSTS fields from platform plus application.** Netlify's default HSTS plus a user's own produced two lines and broke the preload requirement ([Netlify answers](https://answers.netlify.com/t/define-strict-transport-security-header-cause-duplicate-headers/28179)). HestiaCP's HSTS toggle plus Drupal's Seckit module did the same, and securityheaders.com flagged it ([HestiaCP forum](https://forum.hestiacp.com/t/solved-strict-transport-security-in-doble-declaration/12283)).
- **Conflicting X-Frame-Options.** Safari reported `X-Frame-Options: SAMEORIGIN, SAMEORIGIN` as conflicting ([Roots discourse](https://discourse.roots.io/t/safari-conflicting-multiple-x-frame-options/10077)).

The opposite need is real too. A Kirby site behind Caddy sent `Cache-Control: public,max-age=31536000,immutable` on `/media/` answers "even when they were 404s". The maintainer could only suggest a `handle_response` matcher inside `php_fastcgi` ([Caddy community 26158](https://caddy.community/t/header-only-on-successful-response/26158)).

**Security headers that outlive the configuration.** HSTS is the field administrators most regret. Removing it from the configuration "doesn't remove the policy from the cache"; the cure is `max-age=0` and waiting ([SF 1011861](https://serverfault.com/questions/1011861/how-to-disable-hsts-header-in-apache-2-4)). Sending it over plain HTTP is common enough that "How to set HSTS header from .htaccess only on HTTPS" has 100,387 views ([SO 24144552](https://stackoverflow.com/questions/24144552/how-to-set-hsts-header-from-htaccess-only-on-https)). Chromium's preload removal batches record `includeSubDomains` "added by mistake", and subdomains CNAMEd to third-party services without certificates (search summary) ([Chromium CL 2306423004](https://codereview.chromium.org/2306423004)).

The Web Almanac 2024 gives the deployment picture ([Web Almanac 2024](https://almanac.httparchive.org/en/2024/security)):

- **CSP** is on 19 % of hosts, and **91 % of policies keep `unsafe-inline`**. "Refused to load the script because it violates the following Content Security Policy directive" has 1,087,437 views ([SO 31211359](https://stackoverflow.com/questions/31211359/refused-to-load-the-script-because-it-violates-the-following-content-security-po)).
- **X-Frame-Options** still carries the ignored `ALLOW-FROM` on 0.6 % of desktop hosts that send XFO.

**CORS** produces the largest questions of the whole topic:

- "Response to preflight request doesn't pass access control check" has 2,566,021 views ([SO 35588699](https://stackoverflow.com/questions/35588699/response-to-preflight-request-doesnt-pass-access-control-check-no-access-con)).
- "Access-Control-Allow-Origin Multiple Origin Domains?" has 1,304,026 views ([SO 1653308](https://stackoverflow.com/questions/1653308/access-control-allow-origin-multiple-origin-domains)). The answer is impossible with a static header: MDN says the server "must return the origin for the specific client" and add `Vary: Origin` ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Origin)).

Scanners drive most of this work. securityheaders.com celebrated 250 million scans in 2023 and changed its grading in 2019 (no more X-XSS-Protection requirement, and frame-ancestors accepted in place of XFO) ([Scott Helme](https://scotthelme.co.uk/security-headers-updates/)). The MDN HTTP Observatory rescored sites at its 2024 launch ([MDN blog](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch)). A typed vocabulary therefore needs a maintained list of deprecated fields and values. Removal demand comes from the same checklists:

- "Removing X-Powered-By" has 160,163 views ([SO 2661799](https://stackoverflow.com/questions/2661799/removing-x-powered-by)).
- "Remove/Modify IIS 10 Server Header" has 176,730 views ([SF 991045](https://serverfault.com/questions/991045/remove-modify-iis-10-server-header-which-discloses-iis-version)).

**Redirects that cannot be taken back, loop or leak.** "How long do browsers cache HTTP 301s?" has 550 votes and 335,479 views. Its top answer: without cache directives "a 301 redirect defaults to being cached without any expiry date", although "it is still possible to override this default behavior using caching directives" ([SO 9130422](https://stackoverflow.com/questions/9130422/how-long-do-browsers-cache-http-301s)). Loops come from two layers that each force HTTPS. On "ERR_TOO_MANY_REDIRECTS with nginx", the most-voted answer (113) is "In my case it was Cloudflare" ([SO 46413494](https://stackoverflow.com/questions/46413494/err-too-many-redirects-with-nginx)). Other loops come from nginx's internal rewrite cycle ([SF 505098](https://serverfault.com/questions/505098/what-does-this-nginx-error-rewrite-or-internal-redirection-cycle-mean), 253,996 views) and from automatic trailing-slash redirects. For the last one, the advice is `absolute_redirect off`, because absolute URLs leak an internal host or port behind a proxy ([SO 15555428](https://stackoverflow.com/questions/15555428/nginx-causes-301-redirect-if-theres-no-trailing-slash)). Queries get lost or doubled depending on `?` suffixes and the `QSD` flag ([SO 21118511](https://stackoverflow.com/questions/21118511/htaccess-301-redirect-remove-query-string-qsa)).

The open-redirect record has one shape: a "keep the rest of the path" or slash-normalising join that emits `//host`. Cases:

- **Django** (CVE-2018-14574): the fix escapes leading slashes ([Django 2.0.8](https://docs.djangoproject.com/en/5.2/releases/2.0.8)).
- **Tomcat** (CVE-2018-11784) ([Tenable](https://tenable.com/cve/CVE-2018-11784)).
- **fastify-static** (CVE-2021-22963) ([GHSA-p6vg-p826-qp3v](https://github.com/advisories/GHSA-p6vg-p826-qp3v)).
- **Astro** (CVE-2025-54793): `Location: //target.domain/subpath/` ([OSV](https://osv.dev/vulnerability/GHSA-cq8c-xv66-36gw)).
- **The MCP Registry** (CVE-2026-44427): `//evil.com` from a trailing-slash middleware ([OSV](https://osv.dev/vulnerability/CVE-2026-44427)).

Browsers also read `/\host` as protocol-relative, because the URL Standard treats `\` like `/` for http(s) ([URL Standard](https://url.spec.whatwg.org/#relative-slash-state)).

**What administrators praise is predictability and visibility.** The evidence for preferences is thinner than the evidence for pain. It consists mostly of maintainers' recommendations and the votes on answers that recommend a tool. Gixy says headers-more "has better inheritance behavior" ([gixy](https://gixy.getpagespeed.com/checks/add-header-redefinition/)). HAProxy users treat map files as the answer for bulk redirects. Debugging rewrite rules is a genre of its own: "How to debug Apache mod_rewrite" has 257,383 views ([SO 9632852](https://stackoverflow.com/questions/9632852/how-to-debug-apache-mod-rewrite)), and the nginx equivalent 110,534 ([SF 333048](https://serverfault.com/questions/333048/best-way-to-debug-nginx-rewrite-rules-in-config-file)). The recurring testing routine is `curl -sIL`, a private window and DevTools "Disable cache" ([SO 16154672](https://stackoverflow.com/questions/16154672/how-long-does-chrome-remember-a-301-redirect)). These threads keep asking two things: which layer set this field, and which rule fired. No server answers either question directly.

## Panels give owners a redirect form and keep headers behind a ticket

Classic panels split the topic in two. A non-shell owner gets a small redirect form. Response headers mean a raw configuration field that is admin-only, or a support ticket:

- **cPanel** offers 301 or 302, a www option and a "Wild Card Redirect" that keeps the remainder. It writes the rule "at the bottom of the .htaccess file", where a WordPress block ending in `[L]` makes Apache stop first. cPanel's own page warns that "some third-party applications will ignore your rules", and existing redirects cannot be edited, only deleted and recreated ([cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/), [InMotion](https://help.inmotionhosting.com/hc/en-us/articles/14609412204183-cPanel-Redirects-Not-Working-in-WordPress)).
- **Plesk** has a "Preferred domain" 301 and a "Permanent SEO-safe 301 redirect from HTTP to HTTPS" checkbox. Its "Additional nginx directives" are admin-only, and on shared hosting a customer asks support (search summaries) ([Plesk KB](https://www.plesk.com/kb/support/how-to-add-custom-apache-nginx-configuration-for-a-domain-in-plesk), [Rebel.ca](https://support.rebel.ca/hc/en-us/articles/55658433339291-How-to-Request-Custom-Nginx-Directives-on-Plesk-Hosting)). Its only typed header is HSTS through SSL It!, which has no preload option, and users report HSTS appearing twice ([Plesk forum](https://talk.plesk.com/threads/ssl-it-hsts-appearing-twice-in-headers.352417/post-959417)).
- **ISPConfig** has an "SEO Redirect" drop-down and a validated rewrite field. That field rejected a valid rule, and the developer sends custom rules to the raw "nginx Directives" field (search summary) ([HowtoForge](https://forum.howtoforge.com/posts/310933)).
- **DirectAdmin** offers path redirects with 301, 302 or 303 and nothing for headers ([Snel](https://www.snel.com/support/create-redirect-directadmin/)).
- **HestiaCP** hard-codes its HTTP-to-HTTPS 301, so a user who chose 302 still saw a 301 ([HestiaCP forum](https://forum.hestiacp.com/t/redirect-users-to-a-custom-domain-or-web-address-you-cant-use-code-302/18233)).
- **Laravel Forge**'s redirects "are wrappers around Nginx's `rewrite` rules", regex included, and the docs call changing a permanent redirect "bad practice" ([Forge](https://laravel.com/forge/docs/sites/network)).

Hand edits do not survive either. cPanel users report nginx files "rebuilt every few days" (search summary) ([cPanel community](https://support.cpanel.net/hc/en-us/community/posts/26854229656215-Unable-to-stop-nginx-conf-files-from-being-rebuilt-frequently)).

Four things stand out:

- **WP Engine's success-or-all switch** is the clearest platform answer to the cache-on-errors problem.
- **The deny-lists converge.** Every platform protects framing and server-owned names.
- **Specificity order is the exception.** Every list-based platform documents first-match-wins and tells users to put specific rules first. Kinsta warns that a missing `^` makes `/blogpost` also match `/category/blogpost`, and a missing `$` can loop.
- **Query defaults split.** Netlify and Vercel's configuration redirects pass the query on. Cloudflare's and Vercel's bulk redirects drop it unless told otherwise.

An agent trained on those platforms will bring those habits along.

What owners need, and rarely get, follows from this. First, a redirect that works whatever the application's own rewrites do. cPanel's `.htaccess` position fails exactly there, and Kinsta sells its server-level redirects against plugins that call `wp_redirect`. Second, a way to test before going permanent. Third, bulk import after a migration, with chains, loops and blanket homepage redirects caught, and export for the next move. WP Engine sends larger sets to the Redirection plugin, and one support thread shows 5,142,793 rows in its redirect log table (search summary) ([support thread mirror](https://remarpro.com/support/?p=4739358)). Fourth, security headers without a shell and without duplicates when the application sends its own. Fifth, a staging `X-Robots-Tag: noindex` that cannot leak into production, which Vercel advises scoping to the host ([Vercel](https://vercel.com/docs/routing/redirects)).

Google's rules frame the SEO side of this ([redirects](https://developers.google.com/search/docs/crawling-indexing/301-redirects), [status codes](https://developers.google.com/search/docs/crawling-indexing/http-network-errors), [site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)):

- 301 and 308 are strong canonical signals; 302, 303 and 307 are weak ones.
- Crawlers follow up to 10 hops, and Google advises "redirecting to the final destination directly".
- Keep redirects "generally at least 1 year", and do not send many old URLs to the home page.
- For maintenance, use a 503 with Retry-After for a few days at most, not a redirect ([pause guidance](https://developers.google.com/search/docs/crawling-indexing/pause-online-business)).

## Standards set the hard edges: grammar, permanence, HSTS, CORS and tenants

**Field grammar.** A field value must be `field-content`: visible ASCII with inner spaces or tabs, no leading or trailing whitespace. "Field values containing CR, LF, or NUL characters are invalid and dangerous", and other control characters are invalid too ([RFC 9110 5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.5)). HTTP/2 additionally makes uppercase name bytes and leading or trailing whitespace in values malformed ([RFC 9113 8.2.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.1)). It also forbids Connection, Keep-Alive, Proxy-Connection, Transfer-Encoding and Upgrade in any message ([RFC 9113 8.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2)). The RFC's own defence against response splitting is "to prevent anything other than the server's core protocol libraries from sending a CR or LF within the header section" ([RFC 9112 11.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-11.1)). Fixed values validated at load satisfy it by construction. A sender must not repeat a non-list field, and Set-Cookie is the special case ([RFC 9110 5.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.3)). HTTP sets no size limit. The OWASP Permissions-Policy value alone is 478 bytes, nearly half the proposed 1 KB cap, before any origin is allowed ([OWASP headers_add.json](https://raw.githubusercontent.com/OWASP/www-project-secure-headers/master/ci/headers_add.json)).

**Location and permanence.** `Location` may be a relative reference. It inherits the request's fragment unless it carries its own, and several Location lines cannot be recovered ([RFC 9110 10.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2)). A relative `/path` never depends on the Host header. That matters on a catch-all site, where an absolute URL built from Host would put an attacker-chosen host into the answer. 301 and 302 let clients turn POST into GET, while 307 and 308 must not. Only 300, 301 and 308 among redirects are heuristically cacheable ([RFC 9110 15.1, 15.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4)). The browser sources show what that means in practice:

- **Chromium** treats 300, 301, 308 and 410 without explicit freshness as fresh forever (`base::TimeDelta::Max()`, "It should never be stale") ([http_response_headers.cc](https://github.com/chromium/chromium/blob/main/net/http/http_response_headers.cc)).
- **WebKit** gives 301 one year ([CacheValidation.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/network/CacheValidation.cpp)).
- **Firefox** has revalidated redirects that carry no max-age or Expires since a change landed on 2 April 2025 ([Bugzilla 1957619](https://bugzilla.mozilla.org/show_bug.cgi?id=1957619)).

All three read `Cache-Control: max-age` first. A server that sends one on its permanent redirects can therefore take a mistake back. A server that sends none cannot. One 2019 SEO test found no browser caching 301s, which contradicts the others (search summary) ([Jaywing](https://www.jaywing.com/views/opinion/do-modern-browsers-still-cache-301-redirects/)). The engine sources above are the stronger evidence.

**HSTS.** A host "MUST NOT include the STS header field in HTTP responses conveyed over non-secure transport", and a user agent processes only the first STS field ([RFC 6797 7.2, 8.1](https://www.rfc-editor.org/rfc/rfc6797.html#section-7.2)). `includeSubDomains` renders subdomains without proper TLS "unreachable" ([RFC 6797 14.5](https://www.rfc-editor.org/rfc/rfc6797.html#section-14.5)). Preload requires the following ([hstspreload.org](https://hstspreload.org/)):

- an HTTP-to-HTTPS redirect "on the same host";
- `max-age` of at least 31536000, with `includeSubDomains` and `preload`;
- the HSTS header on every HTTPS redirect too.

hstspreload.org recommends a ramp from five minutes through a week and a month, says not to include `preload` by default, and warns that removal "takes months".

**CORS.** `Access-Control-Allow-Origin` is one value: `*`, `null` or a single origin. It cannot be `*` with credentials. A static value should go on every response *without* `Vary`, while a per-origin value needs `Vary: Origin` ([Fetch](https://fetch.spec.whatwg.org/#cors-protocol-and-http-caches)). A static rule can serve the first case. Only a typed feature that matches the request's `Origin` can serve the second.

**Fields that cross tenants.** On a host serving many sites, some fields reach beyond the site that sets them:

- **Set-Cookie** with a parent `Domain` lands on sibling sites ([RFC 6265 8.6](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.6)).
- **Clear-Site-Data** `"cookies"` clears the whole registrable domain ([Clear Site Data](https://w3c.github.io/webappsec-clear-site-data/)).
- **Alt-Svc** injection can hijack an origin ([RFC 7838 9](https://www.rfc-editor.org/rfc/rfc7838.html#section-9)).
- **Service-Worker-Allowed** lifts the path restriction that keeps one user's service worker out of another's directory ([Service Workers](https://w3c.github.io/ServiceWorker/#path-restriction)).

A second CSP field only narrows ("each must be enforced"). `set` on CSP replaces the application's policy and can therefore *loosen* it ([CSP3 8.1](https://w3c.github.io/webappsec-csp/#multiple-policies)). Finally, OWASP's two sources disagree on Referrer-Policy, CORP and `preload`. Its list of headers to add includes `Clear-Site-Data` and `Cache-Control: no-store`, which suit a logout page, not a site ([OWASP list](https://raw.githubusercontent.com/OWASP/www-project-secure-headers/master/ci/headers_add.json), [cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)). Copy-pasting either list site-wide is a mistake that a typed design should not invite.

## Keep the core, fix the semantics, add the checks agents need

### Three findings in agensio's code shape the first step

**Today's `add_headers` reproduces nginx's two worst traps, and the managed `hsts` inherits them.** On the alpha.72 binary (commit `eadce75`), the test site's `/` location added `Strict-Transport-Security`. The field came back on `/`, but not in these cases:

- on `/assets/x.css`, served by a location with its own `add_headers`;
- on a 404;
- on an answer that `try_files` handed to a `.cgi` suffix location.

That matches the code. Static `add_headers` apply on 200 and 304 only, upstream ones only on nginx's success list ([upstream_common.cpp](../src/handlers/upstream_common.cpp)). A headers-only `/` location joins only the location at `/` (`merge_into` in [config.cpp](../src/config.cpp)). The FastCGI handler takes the same path as CGI ([fastcgi.cpp](../src/handlers/fastcgi.cpp)). By code reading, a managed PHP site with `hsts: true`, rendered as exactly such a `/` location ([sites.cpp](../src/control/sites.cpp)), therefore sends HSTS on static files under `/` but not on its PHP pages, its `rules.cache` directories, its preset's other locations or any error answer. The new rules fix this only if the managed `hsts` moves onto them.

**`[[site.redirect]]` cannot coexist with the existing key.** `redirect = "https"` is already a string key of `[[site]]` ([reference.cpp](../src/control/reference.cpp)). TOML cannot give one key both a string and an array-of-tables value. A second naming hazard: `proxy = { headers }` already means request fields forwarded to the origin, *with* `$` variables. A response rule table named `headers` invites an agent to put `$remote_addr` into it.

**Some of the work exists already.** `[server] server_header` sets or removes `Server` on reload. The `private_cache` guard rewrites Cache-Control on password-protected answers, and access refusals carry `Cache-Control: no-store` naming the tested address. `rules.cache` renders success-only cache lifetimes. The new rules must sit *before* those guards, so that no rule can make a protected answer or a 403 shared-cacheable.

### The semantics, stated once

**Matching.** A rule matches the client's path once, normalised, as access rules do: an exact path, or a prefix covering whole segments in any capitalisation. Rules never match internal `try_files` or index targets. That removes the "which location am I in now" question from SO 18450310 and from nginx's `error_page`.

**Resolution.** For each field name, the **longest matching rule that names it decides**, and rules naming different fields all apply. This gives the same result as "shortest first, longer wins" when two rules both `set` a field. It differs in the two cases where the sequential reading breaks:

- A deeper `default` under a shallower `set` would never fire in sequence, because the field is already present.
- A deeper `remove` under a shallower `set` cleanly drops the parent's field for that subtree. This is the per-field answer to OpenLiteSpeed's `NONE` and nginx's `add_header_inherit off`, without a mode switch.

**Applying a decision to the answer.** `remove` deletes every copy, `set` deletes every copy and adds one, and `default` adds the field only if no copy is present after the application's and the server's own fields are in place. That definition of "absent" follows Apache's warning about Content-Type and `setifempty`. The safety guards (protected paths, refusals) run last, then framing. Every result can be computed at load per rule node, so `path_check` can print it.

```toml
[[site.response_headers]]          # name chosen to stay clear of proxy.headers
path = "/"
set = { "X-Content-Type-Options" = "nosniff", "Referrer-Policy" = "strict-origin-when-cross-origin" }
default = { "Content-Security-Policy" = "frame-ancestors 'self'" }
remove = ["X-Powered-By"]

[[site.response_headers]]
path = "/assets/"
when = "success"                   # 2xx and 304; required for freshness-granting Cache-Control
set = { "Cache-Control" = "public, max-age=604800" }

[[site.redirects]]                 # not [[site.redirect]]: that key is redirect = "https"
from = "/blog"                     # prefix on whole segments: /blog, /blog/..., never /blogger
to = "/news"
status = 301                       # required: 301, 302, 307, 308
# remainder = "keep", query = "keep" (defaults); cache = 86400 (default on 301/308)
```

### Cost, order of work and the agent's view

**Cost.** A site without rules pays one emptiness test, as with `access_first`. A site whose only header rule is on `/` pays nothing per request beyond appending a prebuilt block, because its resolved op list is the site default. An upstream answer adds a per-field check inside the loop `apply_upstream_result` already runs over every application field. Only redirect answers pay for encoding. Under the project's gate, this needs `bench/ab.sh <base> -A` with two new rows: a site with a `/` header rule and a deeper one, measured on a path under the deeper rule, and a site with 1,000 exact redirects measured on a path that misses them all.

**Order of work.** Row 14 together with the alpha.72 finding is a bug in today's managed `hsts`, and it ships first with the new rules or as its own fix. The test that fails first: HSTS on a WordPress fixture's PHP page and on its 404. Rows 15 and 19 deserve a fuzz target over (`from`, `to`, request path, query). It should assert that the `Location` origin always equals the origin of `to`, in the habit of `fuzz_path`.

**The agent's view.** These rules give the MCP agent what no panel offers: a pure function from (site, path, query) to the redirect and the final field list, with the rule that decided each field. Agents arrive with habits from other platforms (first match wins, queries dropped, 301 by default), so the tool descriptions have to state agensio's differences in plain words. The refusals have to name the rule, the field and the alternative (`server_header`, `rules.cache`, `hsts`).

## Conclusion

The servers' header traps share one root cause. They attach header operations to wherever the request *ends up*: nginx's current location, Apache's internal table, Caddy's handler position, Traefik's middleware chain. The administrator thinks in the URL the client asked for. agensio's rules are resolved per field at load, against the client's path, so the outcome stops depending on the route the request took. That also lets `path_check` answer the question behind the most-viewed threads, "where did this header come from". The same lesson shows in agensio's own `add_headers`, which attaches to locations and so inherits nginx's failures. The new rules should replace it rather than sit beside it.

On redirects, the evidence says safety comes from *removing* defaults and power: no implicit status, no regex, no request-derived variables, and a join whose output agensio checks. The remaining risk is permanence that outlives the configuration, in 301 caches, HSTS and preload lists. That is the one place where the server should act by default rather than wait to be asked: bound the lifetime of what it cannot take back, and make the irreversible steps (preload, a year-long `max-age`) ones the user confirms in person.
