# Gate before routing, verify each password once

agensio's Basic-authentication proposal (design section 25) already does the two things no incumbent does together. It binds the password to the normalised request path before any location is chosen, which removes the nginx regex-location hole and the panel-translation bugs behind most administrators' complaints. It also verifies a strong hash off the event loop and remembers the result. nginx, Apache httpd, Traefik, HAProxy, OpenLiteSpeed and h2o re-run the hash on every request, and Caddy remembers results only by keeping plaintext passwords and failed guesses in memory. The research supports keeping the proposal's structure: site-level rules on the access rules' matcher, libxcrypt's strong formats only, a bounded verifier pool, a success cache under an HMAC, no prompt over plain HTTP, `charset="UTF-8"` with `no-store`, users managed by the helper, and `skip_for` as the one way to say "office or password". **Five details would make it fail in practice.** First, the cache key leaves out the stored hash, so a password verified against one user file would open another rule's area for the same user name. Second, dropping the cache at every reload makes each agent-driven `site_update` re-verify every active user on every worker. Third, the shipped `agensio-auth` jail counts every 401, including the credential-less challenge that starts every browser login, which fail2ban's own filters and CrowdSec deliberately ignore. Fourth, stripping `Authorization` for every application breaks WordPress's documented loopback check on a protected staging site. Fifth, the presets' `Cache-Control: public` on uploads and hashed assets lets a CDN in front serve protected files to anyone under RFC 9111 3.5. Two additions make the feature cheap and useful: a per-connection memo makes a returning browser cost a byte comparison rather than an HMAC, and per-user expiry and labels give site owners the temporary, per-person access that no hosting panel or managed host offers. What Basic auth cannot give (logout, password-manager fill, in-app browsers) belongs to a later signed-link or login-page feature, not this one.

## Six of seven servers pay the slow hash on every request

HTTP Basic resends the password with every request, each image and stylesheet of a protected page included. What separates the servers is therefore less their syntax than when the deliberately slow hash runs. The table compresses what the source code and documentation of the seven servers show; the paragraphs after it give the evidence. Where a cell says "not verified", the research could not establish it.

| Server | Where the rule attaches | Hashes accepted | When the hash runs | What the application receives | Failure logging |
|---|---|---|---|---|---|
| nginx 1.31 | A configuration level (`auth_basic`, cancelled by `off`); exactly one location serves a request | libc `crypt()` (bcrypt and yescrypt only where libxcrypt provides them), `$apr1$`, `{PLAIN}`, `{SHA}`, `{SSHA}` | Every request: the user file is opened and read, then `crypt_r` runs inline on the event loop. No cache. An unknown user skips the hash. | `Authorization` to proxies and FastCGI (PHP builds `PHP_AUTH_*` from it); no `REMOTE_USER` in the shipped `fastcgi_params` | Error log `user "X": password mismatch` or `was not found`; missing credentials at info level |
| Apache httpd 2.4 | Sections merged (Directory, Files, Location, If); a later authorization replaces an earlier one | Bundled bcrypt, `$apr1$` (the `htpasswd` default), `{SHA}`, system `crypt` | Every request: the file is scanned, then a timing-safe compare. `mod_authn_socache` caches the stored hash, not the result. | Proxies get `Authorization`. CGI and FastCGI get `REMOTE_USER` but not the header, unless `CGIPassAuth On` | AH01617 / AH01618; nothing for a request without credentials |
| Caddy 2.11 | Directive with a matcher; `rewrite` and `try_files` sort before it | bcrypt (default cost 14) or argon2id; plaintext refused | Result cache, on by default from the Caddyfile: key is stored hash plus plaintext, failures cached too, 1,000 entries | Request passed unchanged; `{http.auth.user.id}` available | `user_id` in the access log, on success only |
| Traefik 3.7 | Middleware on a router; router priority comes from rule length | `$apr1$`, `$1$`, `{SHA}`, bcrypt | Every request; concurrent identical checks collapsed; a result cache was declined in 2021 | Forwarded unless `removeHeader`; optional user header | Attempted user name in the access log; failures at debug level |
| HAProxy 3.x | `http-request auth` behind an ACL; the auth action stops rule evaluation | Platform `crypt(3)`; `insecure-password` plaintext | Every request: `crypt_r` on the worker thread (a global lock where only `crypt` exists), compared with `strcmp` | Forwarded unless deleted; the `http_auth_user` fetch is unverified | Only through a custom `log-format` |

### nginx and Apache: per request, on the worker

**nginx re-reads the user file and runs `crypt_r()` inside the event-loop worker for every protected request**, with no cache of the file or of results ([ngx_http_auth_basic_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_auth_basic_module.c)). Its maintainer measured bcrypt at `htpasswd`'s default cost of 5 at about 4 ms ([nginx mailing list, 2017](https://mailman.nginx.org/pipermail/nginx/2017-June/054130.html)). He concluded that a worker then blocks "the event loop for 4 milliseconds 100 times per second", which allows "no more than 250 requests per second on a single core" ([nginx mailing list, 2017](https://mailman.nginx.org/pipermail/nginx/2017-June/054134.html)). Asked about high costs two years later, he warned that they would "make your site completely unusable" ([nginx-devel, 2019](https://mailman.nginx.org/pipermail/nginx-devel/2019-July/012362.html)). Every other connection on that worker waits while one request is checked, so the stall is shared.

Apache does the same per request in a worker thread. Its how-to says the password "must be verified every time you request a document ... for every image on the page" ([httpd auth howto](https://httpd.apache.org/docs/2.4/howto/auth.html)). `mod_authn_socache`, built for pages with "hundreds of objects", caches the provider's stored hash for 300 s but still runs the hash on every request ([mod_authn_socache](https://httpd.apache.org/docs/2.4/mod/mod_authn_socache.html), [source](https://github.com/apache/httpd/blob/2.4.x/modules/aaa/mod_authn_socache.c)). Only unreleased httpd trunk remembers the last result per connection ([trunk util.c](https://github.com/apache/httpd/blob/trunk/server/util.c)).

The field reports fit that design. An nginx user saw Basic auth add 100 to 150 ms to a 30 to 40 ms page ([nginx mailing list, 2015](https://mailman.nginx.org/pipermail/nginx/2015-November/049322.html)). A Traefik page went from about 20 ms to 25 ms at bcrypt cost 5 and to 200 ms at cost 11 ([traefik#4791](https://github.com/traefik/traefik/issues/4791)). A MediaWiki behind Apache took **5.7 s per full page load at bcrypt cost 10 and 88.9 s at cost 18**, and the author's advice was "perhaps 9 or less" ([End Point Dev](https://www.endpointdev.com/blog/2016/02/bonked-by-basicauth-because-bcrypt/)).

### Caddy: a result cache that keeps plaintext and failures

Caddy is the only server that fixed this, and its fix came from pain. On a one-vCPU Linode, 10 to 20 requests a second from one browser took 60 to 80 % of the CPU, with more than 92 % of it in bcrypt's `blowfish/encryptBlock` ([caddy#3462](https://github.com/caddyserver/caddy/issues/3462)). The resulting `hash_cache` keys on `hex(stored_hash || plaintext)` and stores a boolean, so **failed guesses are cached too**. It holds 1,000 entries, evicts about a tenth at random when full, and is on by default from the Caddyfile ([basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)). Its maintainer says there is "really no situation where it ever makes sense to turn off" ([PR #3465](https://github.com/caddyserver/caddy/pull/3465)).

A second fix followed. After a restart, 18 parallel requests from one dashboard all missed the cache and produced a 15-second CPU spike, at 2.18 s per cost-14 hash on a $6 droplet. Concurrent identical checks are now collapsed into one ([caddy#5338](https://github.com/caddyserver/caddy/issues/5338)). The design still has three costs. Plaintext passwords stay in memory, which the code comment accepts "as long as your machine is not compromised". A password sprayer fills the bounded cache with failures and, by inference from the code, evicts good entries at random. And the default cost stays at a level even its maintainer calls "kinda ridiculously high", adding "we had to do caching which is kinda cheating" ([PR #7186](https://github.com/caddyserver/caddy/pull/7186)).

### Traefik: a declined cache, then three advisories in one year

Traefik declined a result cache in 2021. Its maintainers asked "What would be the strategy to revoke users?" and whether frequent configuration reloads would empty the cache anyway ([PR #7900](https://github.com/traefik/traefik/pull/7900)). Users answered that "only MD5 seems to be viable" and that Basic auth without an IP list is "a very simple and effective DoS" ([traefik#7897](https://github.com/traefik/traefik/issues/7897)).

What followed in 2026 shows that **verification shortcuts are security code**. First, an unknown user answered in about 0.6 ms against 166 ms for a real one, a user-enumeration oracle ([CVE-2026-32595](https://nvd.nist.gov/vuln/detail/cve-2026-32595)). Then the patch for it turned out to be a no-op, because a map confusion left the fallback hash empty ([CVE-2026-41263](https://vuln.today/cve/CVE-2026-41263)). Finally, the deduplication added for performance keyed concurrent checks on `password + secret` with no delimiter, so an attacker could share a legitimate user's in-flight success and "authenticate as an arbitrary username". The fix length-prefixes the user into the key ([GHSA-6765-c87h-8mrf](https://github.com/traefik/traefik/security/advisories/GHSA-6765-c87h-8mrf)).

### HAProxy, OpenLiteSpeed and h2o

HAProxy's manual warns that hashed passwords "can quickly become a major factor in HAProxy's overall CPU consumption, and can even lead to application crashes" ([HAProxy manual, 12.2](https://docs.haproxy.org/dev/configuration.html)). The code calls `crypt_r` synchronously on the worker thread, under a global spinlock where only `crypt` exists ([auth.c](https://github.com/haproxy/haproxy/blob/master/src/auth.c)).

OpenLiteSpeed caches user records but runs the hash per request inside its event loop ([userdir.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/userdir.cpp)). For lines it does not recognise, it tries a plaintext compare before `crypt()`. Read from the source and not tested: a classic crypt hash in its user file would then also accept the literal hash string as the password.

h2o's bundled script reopens the file for every request and knows only `$apr1$` and `{SHA}`; a bcrypt line answers 500 ([htpasswd.rb](https://github.com/h2o/h2o/blob/master/share/h2o/mruby/htpasswd.rb)).

### Weak formats survive because strong ones cost too much per request

The incumbents still accept weak formats. nginx verifies `{PLAIN}`, unsalted `{SHA}`, `{SSHA}` and `$apr1$` itself, but reaches bcrypt only through the C library ([nginx auth_basic](https://nginx.org/en/docs/http/ngx_http_auth_basic_module.html)). A bcrypt file on a C library without bcrypt therefore yields `crypt_r() failed` and a 500, the top answer on a 32,934-view question ([SO 31833583](https://stackoverflow.com/questions/31833583/nginx-gives-an-internal-server-error-500-after-i-have-configured-basic-auth)). **Apache's `htpasswd` has written `$apr1$` (1,000 MD5 rounds) by default since 2.2.18**, and its opt-in bcrypt defaults to cost 5 ([htpasswd](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)).

Current guidance points the other way. OWASP ranks Argon2id first and scrypt second, and keeps bcrypt "for legacy systems" at cost 10 or more with a 72-byte input limit ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). NIST SP 800-63B-4 (August 2025) requires a salt of at least 32 bits and a cost "as high as practical", and it forbids truncating the password ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)). libxcrypt, the system `libcrypt` on Debian, Ubuntu and Fedora since glibc dropped its own in 2.39 ([glibc NEWS](https://sourceware.org/git/?p=glibc.git;a=blob_plain;f=NEWS;hb=HEAD)), recommends yescrypt for new hashes. It calls sha-crypt's default of 5,000 rounds "too low for modern hardware", and says md5crypt, DES and NT "should not be used" ([crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)). It offers neither Argon2 nor `$apr1$` ([hashes.conf](https://github.com/besser82/libxcrypt/blob/develop/lib/hashes.conf)).

A measurement made for this research on the project's Linux box puts numbers on the trade-off. It used libxcrypt 4.4.38, one thread of a Ryzen 9 9900X, and `crypt_rn` with a precomputed setting; it is first-hand, not a published source.

| Setting | ms per verification | Scratch memory per verification |
|---|---|---|
| yescrypt cost 5 (`$y$j9T$`, Debian's default) | 6.6 | about 16 MiB |
| yescrypt cost 7 | 28 | about 64 MiB |
| yescrypt cost 9 | 115 | about 256 MiB |
| bcrypt cost 5 (`htpasswd -B` default) | 1.1 | about 1.5 MB |
| bcrypt cost 10 (OWASP's floor) | 32.6 | about 1.5 MB |
| bcrypt cost 12 | 131 | not measured |
| sha512crypt, 5,000 rounds | 1.3 | about 1.6 MB |
| md5crypt `$1$` | 0.12 | not measured |

The same run confirmed that bcrypt truncates silently: two 73-byte passwords that differ only in the last byte verify as equal, while yescrypt tells them apart.

**The per-request design is the reason the industry's defaults are weak.** Server Fault's popular answers recommend bcrypt cost 12 to 14 against guessing ([SF 421046](https://serverfault.com/questions/421046/how-to-limit-nginx-auth-basic-re-tries)). The nginx maintainer, meanwhile, warns that high costs make a site unusable, so administrators settle on `$apr1$`. A cache of successful verifications removes the conflict. The slow hash is then paid once per user and worker, and on every guess, which is exactly the rate brute-force defence wants to make expensive.

### Rules attached to handlers leak, and panels inherit the leak

The traps come from attaching the password to whatever ends up serving the request.

**nginx** hands each request to exactly one location, and a regex location beats any prefix location without `^~`. So `location ~ \.php$` runs `/admin/x.php` without the password set on `/admin/`. The maintainers' fix is to nest the PHP location inside a protected `^~` prefix ([nginx mailing list, 2011](https://mailman.nginx.org/pipermail/nginx/2011-December/031004.html)), and the question keeps coming back ([SF 375961](https://serverfault.com/questions/375961/nginx-basic-http-authentication-on-php-script), [SF 119076](https://serverfault.com/questions/119076/how-to-use-fastcgi-globally-and-basic-auth-in-sublocations-in-nginx)). The top-voted exception question failed for a related reason: `location /api/ { auth_basic off; }` matched, but it had no `proxy_pass`, because handlers are not inherited ([SF 330580](https://serverfault.com/questions/330580/enable-basic-auth-sitewide-and-disabling-it-for-subpages)).

**Apache** merges sections instead of choosing one, and that brings its own traps. With the default `AuthMerging Off`, a later section's authorization replaces an earlier one, so a `<Location>` overrides a `<Directory>`. A `<Limit>` inside a `<Location>` "can silently grant access" for the methods it does not list ([httpd sections](https://httpd.apache.org/docs/2.4/sections.html), [mod_authz_core](https://httpd.apache.org/docs/2.4/mod/mod_authz_core.html#require)).

**The other three servers** each have their own trap. Caddy's default directive order runs `rewrite` and `try_files` before `basic_auth` ([directives.go](https://github.com/caddyserver/caddy/blob/master/caddyconfig/httpcaddyfile/directives.go)), so by inference a front-controller rewrite can make a path matcher on `basic_auth` miss. HAProxy's `auth` action ends rule evaluation. Traefik's bcrypt hashes in Docker labels need every `$` doubled ([SO 65404777](https://stackoverflow.com/questions/65404777/basic-auth-is-not-working-for-traefik-v2-1)).

**Hosting panels that translate Apache directory protection into nginx locations keep shipping the nginx trap.** In February 2024, Plesk 18.0.57 and 18.0.58 served PHP files in a protected directory without a login, and 18.0.59 made them download instead of execute ([Plesk forum](https://talk.plesk.com/threads/protected-directory-not-working-for-php-files.373318/)). An earlier Plesk bug answered 404 or 500 for static files in protected directories and was fixed in 2023, only for default templates ([Plesk KB](https://support.plesk.com/hc/en-us/articles/13499309025687-Static-files-in-Plesk-protected-directory-are-inaccessible-ERROR-404-not-found)). DirectAdmin's staff had explained the same bug in 2014: "locations cannot overlap with nginx" ([DirectAdmin forum](https://forum.directadmin.com/threads/protect-directory-via-da-with-nginx-setup.47415)).

The opposite failure recurs too. When certbot added HTTPS, it generated a port-443 virtual host without the auth sections, and "every part of the website [was] accessible to everybody" ([LE 45372](https://community.letsencrypt.org/t/45372), again in [LE 119892](https://community.letsencrypt.org/t/119892)). Protection tied to a listener rather than to the site is lost when a listener is added.

### The same few exceptions recur everywhere

The exceptions administrators need form a short, stable list. The ACME challenge fails with 401 behind a realm, in Let's Encrypt threads that run from 2016 to 2025 ([LE 12944](https://community.letsencrypt.org/t/12944), [LE 222749](https://community.letsencrypt.org/t/222749)), and ISPConfig and Ploi had to add exemptions for it ([ISPConfig #4416](https://git.ispconfig.org/ispconfig/ispconfig3/issues/4416)). Load-balancer health checks need one too ([SO 46500271](https://stackoverflow.com/questions/46500271/how-to-avoid-basic-authentication-for-aws-elb-health-check-with-nginx-configurat)). CORS preflights need one because "a CORS-preflight request never includes credentials", so a 401 on `OPTIONS` breaks a cross-origin API ([Fetch Standard](https://fetch.spec.whatwg.org/#cors-preflight-fetch)). WordPress's `admin-ajax.php` and `admin-post.php` are public endpoints inside `/wp-admin/` that the front end calls ([SecuPress](https://secupress.me/blog/dont-use-password-protection-wp-admin-folder)). And APIs that carry their own Bearer token cannot coexist with a Basic gate, because a browser has only one `Authorization` header: LibreChat's front end replaced the site's Basic credentials, and every API call failed until `/api/` was exempted ([LibreChat #890](https://github.com/danny-avila/LibreChat/discussions/890)).

agensio already covers two of these. It answers the ACME challenge in the dispatcher before site routing (`src/handlers/dispatch.cpp`), and its access rules keep WordPress's `admin-ajax.php`, `css/`, `js/` and `images/` open under a `/wp-admin` restriction (design section 23).

### "Office or password" means opposite things in nginx and Apache

nginx and Apache default to opposite logic for combining an address list with a password. nginx defaults to `satisfy all`, which requires both; under `satisfy any`, a client outside the list gets a 401 rather than a 403, because 401 takes precedence in the access phase ([nginx satisfy](https://nginx.org/en/docs/http/ngx_http_core_module.html#satisfy), [ngx_http_core_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c)). Apache treats several `Require` lines as an implicit `<RequireAny>`, so `Require ip` next to `Require valid-user` means address *or* password ([mod_authz_core](https://httpd.apache.org/docs/2.4/mod/mod_authz_core.html#require)).

The confusion persists. A `satisfy any` that admitted every client turned out to be a third-party module returning OK ([SF 493413](https://serverfault.com/questions/493413/nginx-reverse-proxy-satisfy-any-causing-all-clients-to-be-permitted)). The accepted modern nginx answer avoids `satisfy` entirely, using a `geo` variable that evaluates to `off` ([SO 48279160](https://stackoverflow.com/questions/48279160/nginx-http-basic-authentication-with-exceptions-for-particular-ip-addresses)). Traefik cannot express an OR between middlewares at all; that is its most-reacted allowlist issue, with 93 thumbs-up ([traefik#6007](https://github.com/traefik/traefik/issues/6007)). Among the panels, only CloudPanel exposes the need directly, as "Whitelisted IPs" that skip the prompt ([AZDIGI on CloudPanel](https://azdigi.com/en/blog/cloudpanel/set-up-basic-authentication-on-cloudpanel)).

The lesson is to name the combination once, explicitly. Answer 401 when a password could still succeed, and 403 when the refusal has nothing to do with credentials, the split RFC 9110 11.4 and 15.5.4 draw ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.4)).

## Applications, transport and logs each inherit a wrong default

### Who should see the password depends on the application

**Every server whose proxy behaviour could be checked forwards the client's `Authorization` header to a proxied application by default.** nginx passes all request headers ([proxy_pass_request_headers](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass_request_headers)), Apache's `mod_proxy` removes only `Proxy-Authorization` ([proxy_util.c](https://github.com/apache/httpd/blob/2.4.x/modules/proxy/proxy_util.c)), Caddy leaves the request untouched, and Traefik strips the header only with `removeHeader`. RFC 9110 11.6.2 forbids a forwarding proxy to modify the header, and section 17.16.3 names "not making the content of the Authorization request header field available" as the defence when one origin serves several parties ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.3)).

The complaints run both ways. Jenkins prompts twice until `proxy_set_header Authorization ""` is added (the accepted answer scores 41: [SO 35563508](https://stackoverflow.com/questions/35563508/jenkins-nginx-double-prompted-for-basic-auth-why-why-is-there-an-internal-je)), and JIRA needs the same fix ([SF 511846](https://serverfault.com/questions/511846/basic-auth-for-a-tomcat-app-jira-with-nginx-as-reverse-proxy)). A self-hosted Bitwarden read the site's user name as its own client id and broke login ([Bitwarden community](https://community.bitwarden.com/t/adding-basic-auth-to-self-hosted-vault-breaks-login/2132)). Other applications want the user name handed on in `X-Forwarded-User` instead ([SF 511206](https://serverfault.com/questions/511206/nginx-forward-http-auth-user)).

PHP shows the asymmetry most clearly. Behind nginx, PHP-FPM builds `PHP_AUTH_USER` and `PHP_AUTH_PW` from `HTTP_AUTHORIZATION`, and no `REMOTE_USER` is set ([fpm_main.c](https://github.com/php/php-src/blob/master/sapi/fpm/fpm/fpm_main.c), [fastcgi_params](https://github.com/nginx/nginx/blob/master/conf/fastcgi_params)). Behind Apache it is the reverse: `REMOTE_USER` is set, and the header is hidden unless `CGIPassAuth On` (2.4.13 and later) ([CGIPassAuth](https://httpd.apache.org/docs/2.4/mod/core.html#cgipassauth)).

**WordPress depends on the nginx behaviour.** Its Site Health loopback check copies `PHP_AUTH_USER` and `PHP_AUTH_PW` into an `Authorization: Basic` header, so that loopbacks work on password-protected staging sites ([WordPress reference](https://developer.wordpress.org/reference/classes/wp_site_health/can_perform_loopback/)). A secondary source adds that a failing loopback affects WP-Cron and the file editors ([WPFixIt](https://www.wpfixit.com/fix-wordpress-loopback-failures/)). WordPress core already resolved the clash with its own Application Passwords, which since 5.6 are checked only once one exists ([Trac #51939](https://core.trac.wordpress.org/ticket/51939)).

Whether the application should see the credentials is therefore a property of the application, not of the server. agensio today behaves like nginx: `FcgiHandler::append_http_params` passes `HTTP_AUTHORIZATION`, and the proxy handler forwards the header.

### Identity headers must be deleted unconditionally

Where a proxy hands the user name on in a header, the recurring vulnerability is a client that sends that header itself. Caddy's `forward_auth` set copied identity headers only when the auth service returned them and never deleted the client's own copy; that was a high-severity advisory, fixed in 2.11.2 ([GHSA-7r4p-vjf4-gxv4](https://github.com/caddyserver/caddy/security/advisories/GHSA-7r4p-vjf4-gxv4)). Traefik added `aliasHeadersStrategy` because "backends normalizing the header names can be spoofed with an aliasing name", for example `X_Auth_User` ([Traefik entry points](https://doc.traefik.io/traefik/reference/install-configuration/entrypoints/#aliasheadersstrategy)). Authentik's HAProxy template deletes every header containing an underscore before the check ([Authentik header authentication](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/header_authentication.mdx)).

agensio's FastCGI path already drops header names with an underscore. The proxy path does not, which matters for the proposal's `forward_user`.

### No server refuses to ask for a password in clear

**No server refuses, or even warns about, Basic over plain HTTP.** Neither nginx's nor Apache's handler looks at the connection's TLS state ([mod_auth_basic.c](https://github.com/apache/httpd/blob/2.4.x/modules/aaa/mod_auth_basic.c)). nginx's own admin-guide example protects a location on a plain listener on port 8080 ([NGINX admin guide](https://docs.nginx.com/nginx/admin-guide/security-controls/configuring-http-basic-authentication/)). Only Caddy's documentation says Basic auth "is not secure over plain HTTP" ([Caddy basic_auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth)).

RFC 9110 17.16.1 requires "a secured connection prior to exchanging credentials" ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.1)), and browsers are closing the door. Chrome administrators have been able to forbid Basic over HTTP since Chrome 88 ([Chromium commit](https://chromium.googlesource.com/chromium/src/+/a8cb48c920b87f5ad23b2e685c201e14e80274e7)), Firefox 136 added the same switch ([Bugzilla 1763671](https://bugzilla.mozilla.org/show_bug.cgi?id=1763671)), and Chrome 154, scheduled for this month, warns before any public site without HTTPS ([Google Security Blog](https://security.googleblog.com/2025/10)). The scheme is also part of the protection space (RFC 9110 11.5). A prompt on port 80 followed by a redirect to HTTPS therefore asks twice, and the standing advice is to redirect on 80 and authenticate only on 443 ([SF 146266](https://serverfault.com/questions/146266/force-https-with-apache-before-htpasswd)).

### Every challenge leaves out the charset, and caches matter

Every server answers 401 with `WWW-Authenticate: Basic realm="..."`. **None of the six whose code was read sends RFC 7617's `charset="UTF-8"`**, the only defined way to say how non-ASCII credentials are encoded ([RFC 7617 2.1](https://datatracker.ietf.org/doc/html/rfc7617#section-2.1)). Firefox switched to UTF-8 only in version 59, a change that "actually broke some sites" ([Mozilla bug 1419658](https://bugzilla.mozilla.org/show_bug.cgi?id=1419658)). nginx, Caddy and HAProxy insert the realm between quotes without escaping it, so a realm containing `"` corrupts the header. Browsers no longer show the realm, but it still scopes the credentials they keep ([mod_authn_core](https://httpd.apache.org/docs/2.4/mod/mod_authn_core.html)).

RFC 9111 3.5 forbids a shared cache to reuse a response to a request that carried `Authorization`, unless the response says `public`, `s-maxage` or `must-revalidate` ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5)). Managed hosts switch their CDN and page cache off while a site is protected for exactly this reason ([Kinsta](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/), [WP Engine](https://wpengine.com/support/password-protecting-wp-engine-site/)).

### fail2ban works only because it ignores the first 401

**Only nginx and Apache have failure lines that fail2ban ships filters for, and both treat the credential-less 401 as normal.** nginx logs `user "X": password mismatch` and `user "X" was not found` at error level, but a request with no credentials only at info level ([nginx source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_auth_basic_module.c)). Apache logs nothing for it. fail2ban's filter explains: "An unauthorized response 401 is the first step for a browser to instigate authentication" ([apache-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/apache-auth.conf)). Its `nginx-http-auth` filter likewise matches only the two failure lines ([nginx-http-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/nginx-http-auth.conf)).

CrowdSec tried counting GET 401s for Traefik and reverted the change after "a lot of feedback ... about false positives". The reason given: from an access log alone, "we do not know it's a failed authentication" ([CrowdSec forum](https://discourse.crowdsec.net/t/traefik-failed-basic-auth-attempts-aren-t-banned/2195)).

The user field in access logs is unreliable for a related reason. nginx's `$remote_user` decodes the header whether or not the password was verified ([ngx_http_variables.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_variables.c)), Apache's `%u` "may be bogus if return status ... is 401" ([mod_log_config](https://httpd.apache.org/docs/2.4/mod/mod_log_config.html)), and Traefik logs the attempted name on failure. Only Caddy writes `user_id` on success alone.

No server limits failed attempts itself, and the accepted answer is "use Fail2ban" ([SF 421046](https://serverfault.com/questions/421046/how-to-limit-nginx-auth-basic-re-tries)). For anything built in, NIST caps consecutive failures per account at 100 and prefers growing delays to hard lockouts ([NIST SP 800-63B-4 3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html)). OWASP warns that lockouts can themselves deny service, and asks for every failure to be logged ([OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)).

## Site owners want named, expiring access; panels sell one shared password

### Panels: one realm on a directory, one user list

Every hosting panel examined offers one Basic realm on a directory or a whole site, plus a list of user names and passwords. cPanel's "Directory Privacy" writes `.htaccess` and `.htpasswd`, protects subdirectories by inheritance, and states that it does nothing for FTP or WebDAV ([cPanel docs](https://docs.cpanel.net/cpanel/files/directory-privacy/)). Plesk binds each user to one directory: "This user will only have access to this specific directory" ([Plesk docs](https://docs.plesk.com/en-US/obsidian/customer-guide/websites-and-domains/restricting-access-to-content.65152/)). ISPConfig splits the feature into two records and says the password cannot be shown again ([Noiz docs](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/)). RunCloud offers one user name and password ([RunCloud docs](https://runcloud.io/docs/password-protection-website)). SpinupWP offers a toggle with a built-in `/.well-known/` exemption, where an IP bypass means editing nginx by hand over SSH ([SpinupWP](https://spinupwp.com/doc/enable-basic-authentication-for-your-spinupwp-site/)). HestiaCP has nothing; a 2024 request asked for `wp-admin` protection precisely because "attackers bypass CAPTCHA and two-factor" in the application ([HestiaCP forum](https://forum.hestiacp.com/t/directory-privacy-feature/16360)). SiteGround's Site Tools are the exception, since one user can be attached to several protected URLs ([SiteGround KB](https://www.siteground.com/kb/password-protect-url)).

None of the panel documents reviewed mentions expiry, user-defined exceptions inside the protected tree, logout, an access record, or the hash algorithm.

### Managed hosts: one shared credential per environment

The managed WordPress hosts converge on one shared credential per environment, with caching off while it applies. Kinsta protects the whole site with one pair, refuses its CDN while protection is on, and says "there isn't a way for the server to log a user out" ([Kinsta](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)). WP Engine fixes the user name to the environment name and switches Varnish off ([WP Engine](https://wpengine.com/support/password-protecting-wp-engine-site/)). Flywheel shows the password "in plain text" and advises against reusing a personal one ([Flywheel](https://getflywheel.com/wordpress-support/why-are-my-sites-password-protected/)). Cloudways users, according to the feedback board's search summary, asked for weaker staging passwords so that clients can type them ([Cloudways feedback](https://feedback.cloudways.com/forums/203824-product-improvements-flexible/suggestions/38938630-enable-less-strong-staging-site-passwords)).

**Clients get access by being sent the shared password. Nothing records who used it, and nothing ends it except changing it for everyone.**

### The unmet needs, and the dialog end users trip over

The unmet needs show up where people install or pay to get them. The clearest is **temporary, per-person access**. "Temporary Login Without Password", which creates self-expiring, revocable login links and records their use, has more than 100,000 active installs ([WordPress.org](https://wordpress.org/plugins/temporary-login-without-password/)). Vercel's shareable links give external reviewers access that is revoked centrally ([Vercel](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)). Cloudflare Access emails a one-time PIN that "expires 10 minutes after the initial request" ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)). The need for two-factor login and SSO pushes administrators further, to forward-auth services such as Authelia, which plug into every major proxy ([Authelia](https://www.authelia.com/integration/proxies/introduction/)).

For end users, the native dialog is the weak point. It looks different in every browser, and Cancel shows a bare 401 page ([Kinsta](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)). Bitwarden fills it only when exactly one login matches ([Bitwarden](https://bitwarden.com/help/basic-auth-autofill/)), iOS Safari has a long tail of endless-prompt reports ([traefik#11054](https://github.com/traefik/traefik/issues/11054)), and assets on a second host name prompt again ([WP Engine](https://wpengine.com/support/password-protecting-wp-engine-site/)). Browsers also send Basic credentials on cross-site requests, which MDN flags as a CSRF exposure ([MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)). The only server-side logout is `Clear-Site-Data: "cookies"`. It works only over HTTPS and clears cookies and credentials "for the entire registered domain, including subdomains", so it would also sign the user out of the application ([MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data)).

The conclusion for agensio is a division of labour. Basic auth stays the right tool for machine clients (curl, CI, monitoring) and for a simple gate in front of staging. A server can add the missing pieces of the staging workflow almost for free: a credential per person, an end date, a label saying who it is, and a log of who came in. Logout, password managers and in-app browsers need a cookie issued by a login page or a signed link, which is a separate and later feature.

## Keep the structure, fix five details, add four features

The proposal places protection on the normalised path before routing and on every `try_files` hop. That removes the nginx and panel bypass class by construction. It accepts only the strong libxcrypt formats, verifies off the worker, remembers successes rather than plaintext, refuses to prompt in clear, sends the RFC 7617 charset with `no-store`, and gives "office or password" one explicit name. ### Five changes that prevent real failures

**The cache key must carry the stored hash.** As written, the key is an HMAC "of the site, the user and the password". Take a site with a `/admin` rule using one user file and a `/staging` rule using another, both listing `anna` with different passwords. Once `anna` verifies at `/admin`, the cached entry (site, `anna`, password) would also admit her at `/staging`. **That is the class of bug Traefik's deduplication key had: a component missing from the key let one identity's success serve another.**

The key should be an HMAC, under the process secret, of three length-prefixed parts: the user name, the stored hash string and the password. It is looked up only after the user has been found in the rule's current table. With that key, a password change or a deleted user is simply a cache miss, with no invalidation logic at all, because the stored hash differs or the lookup fails first. Revocation is then a reload, and the cache cannot outlive it, which answers the question that made Traefik decline a cache. Rules or sites that share a user file can also share an entry, which is correct, since the same hash verifies the same password.

**The cache must survive reloads.** agensio reloads on every `site_update`, and agents make such changes often. If each reload empties the per-worker caches, every active user pays a fresh verification on every worker that serves them, after every change. On a twelve-worker box with twenty active users, that is up to 240 verifications, about 1.6 s of CPU at yescrypt cost 5. Those verifications also land in the bounded pool at the moment legitimate browsers are retrying. **Caddy's 15-second post-restart spike is that effect at cost 14** ([caddy#5338](https://github.com/caddyserver/caddy/issues/5338)). Because the key above invalidates itself, the cache can live across generations: keep the HMAC key for the process lifetime and bound entries only by the five-minute TTL and the user's expiry.

**fail2ban must count failed credentials, not challenges.** The shipped filter (`packaging/fail2ban/filter.d/agensio-auth.conf`, rendered by `control/protection.cpp`) matches every access-log line with status 401 or 403 and bans after ten in ten minutes. Today agensio emits no 401 of its own, so the jail counts only applications' 401s; that already invites false positives from an API client retrying an expired token. With Basic auth, every new visitor's first request becomes a credential-less 401. RFC 7617 2.2 also lets a browser send credentials unprompted only under the directory of the first protected URI it fetched ([RFC 7617](https://datatracker.ietf.org/doc/html/rfc7617#section-2.2)). By inference, a page whose assets sit in other directories can draw further challenges before the browser resends; that should be measured with Chromium and Firefox in the test bed.

Either way, fail2ban's own filters and CrowdSec's revert show that the credential-less 401 must never count. The server should write one error-log line per failed verification, in the form `auth failed: site S user "X": password mismatch` (or `unknown user`) with `client ADDR`. The user name is escaped and capped, and the password and the raw header are never written. The pool bounds these lines to its own throughput, so they cannot flood, while malformed headers and over-limit refusals, which cost an attacker nothing, go into the existing one-line-a-second summary. The protection renderer then renders a jail over that line, from the error log or from the journal as it already does for journal-mode jails, and 401 leaves the `agensio-auth` filter. Finally, the access log's user field, which `format_combined` writes as `-` today, should carry verified users only. User names should be restricted at load to letters, digits and `._@-`, at most 64 bytes, so the `\S+ \S+` that all four shipped filters rely on still parses every line.

**The preset should decide what the application receives.** Stripping `Authorization` everywhere fixes Jenkins, JIRA, Bitwarden and the RFC 9110 17.16.3 harvesting risk. It also breaks WordPress's loopback on exactly the deployment the managed hosts sell, a password-protected staging site, while WordPress core has already made its Application Passwords coexist with pass-through. A per-rule `credentials = "strip" | "pass"` should therefore take its default from the preset: `pass` for WordPress and the other PHP presets, which is what nginx gives them today, and `strip` for `proxy`, `rails`, `redmine`, `django`, `wagtail` and `node`, whose applications have their own logins. In both modes, `REMOTE_USER` and `AUTH_TYPE = Basic` are set only after a successful verification, never from a decoded but unverified header (nginx's `$remote_user` mistake). A path left open leaves the request untouched, so a Bearer-token API under it keeps working. For `forward_user` on a proxy, delete the client's field unconditionally, in every spelling that maps to the same name (case-folded, `_` read as `-`), before setting the verified value. That combines the Caddy and Traefik lessons above.

**Protected answers must be private.** The presets prebuild `Cache-Control: public, max-age=...` in several places (`src/config.cpp`): WordPress's `/wp-content/uploads/` and `/wp-includes/`, Laravel's `/build/`, and Django's `/static/` and its content-hashed files. Under RFC 9111 3.5, `public` is precisely what allows a shared cache in front to reuse an authenticated response for anyone. On paths an auth rule covers, the prebuilt block should say `private` instead: one more variant of the block, built at load. The managed hosts get the same effect by switching their CDNs off.

### Smaller corrections

**Naming and realms.** `users = "none"` reads as "no user may enter", the opposite of what it means; `open = true` cannot be misread. The realm should come from the user list rather than from the site. RFC 9110 11.5 makes origin plus realm one protection space, so two rules on one site with different user lists but one realm would make a browser replay one area's credentials to the other and re-prompt back and forth. Rules that share a list should share a realm, so one prompt covers them. Realms should be validated as printable ASCII without `"` or `\`, and each rule's challenge prebuilt at load.

**One list per rule.** Keeping one user list per rule, with no groups, means a correct password for the wrong area never arises. No 403 can then tell an attacker that a guess was right, the leak Apache warns about under `AuthzSendForbiddenOnFailure`.

**Hash settings.** Caddy and Go's bcrypt write `$2a$`, which libxcrypt classes as strong; only `$2x$` is explicitly bug-compatible and should be refused. Timing each distinct setting once at load also produces the dummy hash used for timing parity. The server should warn above roughly 100 ms per verification and refuse a setting whose scratch memory, multiplied by the pool size, exceeds a ceiling: yescrypt cost 9 needs about 256 MiB per verification. Health should flag sha-crypt at 5,000 rounds as weak, and also files that mix hash kinds, because the timing of a mixed file reveals which algorithm a user has, and so which users exist.

**Builds without libxcrypt must fail closed.** The proposal compiles the feature out where libxcrypt is missing. That must be a load error for any configuration with `[[site.auth]]`, never a warning that leaves the path open. macOS's system `crypt` verifies only DES and BSDI hashes ([hashes.conf](https://github.com/besser82/libxcrypt/blob/develop/lib/hashes.conf)). Whether Homebrew packages libxcrypt, and which formats Alpine's musl verifies, could not be established; both need checking before the dependency row is written.

**Bounding the miss path.** One HTTP/2 connection can open a hundred streams carrying a hundred guesses. Verifications in flight should therefore be capped per connection and per address: 429 to the client over its cap, 503 with `Retry-After` when the pool is full. Concurrent jobs should be collapsed under the full key above, so a fresh login's parallel asset requests cost one verification, not eighteen. A queued job should be dropped when its client aborts, as E9 already does for upstream exchanges. Verification also happens before any body is read, so an unauthenticated upload never reaches php-fpm or a temporary file; with `Expect: 100-continue` the answer comes with `Connection: close`. An integration check should hold all of this.

**Plain HTTP.** A site with `redirect = "https"` already sends plain requests away before routing, so it never prompts in clear. For a site that serves both schemes, a 308 to the HTTPS URL for GET and HEAD lands the user where a prompt is allowed. The 403 that explains HTTPS stays for other methods and for sites with no HTTPS at all. Credentials that arrive in clear are never verified, and a rate-limited warning names the site so the owner knows to rotate them.

**Headers and preflights.** The site's own headers, HSTS and any configured CORS fields, must ride on the 401 too; nginx needed `always` for that ([SF 628448](https://serverfault.com/questions/628448/nginx-hsts-on-a-page-with-www-authentication)). CORS preflights should pass without credentials only on rules that ask for it with `preflight = "open"`. An application location then receives an unauthenticated `OPTIONS`, which some PHP front controllers answer like GET.

### Four additions

**A per-connection memo in front of the per-worker cache.** The proposal estimates the remembered-user path (base64 decode, user lookup, HMAC, probe) at about 0.5 µs. That is a quarter of the 2.0 µs a plain 1 KB request costs on the Linux box (CLAUDE.md performance notes). A browser sends the identical header on every request of a keep-alive or HTTP/2 connection, and over HTTP/2 a whole browsing session usually runs on one connection.

Following httpd trunk, the connection can keep the last verified value together with its generation and the user's expiry. A hit is then a length check and a constant-time compare of a few dozen bytes. The memo holds the same bytes the receive buffer held a moment earlier, and it is wiped with `explicit_bzero` at the 2-second idle shed and at close. That is a narrower window than Caddy's process-wide plaintext cache. An owner who wants no resident credential at all can keep only the HMAC and pay for it on every request.

**Per-user expiry, labels and audit.** An `expires` date and a `label` per user ("Maria, client review") turn Basic auth into the per-person, time-boxed access that panels and managed hosts lack. Both are checked at lookup, and the expiry caps any cache entry's lifetime. With the verified user in the access log, "who opened staging this week" becomes a `logs_query` by user. Health should report a site protected as a whole as an informational finding, so that a staging gate is not forgotten after launch.

**Passwords people can type, and a way around the agent.** The helper should generate passwords a client can read off a message and type: at least 15 characters (NIST's single-factor minimum), from an alphabet without look-alike characters. Each is revealed once, as `site_env` reveals, and hashed with yescrypt at cost 5. An owner who does not want the password in an agent's transcript gets `agensio ctl site-auth-user-set SITE USER --prompt`, read from the terminal without echo.

Hand-written files in `user:hash` format with `#` comments let administrators bring their bcrypt and sha-crypt files from nginx and Apache. Their `$apr1$` lines are refused, with the re-hash command in the error, because apr1 is crackable offline. The reason operators chose it, per-request cost, disappears with the cache.

**A clear seam for what comes later.** The evidence asks next for signed expiring links and a styled login page that sets a cookie, then for forward auth to SSO. Keeping the auth rule's interface as "credentials in, verified identity out" lets a link or cookie source later feed the same `REMOTE_USER`, log field and cache.

### The owner's five decisions

**The platform rule** (libxcrypt, compiled out where it is missing) is right as long as it fails closed. libxcrypt is LGPL-2.1+, linked dynamically and already part of Debian, Ubuntu and Fedora base systems, so it needs one row in the dependency table. **No prompt over plain HTTP** is right too, with a redirect for GET and HEAD where HTTPS exists; no incumbent constrains this, and browsers are converging on it. **Removing `Authorization` by default** should become a per-preset default instead, as the fourth change above argues, with WordPress's documented loopback as the deciding evidence. **Users kept by the helper, in a second step,** is right, provided hand-written, htpasswd-compatible files ship first, so the feature is usable and testable before the helper exists.

**`skip_for` as the only way to combine addresses and passwords** is right. "Address and password" is then the composition of `[[site.access]]` with `[[site.auth]]`, and "address or password" is `skip_for`, which avoids the opposite defaults that confuse nginx and Apache users and answers Traefik's most-reacted issue. `skip_for` should refuse `"any"`, which would silently disable the rule, and its entries should go through the same `access_notices` warnings as access rules, such as a loopback entry behind a local proxy.

### Cost and tests

| Request | Work on the request path |
|---|---|
| Site without auth rules | One emptiness test |
| Site with rules, path no rule covers | One bit test (the access rules' first-byte bitmap) |
| Covered path, `skip_for` address | Compare of the already-parsed address |
| Covered path, returning connection | Header lookup and a constant-time byte compare (memo) |
| Covered path, new connection, remembered user | Base64 decode, user lookup, HMAC with keyed state set up once per worker, cache probe |
| First login or a guess | Queued to the verifier pool: 6.6 ms at yescrypt cost 5, never on the worker |

**The A/B gate.** `bench/ab.sh <ref> -A` should gain three rows: a covered path with a remembered user over HTTP/1 keep-alive, the same over HTTP/2 with ten streams, and an uncovered path on a site with auth rules.

**The tests.** Under the project's test-first rule, each of the following should fail before its code exists. The `Authorization` parser needs cases for scheme case, spaces, RFC 4648 padding, the split at the first colon, refused CTL and NUL bytes (a NUL would otherwise truncate the input to `crypt_rn`) and a length cap before decoding, plus a fuzz target like every other parser. The cache needs the two-file case and a reload that keeps its entries. The jail filter must not match a credential-less 401, covered paths must answer `private` where the preset says `public`, and WordPress's loopback must pass in the test bed.

## Conclusion

The servers' histories turn the usual framing around: performance work on password verification is security work. The weakest defaults in the field, `$apr1$` as `htpasswd`'s default and `{SHA}` among nginx's accepted formats, survive because hashing on every request makes strong hashes unaffordable. Traefik's three advisories in 2026 came from a missing dummy hash, a broken fix for it and a deduplication shortcut, not from cryptography. In agensio, the cache key, the pool's bounds and the dummy hash therefore deserve the scrutiny the project gives its parsers. So does the fail2ban jail, because it is the one component whose meaning changes when Basic auth arrives: the first 401 of every login is a normal event, not a failed attempt.

agensio's advantage is the one the access-control research found. Rule, router, normaliser, log format, fail2ban renderer, presets and control plane are one codebase. That lets it make per-application decisions that nginx leaves to every administrator: WordPress keeps its credentials while Jenkins never sees them, protected assets turn private, and the preset already knows which WordPress paths must stay open. Basic auth will not fix what users dislike about the browser's dialog. A gate with a name, an end date and a log line per person is still worth building now, because it is what agencies improvise today with one shared staging password, and a later signed-link login can reuse it.
