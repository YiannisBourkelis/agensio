## Notes

- Throughput is the application's: eight php-fpm children at 2.2-2.3 ms of CPU per request
  cap both servers at about 3.4k (welcome page, 78 KB) and 3.5k (`/json`) req/s; latency is
  the queue in front of those children. The web server's own cost is the `web us/req`
  column: agensio 85-86 us vs nginx 110-111 us on the 78 KB page (22 % less), 54-55 vs
  58-59 us on the JSON route (7 % less). Both numbers are dominated by the TCP connection
  opened to php-fpm for every request (FastCGI keep-alive is off in both configurations)
  and, on the page, by copying 78 KB in and out.
- FastCGI keep-alive (`bench/results/laravel-20260917-100827.md`, agensio only,
  `keep_conn = true, max_connections = 8` so no child is pinned by an idle connection
  the others cannot use): `/json` 3840 req/s at 26.6 us per request (half the CPU, p99
  19 ms). The 78 KB page however dropped to 1354 req/s (p50 44 ms) with no errors; not
  understood yet, docker-proxy sits on the path (the pool is a published container port).
  Noted in the roadmap under C3b; `keep_conn` stays off by default.
- Bed changes needed for a meaningful run (in `bench/laravel/.ddev/setup.sh`): Laravel's
  default `SESSION_DRIVER=database` on sqlite serialises every request on the session
  table (170 req/s at 3 ms of CPU); `file` sessions leave one file per benchmark request
  behind and the session garbage collection tripled the CPU per request after 80k files.
  `cookie` sessions keep no server state: stable at 2.2 ms per request.
- Harness lesson: wrk ends a run by closing its 64 connections with their requests still
  queued for php-fpm. agensio notices a closed client only when it writes the response
  (roadmap E9), so those requests keep their queue slots until the children have executed
  them, and a run started immediately afterwards begins with a 0.5 s burst of 503s.
  `bench.sh` waits 2 s after the warm-up and between cases; the rows above have no errors.
- The php-fpm children respawn every 500 requests (`pm.max_requests`), so their CPU is
  read from the web container's cgroup, not from the processes.
