## 1. Content codings, the registry, and what Content-Encoding means (RFC 9110 8.4, 16.6, 18.6)

### Takeaway
A content coding is a property of the representation, not of the message. Once a server applies gzip, the gzip bytes are the representation: Content-Length, ETag and byte ranges all describe the coded form. The sender that applies a coding MUST list it in Content-Encoding, in the order applied. "identity" SHOULD NOT appear there. The IANA registry now lists br, zstd, dcb and dcz next to RFC 9110's gzip, deflate and compress.

### Cited Findings
- "If one or more encodings have been applied to a representation, the sender that applied the encodings MUST generate a Content-Encoding header field that lists the content codings in the order in which they were applied. Note that the coding named "identity" is reserved for its special role in Accept-Encoding and thus SHOULD NOT be included." — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)
- "Unlike Transfer-Encoding (Section 6.1 of [HTTP/1.1]), the codings listed in Content-Encoding are a characteristic of the representation; the representation is defined in terms of the coded form, and all other metadata about the representation is about the coded form unless otherwise noted in the metadata definition." — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)
- Formats with built-in compression are not tagged again: "If the media type includes an inherent encoding, such as a data format that is always compressed, then that encoding would not be restated in Content-Encoding even if it happens to be the same algorithm as one of the content codings." — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)
- Content-Encoding is a list (`Content-Encoding = #content-coding`), and content codings are case-insensitive tokens that "ought to be registered within the "HTTP Content Coding Registry"". — [RFC 9110 8.4, 8.4.1](https://www.rfc-editor.org/rfc/rfc9110#section-8.4.1)
- Aliases: "A recipient SHOULD consider "x-gzip" to be equivalent to "gzip"", and the same for "x-compress" and "compress". — [RFC 9110 8.4.1.1, 8.4.1.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.4.1.3)
- deflate is ambiguous in practice: "The "deflate" coding is a "zlib" data format [RFC1950] containing a "deflate" compressed data stream [RFC1951] ... *Note:* Some non-conformant implementations send the "deflate" compressed data without the zlib wrapper." — [RFC 9110 8.4.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-8.4.1.2)
- Registry rules: registrations need Name, Description and a pointer to the specification. "Names of content codings MUST NOT overlap with names of transfer codings ... unless the encoding transformation is identical (as is the case for the compression codings defined in Section 8.4.1)". New values require IETF Review. — [RFC 9110 16.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-16.6.1)
- RFC 9110's own table registers compress, deflate, gzip, identity ("Reserved"), x-compress and x-gzip (the last two "Deprecated"). — [RFC 9110 18.6](https://www.rfc-editor.org/rfc/rfc9110#section-18.6)
- The IANA "HTTP Content Coding Registry" (file updated 2025-10-02) lists: aes128gcm (RFC 8188), br (RFC 7932), compress, dcb (RFC 9842), dcz (RFC 9842), deflate, exi (W3C), gzip, identity (Reserved), pack200-gzip, x-compress, x-gzip, and zstd ("A stream of bytes compressed using the Zstandard protocol with a Window_Size of not more than 8 MB", RFC 9659 and RFC 8878). — [IANA HTTP Parameters](https://www.iana.org/assignments/http-parameters/)
- An origin server MAY answer 415 when a request's content coding is not acceptable. This rule concerns request bodies, not response negotiation: "An origin server MAY respond with a status code of 415 (Unsupported Media Type) if a representation in the request message has a content coding that is not acceptable." — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)

### Inferences
- Because "deflate" is ambiguous ([RFC 9110 8.4.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-8.4.1.2)), a server gains nothing by producing it when gzip, br or zstd is offered. A decoder of request bodies has to choose whether to tolerate raw deflate.
- Several codings can be stacked (`Content-Encoding: gzip, br`). A compressor should never stack its own coding on a response that already has a Content-Encoding. nginx, Apache, Caddy and Django all skip such responses (sections 4 and 12). A request-body decoder must bound the total output across every layer (section 14).
- The aes128gcm entry shows that not every registered coding compresses. A server that sees an unknown Content-Encoding on an upstream response should pass it through untouched.

### Gaps
- None found for the standards text.

## 2. Accept-Encoding negotiation: q-values, "identity", "*", and what to do when nothing is acceptable (RFC 9110 12.1, 12.4, 12.5.3)

### Takeaway
RFC 9110 12.5.3 gives three acceptability rules. Without an Accept-Encoding field, any coding is acceptable. Identity is acceptable unless the field excludes it with `identity;q=0`, or with `*;q=0` and no explicit identity entry. A listed coding is acceptable unless its q is 0. When nothing listed is available, the origin SHOULD send identity unless identity is excluded. In that case it may either send 406 or ignore the field and send identity anyway. 415 is never the answer to response negotiation; it is for request content.

### Cited Findings
- Grammar: `Accept-Encoding = #( codings [ weight ] )`, `codings = content-coding / "identity" / "*"`. "The asterisk "*" symbol in an Accept-Encoding field matches any available content coding not explicitly listed in the field." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- The three rules, verbatim: "1. If no Accept-Encoding header field is in the request, any content coding is considered acceptable by the user agent. 2. If the representation has no content coding, then it is acceptable by default unless specifically excluded by the Accept-Encoding header field stating either "identity;q=0" or "*;q=0" without a more specific entry for "identity". 3. If the representation's content coding is one of the content codings listed in the Accept-Encoding field value, then it is acceptable unless it is accompanied by a qvalue of 0." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- Choosing among codings: "When selecting between multiple content codings that have the same purpose, the acceptable content coding with the highest non-zero qvalue is preferred." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- An empty field: "An Accept-Encoding header field with a field value that is empty implies that the user agent does not want any content coding in response." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- No acceptable coding: "If a non-empty Accept-Encoding header field is present in a request and none of the available representations for the response have a content coding that is listed as acceptable, the origin server SHOULD send a response without any content coding unless the identity coding is indicated as unacceptable." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- When even identity is excluded: "the origin server can either honor the header field by sending a 406 (Not Acceptable) response or disregard the header field by treating the response as if it is not subject to content negotiation for that request header field." — [RFC 9110 12.4.1](https://www.rfc-editor.org/rfc/rfc9110#section-12.4.1). A user agent "cannot rely on proactive negotiation preferences being consistently honored, since the origin server ... might decide that sending a response that doesn't conform to the user agent's preferences is better than sending a 406 (Not Acceptable) response." — [RFC 9110 12.1](https://www.rfc-editor.org/rfc/rfc9110#section-12.1)
- 406 content: "The server SHOULD generate content containing a list of available representation characteristics and corresponding resource identifiers". — [RFC 9110 15.5.7](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.7)
- q-values: range 0 to 1, "a value of 0 means "not acceptable". If no "q" parameter is present, the default weight is 1." `qvalue = ( "0" [ "." 0*3DIGIT ] ) / ( "1" [ "." 0*3("0") ] )`; "A sender of qvalue MUST NOT generate more than three digits after the decimal point." The parameter name "q" is case-insensitive. — [RFC 9110 12.4.2](https://www.rfc-editor.org/rfc/rfc9110#section-12.4.2)
- Preferences cover error pages too: "The preferences sent in these fields apply to any content in the response, including representations of the target resource, representations of error or processing status". — [RFC 9110 12.1](https://www.rfc-editor.org/rfc/rfc9110#section-12.1)
- 415 belongs to request content codings: "Servers that fail a request due to an unsupported content coding ought to respond with a 415 (Unsupported Media Type) status and include an Accept-Encoding header field in that response ... servers that fail a request with a 415 status for reasons unrelated to content codings MUST NOT include the Accept-Encoding header field." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3); also [RFC 9110 15.5.16](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.16) and the original [RFC 7694 section 3](https://www.rfc-editor.org/rfc/rfc7694#section-3)
- What servers do in practice: Django's GZipMiddleware will not compress when "The request (the browser) hasn't sent an `Accept-Encoding` header containing `gzip`" ([Django middleware docs](https://docs.djangoproject.com/en/5.2/ref/middleware/)). With no client q-factors, Caddy uses the first supported coding in its own order, zstd then gzip by default ([Caddy encode docs](https://caddyserver.com/docs/caddyfile/directives/encode)).

### Inferences
- Rule 1 allows compressing when Accept-Encoding is absent, but every server checked compresses only when the client asks. A client without the field (an old HTTP/1.0 tool, a health checker) may not decode. The safe default is identity when the field is absent.
- 406 is optional. Sending identity is always conformant unless identity is excluded, and even then 12.4.1 allows ignoring the field. A server does not need 406 for content codings unless it wants strictness.
- A parser needs to handle `*`, `identity`, `q=0`, case-insensitive tokens and the "x-gzip" alias. The aliases are recipient-side SHOULDs in 8.4.1, so honouring them in Accept-Encoding is reasonable, but the server should send the canonical names.
- On ties (equal q), the RFC defines no order, so the server's own preference order decides. Caddy's default prefers zstd, then gzip.

### Gaps
- RFC 9110 does not say whether a server should keep the client's list order on equal q. Implementations differ; not researched here.

## 3. Vary: when to send Vary: Accept-Encoding, including on uncompressed responses (RFC 9110 12.5.5; RFC 9111 4.1)

### Takeaway
Any cacheable response whose coding depends on Accept-Encoding SHOULD carry `Vary: Accept-Encoding`, the identity variant included. RFC 9111 describes leaving Vary off the default (identity) response as a mistake that makes caches prefer that response. 304 and 206 responses MUST repeat the Vary that the 200 would carry.

### Cited Findings
- "An origin server SHOULD generate a Vary header field on a cacheable response when it wishes that response to be selectively reused for subsequent requests. Generally, that is the case when the response content has been tailored to better fit the preferences expressed by those selecting header fields". — [RFC 9110 12.5.5](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.5)
- Vary lists fields that "might have had a role in selecting the representation", and its example says the server "might have used the request's Accept-Encoding and Accept-Language header fields (or lack thereof) as determining factors". — [RFC 9110 12.5.5](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.5)
- Caches: "the cache MUST NOT use that stored response without revalidation unless all the presented request header fields nominated by that Vary field value match those fields in the original request". If a field is absent from a request, "it can only match another request if it is also absent there"; "A stored response with a Vary header field value containing a member "*" always fails to match." — [RFC 9111 4.1](https://www.rfc-editor.org/rfc/rfc9111#section-4.1)
- The identity variant: "Some resources mistakenly omit the Vary header field from their default response (i.e., the one sent when the request does not express any preferences), with the effect of choosing it for subsequent requests to that resource even when more preferable responses are available. When a cache has multiple stored responses for a target URI and one or more omits the Vary header field, the cache SHOULD choose the most recent ... stored response with a valid Vary field value." — [RFC 9111 4.1](https://www.rfc-editor.org/rfc/rfc9111#section-4.1)
- Vary may be left off: "Vary might be elided when an origin server considers variance in content selection to be less significant than Vary's performance impact on caching, particularly when reuse is already limited by cache response directives". "A proxy MUST NOT generate "*" in a Vary field value." — [RFC 9110 12.5.5](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.5)
- 304 MUST carry Vary: "The server generating a 304 response MUST generate any of the following header fields that would have been sent in a 200 (OK) response to the same request: Content-Location, Date, ETag, and Vary; Cache-Control and Expires". — [RFC 9110 15.4.5](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.5)
- 206 MUST carry Vary: "A server that generates a 206 response MUST generate the following header fields ... if the field would have been sent in a 200 (OK) response to the same request: Date, Cache-Control, ETag, Expires, Content-Location, and Vary." — [RFC 9110 15.3.7](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.7)
- Server practice:
  - nginx sends nothing by default: `gzip_vary off;`, which "Enables or disables inserting the "Vary: Accept-Encoding" response header field if the directives gzip, gzip_static, or gunzip are active" ([nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)).
  - Apache's mod_deflate adds Vary even when it does not compress. Its source says "Even if we don't accept this request based on it not having the Accept-Encoding, we need to note that we were looking for this header and downstream proxies should be aware of that" before `apr_table_mergen(r->headers_out, "Vary", "Accept-Encoding")` ([mod_deflate.c, httpd trunk 49166911](https://github.com/apache/httpd/blob/49166911e75cecd58c28005e5dd94d743899b715/modules/filters/mod_deflate.c)). Its docs advise `Vary: *` when the decision depends on other information, such as the HTTP version ([mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)).
  - Caddy adds Vary to compressed responses, and adds it to 304s explicitly, citing RFC 9110 15.4.5 and its issue #5849 ([encode.go, caddy 4e8de214](https://github.com/caddyserver/caddy/blob/4e8de214bc77bce405a5355a9d17d4845823c684/modules/caddyhttp/encode/encode.go)).
- RFC 9842 makes Vary a MUST for dictionary codings: "If the response is cacheable, it MUST include a "Vary" header ... For example: Vary: accept-encoding, available-dictionary". — [RFC 9842 6.2](https://www.rfc-editor.org/rfc/rfc9842#section-6.2)

### Inferences
- A resource is "negotiable" when the server might compress it for some request (a type and size that qualify). Every 200, 206 and 304 for such a resource should carry `Vary: Accept-Encoding`, whether this particular response was compressed or not. Apache works this way. nginx's default does not.
- Vary on a response that is never compressed (an image type the server never compresses, or one below the minimum size for every request) costs shared caches a split key for nothing. The RFC lets the server leave it off.
- If the compression decision also depends on User-Agent, HTTP version or anything other than Accept-Encoding, that dependency belongs in Vary too. Apache's docs say exactly this.

### Gaps
- I did not check how many CDNs normalise Accept-Encoding before keying. That is outside this standards-and-security scope.

## 4. Validators: ETag and Last-Modified for compressed variants (RFC 9110 8.8), and what servers do

### Takeaway
A strong ETag shared by the gzip and identity variants is not strong, by definition. The server must either give each coded variant its own strong ETag or mark the shared tag weak (W/). Weak tags still work for If-None-Match (weak comparison). They do not work for If-Range or If-Match, which use strong comparison, so weakening loses ranges and lost-update checks on compressed variants. Servers split: nginx and Django weaken; Apache and Caddy append a suffix such as "-gzip". A suffix needs If-None-Match translated back on the way in, which Caddy does and Apache's default does not. Last-Modified needs no change for the coding.

### Cited Findings
- Definition: "A "strong validator" is representation metadata that changes value whenever a change occurs to the representation data that would be observable in the content of a 200 (OK) response to GET." — [RFC 9110 8.8.1](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.1)
- The gzip case is named: "a validator is weak if it is shared by two or more representations of a given resource at the same time, unless those representations have identical representation data. For example, if the origin server sends the same validator for a representation with a gzip content coding applied as it does for a representation with no content coding, then that validator is weak." — [RFC 9110 8.8.1](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.1)
- MUST mark weak: "If an origin server provides an entity tag for a representation and the generation of that entity tag does not satisfy all of the characteristics of a strong validator (Section 8.8.1), then the origin server MUST mark the entity tag as weak by prefixing its opaque value with "W/" (case-sensitive)." — [RFC 9110 8.8.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3)
- The worked example in 8.8.3.3 sends ETag "123-a" for the identity variant and "123-b" for gzip, both with `Vary: Accept-Encoding`. "*Note:* Content codings are a property of the representation data, so a strong entity tag for a content-encoded representation has to be distinct from the entity tag of an unencoded representation to prevent potential conflicts during cache updates and range requests. In contrast, transfer codings ... apply only during message transfer and do not result in distinct entity tags." — [RFC 9110 8.8.3.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.3)
- Strong vs weak comparison, and where each applies: strong validators are "usable for all conditional requests, including cache validation, partial content ranges, and "lost update" avoidance"; weak ones only "when the client does not require exact equality". — [RFC 9110 8.8.1](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.1); comparison table in [RFC 9110 8.8.3.2](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.2)
- If-Range needs strong comparison: "If the entity-tag validator provided exactly matches the ETag field value for the selected representation using the strong comparison function (Section 8.8.3.2), the condition is true." "A client MUST NOT generate an If-Range header field containing an entity tag that is marked as weak." — [RFC 9110 13.1.5](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.5)
- Caches pick which stored variant a 304 refreshes by strong validator first: "If the new response contains one or more "strong validators" ... All the stored responses in the initial set with one of those same strong validators are identified for update." With only weak validators, "the most recent of those matching stored responses is identified for update". — [RFC 9111 4.3.4](https://www.rfc-editor.org/rfc/rfc9111#section-4.3.4)
- Last-Modified: "An origin server SHOULD send Last-Modified for any selected representation for which a last modification date can be reasonably and consistently determined"; an origin with a clock "MUST NOT generate a Last-Modified date that is later than the server's time of message origination". As a validator it is "implicitly weak unless it is possible to deduce that it is strong". — [RFC 9110 8.8.2.1, 8.8.2.2](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.2.1)
- nginx (since 1.7.3, 08 Jul 2014): "weak entity tags are now preserved on response modifications, and strong ones are changed to weak." — [nginx CHANGES](https://nginx.org/en/CHANGES). The gzip filter calls `ngx_http_weak_etag(r)` when it compresses ([ngx_http_gzip_filter_module.c, nginx 9a7439fd](https://github.com/nginx/nginx/blob/9a7439fd79076de03c408de136ba1772347030c2/src/http/modules/ngx_http_gzip_filter_module.c)).
- Django: "If the response has an `ETag` header, the ETag is made weak to comply with RFC 9110 Section 8.8.1." — [Django GZipMiddleware](https://docs.djangoproject.com/en/5.2/ref/middleware/)
- Apache: `DeflateAlterETag AddSuffix|NoChange|Remove`, default AddSuffix (the directive exists since 2.4.58). The docs: AddSuffix "Append[s] the compression method onto the end of the ETag ... This has been the default since 2.4.0, but prevents serving "HTTP Not Modified" (304) responses to conditional requests for compressed content." NoChange "does not satisfy the HTTP/1.1 property that all representations of the same resource have unique ETags." Remove drops the ETag from compressed responses. — [mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html). The source comment reads "This routine appends -transform (e.g., -gzip) to the entity-tag" ([mod_deflate.c](https://github.com/apache/httpd/blob/49166911e75cecd58c28005e5dd94d743899b715/modules/filters/mod_deflate.c)).
- Caddy appends `-<encoding>` to strong ETags only (`if etag != "" && !strings.HasPrefix(etag, "W/")`). It strips that suffix from If-None-Match before passing the request on, with the comment: "the client will send back that Etag in an If-None-Match header, but upstream handlers that set the Etag in the first place don't know that we appended to their Etag! so here we have to strip our addition". — [encode.go](https://github.com/caddyserver/caddy/blob/4e8de214bc77bce405a5355a9d17d4845823c684/modules/caddyhttp/encode/encode.go)

### Inferences
- For on-the-fly compression, Caddy's design is the only one of the four that keeps strong validators and still answers 304. Each variant gets a distinct strong tag (base tag plus "-gzip", "-br", "-zstd"), and the suffix is stripped when matching If-None-Match. The RFC does not prescribe a scheme; 8.8.3.1 only says a tag might combine a revision with "a variance identifier for content negotiation" ([RFC 9110 8.8.3.1](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.1)).
- A per-coding strong tag is honest only if the coded bytes are stable. On-the-fly output changes with compressor version, level and buffering. Strictly, a strong tag must change "whenever a change occurs to the representation data", so a server that may recompress the same file differently (a level change, a library upgrade) should either keep the output stable for the tag's lifetime or tag on-the-fly variants weak. Pre-compressed twins on disk have fixed bytes and can carry a strong tag of their own, for example one derived from the twin's own mtime and size.
- Weakening (nginx, Django) is the simplest conformant choice. It costs If-Range (a weak tag can never satisfy it, so a resumed download restarts with a full 200) and If-Match.

### Gaps
- Apache's 304 failure with AddSuffix is stated in its docs. I did not look up the httpd bug tracker entry.

## 5. Content-Length, Range, If-Range and 206 with content codings (RFC 9110 8.6, 14, 13.1.5, 15.3.7)

### Takeaway
Content-Length and byte ranges count the encoded bytes. A server compressing on the fly cannot know the length in advance, so it drops Content-Length and frames the body by chunked encoding (HTTP/1.1), END_STREAM (HTTP/2, HTTP/3) or connection close (HTTP/1.0). It also cannot serve ranges of a representation it has not produced yet. Ranges are optional, and nginx, Apache and Caddy all avoid compressing partial responses.

### Cited Findings
- Content-Length "indicates the associated representation's data length as a decimal non-negative integer number of octets. When transferring a representation as content, Content-Length refers specifically to the amount of data enclosed so that it can be used to delimit framing". — [RFC 9110 8.6](https://www.rfc-editor.org/rfc/rfc9110#section-8.6). Because 8.4 says the representation "is defined in terms of the coded form", that length is the coded length ([RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)).
- "in the absence of Transfer-Encoding, an origin server SHOULD send a Content-Length header field when the content size is known prior to sending the complete header section." — [RFC 9110 8.6](https://www.rfc-editor.org/rfc/rfc9110#section-8.6)
- Ranges count encoded bytes: "If the representation data has a content coding applied, each byte range is calculated with respect to the encoded sequence of bytes, not the sequence of underlying bytes that would be obtained after decoding." — [RFC 9110 14.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-14.1.2)
- Ranges are optional: "Range requests are an OPTIONAL feature of HTTP ... recipients not implementing this feature (or not supporting it for the target resource) can respond as if it is a normal GET request". "A server MAY ignore the Range header field. However, origin servers and intermediate caches ought to support byte ranges when possible". — [RFC 9110 14, 14.2](https://www.rfc-editor.org/rfc/rfc9110#section-14.2)
- If-Range: "A recipient of an If-Range header field MUST ignore the Range header field if the If-Range condition evaluates to false." An entity-tag If-Range is true only on a strong match (section 4 above). "An origin server MUST ignore an If-Range header field received in a request for a target resource that does not support Range requests." — [RFC 9110 13.1.5](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.5)
- 206 headers: Date, Cache-Control, ETag, Expires, Content-Location and Vary MUST be sent when a 200 would have them. "A Content-Length header field present in a 206 response indicates the number of octets in the content of this message". — [RFC 9110 15.3.7](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.7)
- Server practice:
  - Caddy disables encoding for 206 ("partial representations must not be dynamically re-encoded") and removes `Accept-Ranges` when it encodes ("we don't know ranges for dynamically-encoded content"), deleting Content-Length too ([encode.go](https://github.com/caddyserver/caddy/blob/4e8de214bc77bce405a5355a9d17d4845823c684/modules/caddyhttp/encode/encode.go)).
  - nginx compresses only statuses 200, 403 and 404, then calls `ngx_http_clear_content_length` and `ngx_http_clear_accept_ranges` ([ngx_http_gzip_filter_module.c](https://github.com/nginx/nginx/blob/9a7439fd79076de03c408de136ba1772347030c2/src/http/modules/ngx_http_gzip_filter_module.c)).
  - Apache's mod_deflate skips responses carrying `Content-Range`, as well as 204s, subrequests and the `no-gzip` environment variable ([mod_deflate.c](https://github.com/apache/httpd/blob/49166911e75cecd58c28005e5dd94d743899b715/modules/filters/mod_deflate.c)). Its docs warn about request inflation: "don't trust the Content-Length header! The Content-Length header reflects the length of the incoming data from the client and not the byte count of the decompressed data stream." ([mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html))

### Inferences
- A conformant design for on-the-fly compression: for a Range request, either ignore the Range and send the full response (compressed if acceptable), or serve the range from the identity representation with the identity ETag and `Vary: Accept-Encoding`. Never compress a 206 on the fly. When compressing, drop `Accept-Ranges: bytes` so clients do not assume the coded variant supports ranges.
- A pre-compressed file is a stable coded representation, so ranges over its bytes are legitimate ("calculated with respect to the encoded sequence of bytes"). That requires a strong ETag of its own, Content-Range against the twin's size, and Vary.
- Ignoring Range on a coded variant is allowed (14.2 MAY). Answering an identity 206 to a client that sent `Accept-Encoding: gzip` is also allowed. Both are choices the RFC permits; neither is required.

### Gaps
- I found no normative text on serving `Range` with `Accept-Encoding` where the client expects the range to apply to a specific coded variant. The RFC's only answer is the strong-ETag binding through If-Range.

## 6. HEAD, 204 and 304 (RFC 9110 6.4.1, 8.6, 9.3.2, 15.3.5, 15.4.5; RFC 9111 3.2)

### Takeaway
None of these responses has content, so nothing is compressed. HEAD SHOULD carry the same fields as GET, including the Content-Encoding the GET would get. It MAY omit fields known only once the content is produced, such as a compressed Content-Length, and MUST NOT send a Content-Length different from the GET's. A 204 MUST NOT carry Content-Length. A 304 MUST carry the ETag and Vary the 200 would carry. It SHOULD NOT carry other representation metadata, Content-Encoding included. If it does, that metadata must match the stored variant, because caches merge it into what they hold.

### Cited Findings
- "Responses to the HEAD request method (Section 9.3.2) never include content ... All 1xx (Informational), 204 (No Content), and 304 (Not Modified) responses do not include content." — [RFC 9110 6.4.1](https://www.rfc-editor.org/rfc/rfc9110#section-6.4.1)
- HEAD: "The server SHOULD send the same header fields in response to a HEAD request as it would have sent if the request method had been GET. However, a server MAY omit header fields for which a value is determined only while generating the content. For example, some servers buffer a dynamic response to GET ... Such a response to GET might contain Content-Length and Vary fields, for example, that are not generated within a HEAD response. These minor inconsistencies are considered preferable to generating and discarding the content for a HEAD request". — [RFC 9110 9.3.2](https://www.rfc-editor.org/rfc/rfc9110#section-9.3.2)
- HEAD Content-Length: "a server MUST NOT send Content-Length in such a response unless its field value equals the decimal number of octets that would have been sent in the content of a response if the same request had used the GET method." — [RFC 9110 8.6](https://www.rfc-editor.org/rfc/rfc9110#section-8.6)
- HEAD and caches: "A response to the HEAD method is identical to what an equivalent request made with a GET would have been, without sending the content. This property of HEAD responses can be used to invalidate or update a cached GET response". — [RFC 9111 4.3.5](https://www.rfc-editor.org/rfc/rfc9111#section-4.3.5)
- 204: "A server MUST NOT send a Content-Length header field in any response with a status code of 1xx (Informational) or 204 (No Content)." — [RFC 9110 8.6](https://www.rfc-editor.org/rfc/rfc9110#section-8.6). Also "A server MUST NOT send a Transfer-Encoding header field in any response with a status code of 1xx (Informational) or 204 (No Content)." — [RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1)
- 304, required fields: Content-Location, Date, ETag and Vary, plus Cache-Control and Expires, whenever a 200 would carry them. Then: "a sender SHOULD NOT generate representation metadata other than the above listed fields unless said metadata exists for the purpose of guiding cache updates (e.g., Last-Modified might be useful if the response does not have an ETag field)." "A 304 response is terminated by the end of the header section; it cannot contain content or trailers." — [RFC 9110 15.4.5](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.5)
- 304 Content-Length: "a server MUST NOT send Content-Length in such a response unless its field value equals the decimal number of octets that would have been sent in the content of a 200 (OK) response to the same request." — [RFC 9110 8.6](https://www.rfc-editor.org/rfc/rfc9110#section-8.6)
- Caches merge 304 fields into the stored response, Content-Length excepted, and Content-Encoding is called out as dangerous: "a browser might decode the content coding of a response while it is being received, creating a disconnect between the data it has stored and the response's original metadata. Updating that stored metadata with a different Content-Encoding header field would be problematic." — [RFC 9111 3.2](https://www.rfc-editor.org/rfc/rfc9111#section-3.2)
- Server practice:
  - nginx skips gzip on `r->header_only` responses, which covers HEAD and 304 ([ngx_http_gzip_filter_module.c](https://github.com/nginx/nginx/blob/9a7439fd79076de03c408de136ba1772347030c2/src/http/modules/ngx_http_gzip_filter_module.c)).
  - Caddy, for a HEAD with a declared Content-Length above its minimum, runs its header setup (adds Content-Encoding and Vary, deletes Content-Length, rewrites the ETag) without writing a body ([encode.go](https://github.com/caddyserver/caddy/blob/4e8de214bc77bce405a5355a9d17d4845823c684/modules/caddyhttp/encode/encode.go)).
  - Apache's mod_deflate handles 304 by changing only the headers; it has explicit `HTTP_NOT_MODIFIED` branches ([mod_deflate.c](https://github.com/apache/httpd/blob/49166911e75cecd58c28005e5dd94d743899b715/modules/filters/mod_deflate.c)).

### Inferences
- Best fit for HEAD: run the same negotiation as GET and send Content-Encoding and Vary. Drop Content-Length for an on-the-fly coding, since the coded length is unknown. For a pre-compressed twin, send the twin's exact Content-Length. If HEAD skips compression entirely, as nginx does, HEAD and GET disagree on Content-Encoding and ETag. The 9.3.2 SHOULD tolerates some inconsistency, but 9111 4.3.5 lets a cache use a HEAD to update or invalidate stored GETs, so the mismatch can cost cache entries.
- A 304's ETag must be the tag of the variant this request would have received under its own Accept-Encoding. If the ETag is suffixed per coding, a 304 to a gzip-accepting client carries the "-gzip" tag and `Vary: Accept-Encoding`. Content-Encoding is best left off; RFC 9111 3.2's warning shows how it can corrupt a cache.
- A 204 has nothing to compress. A compressing filter must not add Content-Encoding or Vary-only changes that imply content to a 204. Apache skips 204 explicitly.

### Gaps
- None for the normative text.

## 7. Transfer codings vs content codings; TE (RFC 9110 10.1.4; RFC 9112 6.1, 6.2, 7)

### Takeaway
`TE: gzip` with `Transfer-Encoding: gzip, chunked` is hop-by-hop compression in HTTP/1.1 only. It does not change the representation, so ETag, Range and Vary stay the same, but browsers do not use it. HTTP/2 and HTTP/3 forbid Transfer-Encoding outright. Content-Encoding is the end-to-end form everyone uses. A server may offer compression transfer codings only to an HTTP/1.1 client whose TE lists them, and must keep chunked as the final coding or close the connection.

### Cited Findings
- "Unlike Content-Encoding ..., Transfer-Encoding is a property of the message, not of the representation. Any recipient along the request/response chain MAY decode the received transfer coding(s) or apply additional transfer coding(s) to the message body, assuming that corresponding changes are made to the Transfer-Encoding field value." — [RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1)
- Framing: "If any transfer coding other than chunked is applied to a response's content, the sender MUST either apply chunked as the final transfer coding or terminate the message by closing the connection." "A sender MUST NOT apply the chunked transfer coding more than once". Example: `Transfer-Encoding: gzip, chunked`. — [RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1)
- HTTP/1.0 clients: "A server MUST NOT send a response containing Transfer-Encoding unless the corresponding request indicates HTTP/1.1 (or later minor revisions)." — [RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1)
- "A sender MUST NOT send a Content-Length header field in any message that contains a Transfer-Encoding header field." — [RFC 9112 6.2](https://www.rfc-editor.org/rfc/rfc9112#section-6.2)
- The compression transfer codings (compress, deflate, gzip) "are defined by the same algorithm as their corresponding content coding", and "The presence of parameters with any of these compression codings SHOULD be treated as an error." — [RFC 9112 7.2](https://www.rfc-editor.org/rfc/rfc9112#section-7.2)
- TE: "If the TE field value is empty or if no TE field is present, the only acceptable transfer coding is chunked. A message with no transfer coding is always acceptable." "A client MUST NOT send the chunked transfer coding name in TE"; a sender of TE "MUST also send a "TE" connection option within the Connection header field". — [RFC 9112 7.4](https://www.rfc-editor.org/rfc/rfc9112#section-7.4); grammar in [RFC 9110 10.1.4](https://www.rfc-editor.org/rfc/rfc9110#section-10.1.4)
- Transfer codings give no new ETag: "transfer codings ... apply only during message transfer and do not result in distinct entity tags." — [RFC 9110 8.8.3.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.3). no-transform does not cover them: it "does not apply to message transformations that do not change the content, such as the addition or removal of transfer codings". — [RFC 9110 7.7](https://www.rfc-editor.org/rfc/rfc9110#section-7.7)
- HTTP/2: "An endpoint MUST NOT generate an HTTP/2 message containing connection-specific header fields ... (that is, Proxy-Connection, Keep-Alive, Transfer-Encoding, and Upgrade)." TE "MAY be present in an HTTP/2 request; when it is, it MUST NOT contain any value other than "trailers"." — [RFC 9113 8.2.2](https://www.rfc-editor.org/rfc/rfc9113#section-8.2.2)
- HTTP/3: "Transfer codings (see Section 7 of [HTTP/1.1]) are not defined for HTTP/3; the Transfer-Encoding header field MUST NOT be used." — [RFC 9114 4.1](https://www.rfc-editor.org/rfc/rfc9114#section-4.1)
- Its own transfer-coding registry lists only chunked, compress, deflate, gzip, the x- aliases, trailers (reserved) and identity (withdrawn). It has no br or zstd transfer coding. — [IANA HTTP Parameters](https://www.iana.org/assignments/http-parameters/)

### Inferences
- A server targeting HTTP/2 and HTTP/3 can treat transfer-coding compression as out of scope. On HTTP/1.1 it is optional and rarely requested. Ignoring `TE: gzip` is conformant: "A message with no transfer coding is always acceptable."
- An on-the-fly compressed response to an HTTP/1.0 request cannot use chunked. It must be delimited by closing the connection, which kills keep-alive. Not compressing for HTTP/1.0 is simpler; nginx's default `gzip_http_version 1.1` does exactly that ([nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)).

### Gaps
- I found no measurement of how often browsers or tools send `TE: gzip`. Treat the claim that "browsers do not use it" as unverified common knowledge, not a sourced fact.

## 8. Cache-Control: no-transform (RFC 9111 5.2.1.6, 5.2.2.6; RFC 9110 7.7) and what a reverse proxy counts as

### Takeaway
no-transform binds intermediaries ("an intermediary (regardless of whether it implements a cache) MUST NOT transform the content"). Adding a content coding is a transformation, because codings change the representation. The origin server is not bound when it codes its own resources. A reverse proxy (a "gateway") is defined as an intermediary that acts as an origin server outbound. A gateway that compresses an upstream application's response carrying `no-transform` therefore breaks the directive. Caddy honours it on both request and response; the nginx gzip filter and Apache's mod_deflate show no no-transform check in source.

### Cited Findings
- Response directive: "The no-transform response directive indicates that an intermediary (regardless of whether it implements a cache) MUST NOT transform the content, as defined in Section 7.7 of [HTTP]." — [RFC 9111 5.2.2.6](https://www.rfc-editor.org/rfc/rfc9111#section-5.2.2.6)
- Request directive: "The no-transform request directive indicates that the client is asking for intermediaries to avoid transforming the content". — [RFC 9111 5.2.1.6](https://www.rfc-editor.org/rfc/rfc9111#section-5.2.1.6)
- 7.7: "A proxy MUST NOT transform the content (Section 6.4) of a response message that contains a no-transform cache directive ... Note that this does not apply to message transformations that do not change the content, such as the addition or removal of transfer codings". "A proxy MAY transform the content of a message that does not contain a no-transform cache directive. A proxy that transforms the content of a 200 (OK) response can inform downstream recipients that a transformation has been applied by changing the response status code to 203 (Non-Authoritative Information)". — [RFC 9110 7.7](https://www.rfc-editor.org/rfc/rfc9110#section-7.7)
- Terms: an "intermediary" is a "proxy, gateway, [or] tunnel". "A "gateway" (a.k.a. "reverse proxy") is an intermediary that acts as an origin server for the outbound connection but translates received requests and forwards them inbound to another server or servers ... All HTTP requirements applicable to an origin server also apply to the outbound communication of a gateway." A "proxy" is "a message-forwarding agent that is chosen by the client". — [RFC 9110 3.7](https://www.rfc-editor.org/rfc/rfc9110#section-3.7)
- Content codings change the representation (section 1: "the representation is defined in terms of the coded form") — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)
- Caddy checks `no-transform` in the request's Cache-Control before choosing an encoder, and again in the response's Cache-Control before encoding (`isEncodeAllowed`) — [encode.go](https://github.com/caddyserver/caddy/blob/4e8de214bc77bce405a5355a9d17d4845823c684/modules/caddyhttp/encode/encode.go)
- A text search for "no-transform" and "transform" in nginx's `ngx_http_gzip_filter_module.c` and `ngx_http_core_module.c`, and for "no-transform" and "Cache-Control" in Apache's `mod_deflate.c`, found no check (source at the linked commits). mod_deflate's "transform" matches are its ETag-suffix code. The nginx and Apache docs do not mention no-transform. — [nginx gzip filter](https://github.com/nginx/nginx/blob/9a7439fd79076de03c408de136ba1772347030c2/src/http/modules/ngx_http_gzip_filter_module.c); [mod_deflate.c](https://github.com/apache/httpd/blob/49166911e75cecd58c28005e5dd94d743899b715/modules/filters/mod_deflate.c); [mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- nginx does not compress for requests that arrived through another proxy (detected by `Via`) unless told to: `gzip_proxied off` is the default, which "disables compression for all proxied requests" — [nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)

### Inferences
- The RFC is ambiguous. 7.7's MUST is worded for a "proxy", which in 3.7 means a client-chosen agent, so it would not cover a gateway. 9111 5.2.2.6's MUST covers "an intermediary", which includes gateways. Read together, the strict reading is that a reverse proxy, or a server relaying FastCGI or CGI output, should not add a content coding to a response marked `no-transform`. Caddy's behaviour is the conservative, defensible choice. The application chose the directive and the server should respect it.
- For files the server itself serves, it is the origin and no-transform is its own decision. An administrator's `no-transform` on static files is therefore advice, which the server may still honour for consistency.
- Honouring the request-side directive (5.2.1.6) is optional ("asking ... to avoid"). Caddy does it; it costs nothing to do.
- On-the-fly compression of an upstream response is a content transformation, so the 7.7 option to change 200 to 203 applies. No common server does this (inference from the source reviewed), and it would break caching semantics for clients. Not recommended.

### Gaps
- I found no IETF erratum or HTTPWG discussion that settles whether a gateway is bound by no-transform for content codings. The reading above is my interpretation of 3.7, 7.7 and 9111 5.2.2.6.

## 9. Framing compressed responses in HTTP/1.1, HTTP/2 and HTTP/3 (RFC 9112, 9113, 9114)

### Takeaway
The coding never touches framing rules except through Content-Length. In HTTP/1.1, a streamed compressed body uses chunked (or close for HTTP/1.0), and Content-Length must not be sent alongside Transfer-Encoding. In HTTP/2 and HTTP/3, Content-Length is optional, but if present it must equal the sum of DATA payloads, which is the compressed size. Otherwise the message is malformed and the stream is reset. Both specifications require that confidential and attacker-controlled data not be compressed together on a secure channel (section 11).

### Cited Findings
- HTTP/1.1: "A recipient MUST be able to parse the chunked transfer coding (Section 7.1) because it plays a crucial role in framing messages when the content size is not known in advance." — [RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1); Content-Length plus Transfer-Encoding is forbidden — [RFC 9112 6.2](https://www.rfc-editor.org/rfc/rfc9112#section-6.2)
- HTTP/2: "A request or response is also malformed if the value of a content-length header field does not equal the sum of the DATA frame payload lengths that form the content, unless the message is defined as having no content. For example, 204 or 304 responses contain no content, as does the response to a HEAD request. A response that is defined to have no content ... MAY have a non-zero content-length header field". Malformed messages "MUST be treated as a stream error ... of type PROTOCOL_ERROR"; "Clients MUST NOT accept a malformed response." — [RFC 9113 8.1.1](https://www.rfc-editor.org/rfc/rfc9113#section-8.1.1)
- HTTP/3: "A request or response that is defined as having content when it contains a Content-Length header field ... is malformed if the value of the Content-Length header field does not equal the sum of the DATA frame lengths received." — [RFC 9114 4.1.2](https://www.rfc-editor.org/rfc/rfc9114#section-4.1.2)
- HTTP/2 security text: "Implementations communicating on a secure channel MUST NOT compress content that includes both confidential and attacker-controlled data unless separate compression dictionaries are used for each source of data. Compression MUST NOT be used if the source of data cannot be reliably determined. Generic stream compression, such as that provided by TLS, MUST NOT be used with HTTP/2". It applies explicitly to "HTTP compressed content-codings (Section 8.4.1 of [HTTP])". — [RFC 9113 10.6](https://www.rfc-editor.org/rfc/rfc9113#section-10.6)
- HTTP/3 has the same text with "separate compression contexts" — [RFC 9114 10.6](https://www.rfc-editor.org/rfc/rfc9114#section-10.6)

### Inferences
- A compressor that sends a Content-Length from the identity file (for example, copying the cache entry's prebuilt header block) produces a malformed HTTP/2 or HTTP/3 message and a broken HTTP/1.1 response. Content-Length must come from the coded bytes, or be absent.
- RFC 9113 and 9114 10.6 are the strongest normative statements about body compression in the HTTP family. "MUST NOT be used if the source of data cannot be reliably determined" literally covers a generic server compressing opaque application output over TLS. In practice servers compress anyway (section 12), but a security-first design can cite this to justify defaults: compress static files the server knows; compress dynamic, cookie-bearing application output only when the operator opts in.

### Gaps
- None for the normative text.

## 10. The coding formats: gzip (RFC 1952), brotli (RFC 7932), zstd (RFC 8878 and RFC 9659), dictionary transport (RFC 9842)

### Takeaway
gzip and brotli are Informational format specifications. zstd's HTTP coding is capped by RFC 9659: encoders MUST NOT need a window above 8 MB, and decoders MUST support up to 8 MB. Brotli's window tops out at 16 MiB minus 16 bytes by format. RFC 9842 (Standards Track, September 2025) defines `dcb` and `dcz`. Those codings come with window rules, MUST-level Vary, HTTPS only, and a server-side test for when not to use a dictionary on cross-origin requests.

### Cited Findings
- gzip structure: CRC32 is "a Cyclic Redundancy Check value of the uncompressed data"; ISIZE "contains the size of the original (uncompressed) input data modulo 2^32". "A compliant compressor must produce files with correct ID1, ID2, CM, CRC32, and ISIZE", and "A compliant decompressor must check ID1, ID2, and CM, and provide an error indication if any of these have incorrect values." — [RFC 1952 2.3.1, 2.3.1.2](https://www.rfc-editor.org/rfc/rfc1952)
- Brotli window: WBITS is "a value in the range 10..24", and "The possible sliding window sizes range from 1 KiB - 16 B to 16 MiB - 16 B." — [RFC 7932 2, 9.1](https://www.rfc-editor.org/rfc/rfc7932). RFC 7932 registers `br`, "Brotli Compressed Data Format" — [RFC 7932 13](https://www.rfc-editor.org/rfc/rfc7932#section-13)
- Brotli compressor sizing: "an output buffer of S(N) = N + (3 * (N >> 16) + 5) bytes is sufficient to hold a valid compressed brotli stream representing an arbitrary sequence of N uncompressed bytes", and "If the system containing a compressor implementation is overloaded, a possible way to reduce resource usage is to switch to more simple algorithms ... or to fall back to the trivial compression algorithm". — [RFC 7932 12](https://www.rfc-editor.org/rfc/rfc7932#section-12)
- zstd before RFC 9659: "it's recommended for decoders to support values of Window_Size up to 8 MB and for encoders not to generate frames requiring a Window_Size larger than 8 MB. It's merely a recommendation though". The maximum Window_Size is (1<<41) + 7*(1<<38) bytes. RFC 8878 registers the `zstd` content coding. — [RFC 8878 3.1.1.1.2, 7.2](https://www.rfc-editor.org/rfc/rfc8878#section-3.1.1.1.2)
- RFC 9659, the HTTP rule: "To ensure interoperability, when using the "zstd" content coding, decoders MUST support a Window_Size of up to and including 8 MB, and encoders MUST NOT generate frames requiring a Window_Size larger than 8 MB". Security: "decoders still need to take into account that they can receive oversized frames that do not follow the window size limit specified in this document and fail decoding when such invalid frames are received." Motivation: "some browsers and user agents limit the maximum Window_Size they will handle. This causes failures to decode responses when the content is compressed with a larger Window_Size than the recipient allows". — [RFC 9659 1, 3, 4](https://www.rfc-editor.org/rfc/rfc9659)
- zstd security: "One should never compress a message whose content must remain secret with a message generated by a third party ... This was demonstrated in the ... (CRIME) attack". "A decoder must always control memory requirements and enforce some (system-specific) limits". — [RFC 8878 8](https://www.rfc-editor.org/rfc/rfc8878#section-8)
- RFC 9842 `dcb`: a 36-byte header (magic 0xff 0x44 0x43 0x42 plus the dictionary's SHA-256) followed by a Shared Brotli stream. "Clients that announce support for dcb content encoding MUST be able to decompress resources that were compressed with a window size of up to 16 MB." — [RFC 9842 4](https://www.rfc-editor.org/rfc/rfc9842#section-4)
- RFC 9842 `dcz`: a 40-byte header, which is a zstd skippable frame carrying the SHA-256. "Clients that announce support for dcz content encoding MUST be able to decompress resources that were compressed with a window size of at least 8 MB or 1.25 times the size of the dictionary, whichever is greater, up to a maximum of 128 MB." The window "MUST be lower than this limit". — [RFC 9842 5](https://www.rfc-editor.org/rfc/rfc9842#section-5)
- RFC 9842 negotiation: the client offers dcb or dcz in Accept-Encoding only when it holds a matching dictionary ("MUST NOT send its dictionary-aware content encodings" otherwise) and names it in `Available-Dictionary`. A cacheable response "MUST include a "Vary" header", for example `Vary: accept-encoding, available-dictionary`. — [RFC 9842 6.1, 6.2](https://www.rfc-editor.org/rfc/rfc9842#section-6)
- RFC 9842 transport and security:
  - "compression dictionary transport MUST only be used in secure contexts (HTTPS)." ([RFC 9842 8](https://www.rfc-editor.org/rfc/rfc9842#section-8))
  - "if the adversary can control the dictionary, the adversary can learn information about the compressed data." ([RFC 9842 9.2](https://www.rfc-editor.org/rfc/rfc9842#section-9.2))
  - Servers should prevent "active use of multiple dictionaries for the same content", disable "compression when any portion of the content comes from uncontrolled sources", and run a Sec-Fetch-Site / Sec-Fetch-Mode / CORS algorithm that returns FALSE for cross-origin requests where dictionary compression should not be used. ([RFC 9842 9.3.3](https://www.rfc-editor.org/rfc/rfc9842#section-9.3.3))

### Inferences
- RFC 9659 does not define "8 MB". zstd window sizes are powers of two plus fractions, so 8 MiB (windowLog 23) is the natural limit an encoder should enforce. A zstd encoder in an HTTP server must cap the window explicitly. zstd's highest levels (the "ultra" levels, from my knowledge rather than a source checked here) use larger windows on large inputs. This should be verified against the zstd manual before relying on it.
- RFC 1952's ISIZE is modulo 2^32 and attacker-controlled on request bodies, so it is not a safe bound for allocating or limiting decompression output.
- RFC 9842 is a separate feature: dictionary storage, `Use-As-Dictionary`, hash matching and the cross-origin algorithm. It needs its own design. Plain br and zstd do not depend on it.

### Gaps
- I did not read RFC 9841 (Shared Brotli) itself.
- I did not check browser support versions for zstd, dcb and dcz. That is outside the standards scope; a separate implementation survey should source it.

## 11. Compression side-channel attacks: CRIME, TIME, BREACH, HEIST, Rupture and later work

### Takeaway
Every attack exploits the same thing: when attacker-chosen bytes share a compression context with a secret, the compressed length shows whether the guess matched, and TLS does not hide lengths.
- CRIME (2012) broke TLS-level and SPDY header compression. TLS compression is gone (TLS 1.3 removed it), and HPACK and QPACK were designed against CRIME.
- BREACH (2013) moved the attack to HTTP body compression. It needs three things: compression, reflected user input, and a secret in the same body.
- TIME (2013) and HEIST (2016) showed lengths can be measured from JavaScript in the victim's browser through timing and TCP congestion-window effects, with no network position.
- Rupture (2016) made BREACH work against block ciphers by statistics.
- No protocol-level fix exists for BREACH; it is mitigated in the application or by not compressing.

### Cited Findings
- CRIME: "At ekoparty 2012, Thai Duong and Juliano Rizzo announced CRIME, a compression side-channel attack against HTTPS traffic", against an attacker able to "inject partial chosen plaintext into a victim's HTTP requests" and "measure the size of encrypted traffic". The ekoparty demonstration recovered HTTP request headers (cookies) and relied on TLS compression. — [BREACH paper, 1. Introduction](https://www.breachattack.com/resources/BREACH%20-%20SSL,%20gone%20in%2030%20seconds.pdf). "The CRIME attack [CRIME] (CVE-2012-4929) allows an active attacker to decrypt ciphertext (specifically, cookies) when TLS is used with TLS-level compression." — [RFC 7457 2.6](https://www.rfc-editor.org/rfc/rfc7457#section-2.6)
- CRIME and SPDY: "SPDY [SPDY] initially addressed this redundancy by compressing header fields using the DEFLATE [DEFLATE] format ... However, that approach exposed a security risk as demonstrated by the CRIME ... attack". — [RFC 7541 1](https://www.rfc-editor.org/rfc/rfc7541#section-1)
- TLS compression removed: in TLS 1.3, legacy_compression_methods "MUST contain exactly one byte, set to zero, which corresponds to the "null" compression method" — [RFC 8446 4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2). For TLS 1.2, "implementations and deployments SHOULD NOT support TLS-level compression"; "the HTTP protocol is known to be vulnerable to compression-related attacks"; BREACH-type issues "can only be mitigated outside of TLS". — [RFC 9325 3.3](https://www.rfc-editor.org/rfc/rfc9325#section-3.3)
- TIME: "at Black Hat Europe 2013, Be'ery and Shulman announced TIME, an attack against compressed HTTPS responses. Their work uses timing – rather than ciphertext length – to harvest the information leaked by compression." — [BREACH paper](https://www.breachattack.com/resources/BREACH%20-%20SSL,%20gone%20in%2030%20seconds.pdf); the reference is Tal Be'ery and Amichai Shulman, "A perfect crime? only time will tell", Black Hat Europe 2013 ([HEIST paper, ref. 2](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows-wp.pdf))
- BREACH ("Browser Reconnaissance and Exfiltration via Adaptive Compression of Hypertext"): Yoel Gluck, Neal Harris and Angelo Prado, paper dated July 12, 2013, presented at Black Hat USA 2013 — [BREACH paper](https://www.breachattack.com/resources/BREACH%20-%20SSL,%20gone%20in%2030%20seconds.pdf); [breachattack.com](https://www.breachattack.com/)
- BREACH conditions, verbatim from the site: the application must "Be served from a server that uses HTTP-level compression", "Reflect user-input in HTTP response bodies", and "Reflect a secret (such as a CSRF token) in HTTP response bodies". The attack "is agnostic to the version of TLS/SSL", "works against any cipher suite" (stream ciphers are simpler, block ciphers need alignment work), and is claimed to run "in under a minute" with "a few thousand requests". — [breachattack.com](https://www.breachattack.com/)
- RFC 7457 on BREACH: TIME and BREACH (CVE-2013-3587, "though the number has not been officially allocated") "make similar use of HTTP-level compression to decrypt secret data passed in the HTTP response". "We are not aware of mitigations at the TLS protocol level to the BREACH attack, and so application-level mitigations are needed ... implementations of HTTP that use Cross-Site Request Forgery (CSRF) tokens will need to randomize them." — [RFC 7457 2.6](https://www.rfc-editor.org/rfc/rfc7457#section-2.6)
- Attack technique: the BREACH paper describes the "Two-Tries Method" and "Guess-Swap" to beat Huffman-coding noise in DEFLATE ([BREACH paper 2.4.1, 2.4.2](https://www.breachattack.com/resources/BREACH%20-%20SSL,%20gone%20in%2030%20seconds.pdf)). RFC 7541 notes that DEFLATE's prefix matching "permitted the attacker to confirm guesses a character at a time, reducing an exponential-time attack into a linear-time attack" ([RFC 7541 7.1](https://www.rfc-editor.org/rfc/rfc7541#section-7.1)).
- Rupture / "Practical New Developments on BREACH": Dimitris Karakostas and Dionysis Zindros, Black Hat Asia 2016. It extends BREACH to block ciphers (AES) with statistical methods, demonstrated against Gmail and Facebook Chat, with an attack framework called Rupture. — [paper (rupture repository)](https://raw.github.com/dionyziz/rupture/develop/etc/Black%20Hat%20Asia%202016/asia-16-Practical-New-Developments-In-The-BREACH-Attack-wp.pdf) (abstract via search, not read in full); [CSO Online](https://www.csoonline.com/article/555575/http-compression-continues-to-put-encrypted-communications-at-risk.html); [Threatpost](https://threatpost.com/breach-attacks-revived-to-steal-private-messages-from-gmail-facebook/117209). The Register reported the optimised attack as about 500 times faster than the original ([The Register](https://www.theregister.co.uk/2016/04/04/spies_rejoice_gmail_facebook_messenger_breached_once_again/)); this is press reporting.
- Their CTX slides (Black Hat Europe 2016) summarise Rupture as "Performs statistical analysis; Bypasses noise/length hiding; Attacks block ciphers, eg AES". — [CTX slides](https://www.blackhat.com/docs/eu-16/materials/eu-16-Karakostas-Ctx-Eliminating-BREACH-With-Context-Hiding.pdf)
- HEIST: Mathy Vanhoef and Tom Van Goethem (KU Leuven), Black Hat USA 2016, "a set of techniques that allows us to carry out attacks against SSL/TLS purely in the browser". It "can be used to determine the exact size of HTTP responses, by increasing the amount of reflected content until the HTTP response no longer fits into the initial TCP congestion window". "the introduction of HTTP/2 further worsens the situation, as it enables even more attack techniques"; "compression-based attacks such as BREACH can be executed without requiring a man-in-the-middle position." — [HEIST white paper](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows-wp.pdf). CVE-2016-7152 (HTTPS) and CVE-2016-7153 (HTTP/2) were assigned to the underlying issue — [Ubuntu CVE-2016-7152](https://ubuntu.com/security/CVE-2016-7152); [OpenCVE CVE-2016-7153](https://www.opencve.io/cve/CVE-2016-7153)
- Kelsey (Fast Software Encryption 2002) first showed compression-based leakage of plaintext — [HEIST paper, Related Work and ref. 8](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows-wp.pdf)
- Later work (2019 to 2024), all from search results and not read in full:
  - DBREACH (Hogan, Michalevsky, Eskandarian; IEEE S&P 2023) uses compression side channels on compressed, encrypted database tables (InnoDB in MariaDB and MySQL, WiredTiger in MongoDB) — [DBREACH paper](https://www.cs.unc.edu/~saba/papers/dbreach.pdf)
  - G-DBREACH, a follow-up — [Springer](https://link.springer.com/chapter/10.1007/978-3-031-95764-2_2)
  - Decomp+Time, a timing side channel in memory compression — [arXiv 2111.08404](https://arxiv.org/pdf/2111.08404)
  - GPU.zip (2023), GPU data compression leaking pixels cross-origin in Chrome — [BleepingComputer](https://www.bleepingcomputer.com/news/security/modern-gpus-vulnerable-to-new-gpuzip-side-channel-attack/)
  - An ETH Zurich master's thesis (2024), "Refined Techniques for Compression Side-Channel Attacks" — [ETH thesis](https://ethz.ch/content/dam/ethz/special-interest/infk/inst-infsec/appliedcrypto/education/theses/masters-thesis_yuanming-song.pdf)

### Inferences
- The threat for an HTTP server's body compression is BREACH and its descendants (TIME, HEIST, Rupture). All need three things together: a secret in a compressed response body, attacker-influenced bytes in that same body, and the ability to make the victim's browser send many authenticated requests. That last condition, in practice, means the victim's cookies ride on cross-site requests.
- Responses that are the same for every user (static files, public pages without per-user tokens) hold no secret to steal. Responses that carry no attacker input give no oracle. Both are safe to compress. A server's static-file and pre-compressed paths fall here, unless an administrator places per-user secrets in static files, which is very unusual.
- HTTP/2 and HTTP/3 multiplexing make measurement easier (HEIST). Protocol version therefore offers no protection.

### Gaps
- I could not read the Rupture paper or the later papers in full, so their numbers (request counts, speed-ups) are from abstracts and press only.
- I found no published BREACH-class attack from 2017 to 2026 against a specific HTTP framework's compressed responses. That may reflect the search rather than the absence of such work.

## 12. Mitigations: standards text, framework and server guidance (2024 to 2026), and what each buys

### Takeaway
The standards and the BREACH authors agree on the order.
- Not compressing secret-bearing responses that also carry attacker input fully removes the risk.
- Separating secrets from attacker-controlled data (different responses or contexts) also fully removes it.
- Masking secrets per response (P || P⊕S) neutralises the attack for that one secret.
- Random length padding, rate limiting and SameSite cookies only raise the attacker's cost, SameSite substantially.

Django masks CSRF tokens and pads gzip output by default. Rails masks. Laravel's `csrf_token()` / `@csrf` form value is the raw session token with no masking (checked in source). nginx and Apache document the risk with a one-line warning and leave it to the operator.

### Cited Findings
- Standards text:
  - "The most effective mitigation for this risk is to disable compression on sensitive data, or to strictly separate sensitive data from attacker-controlled data so that they cannot share the same compression dictionary." ([RFC 9110 17.6](https://www.rfc-editor.org/rfc/rfc9110#section-17.6))
  - HTTP/2 and HTTP/3 make it a MUST on secure channels ([RFC 9113 10.6](https://www.rfc-editor.org/rfc/rfc9113#section-10.6), [RFC 9114 10.6](https://www.rfc-editor.org/rfc/rfc9114#section-10.6); quoted in section 9).
  - Brotli: "applications should not mix sensitive data with non-sensitive, potentially attacker-supplied data in the same compressed stream." ([RFC 7932 12](https://www.rfc-editor.org/rfc/rfc7932#section-12))
- The BREACH paper's mitigations ("we are unaware of a clean, effective, practical solution"):
  - Length hiding "does make the attack take longer, it does so only slightly ... the standard error of the mean in this case is inversely proportional to √N".
  - Separating secrets from user input "completely solves the problem" but "may be very tedious and highly impractical".
  - Disabling compression "completely eliminates the side-channel" at "a rather drastic impact on performance".
  - Masking: "generate a new onetime pad P, and embed P||(P ⊕ S) in the page", which doubles the secret's length and makes it incompressible.
  - Rate-limiting and monitoring slows the attack.
  - Requiring CSRF tokens on "all requests that reflect user input would defeat the attack".
  - Source: [BREACH paper, section 3](https://www.breachattack.com/resources/BREACH%20-%20SSL,%20gone%20in%2030%20seconds.pdf)
- breachattack.com's list, "in order of effectiveness": disabling HTTP compression; separating secrets from user input; randomizing secrets per request; masking secrets; protecting vulnerable pages with CSRF; length hiding; rate-limiting. — [breachattack.com](https://www.breachattack.com/)
- HEIST countermeasures, each graded by the authors:
  - Disabling third-party cookies is "complete": "One of the few, if not the only, adequate countermeasure is to disable third-party cookies."
  - Blocking requests by Origin or Referer is "inadequate": requests can be made without those headers.
  - Disabling compression is "incomplete": it stops BREACH and CRIME but not other length-based attacks.
  - Randomising the TCP congestion window and random padding are "inadequate": the attacker averages over more requests.
  - Source: [HEIST white paper, section 4](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows-wp.pdf)
- SameSite cookies: secondary sources say the attribute blunts BREACH because cookies are not sent on cross-site subresource requests — [igvita.com (2016)](https://www.igvita.com/2016/08/26/stop-cross-site-timing-attacks-with-samesite-cookies/); [Invicti](https://invicti.com/web-vulnerability-scanner/vulnerabilities/breach-attack-detected); [GitLab issue proposing SameSite for BREACH and HEIST](https://gitlab.com/gitlab-org/gitlab/-/issues/21854). Rupture's authors proposed first-party-only cookies in 2016, when no browser implemented them — [Threatpost](https://threatpost.com/breach-attacks-revived-to-steal-private-messages-from-gmail-facebook/117209)
- Length hiding, modern version: "Heal the Breach" (HTB), R. Palacios, A. Fariña Fernández-Portillo, E. F. Sánchez-Úbeda and P. García-de-Zúñiga, IEEE Access vol. 10 (2022), pp. 40381–40390. It randomly changes response sizes through a modified gzip library. For 1 to 10 bytes of variation the authors estimate the attacker needs about 500 times more packets, and argue the repetition makes the attack easier to detect with an IDS. — [IEEE Xplore 9754554](https://ieeexplore.ieee.org/document/9754554); [IIT Comillas record](https://iit.comillas.edu/publicacion/revista/en/1913/HTB:%20a%20very%20effective%20method%20to%20protect%20web%20servers%20against%20BREACH%20attack%20to%20HTTPS). This conflicts in emphasis with the BREACH paper's 1/√N argument and HEIST's verdict that random padding is "inadequate".
- Django, from version 4.2 (released April 3, 2023): "GZipMiddleware now includes a mitigation for the BREACH attack" ([Django 4.2 release notes](https://docs.djangoproject.com/en/6.0/releases/4.2/)). Current docs: "Django implements a technique called Heal The Breach (HTB). It adds up to 100 bytes (see max_random_bytes) of random bytes to each response to make the attacks less effective." The middleware skips bodies under 200 bytes, responses that already have Content-Encoding, and requests without gzip in Accept-Encoding, and makes the ETag weak. — [Django middleware docs](https://docs.djangoproject.com/en/5.2/ref/middleware/)
- Django CSRF masking: "In order to protect against BREACH attacks, the value of this field is not simply the secret. It is scrambled differently with each response using a mask. The mask is generated randomly on every call to get_token(), so the form field value is different each time." Only the secret is compared on validation. — [Django CSRF docs](https://docs.djangoproject.com/en/5.2/ref/csrf/)
- Rails: `mask_token` draws `one_time_pad = SecureRandom.random_bytes(AUTHENTICITY_TOKEN_LENGTH)` per call and XORs it with the token; `unmask_token` splits pad and value. Per-form tokens are an HMAC of the session token with action path and method. — [Rails RequestForgeryProtection API](https://api.rubyonrails.org/classes/ActionController/RequestForgeryProtection.html). A 2025 Full Disclosure post argues that sending the pad with the masked token lets an attacker who has a token re-mask and replay it ([Full Disclosure, April 2025](https://seclists.org/fulldisclosure/2025/Apr/29)). This is a CSRF-replay argument. The BREACH paper's own construction sends the pad alongside (P||P⊕S) on purpose, so it does not weaken the BREACH mitigation. No Rails response or CVE was found.
- Laravel (12.x branch, checked 2026-10-26): `csrf_token()` returns `$session->token()`, the stored `_token`, a 40-character random string set by `regenerateToken()` with `Str::random(self::SESSION_ID_LENGTH)`. `VerifyCsrfToken::tokensMatch` compares the request's `_token` / `X-CSRF-TOKEN` to it with `hash_equals`. The value is not masked per response. The `X-XSRF-TOKEN` cookie is encrypted, but that is a header, not body content. — [helpers.php](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Foundation/helpers.php); [VerifyCsrfToken.php](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Foundation/Http/Middleware/VerifyCsrfToken.php); [Session Store.php](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Session/Store.php)
- Server documentation:
  - nginx: "When using the SSL/TLS protocol, compressed responses may be subject to BREACH attacks." Defaults are `gzip_comp_level 1`, `gzip_min_length 20` (judged from Content-Length only), `gzip_types text/html` and `gzip_proxied off`. — [nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
  - Apache: "Some web applications are vulnerable to an information disclosure attack when a TLS connection carries deflate compressed data. For more information, review the details of the "BREACH" family of attacks." — [mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
  - Caddy's encode docs do not mention BREACH. Defaults: zstd then gzip, `minimum_length` 512, a list of text-like content types. — [Caddy encode docs](https://caddyserver.com/docs/caddyfile/directives/encode)
- OWASP: the TLS cheat sheet says "TLS compression should be disabled in order to protect against a vulnerability (nicknamed CRIME)" and "TLS compression is not available in TLS v1.3 for this reason". A text search of the current CSRF Prevention and HTTP Headers cheat sheets (OWASP CheatSheetSeries master, 2026-10-26) found no mention of BREACH or HTTP compression. — [OWASP TLS Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html); [OWASP CheatSheetSeries repository](https://github.com/OWASP/CheatSheetSeries)
- CTX (Karakostas, Kiayias, Sarafianou, Zindros; Black Hat Europe 2016) is an application-layer, opt-in defence. Each secret is tagged with an "origin" (the party that generated it), and each origin's secrets are rewritten through a per-origin pseudo-random permutation of the secret alphabet, so secrets from different origins do not cross-compress. It needs a server library (Django, Flask, Node.js) and a client script. The slides reject random padding as "Susceptible alignment + statistical analysis (Rupture)". — [CTX slides](https://www.blackhat.com/docs/eu-16/materials/eu-16-Karakostas-Ctx-Eliminating-BREACH-With-Context-Hiding.pdf)

### Inferences
- For a web server (not a framework), the mitigations it controls:
  - (a) What it compresses. Static and pre-compressed files are safe; dynamic application output is the risk. A per-site or per-location opt-in for compressing proxied or FastCGI responses follows RFC 9113 10.6's "if the source of data cannot be reliably determined".
  - (b) Content types. HTML and JSON carry tokens; images and fonts are not compressed anyway.
  - (c) Length hiding, as Django does. The BREACH authors and HEIST call it weak; HTB claims a large factor. It costs bytes and breaks byte-stable output (and so strong ETags on compressed variants).
  - (d) Rate limiting.
- Laravel, a framework this project serves, does not mask its form CSRF token. A compressed Laravel page that reflects user input and holds the `@csrf` field meets all three BREACH conditions. The SameSite=Lax default on Laravel's session cookie (from my knowledge of `config/session.php`, not verified here) blocks the cross-site requests that need cookies. This is a concrete argument for keeping on-the-fly compression of PHP output opt-in, or at least documenting the risk.
- No server examined refuses by default to compress responses that set cookies or answer requests with Authorization. That would be a heuristic a server could add. I found no source recommending it, so it would be this project's own design.

### Gaps
- I found no 2024 to 2026 official nginx, Apache or OWASP guidance on BREACH beyond the one-line warnings and the TLS-compression advice above.
- I did not verify which Django version introduced CSRF masking, or when Rails introduced masked and per-form tokens.
- The current state of third-party cookie blocking per browser (relevant to HEIST's "complete" countermeasure) was not researched.
- I found no primary source for a "don't compress when Set-Cookie is present" policy in any major server.

## 13. Header compression (HPACK, QPACK) vs body compression

### Takeaway
HPACK and QPACK were built after CRIME. A guess must match a whole field value, not one character, and encoders can refuse to index sensitive fields with never-indexed literals. Body content codings get no such structural protection; DEFLATE, brotli and zstd all match substrings. The HTTP/2 and HTTP/3 "Use of Compression" sections apply their MUST NOT to content codings as well as to field compression.

### Cited Findings
- "HPACK mitigates but does not completely prevent attacks modeled on CRIME [CRIME] by forcing a guess to match an entire header field value rather than individual characters. Attackers can only learn whether a guess is correct or not, so they are reduced to brute-force guesses for the header field values." — [RFC 7541 7.1.1](https://www.rfc-editor.org/rfc/rfc7541#section-7.1.1)
- HPACK mitigations: segregating dynamic-table access by the entity that created the value, penalising fields with many distinct values, and never-indexed literals: "Refusing to generate an indexed representation for a header field is only effective if compression is avoided on all hops." — [RFC 7541 7.1.2, 7.1.3](https://www.rfc-editor.org/rfc/rfc7541#section-7.1.2)
- QPACK has the same structure: section 7.1 "Probing Dynamic Table State" says the compression context "can be probed by an attacker who can both define fields to be encoded and transmitted and observe the length of those fields once they are encoded", and 7.1.3 covers never-indexed literals. — [RFC 9204 7.1, 7.1.3](https://www.rfc-editor.org/rfc/rfc9204#section-7.1)
- RFC 9110 names HPACK as the example of safe design: "With careful design, a compression scheme can be designed in a way that is not considered exploitable in limited use cases, such as HPACK". — [RFC 9110 17.6](https://www.rfc-editor.org/rfc/rfc9110#section-17.6)
- RFC 9113 10.6 and RFC 9114 10.6 say "the following concerns also apply to the use of HTTP compressed content-codings". — [RFC 9113 10.6](https://www.rfc-editor.org/rfc/rfc9113#section-10.6); [RFC 9114 10.6](https://www.rfc-editor.org/rfc/rfc9114#section-10.6)

### Inferences
- A response-side HPACK or QPACK encoder that inserts only values the server chooses itself (server, date, content-type) holds no secret and no attacker input in its dynamic table. It is outside the CRIME model. Body compression of mixed-origin content has no equivalent built-in protection; only the mitigations of section 12 apply.

### Gaps
- None.

## 14. Request-body decompression (Content-Encoding on requests) and compression bombs

### Takeaway
A server need not decode compressed request bodies. It may refuse them with 415, and if it does it ought to list the codings it accepts in Accept-Encoding. A server that does decode must bound the output, not the input. Content-Length and gzip's ISIZE describe the compressed bytes or are attacker-chosen. Deflate alone can reach about 1032:1, and stacked codings multiply. Apache's defaults are a reference: an inflated-size limit plus a ratio limit of 200 that may be crossed at most 3 times.

### Cited Findings
- Refusal: "An origin server MAY respond with a status code of 415 (Unsupported Media Type) if a representation in the request message has a content coding that is not acceptable." — [RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4). Such a 415 "ought to" include Accept-Encoding, and a 415 for other reasons "MUST NOT include the Accept-Encoding header field" — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3). RFC 7694 introduced this; "A field value that only contains "identity" implies that no content codings were supported." — [RFC 7694 3](https://www.rfc-editor.org/rfc/rfc7694#section-3)
- Advertising in 2xx: "a resource might include it in a 2xx (Successful) response when the request content was big enough to justify use of a compression coding but the client failed do so." — [RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)
- Size limits in general: "A server can reject a message that has a target URI that is too long ... or request content that is too large (Section 15.5.14)." Recipients "ought to carefully limit the extent to which they process other protocol elements". — [RFC 9110 17.5](https://www.rfc-editor.org/rfc/rfc9110#section-17.5)
- Deflate ratio: "the theoretical limit for the zlib format ... is 1032:1", because "two bits in can give 258 bytes out, or eight bits in give 1032 bytes out. A dynamic block has no length restriction, so you could get arbitrarily close to the limit of 1032:1." — [zlib technical details](https://zlib.net/zlib_tech.html)
- Brotli decoder guidance: compare the decoded meta-block size "against either a hard limit, given by the system's constraints or some expectation about the uncompressed data, or against a certain multiple of the size of the compressed data"; check the total uncompressed size "before decompressing each additional meta-block"; grow a large sliding window gradually rather than allocating it at once. — [RFC 7932 12](https://www.rfc-editor.org/rfc/rfc7932#section-12)
- zstd decoder guidance: "An attacker may provide correctly formed compressed frames with unreasonable memory requirements. A decoder must always control memory requirements and enforce some (system-specific) limits"; fuzz-testing decoders is "highly recommended", and a Frame_Content_Size "smaller than the actual decompressed data" is named as an overflow attempt. — [RFC 8878 8](https://www.rfc-editor.org/rfc/rfc8878#section-8). Decoders must "fail decoding" on frames above the 8 MB window — [RFC 9659 4](https://www.rfc-editor.org/rfc/rfc9659#section-4)
- Apache mod_deflate input filter:
  - It is enabled only explicitly (`SetInputFilter DEFLATE`).
  - "Few browsers have the ability to gzip request bodies. However, some special applications actually do support request compression, for instance some WebDAV clients."
  - `DeflateInflateLimitRequestBody`: if unset, "LimitRequestBody is applied to the inflated body"; 0 means no inflated-size limit. Available since 2.4.10.
  - `DeflateInflateRatioLimit 200` (default) is "the maximum ratio of deflated to inflated size of an inflated request body ... checked as the body is streamed in, and if crossed more than DeflateInflateRatioBurst times, the request will be terminated". `DeflateInflateRatioBurst 3` is the default.
  - It warns not to trust Content-Length for the inflated size.
  - Source: [mod_deflate docs](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- Compressor-side DoS: RFC 7932 notes attacks on a compressor "(e.g., a web server)" that "cause disproportionately large resource consumption by providing, e.g., uncompressible data", and suggests falling back to simpler algorithms under load. — [RFC 7932 12](https://www.rfc-editor.org/rfc/rfc7932#section-12)

### Inferences
- The simplest conformant choice for a static or proxy server: do not decode request bodies at all. Pass `Content-Encoding` through to the application, which may support it (the request body limit then applies to the compressed bytes). Or answer 415 with `Accept-Encoding: identity` where the server itself consumes the body.
- If decoding is ever added, the limit must apply to decoded output (Apache's model). Add a streaming ratio check, cap the number of stacked codings (one is enough), and make zstd and brotli refuse windows above their HTTP limits (8 MB per RFC 9659 and 16 MiB respectively).
- On the response side the CPU-DoS point applies. Compressing every response at a high level on the request path is a cost an attacker can trigger by requesting large compressible resources. A minimum size, a type allow-list, moderate on-the-fly levels and pre-compressed files for static content all reduce it. nginx defaults to level 1 ([nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)).

### Gaps
- I did not survey request-body decompression limits in nginx (which I believe has no core request inflate), Caddy, Envoy, Tomcat or Jetty. This is unverified and should not be stated as fact.
- I found no primary measurements of real brotli or zstd maximum ratios comparable to zlib's 1032:1 figure.
