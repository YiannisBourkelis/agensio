# Response compression in nginx, Apache httpd and LiteSpeed / OpenLiteSpeed (as of 2026-10-26)

Method note: the directive tables come from the official documentation pages, fetched on 2026-10-26. Behaviour the docs leave out (status codes, Range, ETag, flush) comes from reading the current source: nginx `master`, httpd `trunk` (with the 2.4.x CHANGES), google/ngx_brotli `master` and openlitespeed `master`. Claims taken from the source are marked "(source)". Versions current on that date: nginx mainline 1.31.8 (21 Oct 2026), freenginx 1.31.4 (01 Sep 2026), Apache httpd 2.4.69 (released 2026-10-01), LSWS 6.3.7 stable and 6.4.0 RC2 (23 Sep 2026), OpenLiteSpeed v1.9.4 (2026-10-24).

## nginx: ngx_http_gzip_module, gzip_static, gunzip, brotli and zstd modules

### Takeaway
nginx's own code does gzip only. It compresses statuses 200, 403 and 404 for the `text/html` type unless more types are listed, at level 1, with a minimum of 20 bytes taken only from Content-Length. It removes Content-Length and Accept-Ranges, so a Range request gets the full compressed 200, and it has turned a strong ETag into a weak one since 1.7.3. It ignores `Cache-Control: no-transform`. It decides proxied requests by the `Via` request header, and by default does not compress them. Brotli and zstd come only from third-party modules, and F5 packages ngx_brotli only for NGINX Plus. No nginx.org or freenginx release up to Oct 2026 adds official brotli or zstd.

### Cited Findings

**gzip directives (docs, quoted).** Source: [ngx_http_gzip_module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- Module intro: "a filter that compresses responses using the 'gzip' method. This often helps to reduce the size of transmitted data by half or even more." It also warns: "When using the SSL/TLS protocol, compressed responses may be subject to BREACH attacks." The doc's example configuration is: `gzip on; gzip_min_length 1000; gzip_proxied expired no-cache no-store private auth; gzip_types text/plain application/xml;` — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip on | off;` default `gzip off;`, contexts http, server, location, if in location — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip_buffers number size;` default `gzip_buffers 32 4k|16 8k;`, "By default, the buffer size is equal to one memory page. This is either 4K or 8K, depending on a platform." Until 0.7.28 the default was four 4K or 8K buffers — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). The merge in the source is `(128 * 1024) / ngx_pagesize` buffers of one page each — [ngx_http_gzip_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source)
- `gzip_comp_level level;` default `gzip_comp_level 1;`, "Acceptable values are in the range from 1 to 9." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip_disable regex ...;` (since 0.6.23), matched against User-Agent; "The special mask 'msie6' (0.7.12) corresponds to the regular expression 'MSIE [4-6]\.', but works faster. Starting from version 0.8.11, 'MSIE 6.0; ... SV1' is excluded from this mask." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). The 0.8.53 changelog adds a special "degradation" mask — [nginx CHANGES](https://nginx.org/en/CHANGES)
- `gzip_http_version 1.0 | 1.1;` default `1.1`: "Sets the minimum HTTP version of a request required to compress a response." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip_min_length length;` default `20`: "The length is determined only from the 'Content-Length' response header field." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). In the source, a response with an unknown length (`content_length_n == -1`, i.e. chunked or streamed) passes this test and is compressed whatever its size — [gzip filter source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source)
- `gzip_proxied off | expired | no-cache | no-store | private | no_last_modified | no_etag | auth | any ...;` default `off`: "The fact that the request is proxied is determined by the presence of the 'Via' request header field." The values: `off` "disables compression for all proxied requests, ignoring other parameters"; `expired` "if a response header includes the 'Expires' field with a value that disables caching"; `no-cache`, `no-store` and `private` when Cache-Control carries that parameter; `no_last_modified` "if a response header does not include the 'Last-Modified' field"; `no_etag` "if a response header does not include the 'ETag' field"; `auth` "if a request header includes the 'Authorization' field"; `any` "for all proxied requests." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- How `gzip_proxied` is evaluated (`ngx_http_gzip_ok`): with no Via it goes straight to OK. With Via: OFF declines and ANY accepts. AUTH accepts when Authorization is present. If an `Expires` header exists, compression happens only when `expired` is set and Expires is earlier than Date; otherwise it declines. If Cache-Control exists, compression happens only for a matching no-cache, no-store or private; otherwise it declines. Then `no_last_modified` and `no_etag` decline when those fields are present. — [ngx_http_core_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c) (source)
- `gzip_types mime-type ...;` default `gzip_types text/html;`: "Enables gzipping of responses for the specified MIME types in addition to 'text/html'. The special value '*' matches any MIME type (0.8.29). Responses with the 'text/html' type are always compressed." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- `gzip_vary on | off;` default `off`: "Enables or disables inserting the 'Vary: Accept-Encoding' response header field if the directives gzip, gzip_static, or gunzip are active." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). Since 0.7.3 "the 'gzip_vary' directive turned on issues a 'Vary: Accept-Encoding' header line for uncompressed responses too." — [nginx CHANGES](https://nginx.org/en/CHANGES). In the source, the header filter appends `Vary: Accept-Encoding` when `r->gzip_vary` and `clcf->gzip_vary` are both set. `r->gzip_vary` is set once the type, length and status tests have passed, before the client's Accept-Encoding is examined — [ngx_http_header_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_header_filter_module.c), [gzip filter source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source)
- Variable `$gzip_ratio`: "achieved compression ratio, computed as the ratio between the original and compressed response sizes." — [nginx docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- Directives in the source but not in the docs: `gzip_window` (default MAX_WBITS = 15), `gzip_hash` (memLevel, default MAX_MEM_LEVEL-1 = 8), `gzip_no_buffer` and `postpone_gzipping` (default 0) — [gzip filter source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source)

**Exact conditions in the gzip header filter (source).** Source: [ngx_http_gzip_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c)
- No compression when any of these holds: gzip off; status not 200, 403 or 404; a non-empty Content-Encoding already set; a known Content-Length below `gzip_min_length`; a type not in `gzip_types`; `r->header_only`, which covers HEAD and other bodiless responses. 204, 206 and 304 are therefore never compressed. A HEAD response carries no `Content-Encoding: gzip` even when the GET would — (source)
- When it compresses: it adds `Content-Encoding: gzip`, sets `main_filter_need_in_memory`, and calls `ngx_http_clear_content_length(r)`, `ngx_http_clear_accept_ranges(r)` and `ngx_http_weak_etag(r)` — (source)
- `ngx_http_clear_accept_ranges` sets `r->allow_ranges = 0` and removes Accept-Ranges — [ngx_http_core_module.h](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.h) (source). The range header filter is registered before the gzip filter in `auto/modules`. nginx filters run in reverse order of registration, so range runs after gzip. The result is that a compressible response to a Range request is sent whole and compressed as a 200 — [auto/modules](https://github.com/nginx/nginx/blob/master/auto/modules) (source, with inference on filter order)
- `ngx_http_weak_etag` leaves `W/` tags alone, prefixes `W/` to a quoted strong tag, and removes an unquoted (malformed) ETag entirely — [ngx_http_core_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c) (source)
- Last-Modified is not touched by the gzip filter — (source; no call to clear Last-Modified in the filter)
- Subrequests are never gzipped (`if (r != r->main) return NGX_DECLINED;` in `ngx_http_gzip_ok`) — [core source](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c) (source)
- Accept-Encoding parsing: there is a fast path for headers starting `gzip,`. Otherwise the code looks for the token `gzip` and reads its `q`; a q of 0 declines. The 1.1.0 changelog: "nginx did not disable gzipping if client sent 'gzip;q=0'" (fixed) — [core source](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c), [nginx CHANGES](https://nginx.org/en/CHANGES)
- `Cache-Control: no-transform`: the strings "no-transform" and "no_transform" appear nowhere in the gzip filter, core module, gzip_static or ngx_brotli filter sources, so nginx does not honour it when compressing — [gzip filter](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c), [core](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_core_module.c) (source, negative grep)

**ETag changelog (quoted).**
- nginx 1.7.3 (08 Jul 2014): "Feature: weak entity tags are now preserved on response modifications, and strong ones are changed to weak." — [nginx CHANGES](https://nginx.org/en/CHANGES)
- nginx 1.3.3 (10 Jul 2012): "entity tags support and the 'etag' directive." — [nginx CHANGES](https://nginx.org/en/CHANGES)
- Why the weak ETag still gives 304s: the not_modified filter tests If-None-Match with `ngx_http_test_if_match(r, r->headers_in.if_none_match, 1)`, a weak comparison that strips `W/` from both sides. That filter is registered last, so it runs before gzip and compares against the original strong tag. A client that revalidates with `W/"x"` matches `"x"` and gets a 304 — [ngx_http_not_modified_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_not_modified_filter_module.c), [auto/modules](https://github.com/nginx/nginx/blob/master/auto/modules) (source)

**Streaming, flush and memory (source and docs).**
- Body filter: a buffer with the `flush` flag makes zlib run with `Z_SYNC_FLUSH`, and `last_buf` with `Z_FINISH`, so data an upstream flushes is pushed out compressed, not held — [gzip filter source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source)
- Unbuffered-proxy fixes: 1.5.7 (19 Nov 2013) "some data received from a backend with unbufferred proxy might not be sent to a client immediately if 'gzip' or 'gunzip' directives were used"; 1.7.7 (28 Oct 2014) "the last part of a response received from a backend with unbufferred proxy might not be sent to a client if 'gzip' or 'gunzip' directives were used." — [nginx CHANGES](https://nginx.org/en/CHANGES)
- `proxy_buffering`: "When buffering is disabled, the response is passed to a client synchronously, immediately as it is received... Buffering can also be enabled or disabled by passing 'yes' or 'no' in the 'X-Accel-Buffering' response header field. This capability can be disabled using the proxy_ignore_headers directive." — [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)
- Memory: for a known Content-Length, wbits and memLevel are cut down until the window just covers the response ("the actual zlib window size is smaller by 262 bytes"). zlib memory is preallocated in one block, "(200K-400K)", and freed "as soon as a gzipping will complete". A code comment says "With default memory settings zlib starts to output gzipped data only after it has got about 90K" — [gzip filter source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_filter_module.c) (source). There is a zlib-ng allocation workaround (1.19.10, 1.23.4, 1.27.4), and 1.27.0 (29 May 2024) "reduced memory consumption for long-lived requests if 'gzip', 'gunzip', 'ssi', 'sub_filter', or 'grpc_pass' directives are used." — [nginx CHANGES](https://nginx.org/en/CHANGES)

**ngx_http_gzip_static_module.**
- "allows sending precompressed files with the '.gz' filename extension instead of regular files... not built by default, it should be enabled with the --with-http_gzip_static_module configuration parameter." Syntax `gzip_static on | off | always;` default `off`. It takes "gzip_http_version, gzip_proxied, gzip_disable, and gzip_vary" into account. "With the 'always' value (1.3.6), gzipped file is used in all cases, without checking if the client supports it." "It is recommended that the modification date and time of original and compressed files be the same." — [gzip_static docs](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html)
- Source: GET and HEAD only. The `.gz` file's size and mtime give Content-Length, Last-Modified and a strong ETag (`ngx_http_set_etag`), so the ETag differs from the uncompressed file's unless the mtimes are aligned. `r->allow_ranges = 1` — [ngx_http_gzip_static_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_gzip_static_module.c) (source). 1.23.4 (28 Mar 2023): "Feature: byte ranges support in the ngx_http_gzip_static_module." — [nginx CHANGES](https://nginx.org/en/CHANGES)
- Older gzip_static fixes: 0.8.24 "nginx always added 'Content-Encoding: gzip' response header line in 304 responses sent by ngx_http_gzip_static_module"; 0.8.25 "nginx sent gzipped responses to clients those do not support gzip, if 'gzip_static on' and 'gzip_vary off'" — [nginx CHANGES](https://nginx.org/en/CHANGES)

**ngx_http_gunzip_module.**
- "a filter that decompresses responses with 'Content-Encoding: gzip' for clients that do not support 'gzip' encoding method... useful when it is desirable to store data compressed to save space and reduce I/O costs." Not built by default (`--with-http_gunzip_module`). `gunzip on | off;` default `off`; `gunzip_buffers 32 4k|16 8k`. It uses gzip_http_version, gzip_proxied and gzip_disable to decide client support. Added in 1.3.6 (12 Sep 2012) — [gunzip docs](https://nginx.org/en/docs/http/ngx_http_gunzip_module.html), [nginx CHANGES](https://nginx.org/en/CHANGES)

**Brotli (third-party google/ngx_brotli; NGINX Plus package).** Source: [google/ngx_brotli README](https://github.com/google/ngx_brotli)
- Two modules, a "filter module - used to compress responses on-the-fly" and a "static module - used to serve pre-compressed files" — [ngx_brotli README](https://github.com/google/ngx_brotli)
- `brotli on|off` default off (contexts http, server, location, if); `brotli_static on|off|always` default off (".br" files; `always` serves them "without checking if the client supports it"); `brotli_types` default `text/html` ("Responses with the text/html MIME type are always compressed", `*` matches all); `brotli_buffers` "Deprecated, ignored"; `brotli_comp_level` default `6`, range 0-11; `brotli_window` default `512k`, values 1k to 16m; `brotli_min_length` default `20`, taken "only from the Content-Length response header field"; variable `$brotli_ratio` — [ngx_brotli README](https://github.com/google/ngx_brotli)
- Source: same status gate as gzip (200, 403, 404), skips header_only, an existing Content-Encoding, a short Content-Length, and unlisted types. It clears Content-Length and Accept-Ranges and calls `ngx_http_weak_etag`. It sets `r->gzip_vary = 1`, so `gzip_vary` controls its Vary as well. Its request check tests only the main request and Accept-Encoding, then sets `gzip_tested = 1; gzip_ok = 0` so the gzip filter steps aside. It does **not** apply `gzip_proxied`/Via, `gzip_http_version` or `gzip_disable`. Merge defaults: quality 6, lg_win 19, min_length 20 — [ngx_http_brotli_filter_module.c](https://github.com/google/ngx_brotli/blob/master/filter/ngx_http_brotli_filter_module.c) (source)
- Repository activity: commit "Update brotli submodule to v1.2.1 (#174)" on 2026-10-22. The previous commits date from 2023 — [GitHub API commits](https://github.com/google/ngx_brotli/commits/master)
- F5's docs: "The ngx_brotli module enables Brotli compression in F5 NGINX Plus and consists of two modules", installed as the package `nginx-plus-module-brotli` from the NGINX Plus repository — [docs.nginx.com Brotli](https://docs.nginx.com/nginx/admin-guide/dynamic-modules/brotli/)

### Inferences
- nginx's Range behaviour (compression drops Accept-Ranges and range processing, so a full 200 is sent) is the opposite of Apache's (Apache skips compression when Content-Range is present, so an uncompressed 206 is sent). Both avoid compressed ranges.
- Since `gzip_min_length` only sees Content-Length, every chunked or streamed upstream response of a listed type is compressed whatever its size.
- `gzip_vary` is off by default, so a stock nginx config with `gzip on` sends compressed responses without `Vary: Accept-Encoding`, which is unsafe behind shared caches.
- Because of the status gate, nginx never compresses 5xx error pages or 410s, only 200, 403 and 404.

### Gaps
- The docs give no CPU trade-off figures for gzip_comp_level. nginx's documentation has no CPU guidance beyond the BREACH warning.
- I did not check how HTTP/2 and HTTP/3 header filters emit Vary. The HTTP/1 header filter was checked. The v2 and v3 filters very likely mirror it (`r->gzip_vary`) but were not read.
- ngx_brotli's README gives no CPU guidance, and it is not clear whether the NGINX Plus package tracks the 2026 submodule update.

## Apache httpd: mod_deflate, mod_brotli, ETag suffix history, zstd

### Takeaway
mod_deflate and mod_brotli are output filters you enable explicitly with `SetOutputFilter` or `AddOutputFilterByType`. No types are compressed by default. They skip subrequests, 204s, responses carrying Content-Range (so Range requests get uncompressed 206s) and responses already encoded. They always add `Vary: Accept-Encoding`, even when they do not compress. They append `-gzip` / `-br` inside the ETag by default (AddSuffix), which breaks 304s for compressed content, a problem tracked since PR 39727 (2006) and PR 45023 (2008). `DeflateAlterETag` was added only in 2.4.58 (2023-10-19). Neither honours `no-transform`. httpd has no official zstd module; there is a third-party mod_zstd.

### Cited Findings

**mod_deflate docs (2.4, quoted).** Source: [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- "The gzip encoding is the only one supported to ensure complete compatibility with old browser implementations. The deflate encoding is not supported" — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- The sample: `AddOutputFilterByType DEFLATE text/html text/plain text/xml text/css text/javascript application/javascript`. Enabling: `SetOutputFilter DEFLATE` with `SetEnvIfNoCase Request_URI "\.(?:gif|jpe?g|png)$" no-gzip`. "The DEFLATE filter is always inserted after RESOURCE filters like PHP or SSI. It never touches internal subrequests." "There is an environment variable force-gzip, set via SetEnv, which will ignore the accept-encoding setting of your browser and will send compressed output." There is a BREACH warning: "Some web applications are vulnerable to an information disclosure attack when a TLS connection carries deflate compressed data." — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- Proxies: "The mod_deflate module sends a Vary: Accept-Encoding HTTP response header to alert proxies..." For User-Agent-dependent rules, "Header append Vary User-Agent"; for decisions on non-header data such as the HTTP version, "Header set Vary *" — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- INFLATE output filter (e.g. behind ProxyPass) and DEFLATE input filter for gzip request bodies: "If you evaluate the request body yourself, don't trust the Content-Length header!" — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- `DeflateAlterETag AddSuffix|NoChange|Remove`, default `AddSuffix`, server config and virtual host, "Available in Apache 2.4.58 and later". AddSuffix: "Append the compression method onto the end of the ETag... This has been the default since 2.4.0, but prevents serving 'HTTP Not Modified' (304) responses to conditional requests for compressed content." NoChange: "This was the default prior to 2.4.0, but does not satisfy the HTTP/1.1 property that all representations of the same resource have unique ETags." Remove: "prevents some conditional requests from being possible, but avoids the shortcomings of the preceding options." — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- `DeflateBufferSize value` default `8096`: "If the compressed response size is bigger than the one specified by this directive then httpd will switch to chunked encoding... with the side effect of not setting any Content-Length HTTP header... HTTP responses without any Content-Length header might not be cached." — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- `DeflateCompressionLevel value`, default "Zlib's default", range 1-9: "the higher the value, the better the compression, but the more CPU time is required to achieve this." — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html). The source default is `Z_DEFAULT_COMPRESSION` — [mod_deflate.c](https://github.com/apache/httpd/blob/trunk/modules/filters/mod_deflate.c) — which zlib defines as "a default compromise between speed and compression (currently equivalent to level 6)" — [zlib manual](https://zlib.net/manual.html)
- `DeflateMemLevel` default 9 (1-9); `DeflateWindowSize` default 15 (1-15); `DeflateFilterNote [type] notename` (Input, Output, Ratio) — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- Request-body inflate limits (2.4.10 and later; dir and .htaccess contexts too): `DeflateInflateLimitRequestBody` "Default: None, but LimitRequestBody applies after deflation", where 0 means no limit; `DeflateInflateRatioLimit` default 200 ("maximum ratio of deflated to inflated size... checked as the body is streamed in"); `DeflateInflateRatioBurst` default 3 — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html). The 2.4.10 CHANGES entry is a SECURITY item: it "limits the length and compression ratio of inflated request bodies to avoid denial of service via highly compressed bodies" — [httpd 2.4 CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES). The 2.4.10 tarball is dated 2014-07-19 — [archive.apache.org](https://archive.apache.org/dist/httpd/)
- Precompressed serving (official doc recipe): `RewriteCond "%{HTTP:Accept-encoding}" "gzip"`, `RewriteCond "%{REQUEST_FILENAME}\.gz" -s`, `RewriteRule "^(.*)\.(css|js)" "$1\.$2\.gz" [QSA]`, then `RewriteRule "\.css\.gz$" "-" [T=text/css,E=no-gzip:1]` (and the same for .js), with `<FilesMatch "(\.js\.gz|\.css\.gz)$"> Header append Content-Encoding gzip; Header append Vary Accept-Encoding </FilesMatch>` — [mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html)
- The 2.2 docs (removed from the current 2.4 page) have the BrowserMatch recipe: `BrowserMatch ^Mozilla/4 gzip-only-text/html`, `BrowserMatch ^Mozilla/4\.0[678] no-gzip`, `BrowserMatch \bMSIE !no-gzip !gzip-only-text/html`. Netscape 4.x "cannot handle compression of types other than text/html", and 4.06-4.08 "also have problems with decompressing html files." The `gzip-only-text/html` note works only when set to `1` — [mod_deflate 2.2](https://httpd.apache.org/docs/2.2/mod/mod_deflate.html). The current 2.4 page contains no BrowserMatch or gzip-only text — [mod_deflate 2.4](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html) (checked by grep)

**mod_deflate behaviour from the source (trunk).** Source: [mod_deflate.c](https://github.com/apache/httpd/blob/trunk/modules/filters/mod_deflate.c)
- When the whole response is in the first brigade with EOS and is no larger than `sizeof(gzip_header) + VALIDATION_SIZE + 50` (10 + 8 + 50 = 68 bytes), it is not compressed ("Not compressing very small response"). There is no configurable minimum length — (source)
- Skipped when: subrequest (`r->main != NULL`); `HTTP_NO_CONTENT` (204); `no-gzip` env; any `Content-Range` response header (comment: "not a partial response to a Range request"); a non-text/html type when `gzip-only-text/html` = "1"; SSL-level compression active; an existing Content-Encoding other than identity, 7bit, 8bit or binary ("If it's already encoded, don't compress again. (We could, but let's not.)") — (source)
- After those tests and **before** checking the client's Accept-Encoding, it does `apr_table_mergen(r->headers_out, "Vary", "Accept-Encoding")`, so Vary is added even when this client is not served gzip — (source)
- Accept-Encoding: it looks for the `gzip` token. Its q is checked only for zero ("No acceptable token found or q=0"); other q values are not ranked. `force-gzip` bypasses the check. 2.4.42: "mod_deflate, mod_brotli: honor 'Accept-Encoding: foo;q=0' as per RFC 7231" (PR 58158) — (source), [httpd 2.4 CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)
- When it compresses: Content-Encoding is set to gzip (or `gzip` merged onto an existing non-identity list); Content-Length and Content-MD5 are unset; the ETag is altered by `deflate_check_etag`. For a 304 it changes only the headers and passes on: "responding to 304 is handled separately to set the required headers (such as ETag) per RFC7232, 4.1." — (source). 2.4.36: "mod_brotli, mod_deflate: Restore the separate handling of 304 Not Modified responses. Regression introduced in 2.4.35." — [httpd 2.4 CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)
- `deflate_check_etag` "appends -transform (e.g., -gzip) to the entity-tag value inside the double-quotes if an ETag has already been set and its value already contains double-quotes. PR 39727". Remove unsets the ETag — (source)
- HEAD: "If we are a HEAD request and bytes_sent is not zero... we can stop compressing" — (source)
- FLUSH buckets cause `Z_SYNC_FLUSH`, so streamed output is pushed through compressed — (source)
- `Cache-Control: no-transform`: the word "no-transform" appears in neither mod_deflate.c nor mod_brotli.c, so it is not honoured — [mod_deflate.c](https://github.com/apache/httpd/blob/trunk/modules/filters/mod_deflate.c), [mod_brotli.c](https://github.com/apache/httpd/blob/trunk/modules/filters/mod_brotli.c) (source, negative grep)
- Proxied requests: mod_deflate has no Via or gzip_proxied-style logic; the decision is the filter's placement plus env variables — (source; no "Via" handling found)

### Inferences
- Apache puts `Vary: Accept-Encoding` on every response the filter sees, even when it does not compress. nginx, with gzip_vary on, also adds it once the type, length and status tests pass, before Accept-Encoding is examined. Both therefore vary uncompressed answers too.
- AddSuffix (`"abc-gzip"`) plus the core's strong If-None-Match comparison against the unsuffixed tag is what loses the 304. nginx's weak-ETag approach and OpenLiteSpeed's "ignore the last 3 characters" approach (below) both keep revalidation working.
- When both DEFLATE and BROTLI_COMPRESS are configured, the official docs do not say how a client accepting both is resolved; the filter order decides. The mod_zstd README recommends `AddOutputFilterByType ZSTD_COMPRESS;BROTLI_COMPRESS;DEFLATE` (third-party claim).

### Gaps
- The original report date of PR 39727 (2006?) and the exact PR 45023 date could not be read from Bugzilla (login wall). Only the CHANGES entries and tarball dates are confirmed.
- The docs give no measured CPU cost per level, only qualitative statements ("more CPU time", "very slow").
- Whether mod_deflate removes Accept-Ranges was not checked in the source.

## LiteSpeed Web Server (LSWS) and OpenLiteSpeed (OLS)

### Takeaway
Both servers compress by default ("Enable Compression: Yes") from a built-in list of compressible types (text/*, JS, JSON, XML, SVG, fonts, icons, XHTML). Static files get gzip level 6 and Brotli level 5, written once to a compressed-file cache; files from 200 bytes to 10 MB qualify by default. Dynamic responses (PHP over LSAPI included) get gzip at level 6 above 200 bytes. Only LSWS (Enterprise) does dynamic Brotli (level 0-6, default 2); OLS does Brotli for static files only. OLS keeps one ETag base with a `;gz`/`;br` suffix and ignores the suffix in If-None-Match, so 304s keep working. LSWS added Zstandard in 6.4.0 RC1 (2026-08-13, not yet in a stable release); OLS has no zstd.

**OLS behaviour from the source (master, v1.9.4 of 2026-10-24).** Sources under [openlitespeed/src/http](https://github.com/litespeedtech/openlitespeed/tree/master/src/http)
- Accept-Encoding is parsed with `strcasestr(pCur, "gzip")` and `strcasestr(pCur, "br")`, plain substring tests with no q-value handling. A server or vhost switch then sets GZIP_ENABLED or BR_ENABLED — [httpreq.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpreq.cpp) (source)
- The type gate: the response's Content-Type is looked up in the MIME settings; when it is not `compressible()`, both gzip and br are disabled for the request — [httpsession.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpsession.cpp) (source)
- Dynamic responses: `contentEncodingFixup()` adds the gzip filter (`addModgzipFilter(1, getCompressLevel())`) only when there is no Content-Encoding, gzip is required, the type is compressible and `getContentLen() > 200`; it then switches to chunked and deletes Content-Length. `setupGzipFilter()` compresses when the length is above 200 or unknown (< 0). If dynamic gzip is off (`getDynGzipCompress()`), handler responses lose GZIP_ENABLED. There is no Brotli path for dynamic responses (`addGzipEncodingHeader` only) — [httpsession.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpsession.cpp) (source)
- Already-compressed backend output (for example PHP's own gzip over LSAPI, flagged UPSTREAM_GZIP or UPSTREAM_DEFLATE): when the client does not accept gzip, or a module hook needs plain bytes, OLS adds a **decompression** filter (`addModgzipFilter(0, 0)`) and deletes Content-Encoding. Otherwise it passes the compressed body through — [httpsession.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpsession.cpp) (source)
- mod_gzip uses `deflateInit2(..., 16 + MAX_WBITS, ...)` (the gzip wrapper). A flush from the handler maps to `Z_PARTIAL_FLUSH` — [modgzip.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/modules/modgzip/modgzip.cpp) (source)
- Encoding headers: `addGzipEncodingHeader()` adds `Content-Encoding: gzip` plus `Vary: Accept-Encoding` (merged) and calls `updateEtag(ETAG_GZIP)`; `addBrEncodingHeader()` does the same for br — [httprespheaders.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httprespheaders.cpp) (source)
- ETag scheme: a static file's ETag is built from size, mtime and inode, then `;;;` inside the quotes. `updateEtag` rewrites the last two characters to `gz` or `br`, giving `...;gz"` or `...;br"`. On If-None-Match, a leading `W/` is skipped and the last 3 characters are ignored ("ignore trialing ';gz' ';br'"). On a match the server returns 304 carrying the client's own tag ("Since we will return 304, but should use the original Etag") — [staticfilecachedata.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/staticfilecachedata.cpp), [httprespheaders.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httprespheaders.cpp) (source)
- Static compressed cache: files are named by an MD5 hash of the path with the suffix `.lsz` (gzip) or `.lsb...` (brotli), built under a lock file `*.lszl` (a stale lock is removed after 60 s). Creation is refused outside the [min, max] size range or when Auto Update is off. The compiled-in defaults are min 300, max 1 MB, gzip 6, br 6, which differ from the documented 200, 10M and 5; the configuration presumably overrides them (unverified). A helper script `gzipStatic.sh` runs `gzip -c -$LEVEL` to `$FN.lsz` — [staticfilecachedata.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/staticfilecachedata.cpp), [gzipStatic.sh](https://github.com/litespeedtech/openlitespeed/blob/master/dist/admin/misc/gzipStatic.sh) (source)
- Range on static files: `processRange()` is called before the compressed-variant mode is chosen (`readyCacheData(mode)`), so a Range request is answered from the identity file — [staticfilehandler.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/staticfilehandler.cpp) (source)
- zstd: no file or path containing "zstd" exists in the OLS master tree (2,271 entries searched by name) — [GitHub tree API, openlitespeed master](https://github.com/litespeedtech/openlitespeed) (source, negative search). Latest OLS releases: v1.9.4 2026-10-24, v1.9.3 2026-09-30 — [OLS releases](https://github.com/litespeedtech/openlitespeed/releases)

### Inferences
- LiteSpeed's defaults are the most aggressive of the three servers: compression on, a broad type list, level 6 gzip (nginx 1), and precompression of static files into a cache. This explains why a fresh LiteSpeed install already sends Brotli for CSS/JS.
- Because OLS does Brotli only for static files, PHP pages on OLS get gzip at most; LSWS Enterprise adds dynamic Brotli at level 2.
- OLS's substring Accept-Encoding test means `gzip;q=0` would still count as acceptance (reading of the source, untested).
- Because the ETag base stays the same across variants, conditional requests survive compression, unlike Apache's default AddSuffix.

### Gaps
- LSWS's Zstandard settings (names, levels, defaults) are not yet in the Tuning reference I fetched; only the 6.4.0 RC1 release-log line is confirmed.
- LSWS (closed source) behaviour on Range, `no-transform`, HEAD, 304 and proxied responses could not be checked; the OLS source is used as a proxy and may differ.
- Whether OLS or LSWS honour `Cache-Control: no-transform` was not established (not searched in the OLS source).
- I did not find official LiteSpeed CPU-cost figures beyond the qualitative tips quoted above.

## Defaults side by side: MIME types, minimum length, default level, documented CPU trade-off

### Takeaway
nginx is conservative and opt-in: off by default, text/html only, level 1, 20 bytes minimum, no Vary by default. Apache is opt-in per filter: no types until you list them, zlib level 6 for gzip, Brotli quality 5, an implicit 68-byte floor. LiteSpeed is on by default with a broad type list: gzip 6 both static and dynamic, Brotli 5 static, Brotli 2 dynamic on LSWS only, a 200-byte minimum.

### Cited Findings
- nginx gzip: `gzip off`, `gzip_types text/html`, `gzip_comp_level 1`, `gzip_min_length 20`, `gzip_vary off`, `gzip_proxied off`, `gzip_http_version 1.1` — [nginx gzip docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). CPU guidance: none beyond the BREACH warning — [nginx gzip docs](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)
- nginx brotli (third-party): `brotli off`, `brotli_types text/html`, `brotli_comp_level 6`, `brotli_window 512k`, `brotli_min_length 20` — [ngx_brotli](https://github.com/google/ngx_brotli). zstd (third-party): `zstd_comp_level 1`, `zstd_min_length 20`, `zstd_types text/html` — [zstd-nginx-module](https://github.com/tokers/zstd-nginx-module)

- LSWS/OLS: compression on; the built-in types list as quoted above; gzip dynamic 6 and static 6; Brotli static 5; LSWS Brotli dynamic 2 (0-6); static precompression 200 B to 10 MB; dynamic gzip above 200 bytes (OLS source). CPU: "There is not much difference between 6 and 9, except that 9 uses many more CPU cycles"; "Compressing dynamic responses increases CPU and memory utilization" — [LSWS Tuning](https://www.litespeedtech.com/docs/webserver/config/tuning), [OLS httpsession.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/httpsession.cpp)
- Library reference points: the Brotli library's own `BROTLI_DEFAULT_QUALITY` is 11 and `BROTLI_DEFAULT_WINDOW` is 22, so every server overrides the library default downward for on-the-fly use (nginx 6/19, Apache 5/18) — [brotli encode.h](https://github.com/google/brotli/blob/master/c/include/brotli/encode.h), [ngx_brotli filter](https://github.com/google/ngx_brotli/blob/master/filter/ngx_http_brotli_filter_module.c), [mod_brotli.c](https://github.com/apache/httpd/blob/trunk/modules/filters/mod_brotli.c)

### Inferences
- How each server answers a Range request on a compressible resource: nginx sends a full compressed 200 (Accept-Ranges removed); Apache an uncompressed 206 (compression skipped on Content-Range); OLS an identity 206 (ranges handled before the variant is chosen). Only nginx's gzip_static and brotli_static serve ranges of a precompressed file (gzip_static since 1.23.4).
- ETag strategies: nginx turns the tag weak (W/) and compares weakly for If-None-Match; Apache appends `-gzip`/`-br` (AddSuffix, breaks 304), with NoChange and Remove as alternatives since 2.4.58; OLS uses the same base tag with a `;gz`/`;br` suffix that is ignored on comparison.
- None of the three, as far as the source shows (nginx, Apache) or was searched, honours `Cache-Control: no-transform` when compressing.

### Gaps
- No vendor publishes CPU-per-level benchmarks in its official docs; any numbers must come from independent measurement.
- Defaults for LSWS's new zstd support are unknown as of 2026-10-26.
