# What administrators ask for, struggle with and complain about in HTTP response compression (gzip, brotli, zstd)

Method note for the report writer: every vote and view count below is a question's score and view count as returned by the Stack Exchange API on 2026-10-26 (sorted by votes, searched by title or tag). "Top answer N" is the score of that question's highest-voted answer. GitHub figures are reactions (r) and comments (c) from the GitHub REST API the same day. Package versions come from sources.debian.org and Launchpad the same day. These numbers are a snapshot, and they favour old questions, which have had more time to collect votes. A 2012 question with 90,000 views shows a problem that lasted, not one that is current. The 2020-2026 items are flagged by date.

## Which compression problems recur most (ranking by votes and views)

### Takeaway
By votes and views, the problems that come back most often are: (1) "compression is on but this content is not compressed": the type list, the minimum length, proxied responses; (2) "how do I check that compression works"; (3) decoding errors from double or false compression; (4) Vary and caching; (5) the brotli module packaging pain on nginx. Streaming breakage, BREACH and zstd come up less often, but they are recent and keep recurring in proxy projects' issue trackers.

### Inferences
- A rough frequency order for a designer, from the counts above: type coverage and "why isn't X compressed" > verification > decoding errors (double or false compression) > Vary and caching > brotli availability > Content-Length, chunked and ETag side effects > streaming > BREACH > zstd. Streaming and zstd rank low on Stack Exchange, but they are the most active subjects in 2023-2026 GitHub trackers (sections below). That reflects where the current work is, not low importance.

### Gaps
- Reddit (r/nginx, r/selfhosted, r/sysadmin) threads could not be retrieved or counted; web search did not surface the threads themselves. The Reddit sentiment is therefore not quantified here.
- The Stack Exchange counts are lifetime totals. No per-year breakdown of question volume was computed.

## Recurring nginx questions (gzip_proxied, gzip_types, gzip_http_version, Vary, ETag, location inheritance, level)

### Takeaway
Almost every nginx complaint traces to a default that is off, narrow or surprising: `gzip off`, `gzip_types text/html`, `gzip_proxied off` (keyed on the `Via` request header), `gzip_vary off`, `gzip_min_length` read only from Content-Length, and `gzip_http_version 1.1` against `proxy_http_version 1.0`. Each one has produced its own family of "gzip is on but nothing is compressed" questions.

### Cited Findings
- **nginx's documented defaults:** `gzip off`; `gzip_types text/html` ("Responses with the text/html type are always compressed"); `gzip_proxied off` ("The fact that the request is proxied is determined by the presence of the Via request header field"); `gzip_http_version 1.1`; `gzip_min_length 20` ("The length is determined only from the Content-Length response header field"); `gzip_comp_level 1`; `gzip_vary off`. The doc's own example sets `gzip_proxied expired no-cache no-store private auth` and `gzip_types text/plain application/xml` — [nginx ngx_http_gzip_module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html).
- **gzip_types misses JavaScript, JSON, fonts and SVG.**
  - JavaScript: the accepted fix (177 votes) adds `application/javascript` and `text/javascript` next to `application/x-javascript` — [SO 23939722](https://stackoverflow.com/questions/23939722/nginx-gzip-not-compressing-javascript-files).
  - JSON: "gzip not working on nginx for JSON responses", 14,450 views — [SF 887007](https://serverfault.com/questions/887007/gzip-not-working-on-nginx-for-json-responses). The DHIS2 maintainers had to list `application/json;charset=utf-8` beside `application/json` — [DHIS2 sysadmin tip](https://community.dhis2.org/t/sys-admin-tip-gzip-compression-for-async-responses/3102). An iRedMail user found `application/javascript` was missing where `text/javascript` was listed — [iRedMail forum](https://forum.iredmail.org/post75912.html). Frappe users saw XHR JSON uncompressed while other types worked — [Frappe forum](https://discuss.frappe.io/t/gzip-not-working-for-xhr-requests/10915).
  - Fonts: "Config NGINX to GZip Font Files? (Different gzip_types for different directories)", 11,363 views — [SF 321626](https://serverfault.com/questions/321626/config-nginx-to-gzip-font-files-different-gzip-types-for-different-directorie).
  - Keeping two lists in step: "Sharing MIME type list using GZIP and BROTLI in NGINX" (the gzip and brotli type lists have to be kept in sync by hand) — [SO 39827200](https://stackoverflow.com/questions/39827200/sharing-mime-type-list-using-gzip-and-brotli-in-nginx).
- **gzip_min_length misread.**
  - "Why is the gzip minimum length directive not being respected?" (18 votes, 17,413 views): with no Content-Length (a streamed application response), the minimum is never applied, so 100-byte JSON was gzipped — [SO 33269448](https://stackoverflow.com/questions/33269448/why-is-the-gzip-minimum-length-directive-not-being-respected).
  - The opposite trap: an administrator had `gzip_min_length 256k` (meaning 256 bytes) and nothing compressed; "ARGH!" — [SF 887007](https://serverfault.com/questions/887007/gzip-not-working-on-nginx-for-json-responses).
- **Proxied responses: `Via` and `gzip_proxied`.**
  - "Nginx Reverse Proxy Gzip to Client" (14 votes, 33,039 views), answer `gzip_proxied any` — [SF 730883](https://serverfault.com/questions/730883/nginx-reverse-proxy-gzip-to-client). Similar: [SF 360473](https://serverfault.com/questions/360473/gzip-compression-doesnt-work-in-nginx-reverse-proxy-setup) (10,504 views); [SF 731014](https://serverfault.com/questions/731014/nginx-gzip-on-server-is-lost-during-proxy) (10,766 views).
  - The `Via` trigger is explained by Igor Sysoev on the list, and the ticket asking for a change is still referenced — [nginx trac #965](https://trac.nginx.org/nginx/ticket/965). A CDN vendor's origin guide tells customers to set `gzip_proxied any` because CDN requests carry Via — [Alibaba Cloud CDN doc](https://help.aliyun.com/document_detail/205123.html).
  - A 2021 list thread: the user had `gzip off;` in the http block, which silently disabled what they had configured lower down, with no warning — [nginx mailing list, May 2021](https://mailman.nginx.org/pipermail/nginx/2021-May/060678.html).
- **gzip_http_version against proxy_http_version.**
  - The list explains that nginx speaks HTTP/1.0 to backends while gzip by default needs HTTP/1.1 — [nginx mailing list, May 2021](https://mailman.nginx.org/pipermail/nginx/2021-May/060679.html).
  - A Varnish case: Varnish rewrote Accept-Encoding to `gzip`, the nginx origin behind it did not compress, and the fix was to change `gzip_http_version` on the origin and turn off Varnish's gzip handling — [SO 64075897](https://stackoverflow.com/questions/64075897/how-to-prevent-nginx-reverse-proxy-recompress-the-upstream-compressed-response). That answer states "the default for gzip_http_version is 1.0", which contradicts the nginx doc's default of 1.1 — [nginx doc](https://nginx.org/en/docs/http/ngx_http_gzip_module.html). The confusion itself is the finding.
- **Vary.**
  - `gzip_vary` is off by default — [nginx doc](https://nginx.org/en/docs/http/ngx_http_gzip_module.html).
  - "nginx gzip Vary header together with existing Vary headers" (4,716 views): administrators worry about duplicate Vary lines — [SF 821310](https://serverfault.com/questions/821310/nginx-gzip-vary-header-together-with-existing-vary-headers).
  - ngx_brotli had its own Vary bug reports — [ngx_brotli #44](https://github.com/google/ngx_brotli/issues/44) (8 reactions), [PR #98 "Fix 'Vary' header"](https://github.com/google/ngx_brotli/pull/98).
- **ETag.**
  - "nginx - missing etag when gzip is used": before 1.7.3 nginx dropped the ETag on gzipped responses; the accepted answer quotes the 1.7.3 change "weak entity tags are now preserved on response modifications, and strong ones are changed to weak" — [SO 31125888](https://stackoverflow.com/questions/31125888/nginx-missing-etag-when-gzip-is-used).
  - The gzip doc's only ETag mention is `gzip_proxied no_etag` — [nginx doc](https://nginx.org/en/docs/http/ngx_http_gzip_module.html).
- **Content-Length disappears with dynamic gzip.**
  - "Force Nginx to send Content-Length header for static files with gzip?" (15,847 views); the answer is that dynamic gzip is chunked, so the fix is `gzip_static` (pre-compressed files) — [SF 529621](https://serverfault.com/questions/529621/force-nginx-to-send-content-length-header-for-static-files-with-gzip).
  - "Unable to turn off chunked transfer encoding in nginx with gzip" (20,524 views) — [SO 27828576](https://stackoverflow.com/questions/27828576/unable-to-turn-off-chunked-transfer-encoding-in-nginx-with-gzip-for-static-asset).
- **Per-location, per-host and per-type control.**
  - "Turn off gzip for a location in Nginx": 34,088 views — [SF 438237](https://serverfault.com/questions/438237/turn-off-gzip-for-a-location-in-nginx).
  - "nginx: enabling gzip compression based on hostname" — [SF 774742](https://serverfault.com/questions/774742/nginx-enabling-gzip-compression-based-on-hostname).
  - "Nginx: disable gzip on images" — [SF 411791](https://serverfault.com/questions/411791/nginx-disable-gzip-on-images).
- **The application wants to opt out.** "How can I disable nginx gzip from PHP?": the accepted answer is to send `Content-Encoding: identity`, because nginx skips gzip when the upstream response already has a Content-Encoding — [SO 41086260](https://stackoverflow.com/questions/41086260/how-can-i-disable-nginx-gzip-from-php).
- **Request bodies, not responses.** "How do I configure nginx to accept gzip requests?": 23 votes, 15,882 views — [SF 334215](https://serverfault.com/questions/334215/how-do-i-configure-nginx-to-accept-gzip-requests).
- **Compression level.** The top answer (114) measured nginx levels 0-9: phpinfo HTML goes from 20.26 % of its original size at level 1 to 17.05 % at level 9; jQuery from 36.34 % at level 1 to about 30 % at level 6, with little gained after that — [SF 253074](https://serverfault.com/questions/253074/what-is-the-best-nginx-compression-gzip-level).

### Inferences
- The "type list" complaint has three variants a designer must handle: types missing from the list (JS, JSON, fonts, SVG, wasm); parameters that defeat exact matching (`;charset=utf-8`); and older aliases (`application/x-javascript`, `text/javascript`). Matching on the media type with parameters ignored, from a broad built-in list, removes most of these questions.
- `gzip_proxied off` keyed on `Via` makes the common case wrong: an origin behind a CDN or a load balancer stops compressing. A default that compresses for proxies too, with Vary always sent, matches what administrators end up configuring.
- A minimum length that only works when Content-Length is known surprises people both ways. Buffering the first N bytes of a streamed response before deciding, which Caddy does, is the behaviour they expect.

### Gaps
- No official nginx statement was found on why gzip_types defaults to text/html only. The nginx doc gives no rationale.
- nginx's gzip filter is believed to skip responses with statuses other than 200, 403 and 404. A ticket hinting at this exists among the search results, but which ticket says it was not verified, so the claim is not cited.
- Inheritance pitfalls (a `gzip_types` in a location replacing rather than adding to the parent's list) were not confirmed from nginx documentation in this pass.

## Brotli on nginx: the third-party module, rebuilds and packaging

### Takeaway
Brotli on nginx is a long-running source of complaints. It is a third-party module: Google's repository was declared unmaintained for years. A dynamic `.so` breaks on every nginx minor upgrade ("version 1022000 instead of 1022001"), and distribution packages lag behind nginx.org's builds. nginx stated in 2026 that native Brotli is not planned. Debian and Ubuntu now ship it, but only built against their own nginx.

### Cited Findings
- **nginx's position (2026).** On "2024, As a quasi-WHATWG official feature, can Nginx integrate Brotli support?" an nginx maintainer replied on 2026-09-28: "Native Brotli support is not planned at the moment", pointing to ngx_brotli as a dynamic module built `--with-compat` — [nginx/nginx #397](https://github.com/nginx/nginx/issues/397). A similar request was closed — [nginx/nginx #454](https://github.com/nginx/nginx/issues/454).
- **The upgrade trap.** "Why on earth is this so complicated to install in Ubuntu AND have it auto-update?" (11 reactions, 2022): after `apt upgrade` nginx refused to start with `module "/etc/nginx/modules/ngx_http_brotli_filter_module.so" version 1022000 instead of 1022001`. Comments in the same thread:
  - "you need to compile the module from source with each update" (2024);
  - Ubuntu's `libnginx-mod-http-brotli-*` packages are incompatible with nginx.org's 1.26.2/1.27.2, so one user downgraded and held nginx (2024);
  - the official nginx Docker image can build it with `ENABLED_MODULES="brotli"`;
  - third-party repositories (GetPageSpeed, darylounet) offer prebuilt packages.

  All from [ngx_brotli #140](https://github.com/google/ngx_brotli/issues/140).

### Inferences
- What administrators want is brotli (and now zstd) that survives `apt upgrade` without a rebuild, i.e. built into the server. A server that ships gzip, brotli and zstd in the binary removes the most-reacted complaint in this area outright.
- The "gzip_static wins over brotli_static" and "gzip breaks after adding br" bugs show that negotiation across several encodings and pre-compressed variants has to be one decision in one place, not separate filters each deciding alone.

### Gaps
- No count of how many nginx installations run brotli was found.

## Apache: mod_deflate setup, the ETag "-gzip" suffix and 304s, hosting .htaccess snippets, mod_brotli

### Takeaway
On Apache the complaints are: copy-pasted `.htaccess` blocks that may not apply, "is mod_deflate even working", PHP output not compressed or compressed twice, and the ETag suffix that turns every conditional request for a compressed resource into a full 200. The ETag behaviour changed across versions and got a directive (`DeflateAlterETag`) only in 2.4.58. mod_brotli exists since 2.4.26, but questions show it often is not applied to PHP-FPM output.

### Cited Findings
- **ETag and 304s.**
  - "Apache is not sending 304 response (if mod_deflate and AddOutputFilterByType is enabled)": 28 votes, 14,389 views. Top answer (30): Apache bug #45023, with a runtime workaround: `RequestHeader edit "If-None-Match" "^\"(.*)-gzip\"$" "\"$1\""` plus a matching `Header edit "ETag"` — [SO 896974](https://stackoverflow.com/questions/896974/apache-is-not-sending-304-response-if-mod-deflate-and-addoutputfilterbytype-is).
  - Background: bugs #39727 and #45023, where a fix for one introduced the other; the author argues the root cause is using Content-Encoding rather than Transfer-Encoding (2009) — [scarff.id.au](https://scarff.id.au/blog/2009/apache-304-and-mod_deflate-revisited/). The same Content-Encoding versus Transfer-Encoding question has 115 votes and 112,923 views — [SO 11641923](https://stackoverflow.com/questions/11641923/transfer-encoding-gzip-vs-content-encoding-gzip).
- **DeflateAlterETag.** `AddSuffix` (the default since 2.4.0) gives compressed and uncompressed copies distinct ETags but "prevents serving 304 responses to conditional requests for compressed content". `NoChange` (the pre-2.4.0 behaviour) breaks the unique-ETag-per-representation rule. `Remove` drops the ETag. The directive is listed as available in 2.4.58 and later; one 2.5 doc mirror says 2.4.42 — [Apache mod_deflate doc](https://httpd.apache.org/docs/mod/mod_deflate.html).
- **Is it working?** [SO 970151](https://stackoverflow.com/questions/970151/how-to-check-mod-deflate-is-enabled-in-apache) (91,382 views); [SF 334907](https://serverfault.com/questions/334907/how-to-tell-if-mod-deflate-is-actually-working) (25,660 views).
- **Excluding media.** "How to disable Apache gzip compression for some media files in .htaccess file?": 19 votes, 47,413 views — [SO 9249243](https://stackoverflow.com/questions/9249243/how-to-disable-apache-gzip-compression-for-some-media-files-in-htaccess-file). "How to disable mod_deflate in apache2?": 28,201 views — [SO 1922934](https://stackoverflow.com/questions/1922934/how-to-disable-mod-deflate-in-apache2).
- **Pre-compressed files.** "How can I pre-compress files with mod_deflate in Apache 2.x?": 35 votes — [SO 75482](https://stackoverflow.com/questions/75482/how-can-i-pre-compress-files-with-mod-deflate-in-apache-2-x). ### Inferences
- The ETag problem is the clearest correctness trap in the area. - Type-based activation (`AddOutputFilterByType`) that misses responses from PHP-FPM or proxies is a recurring Apache confusion. Compression should apply by the response's type whatever handler produced it.

## Double compression and broken output (PHP zlib.output_compression or ob_gzhandler, WordPress cache plugins, frameworks, Content-Encoding twice)

## Streaming: SSE, long polling, chunked streaming, PHP flush(), Node streaming, WebSockets

### Takeaway
Compression buffers. Every proxy and server in this survey has had a "compression breaks server-sent events" bug: Traefik in 2017, again in 2019 and again in 2025; Caddy in 2021-2024; nginx through FastCGI and gzip buffering. Administrators work around it by turning compression off per location, sending `X-Accel-Buffering: no`, adding `fastcgi_buffering off`, or excluding `text/event-stream`. What they want: SSE and streamed responses are never delayed, headers go out at once, and every application flush is honoured with a compressor flush.

### Cited Findings
- **Traefik.** "Problem with text/event-stream when compress=true" (2017, 39 comments): the Concourse CI UI hung waiting for events — [traefik #2576](https://github.com/traefik/traefik/issues/2576). Fixed by "Do not compress when content type text/event-stream" (2019) — [traefik PR #5120](https://github.com/traefik/traefik/pull/5120). Broken again in v3 and fixed again by "fix(middleware): do not compress text/event-stream responses" (2025-02) — [traefik PR #11511](https://github.com/traefik/traefik/pull/11511).
- **Caddy.** "Problems with reverse proxied server sent events and compression" (2024): `encode` delayed sending the headers until the first body bytes, so the SSE connection was not established until the first event. A maintainer asked whether SSE should be compressed at all; the reporter answered that SSE payloads (HTMX fragments, JSON) compress well. A 2026 commenter's workaround: exclude SSE from encode — [caddy #6293](https://github.com/caddyserver/caddy/issues/6293). The delay came from "encode: ignore flushing until after first write" — [caddy PR #4318](https://github.com/caddyserver/caddy/pull/4318). Caddy's doc now says SSE responses and responses with `Incremental: ?1` "are not held back to reach this threshold: their headers are sent to the client immediately" and "the body is streamed as it is written" — [Caddy encode docs](https://caddyserver.com/docs/caddyfile/directives/encode).
- **Caddy, WebSockets.** "reverse_proxy: h2 websocket stuck if client needs to send the first message and encode is enabled" (2024-12) — [caddy #6733](https://github.com/caddyserver/caddy/issues/6733). (2016, 18 comments) — [caddy #677](https://github.com/caddyserver/caddy/issues/677).
- **nginx with PHP and FastCGI.**
  - The nginx maintainer (2013): gzip, SSI and sub filters can all buffer, so he recommends `fastcgi_buffering off` (nginx 1.5.6+); `proxy_buffering` "does nothing as long as you use fastcgi_pass" — [nginx mailing list, Oct 2013](https://mailman.nginx.org/pipermail/nginx/2013-October/040732.html).

### Inferences
- A complete feature needs four things here:
  1. never hold headers back for a minimum-length decision on `text/event-stream` (or when the application asks for incremental delivery);
  2. turn each application flush (a FastCGI record boundary, a proxy read that empties the upstream, a chunk) into a compressor sync flush;
  3. give a per-response opt-out the application can send (the `X-Accel-Buffering: no` pattern, or simply a Content-Encoding already set);
  4. never compress upgraded or tunnelled connections.
- Compressing SSE is wanted by some users (HTMX/JSON events) and blamed by others. The safe default is the one Caddy reached: compress, but flush per event and never delay the start.

- No measurement was found of the latency added by gzip's buffering on SSE in nginx when proxy buffering is off.
- Whether nginx's gzip filter actually honours `X-Accel-Buffering` was not confirmed from nginx sources.

## CDN and caching interaction: Vary, cache fragmentation, Cloudflare and origin compression

### Takeaway
Vary: Accept-Encoding is the single most-viewed compression header question (171,560 views). The fears are of two kinds: no Vary at all, so gzip reaches clients that cannot decode it; or too many variants, which fragment the cache. Behind CDNs, administrators ask whether their origin's compression matters at all, and see the CDN decompress and recompress. Proxy projects keep getting bugs where a backend's Vary is lost or duplicated.

### Inferences
- Vary: Accept-Encoding must be on every response that could have been compressed: compressed or not, merged with the application's own Vary, never duplicated. That is the cheapest way to make CDNs and shared caches safe. Fragmentation is a CDN's problem to normalise; the origin's job is to be correct.
- Negotiation should follow q-values. At equal q, it should follow a server preference the administrator can set, with a documented default. Both Caddy and Traefik changed their defaults in public, and users noticed each time.
- Without Accept-Encoding, sending identity is the expected behaviour, even though the RFC allows more.

### Gaps
- Cloudflare's current documentation on what it requests from origins (whether it sends zstd upstream) was not fetched directly; only a secondary summary was found.
- No data was found on cache hit-ratio loss from Accept-Encoding fragmentation.

### Takeaway
Administrators ask what minimum size to use, how to keep images, video and archives out, and which level is worth the CPU. Measured answers show gzip levels above about 5-6 buy almost nothing. ### Inferences
- Sensible defaults implied by the evidence:
  - a minimum around 512 bytes to 1.4 KB (Caddy 512; Lighthouse ignores under about 1.4 KiB);
  - gzip level about 5-6, with brotli and zstd at low or moderate levels for dynamic responses;
  - high brotli levels reserved for pre-compressed static files;
  - a built-in exclusion of image, video, audio and archive types, whatever list the administrator writes.
- Pre-compressed twins (`.br`, `.gz`, `.zst` beside the file) are the answer to CPU worries and to the lost Content-Length. They are only safe if a stale twin (older than the file) is ignored.

### Gaps
- No systematic CPU-per-request measurements of dynamic gzip vs brotli vs zstd under web-server load were found in this pass (only Cloudflare's ratio and speed claims and Caddy comments).

## BREACH: how often it is asked, what guidance is given, and the confusion

### Takeaway
BREACH questions are steady but small in number. The guidance is consistent: the attack needs reflected input plus a secret in the same compressed response over TLS, so static assets are safe, and turning compression off everywhere "does not make much sense". The confusion shows up in scanners flagging compression and Google tools complaining when sites disable it, which puts administrators between two tools.

### Cited Findings
- **Questions and counts (Security SE).**
  - "Current State of BREACH (GZIP SSL Attack)?" (19 votes, 12,209 views, 2014). Top answer (20) lists the conditions (compression, reflected input, a static secret in the body, an attacker who can observe sizes and forge requests) and says "Disabling gzip compression for everything does not make much sense" — [Sec.SE 65625](https://security.stackexchange.com/questions/65625/current-state-of-breach-gzip-ssl-attack).
  - "To avoid BREACH, can we use gzip on non-token responses?" (13 votes, 9,062 views, 2017) — [Sec.SE 172581](https://security.stackexchange.com/questions/172581/to-avoid-breach-can-we-use-gzip-on-non-token-responses).
  - "Brotli compression algorithm and BREACH attack" (21 votes, 2017) — [Sec.SE 172188](https://security.stackexchange.com/questions/172188/brotli-compression-algorithm-and-breach-attack).
  - "How are websites actually mitigating BREACH? (HTTPS + compression)" (2019, 5,451 views); the answer lists the ingredients and says every mitigation has trade-offs — [Sec.SE 222677](https://security.stackexchange.com/questions/222677/how-are-websites-actually-mititating-breach-https-compression).
  - "Does TLS 1.3 mitigate the BREACH vulnerability?" (2020) — [Sec.SE 231627](https://security.stackexchange.com/questions/231627/does-tls-1-3-mitigate-the-breach-vulnerability).
  - "Does cloudflare protect against BREACH attacks?" (2019): the answer says scanners "often detect only the circumstances around a vulnerability, like compression" — [Sec.SE 220136](https://security.stackexchange.com/questions/220136/does-cloudflare-protect-against-breach-attacks).
  - "Is a SPA vulnerable to the BREACH https security exploit?" — [Sec.SE 147098](https://security.stackexchange.com/questions/147098/is-a-spa-vulnerable-to-the-breach-https-security-exploit). - **Administrators' framing.** "Should I enable Gzip on Nginx server with SSL for a react app?" (2018); answer: compressed JS and CSS reflect neither user input nor secrets, so "it is completely safe to use Gzip compression for js/css assets" — [SO 52270400](https://stackoverflow.com/questions/52270400/should-i-enable-gzip-on-nginx-server-with-ssl-for-a-react-app).

### Inferences
- What administrators need is a precise per-path switch (turn compression off for the account pages that reflect input and carry tokens) rather than a global choice, plus documentation that says plainly static assets are safe. Pages behind a password, and responses that are already `Cache-Control: private`, are where a selective "no compression" rule would be applied.

### Gaps
- No count of how many production sites disable compression for BREACH was found.
- No web server was found that ships a BREACH-specific default (such as no compression of responses that set cookies); this could not be confirmed either way.

## zstd: requests for support and adoption, 2024-2026

### Takeaway
zstd moved from requests to real deployments within two years. Chrome 123 (March 2024) and Firefox 126 (May 2024) support it; Safari followed partially in 26.3 (February 2026); Cloudflare serves it to browsers since September 2024; Caddy prefers it by default. nginx has no core support. A third-party module was unmaintained for a while and is now forked and packaged (FreeBSD; Debian sid/forky as `libnginx-mod-http-zstd`). Adoption brought its own bugs: negotiation order, a dependency update that silently enabled zstd in Traefik, HEAD Content-Length, and decompression-size concerns.

### Cited Findings
- **Browsers.**
  - Chrome 123 (March 2024) and Firefox 126 (May 2024) support `Content-Encoding: zstd` — [caniuse zstd](https://caniuse.com/zstd).
  - Safari 26.3 (February 2026) added it, but only where the system networking stack supports it, so caniuse marks it partial — [caniuse](https://caniuse.com/mdn-http_headers_content-encoding_zstd), [WebKit bug 279815](https://bugs.webkit.org/show_bug.cgi?id=279815).
  - A 2024 GetPageSpeed guide still says Safari lacks support (outdated) — [GetPageSpeed](https://www.getpagespeed.com/server-setup/nginx/nginx-zstd-compression).
- **Cloudflare.** zstd for all customers since 2024-09-25, with "up to 42% faster than Brotli" and 11.3 % smaller than gzip — [Cloudflare blog](https://blog.cloudflare.com/new-standards/).
- **nginx.**
  - No core zstd. The tokers module has had no release since 2023 (GetPageSpeed's claim), and GetPageSpeed maintains a fork that fixes "streaming bugs that truncated large responses" — [GetPageSpeed zstd module](https://www.getpagespeed.com/server-setup/nginx/zstd-nginx-module).
  - FreeBSD bug "www/nginx add zstd compression module", resolved with the module added to the ports in 2025 — [FreeBSD 284075](https://bugs.freebsd.org/bugzilla/show_bug.cgi?id=284075); a port of the sysadmin-labs module — [FreshPorts](https://www.freshports.org/www/nginx-module-zstd/); an Angie port too — [FreeBSD review](https://reviews-dev.freebsd.org/R11:d52da51671168cbf847447d3252565607997b841).

  - Debian: source package `libnginx-mod-http-zstd` 0.90.9-2 in forky/sid only, not in trixie (2026-10-26) — [sources.debian.org](https://sources.debian.org/src/libnginx-mod-http-zstd/).
  - nginx added `.zst` and other types to its MIME map in 2025 — [nginx PR #733](https://github.com/nginx/nginx/pull/733).
- **Caddy.**
  - "Add zstd compression" requested in 2018 — [caddy #2153](https://github.com/caddyserver/caddy/issues/2153); "zstd (preferred) and gzip are enabled by default" — [Caddy encode docs](https://caddyserver.com/docs/caddyfile/directives/encode).
  - Negotiation complaint (2024) — [caddy #6179](https://github.com/caddyserver/caddy/issues/6179).
  - Shared-dictionary compression requested (2024, open, 8 reactions) — [caddy #6204](https://github.com/caddyserver/caddy/issues/6204); trained zstd dictionaries (2026-09) — [caddy PR #8075](https://github.com/caddyserver/caddy/pull/8075).
  - Bug: HEAD responses carried `Content-Length: 20` (gzip) or `13` (zstd), the sizes of empty streams, against RFC 9110 8.6 (2026-10) — [caddy #8148](https://github.com/caddyserver/caddy/issues/8148).
- **Traefik.** A compression library update silently added zstd to the gzip handler. - **Envoy.** "zstd: incomplete requests in which any partial slice inflates 100x" (2026-10, open) — [envoy #47970](https://github.com/envoyproxy/envoy/issues/47970).
- **Lighthouse.** It initially did not count zstd as compression when Chrome 123 shipped it (2024) — [Lighthouse #15882](https://github.com/GoogleChrome/lighthouse/issues/15882).

### Inferences
- A complete feature today offers gzip, brotli and zstd, negotiates them by q-value with an administrator-set preference at equal q, and lists the codings it applied in the access log. - Updating a dependency must never change the codings a server offers without a configuration change, as the Traefik regression shows.

### Gaps
- No Apache httpd zstd module (core or widely used third-party) was found in this pass.
- No measured share of origins serving zstd in 2025-2026 was found; the caddy #6179 reporter mentions crawling for it but published no numbers in the thread excerpt read.

## What a good compression feature looks like to administrators (defaults, per-site and per-location control, types, minimum size, visibility)

### Takeaway
Caddy's `encode` is the model people point to: one line, zstd and gzip by default, a broad built-in type list, a 512-byte minimum, and streaming-aware behaviour. The other trackers fill in the rest of the list: per-location off switches, include and exclude lists, a choice of algorithms and their order, correct handling of responses that are already encoded, correct Vary, ETag and HEAD behaviour, pre-compressed files, and an easy way to verify.

### Cited Findings
- **Caddy's defaults.** "If omitted, zstd (preferred) and gzip are enabled by default"; `minimum_length` 512; the default matcher covers `text/*`, `application/json*`, `application/javascript*`, `application/wasm*`, `application/xml*`, `application/xhtml+xml*`, `application/rss+xml*`, `application/atom+xml*`, `application/ld+json*`, `application/manifest+json*`, `application/vnd.api+json*`, `application/graphql+json*`, `application/geo+json*`, `application/x-protobuf*`, `image/svg+xml*`, `image/x-icon*`, `image/vnd.microsoft.icon*`, `font/*`, `application/vnd.ms-fontobject*`, `application/eot*`, `application/font*`, `application/opentype*`, `application/otf*`, `application/x-otf*`, `application/x-opentype*`, `application/truetype*`, `application/ttf*`, `application/x-ttf*`, `application/x-javascript*`, `application/x-httpd-cgi*`, `application/x-perl*`, `multipart/bag*`, `multipart/mixed*`; SSE and `Incremental: ?1` are streamed at once — [Caddy encode docs](https://caddyserver.com/docs/caddyfile/directives/encode). ### Inferences
- A checklist a designer can take from the catalogue (inference, built from the cited complaints):
  1. On by default, for a broad media-type list matched without parameters, covering JS, JSON, SVG, fonts and wasm, with images, audio, video and archives always excluded.
  2. gzip, brotli and zstd built in, with no module to rebuild.
  3. Negotiation by q-value, a configurable preference at equal q, identity when the client sends no Accept-Encoding.
  4. A minimum length that also works for streamed responses (decide after the first bytes).
  5. Vary: Accept-Encoding on every response that could have been compressed, merged with the application's own and never duplicated.
  6. Never compress a response that already has a Content-Encoding (no double compression), and pass through the upstream's coding when the client accepts it.
  7. Weak or per-coding ETags with working 304s.
  8. Correct HEAD and Content-Length.
  9. Pre-compressed twins with staleness checks.
  10. SSE and streamed responses flushed per event, headers never held back, tunnels never compressed.
  11. Per-site and per-path off switches (for BREACH-sensitive pages and odd clients).
  12. Visibility: the applied coding in the access log, and a diagnostic that says why a given URL was not compressed.

### Gaps
- No survey or poll of administrators ranking these features was found; the ranking rests on Q&A votes and issue reactions.
- Praise for Caddy's defaults is inferred from configuration comparisons and docs. Specific Reddit or forum posts praising them could not be retrieved in this pass.
