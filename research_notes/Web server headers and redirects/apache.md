# Apache httpd 2.4: response header manipulation and redirects (mod_headers, mod_alias, mod_rewrite, .htaccess)

Method note: everything below was read on 2026-10-12 from the live httpd 2.4 documentation and from the
`2.4.x` branch of the httpd source on GitHub (the branch's CHANGES file is at "Changes with Apache 2.4.70",
the in-development entry, with 2.4.69 and 2.4.68 below it). Where the documentation and the source disagree,
both are given. ASF Bugzilla and svn.apache.org now refuse unauthenticated readers (login page / HTTP 401), so
bug reports are cited only through search-engine summaries and marked as such. Nothing here was tested against
a running httpd: statements marked "source reading" are inferences from the C code, not observed behaviour.

## mod_headers: actions and their exact semantics

### Takeaway
`Header [onsuccess|always] add|append|echo|edit|edit*|merge|set|setifempty|unset|note name [value [replacement]] [early|env=[!]var|expr=...]` edits one of two internal response-header tables just before the response leaves; every action works only on the table it targets, which is the root of most mod_headers surprises.

### Cited Findings
- Syntax: `Header [condition] add|append|echo|edit|edit*|merge|set|setifempty|unset|note header [[expr=]value [replacement] [early|env=[!]varname|expr=expression]]`; context server config, virtual host, directory, .htaccess; in .htaccess needs `AllowOverride FileInfo`; `setifempty` since 2.4.7, `expr=value` since 2.4.10. — [mod_headers, Header](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `set`: "The response header is set, replacing any previous header with this name. The value may be a format string." — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `append`: appends to an existing header of the same name, comma-separated; the doc warns that Set-Cookie is the exception (RFC 6265 needs separate Set-Cookie fields), so use `add` for Set-Cookie. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `add`: adds even if the header exists, which "can result in two (or more) headers having the same name ... in general set, append or merge should be used instead." — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `merge`: like append unless the value already appears in the comma list; comparison is case-sensitive, after format specifiers are expanded, and quoted vs unquoted values count as different. Example: three `Header merge Cache-Control ...` lines give `no-cache, no-store` where `append` would give `no-cache, no-cache, no-store`. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html)
- `setifempty`: set only if there is no previous header with that name. Caveat in the doc: Content-Type "is a special use case since there might be the chance that its value have been determined but the header is not part of the response when setifempty is evaluated"; the doc recommends `Header set Content-Type "text/plain" "expr=-z %{CONTENT_TYPE}"` instead. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `unset`: removes the header; if several fields share the name, all are removed. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `edit` / `edit*`: regex search-and-replace on an existing header's value, once (`edit`) or every match (`edit*`); since 2.4.7 the replacement may contain format specifiers. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header); [CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)
- `echo`: request headers with this name (name may be a regex, case-sensitive) are copied into the response. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `note` (2.4.7+): copies the named response header into an internal note, "useful if a header sent by a CGI or proxied resource is configured to be unset but should also be logged." — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Header names are case-insensitive for set, append, merge, add, unset and edit. Values may contain format specifiers `%t`, `%D`, `%l`, `%i`, `%b`, `%{VAR}e`, `%{VAR}s`, or be an ap_expr string with `expr=`. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Limits: "it is possible to set and/or override most headers, except for some headers added by the HTTP header filter. Prior to 2.2.12, it was not possible to change the Content-Type header". — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `RequestHeader` has the same actions minus echo/note, runs "just before the request is run by its handler in the fixup phase". — [mod_headers, RequestHeader](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#requestheader)
- Security history tied to header values derived from the request: CVE-2024-43204, SSRF "with mod_proxy loaded" when "mod_headers is configured to modify the Content-Type request or response header with a value provided in the HTTP request", fixed in 2.4.64; and a 2.4.x fix where `RequestHeader set|edit Content-Type` "could inadvertently modify the Content-Type _response_ header". CVE-2026-43951: out-of-bounds read in `merge_response_headers` "with mod_headers and mod_mime and multiple response languages", 2.4.0 through 2.4.67. — [httpd 2.4.x CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)

### Inferences
- The action set is wide (nine verbs plus regex edit and expression values). Only `set`, `setifempty` and `unset` match agensio's proposed `set`, `default`, `remove`; `append`/`merge`/`add` exist mainly for list-valued fields (Cache-Control, Vary, Set-Cookie). Apache's own warning about `append` on Set-Cookie and about `add` creating duplicates suggests a typed design that leaves out append is the safer subset. If agensio ever adds append, it needs the Set-Cookie exception.
- The Content-Type caveat on `setifempty` points to a real design question for agensio's `default`: "absent" must be defined against the final header set, including fields the server derives itself (Content-Type from the MIME table, ETag, Last-Modified), not only fields an application sent.
- Apache's CVE history argues against header values computed from request data; agensio's typed, constant values avoid that class of problem.

### Gaps
- No official statement lists exactly which fields "the HTTP header filter" adds after mod_headers runs. From source, at least Date and Server are written there (see the Server section); the full list was not checked.

## The two tables: `onsuccess` (default) vs `always`, and which responses each reaches

### Takeaway
httpd keeps response headers in two tables (`r->headers_out` = `onsuccess`, `r->err_headers_out` = `always`). Locally generated errors and redirects send only the `always` table, and CGI/FastCGI (including PHP-FPM through mod_proxy_fcgi) store their headers in the `always` table. So a plain `Header set`/`unset` misses error pages, redirects, 304s and PHP-FPM headers. The documented workaround (`Header onsuccess unset X` plus `Header always set X`) shows that one "applies to every answer" behaviour has to be built by hand.

### Cited Findings
- Doc: the condition picks "which internal table of responses headers this directive will operate against: onsuccess (default, can be omitted) or always. The difference ... is that the headers contained in the latter are added to the response even on error, and persisted across internal redirects (for example, ErrorDocument handlers)." — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Doc: "always is not a superset of onsuccess with respect to existing headers". The cases where you need it: (1) adding a header to "a locally generated non-success (non-2xx) response, such as a redirect, in which case only the table corresponding to always is used in the ultimate response"; (2) "modifying or removing a header generated by a CGI script or by mod_proxy_fcgi, in which case the CGI scripts' headers are in the table corresponding to always and not in the default table"; (3) a header "generated by some piece of the server but ... not being found by the default onsuccess condition." — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Doc: the split is "a consequence of how httpd internally stores headers for a HTTP response, since it does not offer any 'normalized' single list of headers". The worked example: PHP behind mod_proxy_fcgi sends `X-Foo: bar`, and `Header set X-Foo: baz` ends up "having the header duplicated with both values". The documented fix is `Header onsuccess unset X-Foo` + `Header always set X-Foo "baz"`. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Source: `ap_send_error_response` (used for every locally generated error or redirect) swaps the tables: `r->headers_out = r->err_headers_out; ... apr_table_clear(r->err_headers_out);` with the comment "we need to avoid inheriting the 'normal status' header fields that may have been set by the request handler before the error or redirect, except for Location on external redirects". — [http_protocol.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_protocol.c)
- Source: CGI/FastCGI headers are parsed by `ap_scan_script_header_err_*`, which ends with `apr_table_overlap(r->err_headers_out, merge, APR_OVERLAP_TABLES_MERGE)` (Set-Cookie also into `err_headers_out`); only special fields (Content-Type, Status, Location, Content-Length, Transfer-Encoding, Last-Modified) go to `r->headers_out`. mod_proxy_fcgi uses this parser. — [util_script.c](https://github.com/apache/httpd/blob/2.4.x/server/util_script.c); [mod_proxy_fcgi.c](https://github.com/apache/httpd/blob/2.4.x/modules/proxy/mod_proxy_fcgi.c)
- Source: mod_proxy_http puts the origin's response headers into `r->headers_out` (the onsuccess table), so for HTTP-proxied answers a plain `Header set/unset` does reach them. With ProxyErrorOverride and a 401, `WWW-Authenticate` is copied into `err_headers_out`. — [mod_proxy_http.c](https://github.com/apache/httpd/blob/2.4.x/modules/proxy/mod_proxy_http.c)
- Source: mod_php (apache2handler, in-process) writes PHP's `header()` fields into `r->headers_out`, i.e. the onsuccess table. So the same PHP code behaves differently under mod_php and PHP-FPM with respect to `Header set/unset`. — [php-src sapi_apache2.c](https://github.com/php/php-src/blob/master/sapi/apache2handler/sapi_apache2.c)
- Source: the HTTP header filter finally merges the tables with `r->headers_out = apr_table_overlay(r->pool, r->err_headers_out, r->headers_out)`. Overlay concatenates, so the same name in both tables is sent twice. — [http_filters.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_filters.c)
- Source: mod_headers registers two output filters. `FIXUP_HEADERS_OUT` (normal path) applies the `always` list to `err_headers_out` and then the `onsuccess` list to `headers_out`. `FIXUP_HEADERS_ERR`, inserted through `insert_error_filter` on the error path, applies only the `always` list ("Make sure we propagate any 'Header always' settings on the error path"). — [mod_headers.c](https://github.com/apache/httpd/blob/2.4.x/modules/metadata/mod_headers.c)
- Source: on the error path, `ap_send_error_response` resets `r->output_filters = r->proto_output_filters` and runs `insert_error_filter`, and for 204/304 returns before the table swap. Source reading: a 304 produced by the conditional-request check therefore loses the request-level onsuccess filter and gets only `always` headers. This matches Mark Nottingham's 2014 observation: "when you use mod_headers, it adds those headers to 2xx, but not 304" (in the CORS context). — [http_protocol.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_protocol.c); [W3C list, Dec 2014](https://lists.w3.org/Archives/Public/public-web-platform-tests-notifications/2014Dec/0136.html)
- Bug report (seen only via search summary; Bugzilla now requires login): PR 64646, PHP-FPM via `proxy:fcgi` set a header that `Header set` in .htaccess did not override, so both appeared; switching to `Header always set` fixed it. — [ASF Bugzilla 64646](https://bz.apache.org/bugzilla/show_bug.cgi?id=64646) (not verified directly)
- Commit (seen only via search summary; svn viewer returns 401): r1832092 (2018), "http_protocol.c: avoid duplicate headers when using" `Header always set`, found while debugging PR 61860; the explanation given is the headers_out/err_headers_out swap plus a second pass re-inserting "always" headers. Whether and when it shipped was not confirmed. — [svn r1832092](https://svn.apache.org/r1832092) (not verified directly)
- Related (search summary only): PR 52523, "Headers from mod_expires are wrongly set for redirects too and can't be removed or changed", closed as a duplicate of 44518. — [ASF Bugzilla 52523](https://bz.apache.org/bugzilla/show_bug.cgi?id=52523) (not verified directly)
- The status test escape hatch: "you can limit an action based on HTTP status codes for e.g. proxied or CGI requests", e.g. `Header append Cache-Control s-maxage=600 "expr=%{REQUEST_STATUS} == 200"`. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html)

### Inferences
- Reach of each table, collected from the findings above:
  - `onsuccess`: handler-generated 2xx/3xx and HTTP-proxied answers. It misses httpd's own error and redirect answers (404, 403, 401, 500, Redirect, RewriteRule [R]), 304s produced by the core, and modifications/removals of CGI/PHP-FPM headers.
  - `always`: every answer, error path included, and the ErrorDocument's internal redirect. But it does not see fields held in `headers_out`, so `always set` next to an origin's or mod_php's own field duplicates it, and `always unset` does not remove it.
- This strongly supports agensio's choice of one table and one rule set that applies to every answer: static, PHP, proxied, error and redirect. Apache's documented best practice for security headers (HSTS and similar) amounts to "use always", and its documented fix for application headers amounts to "unset onsuccess, set always". agensio would get both without the user knowing about tables.
- One argument for a nuance: Apache's onsuccess default keeps long-lived caching headers off error answers. A `Cache-Control: max-age=31536000, immutable` rule applied "to every answer" would also make a transient 404 or 502 on that path cacheable for a year. agensio should either document this, warn about it, or offer a status condition (Apache's equivalent is `expr=%{REQUEST_STATUS} == 200`).
- 304s: agensio should make sure header rules reach 304 answers. RFC 9110/9111 expect a 304 to carry the fields a 200 would have carried (Cache-Control, ETag, Vary, Expires and so on). Apache's onsuccess path drops them on core-generated 304s.

### Gaps
- Whether the r1832092 duplicate-"always" fix is in current 2.4 releases was not confirmed (svn and Bugzilla are login-gated).
- Behaviour on HTTP/2 (mod_http2) answers was not checked; mod_http2 converts the same request_rec tables, so the same split probably applies (unverified).

## mod_headers processing time, `early`, `env=` / `expr=` conditions, and merging across contexts

### Takeaway
Response headers are edited late, in an output filter, using the request's final merged per-directory configuration. Lists from all matching sections are concatenated parent-first, so a more specific section's `set` runs last and wins. Section order follows Apache's merge order: Directory shortest to longest, then DirectoryMatch, Files, Location (in config-file order, not by length), then If. `early` is a debugging aid that is valid only at server/vhost level.

### Cited Findings
- Order matters: `RequestHeader append MirrorID "mirror 12"` followed by `RequestHeader unset MirrorID` gives no header, and the reverse order gives one. "Order of processing is important and is affected both by the order in the configuration file and by placement in configuration sections." — [mod_headers, Order of Processing](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#order)
- Late (normal) mode: request headers are set "immediately before running the content generator and Response Headers just as the response is sent down the wire. Always use Late mode in an operational server." Early mode "is designed as a test/debugging aid", runs "right at the beginning of processing the request", "can only be set in a main server or virtual host context" and fails in `<Directory>`/`<Location>`. — [mod_headers, Early and Late Processing](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#early)
- Source: hooks are `post_read_request` (early, APR_HOOK_FIRST), `fixups` (RequestHeader, APR_HOOK_LAST), and output filters `FIXUP_HEADERS_OUT` / `FIXUP_HEADERS_ERR` of type `AP_FTYPE_CONTENT_SET`, inserted at `insert_filter` / `insert_error_filter` with APR_HOOK_LAST. — [mod_headers.c](https://github.com/apache/httpd/blob/2.4.x/modules/metadata/mod_headers.c)
- Source: `merge_headers_config` concatenates `apr_array_append(p, base->fixup_out, overrides->fixup_out)` (and the same for the `always` and request lists): parent directives first, child directives after, all executed in sequence. — [mod_headers.c](https://github.com/apache/httpd/blob/2.4.x/modules/metadata/mod_headers.c)
- Conditions: `env=[!]varname` applies the directive only if the environment variable exists (or not); `expr=expression` applies it only if the ap_expr is true, and "This delays the evaluation of the condition clause compared to <If>", e.g. `Header always set CustomHeader my-value "expr=%{REQUEST_URI} =~ m#^/special_path.php$#"`. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- Section merge order: (1) `<Directory>` (non-regex) and .htaccess together, .htaccess overriding `<Directory>`; (2) `<DirectoryMatch>`; (3) `<Files>`/`<FilesMatch>`; (4) `<Location>`/`<LocationMatch>`; (5) `<If>`, "even when they are enclosed in any of the preceding contexts". `<Directory>` goes from the shortest path to the longest; within the other groups, file order: "a request for /foo/bar will match <Location "/foo/bar"> and <Location "/foo"> ... both sections will be evaluated but in the order they appear in the configuration files." Vhost sections apply after the corresponding main-server sections. For proxied requests `<Proxy>` takes the place of `<Directory>`. — [Configuration Sections, merging](https://httpd.apache.org/docs/2.4/sections.html#merging)
- "When <If> is used in .htaccess, the enclosed directives in a parent directory will be merged after non-enclosed directives in a subdirectory." — [Configuration Sections](https://httpd.apache.org/docs/2.4/sections.html#merging)
- A .htaccess directive in `/www/htdocs/example` "is completely equivalent to placing that same directive in a <Directory "/www/htdocs/example"> section"; deeper .htaccess files may override those higher up. — [.htaccess howto](https://httpd.apache.org/docs/2.4/howto/htaccess.html)

### Inferences
- agensio's "all matching rules combined, shortest path first" matches Apache's `<Directory>` behaviour (shortest to longest, child's `set` last). It improves on `<Location>`, where Apache applies sections in file order rather than by length, so a `<Location "/">` placed after `<Location "/admin">` overrides it. A length-ordered combine removes that trap.
- Apache's concatenate-and-execute model means `unset` in a parent followed by `set` in a child works, and the reverse makes the child's `unset` win over the parent's `set`. agensio's model (later and more specific wins per field) gives the same result for set/default/remove, provided "default" means "absent after the application's and the less specific rules' effects". That precedence is worth stating explicitly in agensio's docs.
- Apache needs `env=`/`expr=` because one directive serves many cases. A typed rule system matched by path covers the common cases (per path), with status as the one condition Apache users actually reach for.

### Gaps
- None material for the comparison.

## Removing X-Powered-By, and the Server header (ServerTokens / ServerSignature)

### Takeaway
X-Powered-By is PHP's (`expose_php`, on by default even in php.ini-production); under PHP-FPM, Apache can strip it only with `Header always unset X-Powered-By`, because FastCGI headers live in the `always` table. The `Server` field cannot be removed with mod_headers. It is written by the HTTP header filter from the banner, which `ServerTokens` (server-wide only, minimum `Prod` = "Apache") shortens but never removes; Apache's docs call hiding it security through obscurity.

### Cited Findings
- `expose_php` default "1", changeable "php.ini only". Both `php.ini-production` and `php.ini-development` ship `expose_php = On`, with the comment "It is no security threat in any way, but it makes it possible to determine whether you use PHP on your server or not." — [PHP manual, core ini](https://www.php.net/manual/en/ini.core.php); [php.ini-production](https://github.com/php/php-src/blob/master/php.ini-production)
- With PHP-FPM via mod_proxy_fcgi, the headers are in the `always` table, so `Header always unset` is needed (see the two-tables section; Plesk's KB gives `Header always unset "X-Powered-By"` for the same reason). — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header); [Plesk KB](https://support.plesk.com/hc/en-us/articles/12387354622999-How-to-remove-X-Powered-By-header-in-Phusion-Passenger)
- `ServerTokens Major|Minor|Min[imal]|Prod[uctOnly]|OS|Full`, default Full, server config only: "This setting applies to the entire server, and cannot be enabled or disabled on a virtualhost-by-virtualhost basis." `Prod` sends `Server: Apache`. "Setting ServerTokens to less than minimal is not recommended ... disabling the Server: header does nothing at all to make your server more secure. The idea of 'security through obscurity' is a myth". — [core, ServerTokens](https://httpd.apache.org/docs/2.4/mod/core.html#servertokens)
- `ServerSignature On|Off|EMail`, default Off: a footer on server-generated documents (error pages, listings); its detail follows ServerTokens. — [core, ServerSignature](https://httpd.apache.org/docs/2.4/mod/core.html#serversignature)
- Source: `basic_http_header` in the HTTP header filter writes `Date` and `Server` itself: for non-proxy requests always from `ap_get_server_banner()`, then unsets them from `headers_out` "so we don't send them again". For proxy requests (`r->proxyreq != PROXYREQ_NONE`) it keeps the origin's `Server` and `Date` from `headers_out`, and falls back to Apache's banner when absent. — [http_filters.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_filters.c)

### Inferences
- Source reading: `Header unset Server` and `Header set Server ...` have no effect on locally served answers, because the banner is emitted after mod_headers and any `Server` in `headers_out` is ignored. On reverse-proxied answers, `Header set Server` replaces the origin's value, and `Header unset Server` makes Apache's own banner appear instead of none. Third-party modules (mod_security's `SecServerSignature`) are the usual way people change it. That last point was not verified here.
- For agensio, `remove` on `Server` is a product decision Apache never offered. RFC 9110 treats `Server` as optional, so allowing its removal is legitimate. `Date` is a different case, as is framing (Content-Length, Transfer-Encoding, Connection): Apache keeps these out of mod_headers' reach, and agensio should refuse rules on them.
- PHP-FPM shows why agensio's `remove` must apply to the application's fields. Apache users routinely get this wrong (plain `Header unset X-Powered-By` silently fails under FPM but works under mod_php).

### Gaps
- Whether `php_admin_flag[expose_php]` in an FPM pool takes effect ("php.ini only") was not checked.

## mod_alias: Redirect, RedirectMatch, RedirectPermanent, RedirectTemp

### Takeaway
`Redirect [status] URL-path URL` is a case-sensitive, whole-segment prefix match on the %-decoded path. It appends the re-escaped remainder and the original query (unless the target has its own `?`), and defaults to 302. `RedirectMatch` is the regex form, where nothing is appended automatically. Within one context the first match in file order wins, and Redirects always beat Aliases.

### Cited Findings
- "The old URL-path is a case-sensitive (%-decoded) path beginning with a slash. A relative path is not allowed. The new URL may be either an absolute URL beginning with a scheme and hostname, or a URL-path beginning with a slash. In this latter case the scheme and hostname of the current server will be added." — [mod_alias, Redirect](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)
- "Additional path information beyond the matched URL-path will be appended to the target URL." Example: `Redirect "/service" "http://foo2.example.com/service"` sends `/service/foo.pl?q=23&a=42` to `http://foo2.example.com/service/foo.pl?q=23&a=42`. "Note that POSTs will be discarded." "Only complete path segments are matched", so `/servicefoo.txt` does not match. — [mod_alias, Redirect](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)
- Status: default 302 ("temporary"); keywords `permanent` (301), `temp` (302), `seeother` (303), `gone` (410, no URL); any numeric code known to httpd; for 300-399 the URL is required, outside that range it must be omitted. `RedirectPermanent` = `Redirect permanent`; `RedirectTemp` = `Redirect temp`. — [mod_alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)
- Source: `try_alias_list` builds `alias->real + ap_os_escape_path(r->uri + l)`, i.e. the target string plus the re-escaped remainder. `translate_alias_redir`/`fixup_redir` turn a `/`-target into an absolute URL with `ap_construct_url` unless `RedirectRelative On`, reject a target that is not an absolute URI or abs_path with 500, and append the query only "if the config didn't supply its own" (`if (r->args && !ap_strchr(ret, '?'))`). `alias_matches` treats any run of slashes as one and requires the last configured segment to end at `/` or end-of-path. — [mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c)
- `RedirectRelative On|Off` (2.4.58+, default Off): send a `/`-relative target as is instead of absolutising it. `AliasPreservePath` was added in the same release series. — [mod_alias, RedirectRelative](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirectrelative); [CHANGES](https://github.com/apache/httpd/blob/2.4.x/CHANGES)
- Self-referential URLs use `UseCanonicalName` (default Off): "Apache httpd will form self-referential URLs using the hostname and port supplied by the client" in the Host header. — [core, UseCanonicalName](https://httpd.apache.org/docs/2.4/mod/core.html#usecanonicalname)
- `RedirectMatch`: the regex is matched against the URL-path and `$n` substituted; as with AliasMatch, nothing past the match is copied automatically, so the regex must cover the whole path (`^...(.*)$` plus `$1`). — [mod_alias, RedirectMatch / AliasMatch](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirectmatch)
- Order: "all Redirects are processed before Aliases ... Aliases and Redirects are processed in the order they appear in the configuration files, with the first match taking precedence", so "you must list the most specific path first". Redirects in `<Location>` with the URL-path omitted (expression form, 2.4.19+) "take precedence over any globally defined" Alias/Redirect. — [mod_alias, Order of Processing](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#order)
- Redirect inside Location (2.4.19+): `<Location "/one"> Redirect permanent "http://example.com/two" </Location>`. The URL argument is then an ap_expr, e.g. `%{env:MATCH_NUMBER}` from a named `LocationMatch` group. — [mod_alias, Redirect](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)
- Source: `merge_alias_config` and `merge_alias_dir_config` build `apr_array_append(p, overrides->redirects, base->redirects)`: child or vhost redirects are tried before parent or main-server ones; the first match wins. — [mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c)
- Doc guidance: use `Redirect` for prefix redirects ("Remember that Redirect preserves path information"), e.g. `Redirect "/one/" "http://one.example.com/"`, and for http to https "a Redirect in a dedicated HTTP virtual host is the cleanest approach". — [When not to use mod_rewrite](https://httpd.apache.org/docs/2.4/rewrite/avoid.html)
- mod_md's `MDRequireHttps permanent` does the http to https 301 and adds `Strict-Transport-Security` (half a year) as one typed setting; doing it with Redirect means excluding `/.well-known/*` yourself. — [mod_md, MDRequireHttps](https://httpd.apache.org/docs/2.4/mod/mod_md.html#mdrequirehttps)

### Inferences
- Source reading, a classic slash pitfall: the remainder is concatenated without inserting or removing a slash. `Redirect /one/ http://x/two` sends `/one/a` to `http://x/twoa`, and `Redirect /one/ ...` does not match `/one` at all. agensio should normalise `from`/`to` slashes, or refuse mismatched forms at load.
- agensio's proposed defaults (remainder kept, query kept, explicit status required) match Apache's `Redirect` on remainder and query and depart from it on status. Apache's silent default of 302 means people add `permanent` only after testing, which is the recommended practice; a required status forces the choice up front. The Apache docs' advice to test with 302 before switching to 301 (next sections) could become agensio's recipe text.
- Apache's "first match in file order within a context, list the most specific first" is a known foot-gun. A longest-prefix or exact-before-prefix rule (agensio's router style) removes it.
- Apache does not keep the original query when the target contains `?`. This "own query replaces client query" rule is a reasonable precedent if agensio lets `to` carry a query.
- "POSTs will be discarded" (301/302 to GET in browsers) argues for agensio's docs to point to 307/308 for non-GET endpoints.

### Gaps
- Case sensitivity: Apache's Redirect is case-sensitive even on case-insensitive filesystems (stated for Alias; Redirect uses the same matcher). How this interacts with agensio's case-insensitive access-rule matching is a design choice, not an Apache finding.

## mod_rewrite: flags, per-directory context, loops, inheritance, cost and reputation

### Takeaway
RewriteRule is regex-driven and context-sensitive. In server/vhost context it matches the full decoded URL-path; in `<Directory>`/.htaccess (and `<If>`) it matches a prefix-stripped relative path, runs in a later phase and re-enters on internal rewrites, where `[L]` loops and `[END]` is needed. Apache's own documentation calls it "a last resort".

### Cited Findings
- "mod_rewrite should be considered a last resort, when other alternatives are found wanting. Using it when there are simpler alternatives leads to configurations which are confusing, fragile, and hard to maintain." The main legitimate case is having only .htaccess access. — [When not to use mod_rewrite](https://httpd.apache.org/docs/2.4/rewrite/avoid.html)
- `[R]`: external redirect, 302 by default, `[R=301]` or `temp|permanent|seeother`; a non-3xx code drops the substitution and stops as with `[L]`; "You will almost always want to use [R] in conjunction with [L]" since `[R]` alone passes the URL to the next rule. — [RewriteRule Flags, R](https://httpd.apache.org/docs/2.4/rewrite/flags.html#flag_r)
- `[L]`: stop processing the rule set; "In per-directory context, [L] stops the current pass through the ruleset, but the rewritten request may be re-processed from the top — which can cause loops." `[END]` (2.3.9+) also prevents later per-directory passes and is "the preferred flag for most per-directory rules"; in server/vhost context `[END]` and `[L]` behave the same. — [Flags, L](https://httpd.apache.org/docs/2.4/rewrite/flags.html#flag_l); [Flags, END](https://httpd.apache.org/docs/2.4/rewrite/flags.html#flag_end)
- Query: "By default, the query string is passed through unchanged"; a `?` in the substitution replaces it, a trailing `?` erases it, `[QSA]` combines them, and `[QSD]` (2.4.0+) discards the original when the target has none (`[QSD]` beats `[QSA]`). — [mod_rewrite, RewriteRule](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#rewriterule); [Flags, QSA/QSD](https://httpd.apache.org/docs/2.4/rewrite/flags.html#flag_qsa)
- `[NE]`: on external redirects, characters outside `A-Za-z0-9$-_.+!*'(),:;@&=/~` are percent-encoded, `%` included ("any percent-encoding already present in the substitution will be double-encoded"); `[NE]` suppresses this, e.g. for a `#fragment` target. — [Flags, NE](https://httpd.apache.org/docs/2.4/rewrite/flags.html#flag_ne)
- Matching is on the decoded path: "/my%20page/cats%3Fdogs is decoded to /my page/cats?dogs"; to see the raw form, use `%{THE_REQUEST}`. `AllowEncodedSlashes` defaults to Off (404 for `%2F`). — [mod_rewrite technical details](https://httpd.apache.org/docs/2.4/rewrite/tech.html)
- Per-directory: "the Pattern is matched against only a partial path ... The directory-path to which the rule applies is stripped ... (up to and including a trailing slash)", so "a Pattern with ^/ never matches in per-directory context"; relative substitutions get `RewriteBase`. Per-directory rewriting requires `FollowSymLinks` or `SymLinksIfOwnerMatch` (error AH00670 otherwise) and `AllowOverride FileInfo`, without which rules "are silently ignored". — [mod_rewrite](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#rewriterule); [Per-directory rewrites](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html)
- Loops: `RewriteRule "^(.*)$" "/index.php?q=$1" [L]` in .htaccess loops until "AH00124: Request exceeded the limit of 10 internal redirects" (LimitInternalRecursion). Fixes: `[END]`, `!-f`/`!-d` conditions, or a `%{THE_REQUEST}` test. Putting a RewriteRule inside `<Directory>`, `<If>` or `<Location>`, "even inside a <VirtualHost>", "silently switches to per-directory context behavior". Rules in `<Location>`/`<Files>` are "unsupported". — [Per-directory rewrites](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html)
- Inheritance: rules are not inherited by default ("mod_rewrite overrides rules when merging sections belonging to the same context"; two `<If "true">` blocks keep only the last). `RewriteOptions Inherit` puts the parent's rules after the child's; `InheritBefore` puts them before; `InheritDown`/`InheritDownBefore` (2.4.8+) push from the parent; `IgnoreInherit` opts out. Rewrite configuration is "not inherited by virtual hosts": each vhost needs `RewriteEngine on`. — [mod_rewrite, RewriteOptions / RewriteEngine](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#rewriteoptions)
- `AllowAnyURI` exists because of CVE-2011-3368 and CVE-2011-4317 ("surprising" pattern expansions, `@` in input); "It is strongly recommended that this option is not used." — [mod_rewrite, RewriteOptions](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#rewriteoptions)
- .htaccess cost: with AllowOverride on, "httpd will look in every directory for .htaccess files. Thus, permitting .htaccess files causes a performance hit, whether or not you actually even use them! Also, the .htaccess file is loaded every time a document is requested"; a file under `/www/htdocs/example` costs 4 extra filesystem lookups. "If you have access to the main server configuration file, you should put all of your configuration there"; "mod_rewrite in particular works better in server configuration context". `AllowOverrideList Redirect RedirectMatch ...` allows single directives. — [.htaccess howto](https://httpd.apache.org/docs/2.4/howto/htaccess.html)
- `RewriteMap` cannot be declared in .htaccess because .htaccess "files are parsed on every request" and map initialisation "would be prohibitively expensive". — [Per-directory rewrites](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html)
- Trace logging (`LogLevel alert rewrite:trace3`): "will slow down your Apache HTTP Server dramatically! Use a log level higher than trace2 only for debugging". — [mod_rewrite, Logging](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#logging)
- For front controllers, `FallbackResource` (mod_dir) "is a simpler and more efficient alternative to mod_rewrite". — [Per-directory rewrites](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html)

### Inferences
- Most mod_rewrite trouble comes from three things a typed rule set does not have: regex-plus-substitution, per-directory re-entry (loops), and a context-dependent meaning of the same rule. agensio's design (prefix/exact match, one pass, no internal re-entry for redirects) sidesteps all three.
- The cost argument against .htaccess (a stat per directory level per request, re-parsing) supports agensio's choice of configuration loaded once, not per-directory files read on requests.

### Gaps
- No quantitative benchmark of .htaccess overhead in the official docs (only the description); none was sought elsewhere.

## Ordering between mod_alias and mod_rewrite

### Takeaway
In server/vhost context both act in the URL-to-filename (translate_name) phase and mod_rewrite runs first, by hook priority rather than file order. In per-directory context, the documentation now says mod_alias runs first. The source shows both in the fixups phase with mod_rewrite registered first; the observable result depends on whether the RewriteRule redirects or rewrites internally.

### Cited Findings
- Doc: "mod_rewrite and mod_alias both operate during the URL-to-filename translation phase, but mod_rewrite runs first regardless of the order in which directives appear in the configuration file", so with `Redirect "/old" ...` before `RewriteRule "^/old" "/other" [L]` in a vhost, "the Redirect is never reached". — [mod_rewrite technical details, Module Processing Order](https://httpd.apache.org/docs/2.4/rewrite/tech.html)
- Doc: "In per-directory context, the situation is different. mod_alias directives like Redirect still run in the URL-to-filename translation phase, but mod_rewrite rules run later, in the Fixup phase ... in per-directory context, Redirect is evaluated before RewriteRule." The advice: "choose one module for a given task." — [mod_rewrite technical details](https://httpd.apache.org/docs/2.4/rewrite/tech.html); same in [When not to use mod_rewrite](https://httpd.apache.org/docs/2.4/rewrite/avoid.html)
- Source, contradicting the doc's mechanism: mod_alias registers `ap_hook_translate_name(translate_alias_redir, ..., APR_HOOK_MIDDLE)` (server/vhost redirects plus the `<Location>` expression form) and `ap_hook_fixups(fixup_redir, ..., APR_HOOK_MIDDLE)`, which handles redirects stored per directory: .htaccess, `<Directory>`, and two-argument Redirects inside `<Location>`, because `add_redirect_internal` pushes into `dirconf->redirects` whenever `cmd->path` is set. mod_rewrite registers `ap_hook_translate_name(hook_uri2file, ..., APR_HOOK_FIRST)` and `ap_hook_fixups(hook_fixup, ..., APR_HOOK_FIRST)`. — [mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c); [mod_rewrite.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_rewrite.c)
- Source: per-directory `hook_fixup` returns the redirect status for `[R]` (which stops the fixups chain) but returns `OK` with `r->handler = "redirect-handler"` for an internal rewrite. — [mod_rewrite.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_rewrite.c)

### Inferences
- Source reading, not tested: in .htaccess, a `[R]` RewriteRule fires before a matching Redirect, because mod_rewrite is first in fixups and its status ends the phase. An internal rewrite does not stop mod_alias's `fixup_redir`, which still matches the original `r->uri` and can redirect, so for internal rewrites the effect looks like "Redirect first", which is what the docs say. The documentation's explanation (Redirect in translate_name for per-directory context) does not match the code.
- Either way, the lesson for agensio is that two redirect mechanisms with different phases and priorities produce order bugs that even the vendor documents inconsistently. One redirect mechanism, evaluated at one fixed point in the request pipeline, avoids it.

### Gaps
- Not verified on a running httpd; a two-line test (.htaccess with `Redirect` plus an internal `RewriteRule` on the same path) would settle it.

## Evaluation order relative to authentication and access control

### Takeaway
It depends on where the Redirect is written. A server/vhost Redirect (and the one-argument `<Location>` form) runs in translate_name, before access control and authentication, so it fires for anonymous clients. A Redirect in .htaccess, `<Directory>`, or a two-argument Redirect inside `<Location>`, runs in fixups, after `Require`/`AuthType`, so the client gets 401/403 first. The same holds for per-directory RewriteRule versus server-level RewriteRule.

### Cited Findings
- Source: `ap_process_request_internal` runs, in order: the Location/If walk, `translate_name`, `map_to_storage` (the directory walk, where .htaccess is read), the Location/If walk again, `post_perdir_config`, `header_parser`, then access checks (`access_checker`, `access_checker_ex`, `check_user_id`, `auth_checker`), then `type_checker`, then `fixups`. — [server/request.c](https://github.com/apache/httpd/blob/2.4.x/server/request.c)
- Doc: mod_rewrite's translate hook "occurs after the HTTP request has been read, but before any authorization starts", and its fixup hook "is after the authorization phases, and after per-directory configuration files (.htaccess files) have been read". — [mod_rewrite technical details, API Phases](https://httpd.apache.org/docs/2.4/rewrite/tech.html)
- Doc: "<Location> sections are run through once before aliases are performed, so they will apply" (Alias); the technical note in sections.html says that walk's results "are completely thrown away after the translation has completed". — [mod_alias, Alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#alias); [sections](https://httpd.apache.org/docs/2.4/sections.html#merging)
- Source: `translate_alias_redir` handles `serverconf->redirects` and `try_redirect` (the per-dir expression form set by the earlier Location walk); `fixup_redir` handles `dirconf->redirects` (per-directory). — [mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c)
- Error answers produced by auth (401/403) go through `ap_send_error_response` and so carry only `always` headers (see the two-tables section). — [http_protocol.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_protocol.c)
- ErrorDocument pitfall in the same area: with a remote-URL ErrorDocument the client gets a redirect instead of the error status, and "if you use a remote URL in an ErrorDocument 401, the client will not know to prompt the user for a password ... it must refer to a local document." — [core, ErrorDocument](https://httpd.apache.org/docs/2.4/mod/core.html#errordocument)

### Inferences
- agensio's "redirects checked before access and password rules" corresponds to Apache's server/vhost-level Redirect, the form Apache recommends (main config over .htaccess; a dedicated HTTP vhost for http to https). It avoids Apache's inconsistency, where moving the same Redirect into .htaccess silently puts it behind auth.
- Before-auth has a consequence agensio should document: a redirect rule under a protected prefix discloses the target URL (and confirms the path exists) to unauthenticated clients. With Apache vhost-level Redirects this is accepted practice. A site that wants a redirect only for logged-in users is an edge case Apache serves through .htaccess placement; agensio could leave it out.
- Header rules reaching 401/403 answers (agensio's "every answer") correspond to Apache's `always`. Apache's default would miss them, which matters for HSTS and other security headers on auth challenges.

### Gaps
- `mod_dir`'s DirectorySlash 301 (fixups) and `[R]` RewriteRules inside `<If>` were not traced.

## Status code semantics and browser caching of 301

### Takeaway
301 and 308 are heuristically cacheable. Apache's own docs warn that a wrong 301 can stay in browsers "indefinitely" and in search engines for weeks, and recommend testing with 302 first. 301/302 let clients turn POST into GET, while 307/308 must not; Apache's Redirect accepts any 3xx it knows.

### Cited Findings
- "When you issue a 301 Moved Permanently redirect (via [R=301] or Redirect permanent), the browser is allowed to cache that response indefinitely ... returning visitors may continue to be sent to the old (wrong) destination without ever contacting your server again. While debugging redirect rules, use [R=302] ... Search engines also cache 301 redirects. An incorrect 301 may take days or weeks to be re-crawled". — [Per-directory rewrites, Browser caching of 301 redirects](https://httpd.apache.org/docs/2.4/rewrite/htaccess.html)
- RFC 9110: status codes "defined as heuristically cacheable (e.g., 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, and 501 ...) can be reused by a cache with heuristic expiration unless otherwise indicated by the method definition or explicit cache controls". On 301: "For historical reasons, a user agent MAY change the request method from POST to GET ... If this behavior is undesired, the 308 (Permanent Redirect) status code can be used instead." 307: the user agent "MUST NOT change the request method". — [RFC 9110 15.1, 15.4.2, 15.4.8, 15.4.9](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.2)
- `R=301` "tells search engines to update their index" (Apache's http-to-https recipe). — [Redirecting and Remapping](https://httpd.apache.org/docs/2.4/rewrite/remapping.html)
- mod_md warns that `MDRequireHttps permanent` (301 + HSTS) "you cannot simply take it back again" and should be used only "for at least half a year!" — [mod_md, MDRequireHttps](https://httpd.apache.org/docs/2.4/mod/mod_md.html#mdrequirehttps)
- Apache's "Note that POSTs will be discarded" on Redirect. — [mod_alias, Redirect](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)

### Inferences
- A required status in agensio's redirect rules makes the 301-is-sticky decision explicit. Following Apache's advice, the recipe text and the MCP descriptions could recommend 302/307 while testing and 301/308 once settled, and point out that 308 keeps POST.
- Because the redirect answer itself is an "error-path" response in Apache (onsuccess headers dropped), Apache users who want `Cache-Control` on a 301 (e.g. to limit its lifetime) must use `Header always`. agensio's header rules reaching redirect answers make that straightforward. Whether header rules should apply to redirect answers for the redirect's `from` path or only to served content is worth deciding explicitly.

### Gaps
- No browser-vendor statement on how long 301s are actually cached was sought (outside Apache scope).

## How Apache's behaviour bears on agensio's proposed design (header rules set/default/remove on every answer, combined shortest path first; redirect rules from/match/to/status, remainder and query kept, before access and password rules)

### Takeaway
Apache mostly argues for agensio's choices: one header table, one ordering rule, redirects at one early phase. Its most-cited pitfalls (onsuccess vs always, PHP-FPM duplicates, `<Location>` file order, mod_alias/mod_rewrite ordering, .htaccess Redirects falling behind auth, the implicit 302, sticky 301s) are each a consequence of a choice agensio's proposal avoids. Apache does point to three places that need explicit rules: caching headers on error answers, what "absent" means for `default`, and which fields may never be touched.

### Cited Findings
- No single normalised header list in httpd; the onsuccess/always split is "a consequence of how httpd internally stores headers", and the documented fix for application headers takes two directives. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header)
- `<Location>` sections apply in file order, `<Directory>` shortest-first. — [sections](https://httpd.apache.org/docs/2.4/sections.html#merging)
- Redirect vs RewriteRule order depends on context; the official advice is to "choose one module for a given task". — [tech](https://httpd.apache.org/docs/2.4/rewrite/tech.html)
- Redirect keeps the remainder and query and defaults to 302. — [mod_alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html#redirect)
- Server/vhost redirects run before auth, per-directory ones after. — [request.c](https://github.com/apache/httpd/blob/2.4.x/server/request.c); [mod_alias.c](https://github.com/apache/httpd/blob/2.4.x/modules/mappers/mod_alias.c)
- `setifempty` and Content-Type; Server/Date written after mod_headers. — [mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html#header); [http_filters.c](https://github.com/apache/httpd/blob/2.4.x/modules/http/http_filters.c)

### Inferences
- **Supports**: "applied to every answer including PHP, proxied and error answers" is what Apache users must assemble from `always` plus `onsuccess unset`. "set replaces the application's field" is exactly what `Header set` fails to do under PHP-FPM (duplicates, documented). "remove" reaching PHP headers is what `Header unset X-Powered-By` fails to do under FPM. "Shortest path first, most specific last" equals Apache's Directory semantics and fixes its Location file-order trap. "Redirect before access/password" equals Apache's recommended vhost-level Redirect. "Remainder and query kept by default" equals Apache's Redirect. "Required status" removes the implicit-302 surprise.
- **Argues for care**: (1) Error answers. Apache's onsuccess default exists partly so success-only headers (long Cache-Control, immutable) do not land on 404/5xx; agensio should warn about or condition caching headers on errors, and make sure header rules reach 304s. (2) "default" (only when absent) needs a precise definition against server-derived fields (Content-Type, ETag, Last-Modified), the spot Apache documents as unreliable. (3) A protected list of fields no rule may touch (framing: Content-Length, Transfer-Encoding, Connection, Upgrade; probably Date), and a decision on Server, which Apache never lets you remove. (4) Redirect slash handling: Apache concatenates the remainder blindly (`/one/` to `http://x/two` gives `twoa`), so agensio should normalise or refuse at load. (5) Query handling when `to` has its own query: Apache drops the client's query, mod_rewrite offers QSA/QSD; agensio should state its rule. (6) Matching on the decoded and normalised path, like Apache, implies `%2F` handling: agensio already 404s encoded separators on filesystem locations; a redirect rule's view of the path should be documented. (7) Before-auth redirects reveal targets under protected prefixes, acceptable but worth one line in the docs. (8) Case sensitivity: Apache's Redirect is case-sensitive while agensio's access rules match in any capitalisation; mixing the two semantics on one path prefix needs a deliberate choice.
- **Nothing in Apache argues for** regex rules, per-directory files, or a rewrite engine in this layer. Apache's own docs push users away from them toward `Redirect`, `FallbackResource` and main-config placement.

### Gaps
- agensio's own documents were not read for this note (out of scope); the comparison is against the design as summarised in the assignment.
