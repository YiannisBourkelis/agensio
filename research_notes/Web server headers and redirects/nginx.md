# nginx: response header manipulation and redirects (state as of October 2026)

Scope: stock nginx (mainline 1.31.6, 15 Sep 2026, is the newest entry in the official changelog — [nginx CHANGES](https://nginx.org/en/CHANGES)), its common extension headers-more (OpenResty), and the forks freenginx and Angie where they diverge. Source-code facts were read from `nginx/nginx` master on GitHub. Each section ends with what the finding means for agensio's proposed typed `headers` and `redirects` rules (site level, prefix or exact path; `set` / `default` / `remove`; every matching rule applied, shortest path first; redirects with `from`, `match`, `to`, a required status, remainder and query kept by default, checked before access and password rules).

## 1. add_header: syntax, contexts, inheritance, `always`, status codes, duplicates

### Takeaway
`add_header name value [always]` works in `http`, `server`, `location` and `if in location`. A level that defines any `add_header` drops everything inherited (the best-known nginx header pitfall). nginx 1.29.3 (28 Oct 2025) added `add_header_inherit on | off | merge`, with `on` still the default. Angie refuses that directive as "poor design". Without `always`, headers go only on 200, 201, 204, 206, 301, 302, 303, 304, 307 and 308. The generic `add_header` always appends a new field even when the upstream already sent one with that name. The exceptions are `Cache-Control` and `Link`, which are appended to a list, and `ETag` and `Last-Modified`, which are replaced.

### Cited Findings
- Syntax `add_header name value [always];`, no default, context `http, server, location, if in location`. "Adds the specified field to a response header provided that the response code equals 200, 201 (1.3.10), 204, 206, 301, 302, 303, 304, 307 (1.1.16, 1.0.13), or 308 (1.13.0). Parameter value can contain variables." — [ngx_http_headers_module](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header)
- Inheritance, quoted from the docs: "There could be several add_header directives. These directives are inherited from the previous configuration level if and only if there are no add_header directives defined on the current level. Inheritance rules can be redefined with the add_header_inherit directive (1.29.3)." — [ngx_http_headers_module](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header)
- `always`: "If the always parameter is specified (1.7.5), the header field will be added regardless of the response code." Changelog 1.7.5 (16 Sep 2014): "Feature: the "always" parameter of the "add_header" directive." — [headers module](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header); [CHANGES](https://nginx.org/en/CHANGES)
- `add_header_inherit on | off | merge;`, default `on`, context `http, server, location, if in location`, "appeared in version 1.29.3". "The merge parameter enables appending values from the previous level to the values defined at the current level. The off parameter cancels inheritance of the values from the previous configuration level. The inheritance rules themselves are inherited in a standard way. For example, add_header_inherit merge; specified at the top level will be inherited in all nested levels recursively unless redefined later." The same directive exists for trailers as `add_trailer_inherit`. — [ngx_http_headers_module](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header_inherit)
- Changelog 1.29.3 (28 Oct 2025): "Feature: the "add_header_inherit" and "add_trailer_inherit" directives." — [CHANGES](https://nginx.org/en/CHANGES)
- The merge code: with `merge`, the parent's entries are appended after the child's (`ngx_memcpy(hv, prev->headers->elts, ...)` after the child's own). With `on` and a child that has its own headers, nothing is taken from the parent. With `off`, nothing is inherited. — [ngx_http_headers_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)
- Before 1.29.3 the rule was only clarified in the documentation. A freenginx-site changeset by Maxim Dounin, February 2014, is titled "Clarified add_header inheritance". It was a docs change, not a behaviour change. — [freenginx nginx-site b841fbb8c577](https://freenginx.org/hg/nginx-site/rev/b841fbb8c577)
- Angie's list of nginx directives it does not support says `add_header_inherit` and `add_trailer_inherit` are "Omitted because of their poor design". It names no replacement. — [Angie: unsupported nginx directives](https://en.angie.software/angie/docs/configuration/nginx-unsupported-directives/)
- Gixy, the nginx config linter, has a dedicated check, `add_header_redefinition`. Its example: a `server` sets `X-Frame-Options "DENY"`, and a location that adds `Cache-Control` and `Pragma` loses `X-Frame-Options`. Gixy states "Only merge fixes the redefinition trap". Its other fixes are to repeat the parent headers, to set every header at one level, or to use headers-more. — [gixy add-header-redefinition](https://gixy.getpagespeed.com/checks/add-header-redefinition/)
- The safe-status switch in the filter lists OK, CREATED, NO_CONTENT, PARTIAL_CONTENT, MOVED_PERMANENTLY, MOVED_TEMPORARILY, SEE_OTHER, NOT_MODIFIED, TEMPORARY_REDIRECT and PERMANENT_REDIRECT. The test is `if (!safe_status && !h[i].always) continue;`. The header filter also returns early for subrequests (`if (r != r->main)`). — [ngx_http_headers_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)
- Duplicates. The generic handler `ngx_http_add_header` does `h = ngx_list_push(&r->headers_out.headers)` without looking for an existing field of that name. Special handlers:
  - `Cache-Control` and `Link` use `ngx_http_add_multi_header_lines`, which appends to the chain.
  - `Last-Modified` uses `ngx_http_set_last_modified`, which replaces.
  - `ETag` uses `ngx_http_set_response_header`, which replaces; an empty value removes the existing ETag.

  — [ngx_http_headers_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)
- A community answer on the nginx forum: add_header "will unconditionally append a new header (even if the header with the same name exists upstream)". The remedy given is `proxy_hide_header` plus `add_header`, with the original still readable as `$upstream_http_*`. — [community.nginx.org thread 676](https://community.nginx.org/t/duplicate-response-headers-in-nginx-despite-using-proxy-pass-and-rewrite-break/676)
- Empty values. The generic handler adds the field only `if (value->len)` ([source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)). Changelog 1.5.7 (19 Nov 2013): "Bugfix: the directive "add_header Cache-Control ''" added a "Cache-Control" response header line with an empty value." — [CHANGES](https://nginx.org/en/CHANGES)
- `add_header` and `expires` did not work for proxied 206 responses until 1.1.9. 201 was added to the list in 1.3.10. — [CHANGES](https://nginx.org/en/CHANGES)
- Contexts and `if`: "Configurations inside the if directives are inherited from the previous configuration level." — [ngx_http_rewrite_module, if](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#if)
- Duplicate fields from upstreams. A changeset of 30 May 2022 (1.23.0 era), "Upstream: duplicate headers ignored or properly linked.", says "Most of the known duplicate upstream response headers are now ignored with a warning. If syntax permits multiple headers, these are now properly linked to the lists, notably Vary and WWW-Authenticate." — [mdounin.ru changeset 413dbda22f7d](https://mdounin.ru/hg/nginx/rev/413dbda22f7d). Changelog 1.23.0 (21 Jun 2022): nginx "combines arbitrary header lines with identical names ... during lookup of the "$http_...", "$sent_http_...", ... "$upstream_http_..." variables". — [CHANGES](https://nginx.org/en/CHANGES)

### Inferences
- An `add_header` inside `if` in a location is its own configuration level. Under the default inheritance it therefore drops the location's own `add_header` set (this follows from the two quoted rules; it is not stated in one sentence anywhere).
- Stock nginx has no primitive for "set, replacing the application's field". The usual composition is `proxy_hide_header X` (or `fastcgi_hide_header X`) plus `add_header X v always`. It also has no primitive for "default, only when absent". The idiom is `map $upstream_http_x $x { "" "fallback"; default ""; }` with `add_header X $x;`. It works because an empty evaluated value adds nothing, but only for upstream answers (`$upstream_http_*`). This idiom is my composition from the cited semantics; I found no official recipe for it.
- agensio's choice to apply rules to every answer matches nginx's own move away from the success-only default (`always` in 1.7.5) and headers-more's default (section 2). The status list is a historical behaviour that operators keep tripping over (section 6).
- agensio's "all matching rules combined, shortest path first" is semantically what `add_header_inherit merge` and headers-more's merge do: parent first, child later. nginx took eleven years to offer it and kept the old default for compatibility. Angie's rejection says nothing about what it would prefer; the only stated reason is "poor design". One likely objection is that a tri-state per-level switch is itself inherited. A typed rule list with explicit `remove` avoids that switch.
- The special cases of `add_header` (Cache-Control and Link appended, ETag and Last-Modified replaced, others duplicated) are an argument for agensio stating per-operation semantics (`set` replaces, `default` adds only when absent) rather than per-field magic.

### Gaps
- Whether freenginx adopted `add_header_inherit`: I found no source either way. Its documentation repository shows only the 2014 clarification.
- Angie's Version History entry that explains the "poor design" judgement was not found.
- Which nginx stable branch (1.30.x) carries `add_header_inherit` was not verified. Mainline 1.29.3 is the first release. One blog claims Ubuntu 26.04 ships nginx 1.28.3, which would not have it; that claim is unverified.

## 2. Removing and replacing application headers: *_hide_header, Server, server_tokens, headers-more

### Takeaway
The stock tools are subtractive per upstream type: `proxy_hide_header`, `fastcgi_hide_header` and their `*_pass_header` counterparts. nginx already hides `Date`, `Server`, `X-Pad` and `X-Accel-*` from proxied answers, and `Status` and `X-Accel-*` from FastCGI answers. Stock nginx cannot remove its own `Server` field: `server_tokens off` still sends `Server: nginx`, and an empty string is a commercial-only feature. headers-more fills these gaps. `more_set_headers` replaces or adds, `more_clear_headers` removes (with `*` wildcards), and both apply to every status by default, with `-s` and `-t` filters. headers-more ships in Debian and in OpenResty.

### Cited Findings
- `proxy_hide_header field;` (context `http, server, location`): "By default, nginx does not pass the header fields "Date", "Server", "X-Pad", and "X-Accel-..." from the response of a proxied server to a client. The proxy_hide_header directive sets additional fields that will not be passed. If, on the contrary, the passing of fields needs to be permitted, the proxy_pass_header directive can be used." — [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_hide_header)
- `fastcgi_hide_header`: "By default, nginx does not pass the header fields "Status" and "X-Accel-..." from the response of a FastCGI server to a client." `fastcgi_pass_header` "Permits passing otherwise disabled header fields". — [ngx_http_fastcgi_module](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_hide_header)
- `proxy_ignore_headers` stops nginx from *acting on* `X-Accel-Redirect`, `X-Accel-Expires`, `X-Accel-Limit-Rate`, `X-Accel-Buffering`, `X-Accel-Charset`, `Expires`, `Cache-Control`, `Set-Cookie` and `Vary`. It is not removal. — [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_ignore_headers)
- `proxy_redirect` (default `default`) rewrites the `Location` and `Refresh` fields of proxied answers. The default derives the replacement from `location` and `proxy_pass`, and is "not permitted if proxy_pass is specified using variables". — [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_redirect)
- `server_tokens on | off | build | string;`, default `on`: "Enables or disables emitting nginx version on error pages and in the "Server" response header field." `build` appeared in 1.11.10. "Additionally, as part of our commercial subscription, starting from version 1.9.13 the signature on error pages and the "Server" response header field value can be set explicitly using the string with variables. An empty string disables the emission of the "Server" field." — [ngx_http_core_module](https://nginx.org/en/docs/http/ngx_http_core_module.html#server_tokens)
- In the source, the final header filter writes `Server:` only when `r->headers_out.server == NULL`. With `off` it writes `"Server: nginx"`, with `on` `"Server: " NGINX_VER`, with `build` the build string. The built-in error page footer follows the same switch. — [ngx_http_header_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_header_filter_module.c); [ngx_http_special_response.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_special_response.c)
- headers-more `more_set_headers [-t <content-type list>]... [-s <status-code list>]... [-a] <new-header>...`, context `http, server, location, location if`, phase output-header-filter. It "Replaces (if any) or adds (if not any) the specified output headers", and "Existing response headers with the same name are always overridden". `-a` appends without clearing the old fields. An empty value clears the field. With no `-s` or `-t`, "no match is required". The README says the module's directives "will by default apply to all the status codes". — [headers-more README](https://github.com/openresty/headers-more-nginx-module)
- `more_clear_headers` takes the same `-s`/`-t` filters. A trailing `*` is a pattern: `more_clear_headers 'X-Hidden-*';` clears every field starting with `X-Hidden-`. Input-side variants are `more_set_input_headers [-r]` (with `-r`, replace only if present) and `more_clear_input_headers`, both in the "rewrite tail" phase. — [headers-more README](https://github.com/openresty/headers-more-nginx-module)
- headers-more limitations: it "does not automatically take care of the constraint among the" `Expires`, `Cache-Control` and `Last-Modified` fields, and "You cannot remove the Connection response header". The README says the module helps with "resetting or clearing "builtin headers" like Content-Type, Content-Length, and Server". Its synopsis shows `more_set_headers 'Server: my-server';`. Elsewhere it says "The behavior of builtin headers such as "Content-Type", "Content-Length", "Server", etc. cannot be changed" (in the context of `-a`). The README is internally inconsistent on this point. — [headers-more README](https://github.com/openresty/headers-more-nginx-module)
- headers-more inheritance (source): the location merge *prepends* the parent level's commands to the child's (`ngx_array_push_n(conf->cmds, prev->cmds->nelts)`, then `cmd[i] = prev_cmd[i]`). Parent and child commands therefore both run, the child's last. The filter does not skip subrequests. — [ngx_http_headers_more_filter_module.c](https://github.com/openresty/headers-more-nginx-module/blob/master/src/ngx_http_headers_more_filter_module.c)
- Distribution and compatibility: "This module is not distributed with the Nginx source." It can be a dynamic module since nginx 1.9.11, and "is included and enabled by default in the OpenResty bundle". The README's last tested version is "1.29.x (last tested: 1.29.2)", and its version line still reads "v0.34 released on 17 July 2022". — [headers-more README](https://github.com/openresty/headers-more-nginx-module)
- Debian packages it as `libnginx-mod-http-headers-more-filter`: bookworm 1:0.34-3, trixie 1:0.38-2, forky and sid 1:0.40-4. — [packages.debian.org search](https://packages.debian.org/search?keywords=headers-more&searchon=names&suite=all&section=all)
- Gixy says headers-more "has better inheritance behavior" than `add_header`. — [gixy add-header-redefinition](https://gixy.getpagespeed.com/checks/add-header-redefinition/)

### Inferences
- In stock nginx, removal works only for fields from an upstream (`proxy_`, `fastcgi_`, `uwsgi_`, `scgi_`, `grpc_hide_header`), one directive per upstream type, and never for fields nginx itself produces (Server, ETag, Last-Modified, Accept-Ranges). That nginx documents `server_tokens ""` as a paid feature and that headers-more is the standard answer both show the demand for an operation like agensio's `remove` that works on every answer, the server's own fields included.
- headers-more's semantics (replace by default, every status by default, parent and child both applied, wildcard removal, status and content-type filters) are the closest existing match to agensio's `set` and `remove`. It is a widely deployed precedent for that design. The `-s` and `-t` filters are a feature agensio's proposal lacks; whether it needs them is an open design question.
- headers-more cannot remove `Connection`, and the README hedges on built-ins. That supports agensio keeping a short list of framing fields no rule may touch: Connection, Content-Length, Transfer-Encoding, and possibly Date and the HTTP/2 or HTTP/3 pseudo-fields.

### Gaps
- No primary source found on whether `more_clear_headers Server` fully suppresses the field in current versions. It is widely used for that, but the README is ambiguous.
- headers-more's compatibility with nginx 1.31.x is not stated; the README stops at 1.29.2.

## 3. Redirects: return, rewrite, absolute vs relative Location, $request_uri vs $uri, last/break, captures, phase order, map, try_files, trailing slash

### Takeaway
nginx has three redirect producers: `return`, `rewrite ... redirect|permanent` (or an absolute replacement), and `error_page ... URL`. They run in the rewrite phases (or error handling), which come before the access phase. A `return` therefore answers without `allow`/`deny` or `auth_basic` ever running, even inside a protected location. A Location that starts with `/` is made absolute at send time from `$scheme`, the Host header (or the primary `server_name`) and the local port, unless `absolute_redirect off` (1.11.8). `rewrite` appends the original query by default; `return` keeps it only when the operator writes `$request_uri` or `$is_args$args`. `$uri` is decoded and normalized. Building a Location from it, or from regex captures over it, is the source of the CRLF-injection and double-encoding pitfalls. nginx itself issues 301 trailing-slash redirects for directories and for prefix locations that end in `/` in front of `proxy_pass` and the like.

### Cited Findings
- **Rewrite module processing order**: the `break`, `if`, `return`, `rewrite` and `set` directives at server level run sequentially. Then, repeatedly, a location is found, its rewrite directives run, "the loop is repeated if a request URI was rewritten, but not more than 10 times". — [ngx_http_rewrite_module](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html)
- **return**: `return code [text];` / `return code URL;` / `return URL;`, context `server, location, if`. "Stops processing and returns the specified code to a client. The non-standard code 444 closes a connection without sending a response header." A URL is accepted "for codes 301, 302, 303, 307, and 308", body text for other codes, both may contain variables. "a redirect URL can be specified as a URI local to this server, in which case the full redirect URL is formed according to the request scheme ($scheme) and the server_name_in_redirect and port_in_redirect directives." The sole-parameter form is a 302 and "should start with the "http://", "https://", or "$scheme" string". 307 is treated as a redirect since 1.1.16/1.0.13, 308 since 1.13.0. — [ngx_http_rewrite_module, return](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#return)
- **rewrite**: `rewrite regex replacement [flag];`. "If a replacement string starts with "http://", "https://", or "$scheme", the processing stops and the redirect is returned to a client." The flags:
  - `last`: "stops processing the current set of ngx_http_rewrite_module directives and starts a search for a new location matching the changed URI".
  - `break`: "stops processing the current set of ngx_http_rewrite_module directives as with the break directive".
  - `redirect`: "returns a temporary redirect with the 302 code; used if a replacement string does not start with "http://", "https://", or "$scheme"".
  - `permanent`: "returns a permanent redirect with the 301 code".

  Inside the location being rewritten, `last` must become `break`, "or otherwise nginx will make 10 cycles and return the 500 error". — [ngx_http_rewrite_module, rewrite](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#rewrite)
- **Query handling in rewrite**: "If a replacement string includes the new request arguments, the previous request arguments are appended after them. If this is undesired, putting a question mark at the end of a replacement string avoids having them appended, for example: `rewrite ^/users/(.*)$ /show?user=$1? last;`". — [ngx_http_rewrite_module, rewrite](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#rewrite)
- **Official guidance** (NGINX blog, Tony Mauro, 7 Oct 2015): use `return` "instead of rewrite when possible". `rewrite` "is less efficient than the equivalent return directive" because it needs regex processing. Domain moves use `return 301 $scheme://www.domain.com$request_uri;`. `rewrite ^(.*)$ $scheme://www.domain.com$1 permanent;` is marked "NOT RECOMMENDED", and so is `if` plus `rewrite`, because it "takes extra processing". — [Creating NGINX Rewrite Rules](https://blog.nginx.org/blog/creating-nginx-rewrite-rules)
- **Variables**: `$request_uri` is the "full original request URI (with arguments)", raw as the client sent it. `$uri` is the "current URI in request, normalized" (decoded); it may change during processing, for example on internal redirects or index files. — [ngx_http_core_module, embedded variables](https://nginx.org/en/docs/http/ngx_http_core_module.html#var_request_uri)
- **Absolute vs relative Location**:
  - `absolute_redirect on | off;`, default `on`, since 1.11.8: "If disabled, redirects issued by nginx will be relative."
  - `server_name_in_redirect`, default `off`: "When the use of the primary server name is disabled, the name from the "Host" request header field is used. If this field is not present, the IP address of the server is used."
  - `port_in_redirect`, default `on`: "Enables or disables specifying the port in absolute redirects issued by nginx."

  — [ngx_http_core_module](https://nginx.org/en/docs/http/ngx_http_core_module.html#absolute_redirect)
- **How the absolute URL is built** (source): when `headers_out.location` starts with `'/'` and `absolute_redirect` is on, the final header filter writes `http` or `https`, `://`, the host (primary `server_name` if `server_name_in_redirect`, else the request's Host, else the local address), and the *local socket* port, dropped when it is 80 on plain or 443 on TLS, or when `port_in_redirect` is off. — [ngx_http_header_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_header_filter_module.c)
- **Phase order**: `NGX_HTTP_SERVER_REWRITE_PHASE` (server-level rewrite directives) → `FIND_CONFIG` → `REWRITE` (location rewrite directives) → `POST_REWRITE` → `PREACCESS` (limit_conn, limit_req) → `ACCESS` ("ngx_http_access_module and ngx_http_auth_basic_module register their handlers at this phase") → `POST_ACCESS` → `PRECONTENT` (try_files, mirror) → `CONTENT` (index, static) → `LOG`. — [nginx development guide, HTTP phases](https://nginx.org/en/docs/dev/development_guide.html#http_phases)
- **Consequence, from the nginx mailing list**: in `location /auth { auth_basic ...; return 200 'hello'; }` no password is asked. Explanation on the list: "a rewrite phase ('return' acts as a rewrite, actually) is run before access phase", and "the order of directives as written in nginx conf is not important". Suggested workaround: `try_files @redir =403;` after `auth_basic`, with the redirect in a named location, which runs after the access phase. — [nginx mailing list, Nov 2016](https://mailman.nginx.org/pipermail/nginx/2016-November/052313.html), [follow-up](https://mailman.nginx.org/pipermail/nginx/2016-November/052314.html). The same ordering ("rewrite directives, including "if", are executed before access checks (and hence auth_basic)") is discussed in [Feb 2014](https://mailman.nginx.org/pipermail/nginx/2014-February/042135.html).
- **try_files**: `try_files file ... uri;` / `try_files file ... =code;`, context `server, location`. It checks files in order and makes "an internal redirect to the uri specified in the last parameter" if none is found. It runs in PRECONTENT (above), after the access phase. `try_files $uri $uri/ @drupal;` is documented as equivalent to `error_page 404 = @drupal; log_not_found off;`. — [ngx_http_core_module, try_files](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files)
- **Trailing-slash redirect for directories** (static module, content phase): for a URI whose target is a directory and that does not end in `/`, the handler sets `Location` to the URI plus `/`, appends `?args` when present, escapes with `ngx_escape_uri` when needed, and returns `NGX_HTTP_MOVED_PERMANENTLY` (301). The value starts with `/`, so the header filter makes it absolute by default. URIs ending in `/` are declined to the index module. Only GET, HEAD and POST are handled; other methods get 405. — [ngx_http_static_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_static_module.c). Changelog 1.21.0 (25 May 2021): "Bugfix: special characters were not escaped during automatic redirect with appended trailing slash." — [CHANGES](https://nginx.org/en/CHANGES)
- **Trailing-slash redirect for upstream locations**: "If a location is defined by a prefix string that ends with the slash character, and requests are processed by one of proxy_pass, fastcgi_pass, uwsgi_pass, scgi_pass, memcached_pass, or grpc_pass, then the special processing is performed. In response to a request with URI equal to this string, but without the trailing slash, a permanent redirect with the code 301 will be returned". An exact `location = /user` avoids it. — [ngx_http_core_module, location](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)
- **map-based bulk redirects**: `map string $variable { ... }`, context `http`; "Since variables are evaluated only when they are used, the mere declaration even of a large number of "map" variables does not add any extra costs to request processing." "Strings are matched ignoring the case." Regex keys `~` and `~*` may capture. The search order is exact string, longest prefix mask, longest suffix mask, "the first matching regular expression (in order of appearance in the configuration file)", then default. `include file` loads values from a file. — [ngx_http_map_module](https://nginx.org/en/docs/http/ngx_http_map_module.html)
- **CRLF injection through $uri**: Gixy's `http_splitting` check flags `$uri` and `$document_uri` because "these variables contain decoded URL-encoded values". It also flags captures of negated classes such as `[^/]+` that can match a newline, and suggests `[^/\s]+`. — [gixy http_splitting](https://gixy.getpagespeed.com/checks/http-splitting/); [yandex/gixy docs](https://github.com/yandex/gixy/blob/master/docs/en/plugins/httpsplitting.md). Acunetix's advisory: `return 302 https://example.com$uri;` is vulnerable; replace `$uri` with `$request_uri` "in all redirect configurations". — [Acunetix: nginx redirect header injection](https://www.acunetix.com/vulnerabilities/web/nginx-redirect-header-injection/)
- **Double decoding or encoding in rewrite**: in trac #1460 ("$uri is double-decoded", closed worksforme), Maxim Dounin showed `$uri` is decoded once. He attributed the reported second decoding to a `rewrite` that uses `$uri` in the replacement, because "rewrite assumes that variables in the replacement string are escaped" and unescapes the URI part as needed. — [trac #1460](https://trac.nginx.org/nginx/ticket/1460)
- **Recent rewrite and map security bugs** (2026):
  - 1.31.0 (13 May 2026): heap overflow "while handling a specially crafted request by ngx_http_rewrite_module" (CVE-2026-42945).
  - 1.31.1 (22 May 2026): heap overflow "when using a configuration with overlapping captures in ngx_http_rewrite_module" (CVE-2026-9256).
  - 1.31.3 (15 Jul 2026): heap overflow "when using the map directive with regex matching if the map variable was included in a string expression after a capture affected by this map" (CVE-2026-42533).

  — [CHANGES](https://nginx.org/en/CHANGES)
- **Predicate locations** (new): 1.31.5 (2 Sep 2026) "Feature: predicate locations". `location $variable { ... }` matches when the variable is non-empty and not "0". It is checked after regex locations, in order of appearance. — [CHANGES](https://nginx.org/en/CHANGES); [ngx_http_core_module, location](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)

### Inferences
- **Remainder and query kept by default (supports agensio)**: nginx's `rewrite` keeps the query by default. The official advice for moves is `$request_uri`, which keeps path and query raw. Keeping the remainder of a prefix match has no non-regex primitive in nginx; it is always `rewrite ^/old/(.*)$ /new/$1 permanent;` or a map with regex captures. That regex construction is exactly where the double-encoding and CRLF pitfalls sit. agensio can avoid both by building `to + remainder + ?query` from the raw (still percent-encoded) target bytes, the `$request_uri` way, never from the decoded and normalized path. If it matches on the normalized path but copies the remainder from the raw target, it must map one onto the other carefully, for example when `..` or `//` were collapsed.
- **Checked before access and password rules (matches nginx, but nginx users find it surprising)**: nginx runs every rewrite-module redirect before `allow`/`deny` and `auth_basic`, so agensio's order is the nginx order. The mailing-list threads show that operators expect the opposite when the redirect sits inside a protected location. A redirect answer discloses only its target, not the protected content, so the order is defensible. agensio could document it explicitly, warn (`-t`, health) when a redirect `from` lies under a password or access rule, or let such a rule opt into "after access". The `try_files @named` workaround is how nginx users get "redirect after auth".
- **Directory and upstream trailing-slash redirects are content-phase (after access)** in nginx, unlike `return`. agensio's own directory redirect should keep its current place; a user redirect rule is a different thing.
- **Case**: map string keys match ignoring case, so `map $request_uri` bulk redirects in nginx are case-insensitive, while location prefixes are case-sensitive (unless `~*`). agensio should state its choice explicitly; RFC 3986 paths are case-sensitive.
- **Absolute Location**: nginx's default absolute URL takes the port from the local socket, a known trap behind TLS terminators and container port mapping (an internal `:8080` leaking into `Location`). Hence `port_in_redirect off` and `absolute_redirect off` in many configs. RFC 9110 allows a relative reference in Location (section 10.2.2). For a local `to` (starting with `/`), agensio sending it as-is (relative) avoids host and port guessing. An absolute `to` would be sent verbatim.
- **No regex is a feature**: three 2026 heap overflows in rewrite captures and map regex captures argue for agensio's exact and prefix only matching with remainder copying instead of captures.

### Gaps
- Not verified in this session: whether a relative `Location` from a proxied upstream is made absolute by nginx's header filter. From memory, `ngx_http_upstream_rewrite_location` deliberately does not set `r->headers_out.location` for a value starting with `/`, to avoid that, but I did not re-read it.
- No official nginx document describes bulk redirects with `map $request_uri $new { include ...; }` plus `if ($new) { return 301 $new; }`. The pattern is folklore built from the map docs. Note that `$request_uri` includes the query string, so a key without the query does not match a request carrying one; `$uri` avoids that but is decoded.

## 4. Status code semantics and defaults as nginx applies them; browser caching of 301

### Takeaway
nginx's defaults are 302 for `return URL`, `rewrite ... redirect`, an absolute `rewrite` replacement without a flag, and `error_page ... URL`, and 301 for `rewrite ... permanent` and its own trailing-slash redirects. 307 and 308 were only recognised as redirects from 1.1.16 and 1.13.0. RFC 9110 lets clients turn POST into GET on 301 and 302, and makes 301 and 308 heuristically cacheable. Browsers keep a 301 without explicit cache headers for a long time, which makes a wrong permanent redirect hard to undo.

### Cited Findings
- Defaults: `return URL` (sole parameter) is a temporary 302. `rewrite` flag `redirect` gives 302 and `permanent` 301. An absolute replacement without a flag stops processing and returns a redirect, which the doc text pairs with 302 ("used if a replacement string does not start with..."). — [ngx_http_rewrite_module](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html)
- `error_page` with a URL: "by default, the response code 302 is returned to the client. It can only be changed to one of the redirect status codes (301, 302, 303, 307, and 308)." In the source, an `overwrite` that is not one of these becomes `NGX_HTTP_MOVED_TEMPORARILY`, and `ngx_http_clear_location` runs before the new Location is set. — [ngx_http_core_module, error_page](https://nginx.org/en/docs/http/ngx_http_core_module.html#error_page); [ngx_http_special_response.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_special_response.c)
- Changelog: 1.1.16 (29 Feb 2012) "the "return" and "error_page" directives can now be used to return 307 redirections"; 1.13.0 (25 Apr 2017) "... 308 redirections. Thanks to Simon Leblanc." — [CHANGES](https://nginx.org/en/CHANGES)
- RFC 9110 15.4.2 (301): "For historical reasons, a user agent MAY change the request method from POST to GET for the subsequent request. If this behavior is undesired, the 308 (Permanent Redirect) status code can be used instead." "A 301 response is heuristically cacheable". 15.4.3 (302) has the same POST→GET note pointing to 307. 15.4.8 (307): the user agent "MUST NOT change the request method". 15.4.9 (308): heuristically cacheable; "This status code is much younger (June 2014) than its sibling codes and thus might not be recognized everywhere." — [RFC 9110 §15.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.4) (local copy `docs/rfc/rfc9110.txt`)
- `msie_refresh on` sends an HTML meta refresh (status 200) instead of a 301 or 302 to MSIE clients; it is off by default. — [ngx_http_core_module, msie_refresh](https://nginx.org/en/docs/http/ngx_http_core_module.html#msie_refresh); [ngx_http_special_response.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_special_response.c)
- Browser caching of 301: a widely cited Stack Overflow answer says that without cache directives a 301 is kept with no expiry until the cache is cleared or evicted (Chrome, Chromium Edge), and that explicit caching headers override this. — [Stack Overflow 9130422 (mirror)](https://dev.library.kiwix.org/content/stackoverflow_en_nopic_2021-08/questions/9130422/how-long-do-browsers-cache-http-301s). Secondary sources only; current browser behaviour is unverified (see Gaps).

### Inferences
- nginx's defaults (302 when nothing is said, 301 for "permanent") are the historical POST-rewriting codes. Requiring an explicit status in agensio removes the "accidental 301 cached forever" and the "POST became GET" surprises. It supports the proposal. A validator hint could suggest 308 or 307 when the source path receives non-GET requests.
- Sending `Cache-Control` on permanent redirects, or letting a header rule apply to redirect answers, is the only lever against indefinite 301 caching. agensio's choice that header rules apply to every answer, redirects included, makes that possible without a special case. Note that nginx's `add_header` does reach 301 to 308 even without `always`.

### Gaps
- No primary browser documentation (Chromium source or MDN) was fetched on 301 and 308 cache lifetime; treat "cached indefinitely" as practitioner knowledge.

## 5. Performance: map hashing, regex cost, location matching order

### Takeaway
Exact-string `map` keys and `server_name`s live in hash tables sized at startup and reload, with a key search of at most two memory accesses when the bucket is one cache line. Regex `map` entries and regex locations are tried sequentially in file order, so their cost grows with their number. Location lookup: an exact `=` match ends the search; otherwise the longest prefix is remembered, then regexes are tried in order (skipped after a `^~` prefix), then predicate locations (1.31.5+).

### Cited Findings
- Hashes: "To quickly process static sets of data such as server names, map directive's values, MIME types, names of request header strings, nginx uses hash tables. During the start and each re-configuration nginx selects the minimum possible sizes of hash tables such that the bucket size that stores keys with identical hash values does not exceed the configured parameter". "If hash bucket size is equal to one processor's cache line size then the number of memory accesses during the key search will be two in the worst case". If nginx asks to increase sizes, "the first parameter should first be increased" (max size). — [nginx: Setting up hashes](https://nginx.org/en/docs/hash.html)
- `map_hash_max_size` defaults to 2048 and `map_hash_bucket_size` to 32|64|128 (cache line dependent), both in `http` context. Map variables cost nothing until used. Regex entries are "the first matching regular expression (in order of appearance in the configuration file)", checked only after the exact and wildcard-string lookups miss. — [ngx_http_map_module](https://nginx.org/en/docs/http/ngx_http_map_module.html)
- Location order: "nginx first checks locations defined using the prefix strings ... the location with the longest matching prefix is selected and remembered. Then regular expressions are checked, in the order of their appearance in the configuration file. The search of regular expressions terminates on the first match ... If the longest matching prefix location has the "^~" modifier, then regular expressions and predicate locations are not checked." For `=`: "If an exact match is found, the search terminates. For example, if a "/" request happens frequently, defining "location = /" will speed up the processing". — [ngx_http_core_module, location](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)
- `rewrite` is "less efficient than the equivalent return directive" because of regex processing, according to the NGINX blog. — [Creating NGINX Rewrite Rules](https://blog.nginx.org/blog/creating-nginx-rewrite-rules)
- Matching is done "against a normalized URI, after decoding the text encoded in the "%XX" form, resolving references to relative path components "." and "..", and possible compression of two or more adjacent slashes into a single slash" (`merge_slashes on` by default). — [ngx_http_core_module, location](https://nginx.org/en/docs/http/ngx_http_core_module.html#location); [merge_slashes](https://nginx.org/en/docs/http/ngx_http_core_module.html#merge_slashes)

### Inferences
- The scalable nginx pattern for thousands of one-to-one redirects is a hashed exact-key `map` (O(1), two cache-line touches), not thousands of `location` or `rewrite` lines. agensio's typed exact rules can use the same structure: a hash on the normalized path for `match = exact` and a longest-prefix structure for prefixes. That keeps a site without redirect rules at a zero or single-bit test, in the spirit of agensio's `access_first` bitmap.
- Rewrite-module directives at the server level run for *every* request before location lookup. A long server-level `rewrite` list is a per-request linear regex cost in nginx; a typed prefix and exact table has no such cost.

### Gaps
- No published benchmark numbers of nginx map lookups or rewrite chains at thousands of entries were found. The cost statements are from the documentation's design description, not measurements.

## 6. Header handling for error pages (error_page) and internal redirects

### Takeaway
Without `always`, `add_header` skips every 4xx and 5xx answer, including application 404s passed through FastCGI or proxy. The most common nginx header complaint ends with "add `always`" (trac #1122 closed invalid). Before nginx's own error pages are sent, `ngx_http_clean_header` resets the output headers, and the built-in page strips Accept-Ranges, Last-Modified and ETag. `error_page` with a local URI is an internal redirect that turns the method into GET (except HEAD) and moves the request to another location. The header rules in force at send time are therefore those of the location the error page lands in, not the original one.

### Cited Findings
- `error_page code ... [=[response]] uri;`, context `http, server, location, if in location`: "This causes an internal redirect to the specified uri with the client request method changed to "GET" (for all methods other than "GET" and "HEAD")." `=response` changes the code. `=` alone takes the code the proxied or FastCGI handler returns. A named location keeps URI and method. "If uri processing leads to an error, the status code of the last occurred error is returned to the client." "These directives are inherited from the previous configuration level if and only if there are no error_page directives defined on the current level." — [ngx_http_core_module, error_page](https://nginx.org/en/docs/http/ngx_http_core_module.html#error_page)
- Internal redirect limit: "There is a limit of 10 internal redirects per request ... If this limit is reached, the error 500 (Internal Server Error) is returned." `recursive_error_pages off` by default. — [ngx_http_core_module, internal](https://nginx.org/en/docs/http/ngx_http_core_module.html#internal)
- `ngx_http_internal_redirect(r, uri, args)` "changes the request URI and returns the request to the NGX_HTTP_SERVER_REWRITE_PHASE phase". Named locations resume at `NGX_HTTP_REWRITE_PHASE`. "all request contexts are erased by both redirect functions". — [nginx development guide, request redirection](https://nginx.org/en/docs/dev/development_guide.html#http_request_redirection)
- Source, error path:
  - `ngx_http_filter_finalize_request` calls `ngx_http_clean_header(r)` before the special response handler.
  - The error-page lookup runs only `if (!r->error_page && clcf->error_pages && r->uri_changes != 0)`.
  - The built-in error page sets `Content-Type: text/html` and calls `ngx_http_clear_accept_ranges`, `ngx_http_clear_last_modified` and `ngx_http_clear_etag`.
  - The footer signature follows `server_tokens`.

  — [ngx_http_special_response.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_special_response.c)
- The headers filter reads `ngx_http_get_module_loc_conf(r, ngx_http_headers_filter_module)`, the request's *current* location configuration at the time headers are sent. — [ngx_http_headers_filter_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)
- Trac #1122, "nginx appears to ignore add_header when 404 handling (possibly rewrite-based) happens?" (Drupal behind FastCGI, via try_files, rewrite, or `error_page 404 = /index.php`). Maxim Dounin replied that the response code is 404 and "the add_header directive is not expected to add headers to such responses", pointing to `always`. Closed invalid on 2016-10-29. — [trac #1122](https://trac.nginx.org/nginx/ticket/1122)
- The same complaint on the list in 2009 ("add_header directive not working for 40x and 50x responses", wanting cookies on error pages), and in 2011, where headers-more was the only workaround before `always`. — [nginx list 2009-10](https://mailman.nginx.org/pipermail/nginx/2009-October/015848.html); [nginx list 2011-10](https://mailman.nginx.org/pipermail/nginx/2011-October/029799.html)
- `proxy_intercept_errors` and `fastcgi_intercept_errors` (off by default) decide whether upstream answers >= 300 are "intercepted and redirected to nginx for processing with the error_page directive". — [proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_intercept_errors); [fastcgi](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_intercept_errors)
- Related changelog entries:
  - 1.13.6: "cache control headers were ignored when caching errors intercepted by error_page".
  - 1.15.4: "the "return" directive did not change the response code when returning errors if the request was redirected by the "error_page" directive".
  - 1.23.0: with intercepted 401s, only the first of several upstream `WWW-Authenticate` lines was sent before the fix.

  — [CHANGES](https://nginx.org/en/CHANGES)

### Inferences
- In nginx, which header rules apply to an error answer depends on where `error_page` sends the request. A site-wide `add_header ... always` in `server` reaches the error location only if that location defines no `add_header` of its own, under default inheritance. agensio's proposal (rules matched once against the request's original path and applied to the final answer, whatever produced it) is easier to reason about. It removes the "which location am I in now" question. agensio should state that rules match the client's path, not an internal fallback or `try_files` target. That is a design decision nginx does not make for you.
- nginx strips ETag, Last-Modified and Accept-Ranges from its own error pages. A rule engine that applies to error answers needs a stance on those validators. For example, a `set` of `Cache-Control` on a 404 or 503 may be undesirable; headers-more offers `-s` status filters for this reason.

### Gaps
- I did not verify in the source whether headers set by `add_header` in the *original* location survive an `error_page` internal redirect. The header filter runs once, at send time, with the then-current location, so in practice they do not; that is an inference from the code structure.

## 7. How nginx's behaviour bears on agensio's proposed design (synthesis)

### Takeaway
Most of agensio's choices line up with where nginx has moved or with what headers-more provides: rules on every answer (`always`, headers-more's default), cumulative rules (1.29.3's `merge`, headers-more's parent-first merge), replace semantics (`more_set_headers`), removal of any field (`more_clear_headers`), a required status, and the query kept (rewrite's default, `$request_uri` advice). Two choices deserve explicit documentation because nginx users have been surprised by them. First, redirects answer before access and password checks; nginx does the same, and it surprises its users. Second, `default` (only when absent) has no nginx primitive, so its interaction with application-sent fields must be precise.

### Cited Findings
- Rules on every answer. nginx added `always` (1.7.5) after years of complaints ([trac #1122](https://trac.nginx.org/nginx/ticket/1122), [2009 list](https://mailman.nginx.org/pipermail/nginx/2009-October/015848.html)). headers-more applies "to all the status codes" by default ([README](https://github.com/openresty/headers-more-nginx-module)).
- Cumulative rules: `add_header_inherit merge` (1.29.3) ([docs](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header_inherit)); headers-more prepends the parent's commands ([source](https://github.com/openresty/headers-more-nginx-module/blob/master/src/ngx_http_headers_more_filter_module.c)); Gixy treats the old rule as a misconfiguration class ([gixy](https://gixy.getpagespeed.com/checks/add-header-redefinition/)). Angie declined `add_header_inherit` as "poor design" ([Angie](https://en.angie.software/angie/docs/configuration/nginx-unsupported-directives/)).
- Duplicates. Stock `add_header` appends ([source](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_headers_filter_module.c)); replacing needs `*_hide_header` plus `add_header` ([forum](https://community.nginx.org/t/duplicate-response-headers-in-nginx-despite-using-proxy-pass-and-rewrite-break/676)); `more_set_headers` overrides ([README](https://github.com/openresty/headers-more-nginx-module)).
- Redirect ordering. Rewrite-phase redirects precede ACCESS (`auth_basic`, `allow`/`deny`) ([dev guide](https://nginx.org/en/docs/dev/development_guide.html#http_phases); [list 2016](https://mailman.nginx.org/pipermail/nginx/2016-November/052313.html)).
- Query and path. `rewrite` appends the original args unless the replacement ends in `?` ([docs](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#rewrite)). Moves use `$request_uri` ([NGINX blog](https://blog.nginx.org/blog/creating-nginx-rewrite-rules)). `$uri` in Location enables CRLF injection ([gixy](https://gixy.getpagespeed.com/checks/http-splitting/), [Acunetix](https://www.acunetix.com/vulnerabilities/web/nginx-redirect-header-injection/)).
- Status. nginx defaults to 302 or 301; 301 and 302 allow POST→GET and 301 and 308 are heuristically cacheable ([RFC 9110 §15.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.4)).

### Inferences
- **Supports**: applying header rules to all answers (PHP, proxied, static, errors, redirects); combining every matching rule shortest-first (equal to `merge` and headers-more); `set` as a true replace; `remove` on any field, the server's own included (stock nginx cannot remove `Server`); requiring the status; keeping the remainder and query by default; prefix and exact matching only (avoids regex cost, order dependence and the 2026 rewrite and map CVEs).
- **Argues for care**:
  1. Redirects before access and password rules copy nginx's order, a known nginx surprise. Document it, and consider a `-t`/health notice when a redirect `from` lies under a password or access rule.
  2. Build the remainder from the raw target (the `$request_uri` way), never from the decoded path, to avoid CRLF injection and double encoding, and refuse CR, LF and NUL in `to`.
  3. Decide and document case-sensitivity (nginx's map is case-insensitive, its locations are not).
  4. Decide whether a local `to` stays relative (avoids nginx's `port_in_redirect` and Host pitfalls) or is made absolute.
  5. Define what `set`, `default` and `remove` may not touch (framing fields, as headers-more cannot remove `Connection`).
  6. Decide whether rules match on the client's original path for error answers produced via fallbacks; nginx uses the *current* location, a frequent source of confusion.
  7. Consider whether a status filter (headers-more `-s`) is needed so a long `Cache-Control` does not land on 5xx answers.
- **Shortest-first with `remove` gives the escape hatch nginx needed `add_header_inherit off` for**: a longer path can remove what a shorter path set. It may need an explicit statement of how `set`, then `remove`, then `set` again on the same name resolve across levels.

### Gaps
- No nginx-family source discusses a "default only if absent" operation; this comparison point is unanswered by nginx (OpenResty's Lua `header_filter_by_lua` can do it, not researched here).
- freenginx's position on `add_header_inherit` remains unknown.
