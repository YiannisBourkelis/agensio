# Headers and redirects in hosting panels and managed platforms, and what site owners need

Research date 2026-10-12. Sources were fetched unless marked "(search snippet)": those come from a search engine's summary of a page that could not be fetched (403, 404 or empty), so their wording is unverified. Context: agensio proposes typed site-level header rules (set, default, remove by path) and redirect rules (from, match prefix or exact, to, required status, path remainder and query kept by default), changed by an agent through `site_update`.

## 1. What panels and managed platforms offer for redirects and response headers, and their limits

### Takeaway
Classic panels (cPanel, Plesk, DirectAdmin, HestiaCP, ISPConfig, Forge) offer a small redirect form (source path, target URL, 301 or 302, sometimes www handling) and send everything else (headers, path-specific rules) to a raw config field that is admin-only or a support ticket. Managed and edge platforms (Kinsta, WP Engine, Netlify, Vercel, Cloudflare) have structured rule lists with explicit ordering, query-string options, bulk import and documented limits. Header control as a typed feature exists only on WP Engine (Set/Unset with conditions), Netlify (`_headers`), Vercel and Cloudflare (set/add/remove); among the panels, only HSTS gets a switch (Plesk SSL It!, HestiaCP).

### Cited Findings

**cPanel (Redirects interface)**
- Two types: Permanent (301), which "prompts search engines to update their records", and Temporary (302), which has no effect on search engine records. — [cPanel docs: Redirects](https://docs.cpanel.net/cpanel/domains/redirects/)
- www options: "Only redirect with www", "Redirect with or without www", "Do Not Redirect www". The www setting is disabled when "All Public Domains" is selected. — [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)
- "Wild Card Redirect" sends every file in a directory to the same file name under the target (`example1.com/pic.jpg` to `example.com/pic.jpg`), which is the path remainder kept. — [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)
- Storage: "the system places redirect rules at the bottom of the .htaccess file." You "cannot change an existing redirect": you delete it and create it again. The target must include a protocol. The docs warn that "Some third-party applications will ignore your rules" (WordPress is the example) and that browsers cache redirects, so visitors may need to clear their cache. HTTP to HTTPS is a separate "Force HTTPS Redirect" toggle in Domains. — [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)
- Why WordPress ignores them: WordPress's block sits at the top of `.htaccess` and ends with `[L]`, so Apache stops before cPanel's rules at the bottom. Hosts tell customers to move the cPanel lines above `# BEGIN WordPress` by hand, or to use a redirect plugin. — [InMotion Hosting](https://help.inmotionhosting.com/hc/en-us/articles/14609412204183-cPanel-Redirects-Not-Working-in-WordPress) (search snippet); [Krystal](https://help.krystal.io/web-hosting/redirection-not-working-or-unexpected-redirection-occurring) (search snippet)
- cPanel feature requests ask for redirect code to be prepended rather than appended to `.htaccess` ("URL redirects are added to the end of .htaccess files and are ignored if that account has a CMS that has already added rules"). — [features.cpanel.net request](https://features.cpanel.net/topic/create-redirect-rules-at-the-beginning-of-htaccess-files) and [prepend request](https://cpanel.useresponse.com/topic/have-redirect-code-prepended-to-htaccess-when-setup-through-cpanel) (search snippets; the page body could not be retrieved, so date, votes and status are unknown)

**Plesk**
- "Preferred domain" in Hosting Settings (www, non-www, or None): Plesk redirects to the preferred one with "the search engine friendly HTTP 301 code"; with None, "search engines will treat both URL versions ... as URLs of different sites" and rankings split. — [Websavers KB on Plesk preferred domain](https://clients.websavers.ca/whmcs/knowledgebase/11/My-website-will-not-work-with-the-www-prefix.html) and [Plesk docs, Hosting Types](https://docs.plesk.com/en-US/onyx/customer-guide/72051) (search snippets)
- A separate checkbox "Permanent SEO-safe 301 redirect from HTTP to HTTPS" in Hosting Settings needs SSL/TLS support and a selected certificate. Plesk support says it is on by default for new subscriptions, and all Obsidian service plans have it enabled by default. — [Exabytes guide](https://support.exabytes.co.id/en/support/solutions/articles/14000131819-enable-http-to-https-redirection-in-plesk), [Colonel Server KB](https://colonelserver.com/kb/redirecting-users-to-ssl-connections-in-plesk/) (search snippets)
- Whole-domain forwarding is a hosting type ("Forwarding"): "Moved permanently (code 301) or Moved temporarily (code 302)". Changing the hosting type deletes the website's data and logs. — [Plesk docs, Hosting Types](https://docs.plesk.com/en-US/onyx/customer-guide/72051) (search snippet)
- "Additional Apache directives" and "Additional nginx directives" (Websites & Domains > Apache & nginx Settings) are stored in `/var/www/vhosts/system/<domain>/conf/vhost_nginx.conf`, and Plesk reloads the services. The fields are "available only to Plesk administrator". For service plans, "for security reasons" the directives can be set only for new domains, and Plesk warns that new directives can overwrite existing configuration and break sites. — [Plesk KB: custom Apache/nginx configuration](https://www.plesk.com/kb/support/how-to-add-custom-apache-nginx-configuration-for-a-domain-in-plesk) (search snippet)
- On shared Plesk hosting the nginx directives field is unavailable to customers, who must ask support. — [Rebel.ca support](https://support.rebel.ca/hc/en-us/articles/55658433339291-How-to-Request-Custom-Nginx-Directives-on-Plesk-Hosting) (search snippet)
- A `location /` block in the additional nginx directives does not match, because it is included after the template's own `location` directive. — [Plesk forum](https://talk.plesk.com/threads/nginx-reverse-proxy-directive-for-location-for-specific-domain-only.355631/) (search snippet)
- HSTS comes from the SSL It! extension (an HSTS button on the domain's SSL/TLS Certificates page). The support article says the header is not sent while the preferred domain is "www". — [Plesk support article](https://support.plesk.com/hc/en-us/articles/12377455612055) (search snippet; 403 when fetched)
- SSL It! offers "include subdomains" and "apply to webmail" but no preload option, so users add the header by hand in the additional directives. Users report duplicate HSTS headers when it is enabled both at subscription level and in site code. — [Plesk forum: SSL It and HSTS options](https://talk.plesk.com/threads/ssl-it-and-hsts-options.371568), [Plesk forum: HSTS appearing twice](https://talk.plesk.com/threads/ssl-it-hsts-appearing-twice-in-headers.352417/post-959417) (search snippets)
- No Plesk "security headers" screen beyond HSTS was found. — searches above

**ISPConfig**
- The website's Redirect tab has an "SEO Redirect" drop-down, which renders an nginx block comparing `$http_host` with the origin and rewriting to the target with `$request_uri`, permanent. A user's advice for a wildcard alias: "just select * => www.domain.tld". — [ISPConfig nginx vhost template (blame view)](https://git.ispconfig.org/isp/ispconfig3/-/blame/86bc6556b8378eb3ff0c3f39f98002d8d42d7a8a/server/conf/nginx_vhost.conf.master), [HowtoForge forum](https://forum.howtoforge.com/posts/360839) (search snippets; both 403 when fetched)
- The Redirect tab's "Rewrite Rules" field is validated, and the filter rejected a valid rule with "Invalid Rewrite Rules" (the cause was spaces in the URL). The developer sends custom rules to the "nginx Directives" field on the Options tab. — [HowtoForge forum thread](https://forum.howtoforge.com/posts/310933), [HowtoForge forum](https://forum.howtoforge.com/posts/304014) (search snippets)
- No ISPConfig documentation on header options was found (the manual is a paid PDF). — gap

**DirectAdmin**
- "Site Redirection" (under Account Manager in the Evolution skin, Advanced Features in Enhanced): a Local URL Path (empty or `/` for the whole domain) and a Destination URL, types 301, 302 and 303. — [Snel](https://www.snel.com/support/create-redirect-directadmin/), [Fozzy](https://fozzy.com/help/articles/how-to-set-a-website-redirection), [ArkHost](https://arkhost.com/knowledgebase/4748/How-to-Set-Up-Site-Redirection-in-DirectAdmin.html) (search snippets, host guides)
- No user-level way to add custom httpd directives was found. Custom httpd configuration is an admin feature. — searches above (official docs.directadmin.com page not fetched; gap)

**HestiaCP**
- CLI `v-add-web-domain-redirect USER DOMAIN REDIRECT HTTPCODE [RESTART]` ("Function creates a forced redirect to a domain"), with examples to `domain.tld`, `www.domain.tld` and `different-domain.com 302`. HSTS is `v-add-web-domain-ssl-hsts`. The reference lists no allowed codes or default. — [HestiaCP CLI reference](https://hestiacp.com/docs/reference/cli)
- The HTTP to HTTPS 301 is hard-coded (`return 301 https://$host$request_uri;`), so a user who chose 302 for a custom-domain redirect still saw a 301 on http://. — [HestiaCP forum](https://forum.hestiacp.com/t/redirect-users-to-a-custom-domain-or-web-address-you-cant-use-code-302/18233)
- Anything finer (path redirects, headers) means custom nginx templates (`.tpl` and `.stpl`) written by hand. — [HestiaCP forum: www to non-www](https://forum.hestiacp.com/t/redirecting-www-to-non-www-nginx-only/1946) (search snippet)

**CloudPanel and RunCloud (nginx-only panels)**
- CloudPanel has no redirect form: redirects are nginx rewrite rules written in the site's Vhost editor, which validates syntax. `.htaccess` does not work. — [CloudPanel tutorial: rewrite rules](https://www.cloudpanel.io/tutorial/nginx-rewrite-rules), [CloudPanel: HTTP to HTTPS](https://www.cloudpanel.io/blog/redirect-http-to-https/) (search snippets)
- RunCloud: an "NGINX Config" editor per web application with config types (`location.main`, `location.root`...), files under `/etc/nginx-rc/extra.d/*.conf`, a "Run and Debug" syntax check, and reusable NGINX Templates with a "Test Template" that simulates the config against a real app without changing the server. — [RunCloud docs: custom nginx config](https://runcloud.io/docs/how-to-create-a-custom-nginx-configuration-file), [RunCloud: testing templates](https://runcloud.io/docs/creating-and-testing-nginx-templates) (search snippets)
- No dedicated redirect-rule page was found for either panel, nor for Ploi or ServerPilot. — gap

**Laravel Forge**
- Site > Network > Redirects: "Redirects are wrappers around Nginx's `rewrite` rules and can use the full redirect syntax supported by Nginx, including regular expressions" (`^/$` matches only the root). Types: Permanent (301) and Temporary (302). — [Forge docs: Network](https://laravel.com/forge/docs/sites/network)
- The docs warn that after changing a permanent redirect "you will need to clear the browser cache ... It's considered bad practice to change a permanent redirect". — [Forge docs](https://laravel.com/forge/docs/sites/network)
- Forge has "security rules" (basic auth per path, a `.htpasswd` per rule) but no IP rules ("Laravel Forge does not provide the ability to configure this") and no header rules on that page. — [Forge docs](https://laravel.com/forge/docs/sites/network)

**Kinsta (MyKinsta Redirects)**
- Sites > site > Redirects > "Add redirect rule": domain or prefix (www, non-www, both), "Redirect from" (always a regex), "Redirect to" (accepts `$1`, `$host`, `$scheme`), 301 or 302. Rules are "implemented at the server level" in the site's nginx config (no `.htaccess`), and Kinsta contrasts this with plugins using `wp_redirect`. — [Kinsta docs: Redirect rules](https://kinsta.com/docs/redirect-rules/)
- Regex pitfalls in the docs: "you should add `^` at the beginning of every 'from' path", or `/blogpost` also matches `/category/blogpost`. Without `$`, `^/blog/about` matches `/blog/about-me` and can loop. Matching is case-sensitive unless `(?i)`. Rules are "checked in the order you add them". — [Kinsta docs](https://kinsta.com/docs/redirect-rules/)
- Query strings: "You cannot use Redirects within MyKinsta to redirect query strings", and query redirects need support. A path redirect carries trailing parameters such as `?utm_content=buffer` through. — [Kinsta docs](https://kinsta.com/docs/redirect-rules/)
- MyKinsta has CSV import and export (details in section 2). — [Kinsta docs](https://kinsta.com/docs/redirect-rules/)
- No MyKinsta header UI was found. — gap

**WP Engine**
- The old "Redirect rules" page is deprecated ("The redirect rules page is deprecated"). New redirects go in the Rewrite rules tab of Web Rules. — [WP Engine: 301 and 302 redirect rules](https://wpengine.com/support/redirect/)
- Legacy redirect fields: Name (a label), Domain (all or one mapped), Source (regex, must start with `^` and end with `/?$`), Destination (no regex, `$1` allowed), type 301 (default), 302 or Break (internal rewrite). "You cannot match a Query String ... in the Source Input" (use Advanced Settings, Match args). A trailing `?` on the destination drops the query, otherwise it is appended. — [WP Engine](https://wpengine.com/support/redirect/)
- Web Rules Engine: three rule types: IP Allow/Deny (403), response headers, rewrites. Header actions are **Set** and **Unset**, with "When": "Only on successes" (2xx) or "All responses". Restricted headers: `server`, `date`, `x-cache`, and any name containing "WPE". Conditions: URI, query string, method, header, GeoIP country, IP, with equal, not equal, regex and negative regex; "all conditions applied to the rule must be met". Rules are read top to bottom, "rules that are read first take priority", and "The first rewrite rule whose conditions are met is triggered". Soft limit "1000 rewrite rules per environment". Rules can be copied between environments, with duplicates skipped. — [WP Engine: Web Rules Engine](https://wpengine.com/support/web-rules-engine/)
- Cloudways (another managed host) Web Rules: 10 header rules and 25 redirect/rewrite rules per application, one condition per redirect/rewrite rule. — [Cloudways support](https://support.cloudways.com/en/articles/12597858-how-to-create-and-manage-web-rules-in-cloudways) (search snippet)

**Netlify**
- `_redirects` (one rule per line: from, to, optional status, `!` to force, conditions) or `[[redirects]]` in `netlify.toml` (`from`, `to`, `status` default 301, `force` default false, `query`, `conditions`, `headers`, `signed`). "The redirects engine will process the first matching rule it finds, reading from top to bottom. Rules in the `_redirects` file are always processed first." "Paths are case-sensitive and special characters in paths must be url-encoded." — [Netlify: Redirects](https://docs.netlify.com/routing/redirects/)
- Headers: `_headers` (path line, indented `Name: value` lines) or `[[headers]]` with `for` and `values`. Repeated names are concatenated into one comma-separated value. "Custom headers apply only to files Netlify serves from our own backing store", so proxied, function or SSR responses do not get them. Headers "are global for all builds and cannot be scoped for specific branches or deploy contexts". Names like `Content-Length`, `Date`, `Location`, `Server`, `Set-Cookie` and `Transfer-Encoding` are ignored. The page documents no remove or unset. — [Netlify: Custom headers](https://docs.netlify.com/manage/routing/headers/)

**Vercel**
- Six mechanisms, each with a stated use: configuration redirects (wildcards, patterns, geolocation; `vercel.json` or framework config), bulk redirects (thousands of simple redirects; CSV, JSON, JSONL), functions, middleware with Global Config (changes "without redeploying"), domain redirects (www to apex in the dashboard), firewall redirects ("Emergency redirects that must execute before other redirects"; the dashboard creates a 307). — [Vercel: Redirects](https://vercel.com/docs/routing/redirects)
- Status guidance: Vercel recommends 307/308 "to avoid the ambiguity of non GET methods". The CDN normalizes `//` to `/` with a 308 before redirects run, and does not lowercase paths. — [Vercel: Redirects](https://vercel.com/docs/routing/redirects)
- For staging or another host: "Use host-scoped `X-Robots-Tag: noindex`", and keep preview hostnames out of production-only redirect rules. — [Vercel: Redirects, canonical domain section](https://vercel.com/docs/routing/redirects)

**Cloudflare**
- Single Redirects (Redirect Rules, per zone): static or dynamic targets, wildcard patterns "without complex functions or regular expressions"; regex only on Business and Enterprise. — [Cloudflare: Single Redirects](https://developers.cloudflare.com/rules/url-forwarding/single-redirects/), [Cloudflare: URL forwarding availability](https://developers.cloudflare.com/rules/url-forwarding/)
- Bulk Redirects (per account): lists of static URL redirects, "do not support string replacement operations or regular expressions"; they run after the WAF. — [Cloudflare: Bulk Redirects](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/)
- Response header Transform Rules: Set static, Set dynamic, Add static, Add dynamic, Remove ("all response headers with the provided name"). `cf-`/`x-cf-` and some others (`server`...) cannot be changed. "Response header transform rules run in order, and later rules can overwrite changes done by previous rules." Changing `cache-control` there does not change Cloudflare's caching, because caching is decided first. The rules also apply to Cloudflare's own error pages. — [Cloudflare: Response header modification](https://developers.cloudflare.com/rules/transform/response-header-modification/)
- Page Rules are legacy. Cloudflare plans to migrate existing ones automatically "late 2025 or beyond" with advance notice. Its HTTPS example uses a Single Redirect `http://*` to `https://${1}`, 301, preserve query string. — [Cloudflare: Page Rules migration](https://developers.cloudflare.com/rules/reference/page-rules-migration/), [Cloudflare community announcement](https://community.cloudflare.com/t/important-page-rules-migration/656021) (search snippets)

### Inferences
- Across the board, a non-shell owner gets a source-to-target redirect form, while response headers mean editing server config or asking support. The exceptions are the managed WordPress hosts and edge platforms (WP Engine Web Rules, Netlify, Vercel, Cloudflare). A typed header rule with set and remove fills a gap the classic panels leave open.
- The common header operations are set, add/append and remove (unset). WP Engine has Set and Unset with a 2xx-only or all-responses switch. Cloudflare has set, add and remove. Netlify has set only (repeats concatenated). agensio's set, default and remove covers WP Engine's model plus a "default" (set only if absent) that none of them name explicitly. WP Engine's "only on successes vs all responses" choice is worth a field or a stated default, since security headers belong on error pages too (nginx's `always`).
- Each platform keeps a short deny-list of headers that cannot be set (Netlify: framing headers such as `Content-Length`, `Date`, `Location`, `Server`, `Set-Cookie`; WP Engine: `server`, `date`, `x-cache`, `*WPE*`; Cloudflare: `cf-*`, `server`). A typed API should refuse framing and hop-by-hop fields, and say why, in the validation answer.
- Plesk's duplicate HSTS (panel plus application) and Netlify's "headers don't apply to proxied or function responses" are the two semantics questions any header feature must answer: what happens when the upstream or application already sends the header. A "default" operation (only if absent) and a "set" (replace) answer them explicitly.
- Panels that write raw rules into a file the application also writes (cPanel `.htaccess`) fail silently because of ordering. agensio's typed rules evaluated in the server before the application avoid that class of bug, and the docs should say so.

### Gaps
- ISPConfig's exact SEO Redirect choices and "Redirect Type" flag list: forum and template pages returned 403. A recollection (unverified) is SEO choices like `domain.tld => www.domain.tld`, `www.domain.tld => domain.tld`, `*.domain.tld => ...`, and nginx flags `last`, `break`, `redirect`, `permanent`, `proxy`.
- Ploi and ServerPilot redirect features: no documentation found.
- DirectAdmin's official docs on Site Redirection storage (.htaccess vs httpd.conf) and limits: not found, only host guides.
- Kinsta header UI: none found. Whether Kinsta adds custom headers (HSTS etc.) through support was not confirmed.
- Plesk HSTS max-age choices in SSL It!: not confirmed.

## 2. Bulk redirect formats, limits, status codes, query handling, regex, splat syntax, ordering

### Takeaway
Bulk imports converge on flat rows: source, target, status, plus a few per-row booleans (case sensitivity, preserve query, subpath matching) in CSV, JSON or JSONL. Static exact-match lists scale to tens of thousands or millions of rows (Cloudflare, Vercel). Pattern rules are capped in the low thousands (Vercel 2,048, WP Engine about 1,000) or tens (Cloudflare 10 to 300, Cloudways 25), with first match wins top to bottom. Query-string defaults differ: Netlify passes the query on, Vercel bulk and Cloudflare bulk drop it unless asked, WP Engine appends unless the target ends in `?`.

### Cited Findings

**Formats**
- Kinsta CSV columns: status code, domain (`all` for every domain), redirect-from path (regex), redirect-to URL, optional country and city, one rule per line: `301,all,^/oldpath/?$,https://newlocation.com/newpath`. Up to 5,000 rules per import, 100 KB file maximum. "There is no limit to the number of redirects you can add." Import adds to the existing rules, and Export to CSV exists. — [Kinsta docs](https://kinsta.com/docs/redirect-rules/)
- WP Engine legacy bulk import goes through support with an htaccess-style file ("Each rule must be on its own line"), `Redirect 301 ^/path/match/?$ http://domain.com/something/` or `RewriteRule` lines. "302 (Temporary) rules cannot be bulk imported at this time, and will be converted to 301 (Permanent) automatically." — [WP Engine](https://wpengine.com/support/redirect/)
- WP Engine Web Rules bulk import takes a .txt or .csv, one redirect per line, and is unavailable if rules already exist on the old Redirect Rules page. Whitespace must be `%20`. Header and access rules cannot be bulk imported. — [WP Engine Web Rules Engine](https://wpengine.com/support/web-rules-engine/)
- Vercel bulk redirects: CSV, JSON or JSONL with fields `source` (path or full URL, no query, max 2048 chars), `destination`, `permanent` (default false: 307, true: 308), `statusCode` (301, 302, 303, 307, 308; overrides `permanent`), `caseSensitive` (default false), `preserveQueryParams` (default false). Booleans may be `t`/`f`. — [Vercel: Bulk Redirects](https://vercel.com/docs/routing/redirects/bulk-redirects)
- Cloudflare bulk redirect row: `source_url` (scheme optional: then both http and https match; no two rows with the same source in a list), `target_url`, `status_code` (301 default, 302, 307, 308), `subpath_matching` (default false), `include_subdomains` (default false), `preserve_query_string` (default false), `preserve_path_suffix` (default true, only with subpath matching). — [Cloudflare: Bulk redirect parameters](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/parameters/)
- Netlify uses plain text `_redirects` lines or TOML. No CSV import was documented. — [Netlify: Redirects](https://docs.netlify.com/routing/redirects/)

**Limits**
- Vercel configuration redirects: 2,048 per array, `source`/`destination` up to 4,096 chars. Above that, Middleware plus Global Config. — [Vercel: Configuration Redirects](https://vercel.com/docs/routing/redirects/configuration-redirects)
- Vercel bulk: Pro includes 1,000 and Enterprise 10,000 per project, more in blocks of 25,000 at $0.002/month per block, at most 1,000,000 per project; not on Hobby. "Bulk redirects do not support wildcard or header matching." — [Vercel: Bulk Redirects](https://vercel.com/docs/routing/redirects/bulk-redirects)
- Cloudflare bulk (per account): 15 rules, 5 lists, 10,000 URL redirects on Free; Pro 15/5/25,000; Business 15/5/50,000; Enterprise 50/25/1,000,000 (several million on request). Single Redirects (per zone): 10, 25, 50, 300 rules, with regex only from Business up. — [Cloudflare: URL forwarding](https://developers.cloudflare.com/rules/url-forwarding/)
- Older Cloudflare docs show Free at 20 bulk URL redirects. The February 2025 changelog raised it to 10,000 (Pro 25,000, Business 50,000). — [Cloudflare changelog 2025-02-12](https://developers.cloudflare.com/changelog/post/2025-02-12-rules-upgraded-limits/) (search snippet)
- WP Engine: the legacy portal "supports up to about 1000 redirects". Beyond that it reports performance problems and recommends the Redirection plugin or Yoast Premium, and regex consolidation. Web Rules: "a soft limit of 1000 rewrite rules per environment". — [WP Engine redirect](https://wpengine.com/support/redirect/), [WP Engine Web Rules](https://wpengine.com/support/web-rules-engine/)
- Netlify states no hard limit: "If you need to set up 10,000 redirects or more, we recommend using wildcards or placeholders as much as possible", and too large a serialized output can fail the deploy. — [Netlify: Redirects](https://docs.netlify.com/routing/redirects/)

**Status codes**
- Netlify: 301 (default), 302, 200 (rewrite), 404. "Use [302] instead of 307, which is currently unsupported." Its redirect-options page does not mention 308. — [Netlify: Redirect options](https://docs.netlify.com/manage/routing/redirects/redirect-options/)
- Vercel: 307/308 defaults, 301/302/303 selectable (bulk). Cloudflare bulk: 301, 302, 307, 308. Kinsta, Forge and cPanel: 301 and 302 only. DirectAdmin: 301, 302, 303. WP Engine: 301, 302, Break. — sources above

**Query strings**
- Netlify: "our service automatically passes on all query string parameters to destination paths for redirects with 200, 301, and 302". A rule may require parameters (`/store id=:id /blog/:id 301`), and such a rule "matches only URLs that have only the id parameter and no others". — [Netlify: Redirect options](https://docs.netlify.com/manage/routing/redirects/redirect-options/)
- Vercel configuration redirects: "Query parameters pass through unless you explicitly replace them in the destination". Bulk: `preserveQueryParams` defaults to false, and a query in `source` is ignored. — [Vercel: Redirects](https://vercel.com/docs/routing/redirects), [Vercel: Bulk](https://vercel.com/docs/routing/redirects/bulk-redirects)
- Cloudflare bulk: `preserve_query_string` defaults to false, and "Any query string on the target URL is discarded" when it is on. — [Cloudflare parameters](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/parameters/)
- Kinsta: no query matching, query carried through. WP Engine: no query matching in source, query appended unless the target ends with `?`. — [Kinsta](https://kinsta.com/docs/redirect-rules/), [WP Engine](https://wpengine.com/support/redirect/)

**Pattern syntax**
- Netlify splat: `/news/* /blog/:splat`. Placeholders `:year`, `:slug` match one segment, or the final segment with extension "excluding a query string". "It's not possible to use an asterisk as a wildcard in the middle of a path" and "not possible to indicate a path to exclude from a splat redirect rule". Paths match "regardless of whether or not they contain a trailing slash", and "You cannot use a redirect rule to add or remove a trailing slash". — [Netlify: Redirect options](https://docs.netlify.com/manage/routing/redirects/redirect-options/)
- Vercel configuration: path-to-regexp style (`/:path*`, `/old-blog/:slug`, regex groups like `/:path((?!uk/).*)`), plus `has`/`missing` conditions on host, header and so on. — [Vercel: Configuration Redirects](https://vercel.com/docs/routing/redirects/configuration-redirects)
- Cloudflare bulk has no wildcards, only subpath matching with path-suffix preservation (a prefix rule with the remainder kept). Single Redirects use wildcards with `${1}`. — [Cloudflare parameters](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/parameters/), [Page Rules migration](https://developers.cloudflare.com/rules/reference/page-rules-migration/) (search snippet)
- Kinsta, WP Engine and Forge use raw regex with `$1`, where anchoring mistakes cause loops. — [Kinsta](https://kinsta.com/docs/redirect-rules/), [WP Engine](https://wpengine.com/support/redirect/), [Forge](https://laravel.com/forge/docs/sites/network)

**Ordering and precedence**
- First match wins, top to bottom: Netlify ("more specific rules should be listed before more general ones"), Kinsta ("checked in the order you add them"), WP Engine ("first rewrite rule whose conditions are met is triggered"; it recommends "Insert rule above/below" over drag and drop). — [Netlify](https://docs.netlify.com/manage/routing/redirects/redirect-options/), [Kinsta](https://kinsta.com/docs/redirect-rules/), [WP Engine Web Rules](https://wpengine.com/support/web-rules-engine/)
- Across products: Cloudflare runs Single Redirects before Bulk, and "the product executed first will apply". Vercel bulk redirects run "before any other route specified in your deployment", and firewall redirects before configuration redirects. — [Cloudflare URL forwarding](https://developers.cloudflare.com/rules/url-forwarding/), [Vercel Bulk](https://vercel.com/docs/routing/redirects/bulk-redirects), [Vercel Redirects](https://vercel.com/docs/routing/redirects)
- Netlify shadowing: a rule does not apply when a file exists at the path unless forced (`!` / `force = true`). — [Netlify: Redirect options](https://docs.netlify.com/manage/routing/redirects/redirect-options/)

**Testing, preview, versioning**
- Vercel runtime bulk changes go "to a staging version first and only take effect once you publish or promote that version", with versioning and rollback through the CLI and local testing with `vercel dev`. Vercel also has an MCP tool `list_bulk_redirects` and a REST `PATCH /v1/bulk-redirects` that "Stages a new change". Its verification advice is to `curl -I` a nested path with a query on both hosts and expect one 308 with the path and query in `Location`. — [Vercel: Bulk Redirects](https://vercel.com/docs/routing/redirects/bulk-redirects) (related-links list), [Vercel: Redirects](https://vercel.com/docs/routing/redirects)
- Cloudflare points to "Trace a request" to see whether a redirect fires. — [Cloudflare: Bulk Redirects](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/), [Single Redirects](https://developers.cloudflare.com/rules/url-forwarding/single-redirects/)
- cPanel's only test is clicking the link in the Current Redirects table. — [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)

### Inferences
- For an agent API, a JSON array of rows is the natural bulk format (Vercel's JSONL rows and Cloudflare's typed rows), with CSV accepted only as an import convenience. Cloudflare's row is close to agensio's proposal: subpath matching = `match = "prefix"`, preserve path suffix = path remainder kept, preserve query string. Defaults differ, though: Cloudflare and Vercel bulk drop the query by default, while Netlify, Vercel config and agensio's proposal keep it. agensio's "kept by default" matches what owners expect (UTM parameters survive), but the docs should name the difference, since agents may carry Cloudflare or Vercel habits.
- Exact and prefix rules with no regex (Cloudflare bulk, Vercel bulk) are what scales and what cannot loop through a forgotten anchor. Every regex-based panel (Kinsta, WP Engine, Forge) documents anchoring pitfalls. A typed exact/prefix model avoids the most documented class of user error, and longest-prefix or exact-before-prefix precedence (like agensio's `Router::location`) removes the "order matters" trap that Netlify, Kinsta and WP Engine document. If agensio keeps specificity order rather than list order, it should say so, because users and agents coming from those platforms assume first-match-wins.
- Limits seen in the field: pattern rules 10 to about 2,000, static rows 1,000 to 1,000,000. A static exact table (a hash map) can be large at no per-request cost, while prefix rules want a bound. A stated count limit and a refusal that names it beat WP Engine's "about 1000, then performance problems".
- Features that suit an agent: staging then publish (Vercel), a dry-run or trace (Cloudflare), export (Kinsta CSV), insert above/below (WP Engine), duplicate-source refusal (Cloudflare lists). agensio's `path_check` is the natural trace. A redirect-aware `path_check` answering "this request gets 301 to X by rule N" would match Cloudflare's trace.
- Status codes to offer: 301, 302, 307, 308 cover every platform's set except 303 (DirectAdmin, Vercel). Requiring the status (no default) is stricter than all platforms surveyed, where the default is 301 (Netlify, Cloudflare, WP Engine) or 307 (Vercel). That prevents an accidental permanent, browser-cached redirect.

### Gaps
- Netlify's support for 303, 308, 410 and 451 is not stated on the fetched page (307 explicitly unsupported).
- Case sensitivity for Cloudflare bulk matching: not stated on the fetched page.
- Kinsta: whether rules are evaluated before the page cache, and how they behave on staging push.
- Exact CSV header layout for Vercel CSV and Cloudflare list CSV import: not fetched.

## 3. What site owners and agencies complain about

### Takeaway
The recurring pains are: redirects that silently do nothing (cPanel's `.htaccess` ordering under WordPress, rules that never match), a mistaken 301 cached by browsers, redirect plugins' database and PHP overhead (mostly logging), 404s and homepage blanket redirects after migrations, redirects locked inside a host's portal (support tickets for bulk import, query redirects or nginx directives), and headers such as HSTS that need a shell, an admin or an extension, with duplicates when two layers set them.

### Cited Findings
- cPanel redirects are ignored under WordPress because they are appended after the `[L]`-terminated WordPress block. Hosts tell users to edit `.htaccess` by hand or install a plugin. — [InMotion Hosting](https://help.inmotionhosting.com/hc/en-us/articles/14609412204183-cPanel-Redirects-Not-Working-in-WordPress) (search snippet), [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)
- cPanel redirects cannot be edited, only deleted and created again. — [cPanel docs](https://docs.cpanel.net/cpanel/domains/redirects/)
- Support tickets as the only path: WP Engine bulk import "requires contacting WP Engine Support", and 302s are converted to 301 on import. Kinsta query-string redirects need support. On shared Plesk, nginx directives must be requested from support. — [WP Engine](https://wpengine.com/support/redirect/), [Kinsta](https://kinsta.com/docs/redirect-rules/), [Rebel.ca](https://support.rebel.ca/hc/en-us/articles/55658433339291-How-to-Request-Custom-Nginx-Directives-on-Plesk-Hosting) (search snippet)
- Kinsta's changelog sells its redirect UI as managing redirects "without having to contact our support team". — [Kinsta changelog](https://kinsta.com/changelog/redirect-rules-mykinsta/) (search snippet)
- Redirect plugins: Redirection's readme claims it handles "a few redirects to sites with thousands" with no noticeable slowdown (vendor claim). UpdraftPlus reports "the only issue we've ever had with it is too much logging". One support thread shows 4,227,487 rows of 404 logs and 5,142,793 rows in `wp_redirection_logs`, with the host threatening deletion over database size. — [Redirection plugin](https://wordpress.org/plugins/redirection/) (search snippet), [UpdraftPlus](https://updraftplus.com/?p=94143) (search snippet), [support thread mirror](https://remarpro.com/support/?p=4739358) (search snippet)
- Opinion pieces: PHP redirects run on every hit (an example of 2,000 redirects on 500,000 monthly visits as the reason to move them to the server). WPJohnny claims half a second to a second gained on slow servers by dropping the plugin (opinion, not isolated). A martech author traced MySQL load to a redirect cache table under attack with pattern redirects. — [woorkup](https://woorkup.com/wordpress-redirects), [WPJohnny](https://wpjohnny.com/dont-use-wordpress-redirection-plugin/), [martech.zone](https://martech.zone/wordpress-redirect-plugin-cache-vulnerability/) (search snippets)
- WP Engine itself recommends the Redirection plugin above about 1,000 redirects because of portal performance, so the host and the owners point in opposite directions. — [WP Engine](https://wpengine.com/support/redirect/)
- Cached 301 mistakes: a 301 without cache directives is cached until the browser cache is cleared. Fixes are DevTools "Disable cache" or a full cache clear. One report says no-cache headers did not stop Chrome caching a 301, so it advises 302/307 when the target may change. A 2019 SEO test found no browser caching 301s, contradicting the others, so current behaviour is unsettled. — [neilwithdata](https://www.neilwithdata.com/chrome-redirect-forget), [Stack Overflow mirror](https://dev.library.kiwix.org/content/stackoverflow_en_nopic_2021-08/questions/9130422/how-long-do-browsers-cache-http-301s), [codenote.net](https://codenote.net/ja/posts/4666/), contradicted by [Jaywing](https://www.jaywing.com/views/opinion/do-modern-browsers-still-cache-301-redirects/) (search snippets)
- Platforms warn about it themselves: Forge calls changing a permanent redirect "bad practice", cPanel tells visitors to clear caches, and the Cloudflare migration guide's third-party commentary advises testing with 302 first. — [Forge](https://laravel.com/forge/docs/sites/network), [cPanel](https://docs.cpanel.net/cpanel/domains/redirects/), [stackharbor](https://stackharbor.com/en/knowledge-base/cf-page-rules-to-modern-rules-migration/) (search snippet)
- Migrations: providers who "say they will take care of 301 redirects ... then just redirect all of your old URLs to the homepage". Soft 404s from odd pages redirected to the homepage. Unmapped pages becoming 404s. Chains compounding losses. — [The Drum](https://www.thedrum.com/opinion/making-the-move-site-migration-without-the-tears), [SEOZoom](https://www.seozoom.com/?p=5639) (search snippets)
- Conflicts between layers: forced-HTTPS in cPanel plus an SSL plugin loop. HestiaCP's hard-coded HTTPS 301 overrides the user's chosen 302 on http://. WordPress's own `_wp_old_slug` redirects confuse WP Engine users. Kinsta warns that a missing `$` loops. — [Krystal](https://help.krystal.io/web-hosting/redirection-not-working-or-unexpected-redirection-occurring) (search snippet), [HestiaCP forum](https://forum.hestiacp.com/t/redirect-users-to-a-custom-domain-or-web-address-you-cant-use-code-302/18233), [WP Engine](https://wpengine.com/support/redirect/), [Kinsta](https://kinsta.com/docs/redirect-rules/)
- Security headers: Plesk users lack HSTS preload in SSL It! and add it by hand, and get duplicate HSTS when panel and site both send it. HestiaCP users editing templates for www handling. Forge offers no IP rules. Netlify headers cannot be scoped to branches or deploy contexts. — [Plesk forum](https://talk.plesk.com/threads/ssl-it-and-hsts-options.371568), [Plesk forum](https://talk.plesk.com/threads/ssl-it-hsts-appearing-twice-in-headers.352417/post-959417) (search snippets), [HestiaCP forum](https://forum.hestiacp.com/t/redirecting-www-to-non-www-nginx-only/1946), [Forge](https://laravel.com/forge/docs/sites/network), [Netlify headers](https://docs.netlify.com/manage/routing/headers/)
- Staging leaks: a leftover `Disallow: /` or `noindex` carried from staging to production "can deindex an entire site", and the advice is to check production response headers for `X-Robots-Tag: noindex`. Blocking staging in robots.txt prevents bots from seeing the header. — [GeoRadar glossary](https://georadar.tenten.co/en/glossary/staging-noindex), [Polemic Digital](https://polemicdigital.com/protect-your-staging-environments) (search snippets)

### Inferences
- The owner-side needs map to a short list: (1) a redirect that verifiably works without knowing the application's own rewrites, (2) a way to test before going permanent (start with 302 or 307, then promote), (3) bulk import after a migration with a report of chains, loops and duplicates, (4) export so redirects survive the next host move, (5) security headers and a staging `noindex` without a shell or a ticket, (6) no duplicate header when the application already sends one.
- An agent-driven API can do things no panel does today: refuse a rule whose target is itself redirected (a chain) or that loops back to its source, warn when a permanent rule replaces an earlier permanent rule with a different target (the cached-301 hazard), and warn when every source of a bulk import points to `/` (the soft-404 pattern Google names).
- A staging `noindex` is a per-site, host-scoped header (Vercel's advice) and must not be copied to production. A typed `X-Robots-Tag` rule tied to a site, with health warning when a production-looking site serves `noindex` site-wide, answers the "launch mistake" complaint.
- Keeping redirects in the server and not the application removes the plugin logging and PHP cost owners complain about, and lets the agent export them with the site (agensio's managed site file and spec JSON).

### Gaps
- No Reddit or WordPress.org thread was fetched directly (search snippets only). The complaint evidence is mostly host KBs and blogs.
- No quantitative benchmark of a redirect plugin at N rules was found. The performance claims are vendor or opinion.
- No direct evidence was found that panels lose redirects in migrations because they lack export (the inference rests on Kinsta offering export and WP Engine requiring support for bulk).

## 4. What makes a redirect "SEO-safe" per Google Search Central, and how platforms present it

### Takeaway
Google treats 301 and 308 as strong canonical signals and 302, 303 and 307 as weak ones (the source may stay indexed). It recommends server-side permanent redirects to the most relevant final destination, no chains (crawlers follow at most 10 hops), keeping redirects at least a year, and not redirecting everything to the homepage. For temporary unavailability it recommends a 503 with Retry-After for at most a few days, not a redirect or `noindex`. Platforms present this as "permanent = SEO" (cPanel, Plesk's "SEO-safe 301", Kinsta "link juice"), and few warn about chains or blanket homepage redirects.

### Cited Findings
- 301 and 308 are permanent: the target becomes canonical. "Use permanent redirects when you're sure that the redirect won't be reverted." 302, 303 and 307 are temporary: Googlebot follows them, but the target "might still be indexed if other canonicalization signals are present". Server-side redirects are the method most likely to be interpreted correctly. A 0-second meta refresh counts as permanent, a delayed one as temporary. JavaScript redirects only if nothing else is possible. — [Google: Redirects and Google Search](https://developers.google.com/search/docs/crawling-indexing/301-redirects)
- "By default, Google's crawlers follow up to 10 redirect hops". 308 is "Equivalent to 301" and 307 "Equivalent to 302". Google treats them the same, but advises using the semantically right code for other clients. — [Google: HTTP status codes and network errors](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)
- Site moves: map every old URL to a new one, use "HTTP permanent redirects if possible, such as 301 and 308", avoid sending many old URLs to an "irrelevant single URL destination, such as the home page", "we advise redirecting to the final destination directly", keep redirects "generally at least 1 year", update internal links, submit a new sitemap. Change of Address only for domain changes, not HTTP to HTTPS or www. — [Google: Site moves with URL changes](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)
- Maintenance or pauses: serve "a 503 HTTP response status code instead of all content" for short outages, use "the retry-after HTTP header", and disable the whole site only "for a very short period of time (a few days at most)". "Don't block the website by returning 403, 404, 410", `noindex` and `X-Robots-Tag` have the same removal effect, and "Don't return a 503 HTTP response status code for the robots.txt file". — [Google: Pause or disable a website](https://developers.google.com/search/docs/crawling-indexing/pause-online-business)
- Persistent 5xx: crawling slows, and URLs that "persistently return a server error" are eventually dropped. All 4xx except 429 are treated the same (404 vs 410 no different). — [Google: HTTP status codes](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)
- `noindex` via `<meta name="robots">` or the `X-Robots-Tag` header has the same effect and works for PDFs and images. It only works if the page is not blocked by robots.txt ("the crawler will never see the noindex rule"). — [Google: Block indexing with noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing)
- Vercel's presentation: a permanent, hostname-scoped redirect "preserving each page's path and query string", or `rel=canonical`, or host-scoped `X-Robots-Tag: noindex` for staging. It notes that Google "doesn't recommend noindex to select a canonical URL", and gives a curl check that expects one 308 with path and query kept. — [Vercel: Redirects](https://vercel.com/docs/routing/redirects)
- How panels phrase it: cPanel says 301 makes search engines update their records and 302 has no effect on them. Plesk labels its checkbox "Permanent SEO-safe 301 redirect from HTTP to HTTPS" and warns that preferred domain None splits rankings. Kinsta says 301 sends "traffic, backlinks, and 'link juice'" to the new URL. — [cPanel](https://docs.cpanel.net/cpanel/domains/redirects/), [Exabytes on Plesk](https://support.exabytes.co.id/en/support/solutions/articles/14000131819-enable-http-to-https-redirection-in-plesk) (search snippet), [Websavers on Plesk](https://clients.websavers.ca/whmcs/knowledgebase/11/My-website-will-not-work-with-the-www-prefix.html) (search snippet), [Kinsta knowledge base](https://kinsta.com/knowledgebase/redirect-rules/) (search snippet)
- Vercel's own status descriptions say 307 and 308 "[do] not affect SEO and search engines will treat them as normal redirects", which is looser than Google's strong/weak split. — [Vercel: Redirects](https://vercel.com/docs/routing/redirects)
- Netlify flattens chains for its conditional rules ("they'll get redirected directly to /israel/he in one step"). — [Netlify: Redirect options](https://docs.netlify.com/manage/routing/redirects/redirect-options/)

### Inferences
- An "SEO-safe" check an agent can run before applying a redirect set: permanent status for a move (301 or 308; 308 also keeps the method, which matters for POST endpoints), no target that is itself a redirect source (chain), no loop, no many-to-homepage mapping unless confirmed, path remainder and query kept for section or domain moves, and a reminder to keep rules at least a year. The MCP text can state these as Google's rules, cited.
- Maintenance should not be modelled as a redirect: Google's guidance is a 503 with Retry-After for a few days at most, with robots.txt still served 200. If agensio offers a maintenance switch it belongs with status answers, not redirect rules, and should exempt `/robots.txt` and the ACME path.
- Staging `noindex` should be a header (`X-Robots-Tag: noindex`) on the staging host, not a robots.txt `Disallow`, because a robots.txt block hides the `noindex` from Google. The typed header rule plus a health check for "production site sends noindex" covers both the need and the launch-mistake risk.
- Requiring an explicit status in agensio's redirect rule (no default) fits Google's "use permanent only when you're sure it won't be reverted" and the cached-301 complaints. The MCP description can tell the agent to propose 302 or 307 while testing and switch to 301 or 308 once confirmed.

### Gaps
- Google's position on how long a 302 can stay before being treated like a 301 is not on the fetched pages.
- No official Google statement on 303 beyond being grouped with 302.
- How Bing treats 307/308 vs 301/302 was not researched.
