# What administrators struggle with when configuring response headers and redirects (real reports, state as of 2026-10-12)

Method and conventions. Vote and view counts for Server Fault (SF) and Stack Overflow (SO) questions come from the Stack Exchange API (`api.stackexchange.com/2.3`, queried 2026-10-12), because the sites themselves cannot be fetched from here. They are written as "score / views, date asked". Most top-voted questions are from 2009-2017, because votes accumulate over time. Where a newer report exists it is cited too, and the age of each source is given. "Search summary" marks a claim seen only in a search engine's summary of the page, because the page itself could not be fetched; treat those as unverified. RFC 9110 is quoted from the copy in this repository (`docs/rfc/rfc9110.txt`). Each section ends with a "Proposal check" under Inferences. It says whether agensio's proposed typed rules avoid each pitfall, and what they should add. The proposal under review has two parts. Header rules: `set` replaces the application's field, `default` sets a field only when it is absent, and `remove` deletes it; rules apply to every answer including errors, and all matching rules combine shortest path first. Redirect rules: `from`, `match` prefix or exact, `to`, a required status, the path remainder and query kept by default, joined so that a prefix redirect cannot produce `//host`.

Context: agensio's current `add_headers` adds fields on 2xx and 3xx answers only ("on 200 and 304" for static locations, `docs/configuration.md` lines 965 and 1412-1414). A location holding only `add_headers` joins the preset's location at the same path. HSTS is deliberately not automatic (`docs/configuration.md` around line 1839).

## 1. nginx add_header inheritance, `always` and error answers, duplicates between application and server, Apache's onsuccess/always tables

### Takeaway
The most reported header problem is headers silently vanishing. In nginx, one `add_header` in a nested block drops every inherited one. Without `always`, headers are skipped on 4xx and 5xx answers. The cause is hard to see when `try_files` moves the request into another location. The second most reported problem is duplicates. nginx `add_header`, Apache `Header set` in the default table, and a panel's or platform's default all append next to the application's own field instead of replacing it. Browsers then reject `Access-Control-Allow-Origin: *, *`, scanners flag two HSTS fields, and RFC 6797 makes the UA honour only the first one. Fixing it takes a separate "hide" step (`proxy_hide_header`, `Header onsuccess unset`) or a third-party module. nginx added an opt-in `add_header_inherit merge` only in 1.29.3 (October 2025).

**Apache: two tables, `always` is not a superset of `onsuccess`**
- mod_headers: the condition "determines which internal table of responses headers this directive will operate against: `onsuccess` (default…) or `always`… `always` is not a superset of `onsuccess` with respect to existing headers". The CGI and `mod_proxy_fcgi` headers "are in the table corresponding to `always` and not in the default table". For a PHP backend that sends `X-Foo: bar`, `Header set X-Foo: baz` "ends up in the wrong result, namely having the header duplicated with both values". The documented workaround is `Header onsuccess unset X-Foo` followed by `Header always set X-Foo "baz"`. For a locally generated non-2xx answer such as a redirect, "only the table corresponding to `always` is used". — [Apache mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html)
- mod_headers also documents order-dependent processing ("These two directives have a different effect if reversed"). It has a `setifempty` action ("set, but only if there is no previous header with this name"), with a caveat that Content-Type may not be visible yet. It also has a `merge` action that appends only when the value is not already in the comma list. — [Apache mod_headers](https://httpd.apache.org/docs/2.4/mod/mod_headers.html)
- SF "Header always edit Set-Cookie not working", 12,235 views, 2020-11-25 — [SF 1043924](https://serverfault.com/questions/1043924/header-always-edit-set-cookie-not-working)

### Inferences
- Two different user models are colliding. nginx appends (and loses inherited fields), Traefik overwrites, and Apache appends or replaces depending on which internal table the field lives in. Administrators cannot predict which one they get, so most fixes are "find every layer that sets it, keep one".
- The failure is silent in every server. No server warns that an inherited field was dropped or that the answer now carries two copies. People learn it from a browser console, securityheaders.com or a scanner report.
- "Applied to errors" is right for security headers (HSTS, CSP, XFO, nosniff) and for CORS on error bodies. It is wrong for cache lifetime headers. The Caddy case shows a year-long `immutable` on a 404 is a real outcome.

**Proposal check**
- Inheritance trap: avoided. "All matching rules combined shortest path first" is nginx's `add_header_inherit merge` as the only behaviour. Add one rule: for a field named by more than one matching rule, the longest path wins (a deeper `remove` cancels a shallower `set`). Also make `path_check` print the final field list with the rule (and path) that produced each field. The SO and SF threads are about not seeing where a header came from.
- `always` trap: avoided, but over-applied. Add a status scope to each rule (`on = "all" | "success"`, or a typed exception). Default it to success-only for `Cache-Control`, `Expires` and similar cache fields, or refuse an `immutable` or long `max-age` rule without an explicit `on`.
- Duplicate trap: avoided by `set` replacing the application's field and `default` filling only when absent. Field names must match case-insensitively (the Netlify case). `set` must also remove every copy the application sent, not just the first.
- Add an application-side duplicate check that needs no rule. When a proxied or PHP answer carries the same singleton security field twice (HSTS, XFO, ACAO, CSP), log it once and report it in health with the fix "add a `set` rule or remove it from the application". This turns the HestiaCP/Seckit case from a scanner finding into a server finding.
- Refuse or flag list-valued fields where `set` semantics surprise. Two CSP fields are both enforced, so an application's CSP plus a `default` CSP is not a duplicate but a narrowing. `Vary` and `Link` legitimately combine, so `Vary: Origin` needs an append/merge op (Apache's `merge`).

### Gaps
- No count was found of how many production nginx configurations still lose headers through inheritance; Detectify's 2020 corpus study did not measure `add_header`.
- The nginx trac ticket #754 discussion and the Arch Linux MR could not be read in full.

## 2. Security headers: HSTS mistakes, CSP breakage, X-Frame-Options vs frame-ancestors, setting them once per site, and scanners driving demand

### Takeaway
HSTS is the field people most regret. Its effect outlives the configuration, because browsers cache it for `max-age` and the preload list takes months to leave. `includeSubDomains` breaks plain-HTTP or third-party subdomains, and it must never be sent over plain HTTP. CSP is widely deployed in a weakened form: 91 % of policies keep `unsafe-inline`. Strict policies break sites, as the SO questions with up to a million views show. X-Frame-Options lives on with confused values (ALLOW-FROM is ignored, duplicates conflict), although CSP `frame-ancestors` supersedes it. Scanners (securityheaders.com with 250 M scans by 2023, the MDN HTTP Observatory since July 2024) are what make administrators touch these headers at all.

The Shields.io grade badge broke with the move (search summary) — [MDN blog](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch), [MDN Observatory FAQ](https://developer.mozilla.org/en-US/observatory/docs/faq), [shields issue 10396](https://github.com/badges/shields/issues/10396)
- The HestiaCP duplicate-HSTS thread started from a securityheaders.com scan — [HestiaCP forum 12283](https://forum.hestiacp.com/t/solved-strict-transport-security-in-doble-declaration/12283)

### Inferences
- Header grades change over time (X-XSS-Protection dropped in 2019, Feature-Policy renamed Permissions-Policy, the Observatory rescored in 2024). A typed header vocabulary needs a maintained list of deprecated fields and values, or agents will keep adding fields the scanners no longer want.
- Setting security headers "once for the whole site" is the request behind most of these threads, and it is exactly what nginx's inheritance breaks.

**Proposal check**
- Once per site: the `/` rule plus shortest-path combination does this directly, and "every answer including errors" covers the scanner case (scanners hit `/` and error pages).
- HSTS: `set` alone does not avoid the irreversible mistakes. Add the following:
  - Typed HSTS validation: drop the field automatically on plain-HTTP answers (RFC 6797 7.2), so a site-wide rule is safe on both listeners.
  - Refuse `preload` unless the user confirms in person (agensio already has `user_confirm` for pip installs). Warn on `includeSubDomains` while listing the subdomains of that domain that this server serves without TLS or does not serve at all (third-party CNAMEs).
  - Offer the hstspreload ramp, or at least warn when the first value set is a year or longer.
  - When an HSTS rule is removed, propose `max-age=0` for a period instead of silence.
- CSP: offer `Content-Security-Policy-Report-Only` as the first step. Warn that `default` plus an application CSP yields two enforced policies. Refuse `frame-ancestors` in a meta-only context (not applicable to agensio).
- XFO: refuse `ALLOW-FROM`, and suggest `frame-ancestors` when an exception for one path is wanted (deeper rule removes XFO and sets a CSP `frame-ancestors`).
- Deprecated fields: warn on `X-XSS-Protection` (deprecated by MDN; dropped from the A+ grade) and `Feature-Policy` (use Permissions-Policy).

### Gaps
- The official hstspreload.org removal page text was not fetched (only its summary); the 6-12 weeks figure is unverified.
- No first-hand data was found on how many sites broke after a CSP rollout; the evidence is SO question volume and the Almanac's `unsafe-inline` share.
- The current securityheaders.com grading criteria (2026) were not checked directly.

## 3. CORS: per-path headers, preflight OPTIONS answered with 405 or without headers, credentials with a wildcard, multiple origins

### Takeaway
CORS produces the largest-volume questions of the whole topic (2.6 M views for one preflight question). The server-side causes repeat. Preflight OPTIONS reaches an application or location that answers 405 or 404, or answers without the headers because they were not `always`. The header is set twice ("`*, *`") by framework and server. People also want several origins in one header, which is impossible: the server must echo one allowed origin and add `Vary: Origin`. Credentials forbid `*`.

### Inferences
- A plain header-rule system cannot express "several allowed origins". Every administrator who tries it either writes `*` (which breaks with credentials) or reflects `Origin` unchecked, which is the classic CORS misconfiguration.
- Preflight failures are mostly about routing. OPTIONS falls into a location or application that does not handle it. That is a method-policy problem, not a header problem.

**Proposal check**
- Duplicates: `set` replacing the application's ACAO avoids "`*, *`".
- Per-path: the path rules give per-API-prefix CORS.
- Not covered: multiple origins, `Vary: Origin`, credentials, preflight. Add a typed `cors` rule, not free-form fields. It would take an allowed-origins list (exact origins, no `null`), credentials as a boolean (refused with `*`), methods, request headers and max-age. The server echoes the matching origin, appends `Vary: Origin`, and answers OPTIONS preflights itself (204) on that path before access rules, auth and the location's method policy (agensio's static locations answer OPTIONS with 204 + Allow today, and other methods with 405). Answers to a disallowed origin get no CORS fields.
- Free-form `set Access-Control-Allow-Origin` should then be refused, or warned, so the typed rule stays the only way.

### Gaps
- No public data was found on how many sites reflect `Origin` without checking it; PortSwigger's research on that (2016) predates the date window and was not fetched.

## 4. Cache headers per path, and X-Robots-Tag noindex leaking from staging or being forgotten

### Takeaway
Cache headers are set per path (long and immutable for hashed assets, short or none for HTML). They fail in two ways. They are lost by inheritance, or they are applied to answers that must not be cached, such as a 404 kept for a year. `X-Robots-Tag: noindex` is a staging safeguard that ends up in production after a deploy or plugin change. Nothing errors, and it shows only as lost search traffic days later.

### Cited Findings

- noindex is environment state, not site configuration. It belongs to a site marked staging, and it should be visible in health when the site looks live (real domain, valid certificate).

**Proposal check**

- X-Robots-Tag: a `set` rule on `/` works, but nothing warns when it is forgotten. Consider a typed `staging = true` site flag that implies noindex and is shown in `site_show`, so removing it is one field change rather than a hunt.

## 6. Redirects: cached 301s, loops, chains, query strings, encoding, open redirects, regex debugging, evaluation order, testing, bulk redirects

### Takeaway
The most-voted redirect complaints are about irreversibility and loops. Browsers cache a 301 with no expiry unless told otherwise, so a mistaken 301 cannot be undone from the server. Loops come from HTTP/HTTPS detection behind a proxy or CDN (Cloudflare Flexible SSL, ELB, `X-Forwarded-Proto`) and from overlapping www/apex/trailing-slash rules. Query strings are appended, dropped or doubled depending on each server's quirks (`?` suffix in nginx and mod_rewrite, the QSD flag). Redirects built from decoded paths (`$uri`) allow CRLF header injection. Slash-normalising redirects keep producing open redirects through `//host` and `/\host`, in Django 2018, Tomcat 2018, fastify-static 2021, Astro 2025 and the MCP Registry 2026. Regex rewrite debugging needs trace logs. Large migrations want exact-match tables, not thousands of regexes.

**Chains**
- hstspreload requires an HTTP-to-HTTPS redirect "on the same host" first, so `http://example.com` → `https://www.example.com` must become two hops — [hstspreload.org](https://hstspreload.org/); see also "HSTS and double redirect" — [SF 930368](https://serverfault.com/questions/930368/hsts-and-double-redirect)
- Google's crawlers reportedly follow up to 10 hops (secondary citations of Google's crawling docs; not verified on developers.google.com) — [frontendchecklist](https://frontendchecklist.io/rules/seo/redirect-chain). **Query strings lost or doubled**
- SO "htaccess 301 redirect - Remove query string (QSA)", 50 / 72,212, 2014: a trailing `?` on the substitution strips the old query; Apache 2.4.0 added the `QSD` flag — [SO 21118511](https://stackoverflow.com/questions/21118511/htaccess-301-redirect-remove-query-string-qsa)
- nginx rewrite: "If a replacement string includes the new request arguments, the previous request arguments are appended after them. If this is undesired, putting a question mark at the end of a replacement string avoids having them appended" — [nginx rewrite module](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html)
- Apache `Redirect` keeps both path remainder and query: `/service/foo.pl?q=23&a=42` → `http://foo2.example.com/service/foo.pl?q=23&a=42`. "Only complete path segments are matched", so `/service` does not match `/servicefoo.txt`. For an Alias, a trailing `/` on the URL-path requires one in the request. — [Apache mod_alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html)
- SF "Using $request_uri in a redirect as query string parameter", 662 views, 2017 — [SF 875400](https://serverfault.com/questions/875400/using-request-uri-in-a-redirect-as-query-string-parameter); "nginx redirect based on $request_uri", 14,760 views — [SF 838866](https://serverfault.com/questions/838866/nginx-redirect-based-on-request-uri)

**Encoding: decoded paths in Location ($uri vs $request_uri), CRLF**
- Detectify (2020-11-10), after analysing "almost 50,000 unique Nginx configuration files downloaded from GitHub": "`$uri` is commonly used when creating redirects in the Nginx configuration which results in a CRLF injection". `return 302 https://example.com$uri;` with `%0d%0a` in the request injects a response header — [Detectify](https://blog.detectify.com/2020/11/10/common-nginx-misconfigurations/). The remediation is `$request_uri`, "the original, unmodified request URI" — [Acunetix](https://www.acunetix.com/vulnerabilities/web/nginx-redirect-header-injection/)
- Apache CVE-2019-10098: "Redirects configured with mod_rewrite that were intended to be self-referential might be fooled by encoded newlines and redirect instead to an an unexpected URL". The page lists it with update 2.4.41 (2019-08-14), and its affects-list includes 2.4.39, inconsistent with the "fixed in 2.4.39" heading the fetch reported. CVE-2020-1927: "some mod_rewrite configurations vulnerable to open redirect" (2.4.0-2.4.41, fixed 2.4.42, 2020-04-01). — [Apache httpd 2.4 vulnerabilities](https://httpd.apache.org/security/vulnerabilities_24.html). CERT-EU's advisory gives the mitigation: anchor captures used as back-references, and prefix self-referential redirects with `/` or the scheme, host and port (search summary) — [CERT-EU 2020-019](https://cert.europa.eu/publications/security-advisories/2020-019)
- Apache CVE-2024-38474 (2.4.60, 2024-07-01): "Substitution encoding issue in mod_rewrite… Some RewriteRules that capture and substitute unsafely will now fail unless rewrite flag 'UnsafeAllow3F' is specified". CVE-2024-38475: unsafe first-segment substitutions now need `UnsafePrefixStat`. CVE-2023-25690 (2.4.56): `RewriteRule "^/here/(.*)" "http://example.com:8080/elsewhere?$1" [P]` allows request splitting. — [Apache httpd 2.4 vulnerabilities](https://httpd.apache.org/security/vulnerabilities_24.html)

**Open redirects from slash handling and path joins (CVE examples)**
- Django CVE-2018-14574 (1.11.15 and 2.0.8, 2018-08-01). With `CommonMiddleware` and `APPEND_SLASH`, and a URL pattern accepting any path ending in a slash, a crafted URL redirected off-site. The fix: "CommonMiddleware now escapes leading slashes to prevent redirects to other domains" (`escape_leading_slashes`, `//` → `/%2F`). — [Django 2.0.8 release notes](https://docs.djangoproject.com/en/5.2/releases/2.0.8), [Red Hat CVE page](https://access.redhat.com/security/cve/CVE-2018-14574)
- Apache Tomcat CVE-2018-11784: when the default servlet redirected a directory request (`/foo` → `/foo/`), "a specially crafted URL could be used to cause the redirect to be generated to any URI of the attackers choice". Affected 9.0.0.M1-9.0.11, 8.5.0-8.5.33, 7.0.23-7.0.90. — [Tenable CVE-2018-11784](https://tenable.com/cve/CVE-2018-11784)
- fastify-static CVE-2021-22963 (October 2021): `redirect: true` plus a double slash followed by a domain redirected off-site; fixed in 4.2.4, with a related advisory fixed in 4.4.1 — [GHSA-p6vg-p826-qp3v](https://github.com/advisories/GHSA-p6vg-p826-qp3v), [GHSA-pgh6-m65r-2rhq](https://github.com/advisories/GHSA-pgh6-m65r-2rhq)
- Astro CVE-2025-54793 (GHSA-cq8c-xv66-36gw, 2025-08-07). The trailing-slash redirect sent `Location: //target.domain/subpath/` for `https://example.com//target.domain/subpath/`. - MCP Registry CVE-2026-44427 (2026-05-14). `TrailingSlashMiddleware` turned a request for `//evil.com/` into `Location: //evil.com`; affected 1.1.0-1.7.4, fixed 1.7.5. — [OSV CVE-2026-44427](https://osv.dev/vulnerability/CVE-2026-44427)
- Express CVE-2024-29041 (fixed 4.19.2). `res.location()`/`res.redirect()` encoded user URLs with `encodeurl`, so a malformed URL passed an allow-list but the browser read it differently. The fix advice is to parse with `new URL` and check the parsed host — [NVD CVE-2024-29041](https://nvd.nist.gov/vuln/detail/CVE-2024-29041)
- Backslash: WHATWG-compliant browsers normalise `\` to `/` for special schemes, so `/\evil.com` is protocol-relative. 2026 advisories show validators that blocked `//` but not `/\`: Saltcorn CVE-2026-42259, Probo CVE-2026-49820 (`/../\evil.com` cleaned by Go's `http.Redirect` into `/\evil.com`), `@astrojs/node` 11.0.2 (a static handler echoed `/\` into a 301 Location) and HTTP.jl JLSEC-2026-617 (fix: collapse any leading run of `/` or `\` into one `/`). **Order of evaluation**
- Apache: "`Redirect` directives take precedence over `Alias` and `ScriptAlias` directives, irrespective of their ordering"; within each kind "the first match taking precedence"; Redirect inside `<Location>` beats Redirect with a URL-path — [Apache mod_alias](https://httpd.apache.org/docs/2.4/mod/mod_alias.html)
- nginx: rewrite directives at server level run sequentially, then a location is selected, then its rewrite directives run, repeated up to 10 times — [nginx rewrite module](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html). The SO 18450310 case (headers in `location /` lost because `try_files` moved the request into the PHP location) is the header-side version of the same confusion — [SO 18450310](https://stackoverflow.com/questions/18450310/nginx-add-header-not-working)

**Testing habits**
- The recurring advice: `curl -sIL https://example.com` to see each hop's Location, a private window, DevTools "Disable cache", and purging the CDN, because browsers and CDNs cache redirects (search summaries) — [stackharbor](https://stackharbor.com/en/knowledge-base/cffix-err-too-many-redirects-flexible-ssl/), [SO 16154672](https://stackoverflow.com/questions/16154672/how-long-does-chrome-remember-a-301-redirect)

**Bulk redirects after migrations**
- nginx mailing list, "map v/s rewrite performance" (2014): Igor Sysoev answered "Exact locations are faster"; Francis Daly listed rewrite, exact location and map as "increasingly more efficient" but said to load-test (search summary) — [nginx list 2014-04](https://mailman.nginx.org/pipermail/nginx/2014-April/043035.html), [2014-03](https://mailman.nginx.org/pipermail/nginx/2014-March/042809.html); "Nginx RP: a lot of rewrite rules" (2013) — [nginx list](https://mailman.nginx.org/pipermail/nginx/2013-April/038408.html)
- Large maps need `map_hash_bucket_size`/`map_hash_max_size` tuning (secondary, 2025 blog) — [oneuptime](https://oneuptime.com/blog/post/2025-12-16-nginx-rewrite-urls-parameters/view). An Adobe AEM thread on "thousands of redirects" says large rule sets cost CPU, latency and memory, and suggests moving redirects to the CDN (search summary) — [Adobe community](https://experienceleaguecommunities.adobe.com/adobe-experience-manager-sites-8/handle-thousands-of-redirects-248377)

### Inferences
- Every open-redirect CVE above has the same shape. Slash-normalisation or a "keep the remainder" join produced a Location whose first two characters are `//` or `/\`. Guarding the join is necessary. The final Location string should also be checked, because that is what the browser parses.
- Loops are rarely inside one rule. They come from two layers each "forcing HTTPS" (CDN plus origin, server plus WordPress plugin) or from a redirect whose target matches its own `from`.
- The "301 is forever" problem is solvable server-side for future mistakes: a 301/308 with `Cache-Control: max-age=N` expires (SO 9130422 top answer).

**Proposal check**
- Required status: good, because it removes the server's silent default (Apache 302, nginx `permanent` 301). Additions:
  - Have the agent-facing text recommend 302/307 while testing.
  - Consider sending `Cache-Control: max-age=<bounded>` on 301/308 by default, so a wrong permanent redirect expires (for example a day; configurable). Add a typed `cache` field on the rule.
  - Refuse or warn on 301/302 for a `from` path that receives POSTs (form endpoints, `xmlrpc.php`, APIs), suggesting 308/307.
- Path remainder and query kept by default: matches Apache `Redirect` and avoids "query lost". Add:
  - A `query = "keep" | "drop"` field (QSD).
  - A defined merge when `to` has its own query: append the request's with `&`, never a second `?`. This avoids "doubled".
  - Segment-boundary prefix matching (`/old` must not match `/oldies`, as Apache does). Define the slash join: `from = "/a/"` with `to = "/b"` must not produce `/bc`. Normalise to one slash at the join.
- Encoding: build Location from the raw (still percent-encoded) target remainder, never the decoded path, and refuse CR, LF and other control characters at load and per request. This avoids the `$uri` CRLF class (Detectify) and the CVE-2019-10098/2020-1927 newline class.
- Open redirect: "joined so a prefix redirect cannot produce //host" covers Django, Tomcat, fastify-static, Astro and MCP Registry. Extend it:
  - Collapse a leading run of `/` and `\` in the remainder.
  - Check the final Location: if relative, it must start with exactly one `/` followed by neither `/` nor `\`; if absolute, its host must be the one configured in `to`.
  - Refuse `\` in the remainder outright, or percent-encode it (`%5C`).
  - A fuzz target over (from, to, request path) asserting that the Location's origin always equals `to`'s origin would hold this, in the agensio habit of fuzzing parsers.
- Loops: at validation, refuse a rule whose `to` (same site) matches its own `from`, such as prefix `/a` to `/a/b`, which grows forever. Also refuse a cycle among a site's rules and across agensio sites on the same server (agensio already refuses `redirect = "https"` on a TLS site). At run time, behind `trusted_proxies`, decide "is this request HTTPS" from `X-Forwarded-Proto` (as agensio already does for FastCGI `HTTPS`), so an https redirect behind a CDN does not loop. Health could report a site whose `redirect = "https"` sees only plain requests from a CDN range (Cloudflare Flexible).
- Chains: when a rule's target is itself redirected by this server (another rule, `redirect = "https"`, the canonical-host site), warn and suggest the direct target, except the hop hstspreload requires.
- Regex debugging: no regex in the proposal is the main win. Keep it that way, and let `path_check` show which redirect rule matched and the exact Location for a given path and query.
- Order of evaluation: state it once and show it in `path_check`. Proposed: ACME challenge, then redirects, then refuse/access/auth, or the reverse; whichever is chosen, document it. A redirect before auth answers unauthenticated clients, which is usually wanted for moved paths but means a redirect can reveal the new location of a protected area. CORS preflight answering (section 3) needs its own fixed slot.
- Testing: an MCP/ctl `redirect_check` that follows the chain server-side across this server's sites, printing each hop, status and cache lifetime, would replace the `curl -sIL` plus private-window routine and see past browser caches.
- Bulk: exact-match rules in a hash map and prefix rules in the same structure the router uses (longest prefix first) keep lookup O(1) or O(depth), not linear in the rule count. Add a cap on the count and a bulk import (CSV of from, to, status) through the control plane.

### Gaps
- Google's current documented hop limit was not verified on developers.google.com.
- No authoritative source was found for "rewrite before auth" confusion in Apache (per-server vs per-directory mod_rewrite phases); it is a known pattern, but no report was fetched.
- WHATWG URL parsing also strips ASCII tab and newline inside URLs, which may allow `/<tab>/evil.com` variants; this was not verified in this session.
- The details of the 2026 backslash advisories (Probo, Saltcorn, HTTP.jl, `@astrojs/node`) were seen only through search summaries.

## 7. Hosting many tenants: one tenant's rule affecting others, panel-generated configuration overwritten

### Takeaway
On panels, the same header can be set in three or four layers (panel toggle, per-domain "additional directives", `.htaccess`, the application), so duplicates are the norm and the fix is always "find the other layer". Hand edits to generated files are overwritten on rebuilds and updates, so administrators resort to read-only files or global `conf.d` snippets that then apply to every tenant. HSTS `includeSubDomains` set by one party affects hosts run by others.

### Cited Findings
- Plesk KB (search summary): per-domain "Additional nginx directives" are stored in `vhost_nginx.conf` under `/var/www/vhosts/system/<domain>/conf`. Plesk says "additional nginx directives can be adjusted only for new domains by means of service plan settings. Otherwise, new directives can overwrite existing configuration and break websites' functionality". Settings meant to persist go into `/etc/nginx/conf.d/directives.conf`, that is host-wide. — [Plesk KB 12377958882455](https://support.plesk.com/hc/en-us/articles/12377958882455)
- Plesk forum: a `map` block fails in per-domain directives because `map` is valid only in the http context, so per-tenant needs end up in host-wide files — [talk.plesk.com 376979](https://talk.plesk.com/threads/map-directive.376979/); "Keep changes in nginx.conf" — [talk.plesk.com 350316](https://talk.plesk.com/threads/keep-changes-in-nginx-conf.350316/latest)
- cPanel community: "Unable to stop nginx .conf files from being rebuilt frequently" ("rebuilt every few days") — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/26854229656215-Unable-to-stop-nginx-conf-files-from-being-rebuilt-frequently); "Edit NGINX config or prevent it from resetting to default" — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/34146406521239-Edit-NGINX-config-or-prevent-it-from-resetting-to-default); `cpanel-proxy.conf` and `/users/USER.conf` "always overwritten when NGINX is updated", with a moderator suggesting a custom file in `/etc/nginx/conf.d` — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/19161255597207-NGINX-as-a-reverse-proxy-Cannot-override-cPanel-s-cpanel-proxy-conf-settings); after updating to v104, a reset that a user countered by making `nginx.conf` read-only — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/19162471808279-After-udpating-to-version-104-0-4-nginx-configuration-resetting) (all search summaries)
- HestiaCP: "Nginx config was overwritten independently" (title) — [HestiaCP forum](https://forum.hestiacp.com/t/nginx-config-was-overwritten-independently/10041); the panel's HSTS toggle plus Drupal Seckit producing two HSTS fields — [HestiaCP forum 12283](https://forum.hestiacp.com/t/solved-strict-transport-security-in-doble-declaration/12283)
- Plesk's three places for ACAO (Apache directives, nginx additional directives, `.htaccess`) — [Plesk KB 12377315860631](https://support.plesk.com/hc/en-us/articles/12377315860631-Error-in-browser-console-on-website-that-requests-content-from-another-website-hosted-on-Plesk-for-Linux-server-The-Access-Control-Allow-Origin-header-contains-multiple-values-but-only-one-is-allowed) (search summary)
- Platform default plus tenant value: Netlify's default HSTS duplicated by a tenant's `netlify.toml` — [Netlify answers 28179](https://answers.netlify.com/t/define-strict-transport-security-header-cause-duplicate-headers/28179)
- Cross-party HSTS: Chromium removal requests for subdomains CNAMEd to third-party services without certificates (search summary) — [Chromium CL 2306423004](https://codereview.chromium.org/2306423004)

### Inferences
- In nginx, a header set at `http{}` level as a host-wide default reaches every tenant's server block only while that block sets no `add_header` of its own. So a host default is silently lost for exactly the tenants that customise anything. This follows from the inheritance rule in section 1 and is not a separately reported incident.
- Panels that keep the raw directive grammar per tenant (Plesk additional directives, ISPConfig directives) both overwrite and leak. Typed per-site fields are the shape that avoids both.

**Proposal check**
- Overwrite: typed `headers`/`redirects` as site fields are data in the managed site file, regenerated by `site_update` from the spec, so nothing a tenant set is lost on regeneration. The root additions file stays the escape hatch. Define precedence between a typed rule and a root-additions `add_headers` at the same path (or refuse the overlap, as agensio refuses duplicate locations), so two layers never both set one field.
- Cross-tenant effect: per-site rules cannot reach another site. Remaining risks:
  - HSTS `includeSubDomains` on a site whose subdomains are other sites on this server (possibly other accounts): warn and list them, and require confirmation.
  - Any future server-wide header default: make it a `default` (only when absent) that a site's `set` or `remove` overrides, never an append.
- Visibility: `site_show` and `path_check` should list the effective headers with origin (preset, typed rule, root addition, application) for a path. The panel threads are all "which of the four layers set this".

### Gaps
- No report was found of one tenant's header rule leaking into another tenant's site on Plesk, cPanel or ISPConfig (as opposed to host-wide snippets applying to all); the cross-tenant risk above is inferred.
- The Plesk KB articles returned 403 to direct fetches; their quoted text comes from search summaries.
