# HTTP Basic authentication and delegated (forward) authentication in Caddy, Traefik, HAProxy, LiteSpeed/OpenLiteSpeed and h2o

Research date 2026-10-08. Versions current at that date: Caddy v2.11.7 (2026-10-03) ([releases](https://github.com/caddyserver/caddy/releases)); Traefik v3.7.14 and v2.11.58 (2026-10-06) ([releases](https://github.com/traefik/traefik/releases)); HAProxy configuration manual "version 3.5" (dev branch text; the Userlists/auth sections are long-standing) ([manual](https://docs.haproxy.org/dev/configuration.html)); OpenLiteSpeed v1.9.3 (2026-09-30) ([releases](https://github.com/litespeedtech/openlitespeed/releases)); h2o master (`htpasswd.rb` since 1.7) ([docs](https://h2o.examp1e.net/configure/basic_auth.html)). Source files were read on their `master` branches on 2026-10-08. Where a statement comes from reading source code rather than documentation, it is said so.

## Syntax and scoping; excluding a sub-path; ordering pitfalls

### Takeaway
Caddy, Traefik and HAProxy put Basic auth into their general request pipeline: a Caddy directive with a matcher, a Traefik middleware attached to a router, a HAProxy `http-request auth` rule behind an ACL. So excluding a sub-path is a matcher or routing question (`not path`, a second router with higher priority, an `allow` rule placed earlier). OpenLiteSpeed and LiteSpeed attach a named *realm* to a *context* (a URI prefix). h2o has no native directive: Basic auth is an mruby Rack handler that returns 399 to hand the request on. Ordering is the main trap. Caddy's directive order runs `rewrite`/`try_files` before `basic_auth`. HAProxy stops at the first `auth`. In Traefik, router priority defaults to rule length.

### Cited Findings
- **Caddy syntax**: `basic_auth [<matcher>] [<hash_algorithm> [<realm>]] { <username> <hashed_password> ... }`. The default algorithm is `bcrypt`, the other is `argon2id`. Example scoping: `basic_auth /secret/* { Bob $2a$14$... }` protects only `/secret/`. Before v2.8.0 the directive was named `basicauth`. — [Caddy basic_auth docs](https://caddyserver.com/docs/caddyfile/directives/basic_auth) ([source md](https://github.com/caddyserver/website/blob/master/src/docs/markdown/caddyfile/directives/basic_auth.md))
- **Caddy**: `basicauth` is still registered as a deprecated alias that logs a warning ("the 'basicauth' directive is deprecated, please use 'basic_auth' instead!"). The Caddyfile adapter accepts 0, 1 (algorithm) or 2 (algorithm, realm) arguments. — [caddyfile.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyfile.go)
- **Caddy**: usernames and hashes may use global placeholders such as `{env.*}`, which are replaced at config load; "any other text in braces is kept as-is". This came from commit "only replace known placeholders in basic auth credentials (#8017)" of 2026-09-26. — [basic_auth docs](https://caddyserver.com/docs/caddyfile/directives/basic_auth); [basicauth.go history](https://github.com/caddyserver/caddy/commits/master/modules/caddyhttp/caddyauth/basicauth.go)
- **Caddy JSON**: the Caddyfile directive compiles to handler `http.handlers.authentication` with provider `http.authentication.providers.http_basic`. Its fields are `hash` (`{"algorithm": ...}`), `accounts` (`username`, `password`), `realm` (default `restricted`) and `hash_cache`. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go); [JSON docs](https://caddyserver.com/docs/json/apps/http/servers/routes/handle/authentication/providers/http_basic/)
- **Caddy ordering**: the default directive order puts `method`, `rewrite`, `uri` and `try_files` *before* `basic_auth`, then `forward_auth`, `request_header`, `encode`, ..., `handle`, `route`, ..., `respond`, `reverse_proxy`, `php_fastcgi` and `file_server`. — [directives.go defaultDirectiveOrder](https://github.com/caddyserver/caddy/blob/master/caddyconfig/httpcaddyfile/directives.go)
- **Caddy**: Authentik's Caddy template wraps `reverse_proxy /outpost.goauthentik.io/*` plus `forward_auth` in `route { }`, commenting "directive execution order is only as stated if enclosed with route". — [Authentik Caddy template](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/_caddy_standalone.mdx)
- **Caddy exclusion tools**: the `not` matcher negates enclosed matchers (`@not-assets { not path /css/* /js/* }`). `client_ip <ranges...>` honours `trusted_proxies` and accepts `private_ranges`; `remote_ip` matches the immediate peer. — [Caddy request matchers](https://caddyserver.com/docs/caddyfile/matchers#not)
- **Traefik syntax**: middleware `basicAuth` with `users` (a list of `name:hashed-password`), `usersFile`, `realm` (default `traefik`), `headerField` and `removeHeader` (default false). If `users` and `usersFile` are both given they are merged and `users` takes precedence. On Kubernetes CRDs a `secret` is used instead of users/usersFile. In Docker labels every `$` of the hash must be doubled (`echo $(htpasswd -nB user) | sed -e s/\\$/\\$\\$/g`). — [Traefik basicAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/basicauth/) ([source md](https://github.com/traefik/traefik/blob/master/docs/content/reference/routing-configuration/http/middlewares/basicauth.md))
- **Traefik**: the users file is read once when the middleware is built. Blank lines and lines starting with `#` are skipped, and each line is split on `:` into exactly two parts. Since 2026-05-18 an empty user list fails the build ("no users found"). — [auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/auth.go); [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go); [commit history](https://github.com/traefik/traefik/commits/master/pkg/middlewares/auth/basic_auth.go)
- **Traefik scoping**: routers match with rules that include `ClientIP(...)` (IPv4, IPv6, CIDR). Router priority is calculated by default (from rule length), and the docs show cases where "the priority must be set". — [Traefik rules and priority](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/rules-and-priority/)
- **HAProxy syntax**: `userlist <name>` holds `group <g> [users a,b]` and `user <name> [password|insecure-password <pw>] [groups g1,g2]`. Access is checked with ACL fetches `http_auth(<userlist>)` (boolean) or `http_auth_group(<userlist>) <group...>`, and challenged with `http-request auth [realm <realm>]`. The manual's example is `acl auth_ok http_auth_group(L1) G1` followed by `http-request auth unless auth_ok`. The `auth` action "stops the evaluation of the rules and immediately responds with an HTTP 401 or 407". Passwords are subject to normal quoting, so "single quoting passwords is therefore recommended". — [HAProxy configuration manual, 12.2 Userlists and `auth` action](https://docs.haproxy.org/dev/configuration.html)
- **HAProxy**: the stats page has its own `stats auth <user>:<passwd>` and `stats realm`, with the password inline in the config. — [HAProxy configuration manual](https://docs.haproxy.org/dev/configuration.html)
- **OpenLiteSpeed**: realms are defined per virtual host (Virtual Host > Security > Authorization Realms: Realm Name, User DB Location, User DB Max Cache Size, User DB Cache Timeout, Group DB Location, ...). "Authorization is performed at context level", and several contexts can share one realm. A context sets `Realm`, `Authentication Name` (shown in the browser pop-up, overriding the realm name), `Require (Authorized Users/Groups)`, `Access Allowed`/`Access Denied` and `Authorizer`. The recommended files are `$SERVER_ROOT/conf/vhosts/$VH_NAME/htpasswd` and `htgroup`, readable by `lsadm` and the server user (usually `nobody`). — [OLS realms guide](https://docs.openlitespeed.org/security/realms/); [VHSecurity_Help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/VHSecurity_Help.html); [Static_Context help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/Static_Context.html)
- **OpenLiteSpeed .htaccess**: "OLS currently supports mod_rewrite rules from Apache", so `.htaccess` auth directives are not read and auth is configured in WebAdmin realms and contexts. — [OLS rewrite rules doc](https://docs.openlitespeed.org/config/rewriterules/). A third-party hosting knowledge base says LiteSpeed Enterprise reads Apache `.htaccess` (basic auth included) while "OpenLiteSpeed does not read" it. — [StackHarbor LiteSpeed .htaccess compatibility](https://stackharbor.com/en/knowledge-base/litespeed-htaccess-compatibility/) (secondary source)
- **h2o**: `mruby.handler: | require "htpasswd.rb"; Htpasswd.new("/path/to/.htpasswd", "realm-name")` placed before `file.dir` on a path. On success the handler returns 399 and "the request is delegated internally to the next handler". Before h2o 2.0 the script had to be required by its full path. The script also refuses files or directories starting with `.ht`. — [h2o Basic Authentication](https://h2o.examp1e.net/configure/basic_auth.html)
- **h2o scoping**: inside an `acl { }` block, `use Htpasswd.new(...) { path.start_with?("/admin") }` applies auth conditionally. ACL rules are evaluated top-down, and the first match (`allow`, `deny`, `respond`, `redirect`, `use`) decides. — [h2o access control](https://h2o.examp1e.net/configure/access_control.html)

### Inferences
- In Caddy, because `try_files` and `rewrite` run before `basic_auth`, a path matcher on `basic_auth` sees the rewritten URI. A front-controller rewrite (for example to `/index.php`) can therefore make `basic_auth /admin/*` miss. Wrapping the directives in `route { }` or using `handle` blocks fixes the order. This is consistent with the order list and the Authentik comment; I did not test it.
- Excluding a sub-path, per server: in Caddy use a named matcher `@protected { path /app/* ; not path /app/health }` passed to `basic_auth`; in Traefik use a second router whose rule also has `PathPrefix(/app/health)` (longer rule, so higher default priority) and no auth middleware; in HAProxy put `http-request allow if { path_beg /app/health }` before `http-request auth`; in OLS/LSWS create a more specific context without a realm; in h2o use a `path` condition in the acl block.
- HAProxy's `auth` action ends rule evaluation, so a rule placed after it never runs for a request that fails auth.

### Gaps
- I did not find primary LiteSpeed Enterprise documentation listing exactly which Apache auth directives (`AuthType`, `AuthUserFile`, `AuthGroupFile`, `Require`, `Satisfy`, `AuthBasicProvider`) LSWS honours in `.htaccess`. The LiteSpeed wiki page was behind bot verification, so the Enterprise claim rests on a third-party KB.
- The Caddy JSON reference page could not be fetched (domain blocked for WebFetch). Its field descriptions were taken from the Go doc comments in `basicauth.go`, from which that page is generated.

## Supported hash formats, defaults, and tooling

### Takeaway
- **Caddy** is the strictest: hashes only, bcrypt (default, cost 14) or argon2id (m=46 MiB, t=1, p=1), generated with `caddy hash-password`. scrypt was removed in 2024.
- **Traefik** accepts what `abbot/go-http-auth` accepts: MD5-crypt (`$apr1$`, `$1$`), `{SHA}` (unsalted SHA-1) and bcrypt (`$2a$/$2b$/$2x$/$2y$`), generated with `htpasswd`. It has no argon2 and no SHA-crypt.
- **HAProxy** hands non-plain passwords to the platform's `crypt(3)` (glibc: DES, MD5, SHA-256, SHA-512; more with libxcrypt) and has `insecure-password` for plaintext.
- **OpenLiteSpeed** (from source) detects `$apr1$`, `{SHA}` and bcrypt, and otherwise tries a plaintext compare and then `crypt(3)`.
- **h2o's** `htpasswd.rb` supports only `$apr1$` and `{SHA}`. A bcrypt line makes it answer 500.

### Cited Findings
- **Caddy**: "Caddy configuration does not accept plaintext passwords; you MUST hash them", using `caddy hash-password`. — [basic_auth docs](https://caddyserver.com/docs/caddyfile/directives/basic_auth)
- **Caddy**: a password starting with `$` is taken as Modular Crypt Format. Otherwise it is base64-decoded, a legacy "redundant base64" form marked TODO for removal. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)
- **Caddy bcrypt**: `defaultBcryptCost = 14` ("strikes a solid balance between security, usability, and hardware performance"). A cost outside [MinCost, MaxCost] falls back to 14. — [bcrypt.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/bcrypt.go)
- **Caddy argon2id** (added by PR #7186, merged 2025-10-06): defaults time=1, memory=46×1024 KiB, threads=1, keylen=32, salt 16 bytes, encoded as the PHC string `$argon2id$v=19$m=47104,t=1,p=1$<salt>$<key>`. Only version 19 is accepted. — [argon2id.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/argon2id.go); [PR #7186](https://github.com/caddyserver/caddy/pull/7186)
- **Caddy `hash-password`**: flags `--plaintext`, `--algorithm <argon2id|bcrypt>` (default bcrypt), `--bcrypt-cost`, `--argon2id-time`, `--argon2id-memory` (KiB), `--argon2id-threads` and `--argon2id-keylen`. Without `--plaintext` it reads stdin, with no echo and a confirmation prompt on a TTY. The help text calls argon2id "recommended for modern security" and bcrypt "legacy, slower". — [command.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/command.go)
- **Caddy history**: scrypt was deprecated in 2022 (#4720) and dropped in 2024 (#6091). Timing-based user enumeration was prevented in 2020 (commit 937ec34). — [basicauth.go commit history](https://github.com/caddyserver/caddy/commits/master/modules/caddyhttp/caddyauth/basicauth.go)
- **Caddy maintainers on cost**: Francis Lavoie: "I'd been thinking we should lower the default bcrypt to 10 instead of 14. ... 14 is kinda ridiculously high ... for basicauth the needs are not so equivalent and we had to do caching which is kinda cheating". Another participant warned that changing the default (and the fake hash) would allow user enumeration against existing cost-14 hashes. The master source still has 14. — [PR #7186 discussion](https://github.com/caddyserver/caddy/pull/7186); [bcrypt.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/bcrypt.go)
- **Caddy argon2id timing**: the PR author measured a first login with the default argon2id settings at 0.026–0.028 s. Lavoie pointed to the Password Hashing Competition discussion that "argon is not as good as bcrypt for hashing under 1s". — [PR #7186](https://github.com/caddyserver/caddy/pull/7186)
- **Traefik**: "Passwords must be hashed using MD5, SHA1, or BCrypt. Use `htpasswd` to generate the passwords." — [Traefik basicAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/basicauth/)
- **Traefik/go-http-auth**: `CheckSecret` dispatches on prefix. `{SHA}` goes to SHA-1. `$2a$`, `$2b$`, `$2x$` and `$2y$` go to `bcrypt.CompareHashAndPassword` (all treated like `$2y$`, so 8-bit passwords are wrong for `$2a$`/`$2x$`). Anything else goes to the default MD5-crypt comparer (`$1$`/`$apr1$`). — [go-http-auth basic.go](https://github.com/abbot/go-http-auth/blob/master/basic.go)
- **Traefik on Kubernetes**: the `kubernetes.io/basic-auth` secret type is supported, but "these keys are not hashed or encrypted in any way". — [Traefik basicAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/basicauth/)
- **HAProxy**: "Encrypted passwords are evaluated using the crypt(3) function, so depending on the system's capabilities, different algorithms are supported. For example, modern Glibc based Linux systems support MD5, SHA-256, SHA-512, and, of course, the classic DES-based method." `insecure-password` stores plaintext. — [HAProxy manual 12.2](https://docs.haproxy.org/dev/configuration.html)
- **HAProxy**: `check_user` uses `crypt_r()` with a thread-local `struct crypt_data` when available, and otherwise `crypt()` under a global spinlock (`HA_SPIN_LOCK(AUTH_LOCK)`). It compares with `strcmp`. A build without `USE_LIBCRYPT` rejects every hashed password. `haproxy -vv` reports "Encrypted password support via crypt(3): yes/no". — [auth.c](https://github.com/haproxy/haproxy/blob/master/src/auth.c); [management guide](https://docs.haproxy.org/dev/management.html)
- **HAProxy on musl**: "musl (e.g. Alpine Linux) implementations are known to be slower than their glibc counterparts when calculating hashes". — [HAProxy manual 12.2](https://docs.haproxy.org/dev/configuration.html)
- **OpenLiteSpeed docs**: each user-file line is `user:crypt()-password[:group1,group2]`, for example `john:HZ.U8kgjnMOHo:admin,user`. Groups in the user DB override the group DB. Group file lines are `group: user1 user2`. — [VHSecurity_Help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/VHSecurity_Help.html)
- **OpenLiteSpeed source**: `updatePasswdEncMethod()` recognises `$apr1$` (APMD5), `{SHA}` (base64 of 20 bytes, case-insensitive) and `$2a$/$2b$/$2y$` (bcrypt via `_crypt_blowfish_rn`, compared with `timing_safe_strcmp`). Everything else stays "PLAIN/UNKNOWN". In `UserDir::authenticate` those fall to `strcmp(password, stored)` first and then to `crypt(password, stored)`. The enum also has MD5, SMD5 and SSHA (salted) variants. — [authuser.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/authuser.cpp); [userdir.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/userdir.cpp)
- **OpenLiteSpeed tooling**: the WebAdmin console can create the files and add users ("CLICK TO CREATE", Add user/password); the guide also allows Apache's `htpasswd` command. — [OLS realms guide](https://docs.openlitespeed.org/security/realms/)
- **h2o**: `Htpasswd.validate` supports `/^\$apr1\$/` (its own Ruby MD5-crypt implementation) and `/^{SHA}/`. Anything else raises "crypt-style password hash is not supported", which the handler turns into `500 Internal Server Error` and a line on stderr. The comparison is Ruby `==`. — [htpasswd.rb](https://github.com/h2o/h2o/blob/master/share/h2o/mruby/htpasswd.rb)
- **oauth2-proxy** (for comparison): `--htpasswd-file` "Entries must be created with `htpasswd -B` for bcrypt encryption". — [oauth2-proxy configuration overview](https://oauth2-proxy.github.io/oauth2-proxy/configuration/overview)

### Inferences
- OpenLiteSpeed plaintext and pass-the-hash (from reading `userdir.cpp`; not tested). Because PLAIN/UNKNOWN entries try `strcmp(submitted, stored)` before `crypt()`, a user-file line holding a classic crypt hash (DES, `$1$`, `$5$`, `$6$`) also accepts the *literal hash string* as the password. Anyone who obtains the htpasswd file could log in without cracking it. Plaintext entries also work. This does not apply to `$apr1$`, `{SHA}` or bcrypt lines, which are detected and verified properly.
- Only Caddy supports a memory-hard KDF (argon2id). SHA-crypt (`$5$`, `$6$`) is available only where `crypt(3)` is used (HAProxy, OLS fallback). yescrypt (`$y$`, Debian's default for `/etc/shadow` since 11) works with HAProxy only when libc/libxcrypt supports it (inferred from the crypt(3) delegation, not verified).
- `{SHA}` (unsalted SHA-1) and `$apr1$` are cheap to brute-force offline. Traefik, h2o and OLS accept them; Caddy does not.

### Gaps
- LiteSpeed Enterprise's exact supported formats (for example whether it adds argon2 or SHA-crypt beyond OLS) were not found in primary docs.
- I did not verify whether musl's `crypt()` supports bcrypt for HAProxy on Alpine.
- HAProxy's `password` keyword docs do not say whether bcrypt `$2b$` works with glibc+libxcrypt. It should by delegation, but I found no documentation.

## Verification cost, caching, event-loop blocking, and reported bcrypt problems

### Takeaway
Basic auth resends the password on every request, so every server either hashes per request or caches.
- **Caddy** caches verification results by default (in the Caddyfile). The cache holds 1000 entries, keyed on stored-hash+plaintext, with random eviction, and singleflight collapses concurrent identical checks. It was added after real CPU complaints (bcrypt cost 14 at ~2 s per hash on a small VPS).
- **Traefik** declined a result cache in 2021. It hashes on every request, and since v3.6.11 only collapses concurrent identical checks with singleflight. That path had a low-severity identity-spoofing bug fixed in 3.6.25/3.7.10.
- **HAProxy** hashes on every request, synchronously on the worker thread, and its manual warns this can drive CPU and "even lead to application crashes".
- **OpenLiteSpeed** caches user *records* (with a timeout to recheck the file) but, by the source, still verifies the password per request.
- **h2o's** script re-opens and scans the htpasswd file per request.

### Cited Findings
- **Caddy hash cache (JSON field `hash_cache`)**: "If non-nil, a mapping of plaintext passwords to their hashes will be cached in memory (with random eviction). This can greatly improve the performance of traffic-heavy servers that use secure password hashing algorithms, with the downside that plaintext passwords will be stored in memory for a longer time (this should not be a problem as long as your machine is not compromised...). Note that a cache hit does not mean it is a valid password." — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go); [JSON docs](https://caddyserver.com/docs/json/apps/http/servers/routes/handle/authentication/providers/http_basic/#hash_cache)
- **Caddy implementation**: the cache key is `hex(stored_hash || plaintext)` and the value is a bool, so negative results are cached too. It is read under an RWMutex. On a miss the comparison runs inside a `singleflight.Group` keyed the same way. At ≥1000 entries `makeRoom()` deletes about 1/10 of entries at random. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)
- **Caddy default**: the Caddyfile adapter always sets `ba.HashCache = new(Cache)`, and there is no Caddyfile option to turn it off. Lavoie: "It's configurable via JSON, but not via Caddyfile. There's really no situation where it ever makes sense to turn off ... because it has such a staggering performance impact." — [caddyfile.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyfile.go); [PR #3465 comments](https://github.com/caddyserver/caddy/pull/3465); [issue #3775](https://github.com/caddyserver/caddy/issues/3775)
- **Caddy origin, issue #3462 (2020-05)**: on a 1-vCPU Linode, "10-20 requests per second are sufficient to occupy 60%-80% of the single CPU", and pprof showed ">92% of that CPU time" in `blowfish/encryptBlock` (a netdata dashboard behind basicauth). Matt Holt: "Caching the results is a good idea -- if we assume that the program memory is absolutely a safe place". On DoS: "caching hashes won't prevent that as an attacker would just use a different password each time ... implement some rate limiting or firewall rules". — [issue #3462](https://github.com/caddyserver/caddy/issues/3462)
- **Caddy cache PR #3465**: "Cache capacity is currently hard-coded at 1000 with random eviction. It is not enabled by default, but the Caddyfile _will_ enable it by default". It shipped in v2.1.0. — [PR #3465](https://github.com/caddyserver/caddy/pull/3465); [issue #4267](https://github.com/caddyserver/caddy/issues/4267)
- **Caddy thundering herd, issue #5338 (v2.6.2, 2023-01)**: after a restart, 18 parallel netdata requests produced a ~15 s CPU spike, because all of them hashed before the first result was cached. `caddy hash-password` at cost 14 took 2.18 s real on a $6/month 1-shared-vCPU droplet. Fixed by singleflight (#5344). Lavoie: "If you want to reduce the spike's size, you can use a lower bcrypt cost". — [issue #5338](https://github.com/caddyserver/caddy/issues/5338); [PR #5344](https://github.com/caddyserver/caddy/pull/5344)
- **Caddy timing side-channel**: for unknown users Caddy compares against a fixed `FakeHash()` (bcrypt or argon2id at the default cost) so that existence does not leak by timing. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go); [bcrypt.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/bcrypt.go); [argon2id.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/argon2id.go)
- **Traefik cache request, issue #7897 / PR #7900 (2021)**: merely having the Traefik dashboard open "slows down _every request_", because `goauth.CheckSecret` runs per request. The PR proposed an LRU cache, which was declined. The maintainers' questions included "What would be the strategy to revoke users? ... A fifo stack won't be beneficial in any way if it's always full of unsuccessful attempts", and whether frequent dynamic-config reloads (which recreate middlewares) make a cache pointless. — [issue #7897](https://github.com/traefik/traefik/issues/7897); [PR #7900](https://github.com/traefik/traefik/pull/7900)
- **Traefik user reports**: with bcrypt cost 12 and fluentbit sending a few requests per second, responses took ~500 ms, against sub-50 ms at cost 8 ([comment, 2023-03](https://github.com/traefik/traefik/issues/7897)). "using the BasicAuth middleware without other precautions (like IP whitelist) opens you to a very simple and **effective DoS**" ([comment, 2023-02](https://github.com/traefik/traefik/issues/7897)). A user migrating from Caddy said "With Traefik - only MD5 seems to be viable solution" ([comment, 2023-04](https://github.com/traefik/traefik/issues/7897)).
- **Traefik now**: `checkPassword` wraps the comparison in `singleflightGroup.Do(key, ...)`. There is no result cache. For an unknown user it hashes against `notFoundSecret`, the first configured user's hash ("assume ... safe only when the users hashes are all from the same algorithm"). — [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go)
- **Traefik GHSA-6765-c87h-8mrf (low, published 2026-08-06)**: the singleflight key was the delimiter-free `password + secret`. An unknown user (empty secret) could pick password `P||H` and share a valid user's in-flight `true` result, then be propagated under the attacker-chosen name via `URL.User`, the access log and `headerField`. Exploitation needs a valid credential *and* the stored hash. It affected 3.6.11–3.6.24 and 3.7.0–3.7.9 (patched in 3.6.25 and 3.7.10); "earlier v3 releases and the v2 line do not carry the vulnerable deduplication path". The key is now `len(user):user:password`, after a follow-up commit (2026-09-01) "Prevent user enumeration through the basic auth singleflight key". — [GHSA-6765-c87h-8mrf](https://github.com/traefik/traefik/security/advisories/GHSA-6765-c87h-8mrf); [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go); [commit history](https://github.com/traefik/traefik/commits/master/pkg/middlewares/auth/basic_auth.go)
- **Traefik 2026 hardening commits**: "Make basic auth check timing constant" (2026-03-17), "Prevent duplicate user headers in basic and digest auth middleware" (2026-03-20), "Remove map lookup making the basic auth notFoundSecret empty" (2026-04-13). — [commit history](https://github.com/traefik/traefik/commits/master/pkg/middlewares/auth/basic_auth.go)
- **HAProxy warning**: "using encrypted passwords might cause significantly increased CPU usage ... the password for each request must be processed through the chosen algorithm ... This can quickly become a major factor in HAProxy's overall CPU consumption, and can even lead to application crashes! ... reduce the number of rounds ... or decrease the 'cost'". — [HAProxy manual 12.2](https://docs.haproxy.org/dev/configuration.html)
- **OpenLiteSpeed cache**: "User DB Max Cache Size ... Recently accessed user authentication data will be cached in memory". "User DB Cache Timeout (secs): how often the backend user database will be checked for changes ... Server reload and graceful restart will clear the cache immediately." — [VHSecurity_Help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/VHSecurity_Help.html)
- **OpenLiteSpeed code**: `UserDir::getUser` returns a cached `AuthUser` (a timestamp check, then `isUserStoreChanged`), and `authenticate()` then runs the hash comparison every time. — [userdir.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/userdir.cpp)
- **h2o**: `lookup()` does `File.open(@path)` and `each_line` on every request with an Authorization header, comparing each line until a match. — [htpasswd.rb](https://github.com/h2o/h2o/blob/master/share/h2o/mruby/htpasswd.rb)
- **Authentik** (forward auth): "We strongly recommend that the client sending requests with HTTP Basic authentication persists the cookies returned by the outpost. Otherwise, every request must be authenticated independently, which increases load on the authentik server". — [Authentik header authentication](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/header_authentication.mdx)

### Inferences
- **Event loop or thread blocking**:
  - Caddy and Traefik run each request on its own goroutine, so a bcrypt check consumes a core but does not stall other connections, apart from CPU contention up to GOMAXPROCS. This is an inference from Go's model and the code.
  - HAProxy calls `crypt_r()` synchronously inside rule evaluation on the worker thread, so every other stream on that thread waits for the hash. The manual's "application crashes" probably refers to HAProxy's watchdog firing on a stuck thread; that reading is mine, not verified.
  - OLS calls bcrypt/`crypt()` inline in its event-driven worker, so the same stall applies (inferred from source).
  - h2o's mruby handler does synchronous file I/O and Ruby MD5-crypt (1000 MD5 rounds) inline on the event loop. That is cheap per call but grows with file size (inferred).
- **Caddy cache caveats**:
  - Plaintext passwords stay in memory, keyed in hex, with up to 1000 entries.
  - Negative results are cached, so a brute-forcer with fresh guesses fills the cache with misses and evicts good entries at random. Repeated identical wrong guesses become cheap for the server, while new guesses still cost a full hash each.
  - Revocation is handled by config reload (a new provisioned handler and a new cache), not by the cache itself.
  - The Go map has no TTL.
- Traefik's singleflight helps only bursts of *concurrent identical* requests (a page load firing parallel subrequests). Sequential requests on one connection still hash every time.

### Gaps
- No published per-request benchmark numbers (req/s with basic auth on vs off) were found for any of the five servers, beyond the anecdotes above (2.18 s per cost-14 hash on a shared vCPU; ~500 ms at cost 12 vs <50 ms at cost 8 in Traefik).
- I did not find whether LiteSpeed Enterprise has a verified-credential cache.
- I did not confirm the exact Traefik release that introduced singleflight. The advisory implies 3.6.11.

## Combining with IP allow lists; what the backend receives

### Takeaway
None of the five offers a one-word "IP *or* password" switch like Apache's `Satisfy Any`, except OLS/LSWS through per-context allow/deny plus realm, where the semantics are AND by the docs. Instead it comes from the matcher or ACL language: a Caddy `not client_ip` matcher, a HAProxy `unless auth_ok || { src ... }`, a Traefik router split on `ClientIP()`, or an h2o `acl { allow {...}; use Htpasswd... }`.

By default all of them **forward the client's `Authorization` header to the backend**:
- Traefik removes it only with `removeHeader: true`.
- Caddy and HAProxy remove it only with explicit header directives.
- Traefik can put the username into a header (`headerField`). Caddy exposes `{http.auth.user.id}`. h2o sets the request variable `REMOTE_USER`. HAProxy has the `http_auth_user` fetch.

### Cited Findings
- **Traefik**: on success it sets `req.URL.User`. If `headerField` is set it deletes any client-supplied copy and sets `req.Header[headerField] = user` (non-canonical key). If `removeHeader` is set it deletes `Authorization`; the default is false, i.e. forwarded. — [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go); [Traefik basicAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/basicauth/)
- **Traefik header aliasing**: the code notes that names aliasing the header field (for example `X_Auth_User`) are not handled, "as the aliasHeadersStrategy entry point option is expected to be enabled to prevent header spoofing". The entry point option `http.aliasHeadersStrategy` (`keep` by default, `delete`, `reject`) handles header names with characters other than letters, digits and dashes. "Backends normalizing the header names can be spoofed with an aliasing name of a header they trust. Setting ... `delete` or `reject` is recommended". It was added 2026-08-24 to the v2.11/v3.7 lines per the commit log. — [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go); [Traefik entry points, aliasHeadersStrategy](https://doc.traefik.io/traefik/reference/install-configuration/entrypoints/#aliasheadersstrategy); [commit history](https://github.com/traefik/traefik/commits/master/pkg/middlewares/auth/basic_auth.go)
- **Traefik IP**: the `ipAllowList` middleware (`sourceRange`, `rejectStatusCode`, default 403) chains with other middlewares, and routers can match on `ClientIP()`. — [ipAllowList reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/ipallowlist/); [rules and priority](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/rules-and-priority/)
- **Caddy**: after success, `{http.auth.user.id}` holds the username (the docs example is `respond "Welcome, {http.auth.user.id}"`). Provider metadata becomes `http.auth.user.*` placeholders. — [basic_auth docs](https://caddyserver.com/docs/caddyfile/directives/basic_auth); [caddyauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyauth.go)
- **Caddy**: `Authenticate()` reads `req.BasicAuth()` and never modifies the request headers. On success the handler sets placeholders and calls `next.ServeHTTP(w, r)` with the request unchanged. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go); [caddyauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyauth.go)
- **Caddy IP**: `client_ip` (honours `trusted_proxies`, has the `private_ranges` shortcut) and `remote_ip` matchers can be negated with `not`. — [Caddy matchers](https://caddyserver.com/docs/caddyfile/matchers#client_ip)
- **HAProxy fetches**: `http_auth_user`, `http_auth_pass` and `http_auth_type` return the *client-supplied* values with "Not checks are performed". `http_auth_group(<userlist>)` returns the username only if the user and password are valid. — [HAProxy manual, fetches](https://docs.haproxy.org/dev/configuration.html)
- **OpenLiteSpeed**: context `Access Allowed`/`Access Denied` lists ("accessibility is determined by the smallest scope that a client's IP address falls into") sit next to `Realm` on the same context. — [Static_Context help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/Static_Context.html)
- **h2o**: on success `htpasswd.rb` returns `[399, {"x-fallthru-set-remote-user" => user}, []]`. "A HTTP response header that starts with `x-fallthru-set-` is handled specially ... the server accepts the value as a request environment variable, taking the suffix of the header name as the name of the variable" (h2o 2.3). The acl DSL can put `allow { addr == "127.0.0.1" }` before `use Htpasswd...`. — [htpasswd.rb](https://github.com/h2o/h2o/blob/master/share/h2o/mruby/htpasswd.rb); [h2o mruby](https://h2o.examp1e.net/configure/mruby.html); [h2o access control](https://h2o.examp1e.net/configure/access_control.html)
- **Authentik** (forward auth): if the credentials are correct, "authentik removes the `Authorization` header to prevent sending the credentials to the proxied application". Authentik's HAProxy template strips client identity headers before the check: `http-request del-header X-authentik- -m beg`, `http-request del-header _ -m sub` ("including underscore aliases") and `http-request del-header Authorization`. — [Authentik header authentication](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/header_authentication.mdx); [Authentik HAProxy template](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/_haproxy_standalone.mdx)

### Inferences
- "IP or password", per server:
  - Caddy: `@needauth not client_ip 10.0.0.0/8` then `basic_auth @needauth {...}`.
  - HAProxy: `http-request auth unless auth_ok || { src -f /etc/haproxy/office.lst }`.
  - Traefik: two routers on the same Host/Path, one with `&& ClientIP(...)` and no auth middleware. Its longer rule gives it higher default priority.
  - h2o: `allow {...}` before `use Htpasswd`.
  - "IP and password" is plain chaining (`ipAllowList` + `basicAuth`; Caddy `abort`/`respond 403` on `not client_ip`, then `basic_auth`).
- Stripping credentials before the backend: Caddy `request_header -Authorization` (or `header_up -Authorization` in `reverse_proxy`); HAProxy `http-request del-header Authorization`; Traefik `removeHeader: true`; h2o has no built-in way (it would need mruby). Forwarding the user: Caddy `request_header X-Forwarded-User {http.auth.user.id}`; HAProxy `http-request set-header X-Forwarded-User %[http_auth_user] if auth_ok`. With HAProxy this is safe only after `auth_ok` is true, because `http_auth_user` is unverified.
- A client-supplied `X-Forwarded-User`/`Remote-User` must be deleted unconditionally before any identity header is set. Traefik's `headerField` does this for the exact name only, so underscore aliases need `aliasHeadersStrategy` (or nginx-style dropping of underscore headers). This matters for PHP/CGI backends, where `X-Remote-User` and `X_Remote_User` both become `HTTP_X_REMOTE_USER`.
- With h2o, a FastCGI backend gets `REMOTE_USER` from the `x-fallthru-set-remote-user` variable, which looks like the intended path for `file.dir`/`fastcgi` successors. The Authorization header is still forwarded.

### Gaps
- I did not verify what OLS/LSWS pass to LSAPI/FastCGI backends on success (`REMOTE_USER`, `AUTH_TYPE`, whether `Authorization`/`PHP_AUTH_*` reach PHP), nor whether OLS combines `Access Allowed` with `Realm` as AND or OR (`Satisfy`-like). The docs list both on a context without stating their combination.
- No Caddy documentation says outright that `Authorization` is forwarded. That comes from code reading.

## Responses (401, WWW-Authenticate realm, charset), logging and fail2ban/CrowdSec

### Takeaway
All five answer 401 with `WWW-Authenticate: Basic realm="..."`:
- Caddy's default realm is `restricted`, with an empty 401 that `handle_errors` can customise.
- Traefik's default realm is `traefik`, with a fixed text body.
- HAProxy's realm defaults to the proxy (frontend/backend) name, `STATS_DEFAULT_REALM` on the stats page; it answers 407/`Proxy-Authenticate` on proxy-mode connections and uses the proxy's errorfile.
- h2o uses the configured realm, with a "Authorization Required" text body.
- OLS uses the context's "Authentication Name" or the realm name.

None of them sends RFC 7617's `charset="UTF-8"` parameter (checked in code for Caddy, Traefik, HAProxy, h2o).

For logs, Caddy writes `user_id` only on success. Traefik's access log carries the *attempted* username even on failure (CLF user field). CrowdSec's generic brute-force scenario reacted to POST 401s only, and its fix for Traefik GET 401s was reverted because of false positives.

### Cited Findings
- **Caddy**: `promptForCredentials` sets `Www-Authenticate: Basic realm="<realm>"`, with the realm defaulting to `restricted`. The handler then returns `caddyhttp.Error(http.StatusUnauthorized, "not authenticated")` "so handle_errors runs and a challenge that set only headers (like basic auth) still returns 401". Provider errors are logged as "auth provider returned error" and exposed as `{http.auth.<provider>.error}`. — [basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go); [caddyauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyauth.go)
- **Caddy, several providers**: since the fix for issue #5190, each provider writes to its own bounded (1 MiB) buffered writer, and one challenge (a redirecting provider preferred) is replayed. — [caddyauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyauth.go)
- **Caddy logging**: the access log entry includes `user_id` from `http.auth.user.id`. — [server.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/server.go)
- **Traefik**: go-http-auth's `RequireAuth` sets Content-Type, `WWW-Authenticate: Basic realm="<realm>"`, the 401 code and a fixed body. Before the check Traefik sets `logData.Core[accesslog.ClientUsername] = user` whatever the outcome, and logs "Authentication failed" at debug level. — [go-http-auth basic.go](https://github.com/abbot/go-http-auth/blob/master/basic.go); [basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go)
- **HAProxy**: the realm is the configured `realm`, else `STATS_DEFAULT_REALM` for stats rules, else `px->id`. The header is `Basic realm="%s"`. The status is 401/`WWW-Authenticate`, or 407/`Proxy-Authenticate` when the transaction uses a proxy connection. It "removes all occurrences" of the header from the error message and adds its own, and the body can be customised with `errorfile`/`http-error`. — [http_act.c](https://github.com/haproxy/haproxy/blob/master/src/http_act.c); [HAProxy manual, auth action](https://docs.haproxy.org/dev/configuration.html)
- **h2o**: the failure response is `401`, `Content-Type: text/plain`, `WWW-Authenticate: Basic realm="#{@realm}"`, body "Authorization Required". A path containing `/.ht` gives `404 not found`. A validation exception gives 500 and a line on stderr. — [htpasswd.rb](https://github.com/h2o/h2o/blob/master/share/h2o/mruby/htpasswd.rb)
- **OpenLiteSpeed**: "The authentication name is displayed on the browser's login pop-up." On failure `authenticate()` returns `SC_401`, and a crypt-path failure logs `[UserDir::authenticate] Failed in ENCRYPT_CRYPT type.` at error level. — [Static_Context help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/Static_Context.html); [userdir.cpp](https://github.com/litespeedtech/openlitespeed/blob/master/src/http/userdir.cpp)
- **CrowdSec**: `crowdsecurity/http-generic-bf` is a leaky bucket on `evt.Meta.sub_type == 'auth_fail'` (capacity 5, leakspeed 10 s, blackhole 1 m). The bundled `LePresidente/http-generic-401-bf` filters `evt.Parsed.verb == 'POST' && evt.Meta.http_status == '401'`. — [CrowdSec hub scenario](https://github.com/crowdsecurity/hub/blob/master/scenarios/crowdsecurity/http-generic-bf.yaml)
- **CrowdSec and Traefik** (Dec 2024 to Jan 2025): a user saw fail2ban ban failed Traefik basicAuth attempts while CrowdSec did not. CrowdSec merged a change removing the verb filter and then reverted it "due to a lot of feedback on the changes about false positives". "The issue with CLF logs with traefik we do not know it's a failed authentication as it a middleware, if the middle was logging some kind of information this would be better to monitor for." Users write local scenarios for GET 401/403. — [CrowdSec forum: Traefik failed basic auth attempts aren't banned](https://discourse.crowdsec.net/t/traefik-failed-basic-auth-attempts-aren-t-banned/2195); [CrowdSec forum: Best practice for Basic Auth](https://discourse.crowdsec.net/t/best-practice-for-basic-auth-crowdsec-blocks-post-attacks-but-ignores-get/2672)

### Inferences
- From the code, none of the servers emits `charset="UTF-8"` (RFC 7617 section 2.1). Go's `req.BasicAuth()` decodes the raw bytes, so non-ASCII passwords work only when browser and hash agree on the encoding.
- Caddy builds the header as `fmt.Sprintf("Basic realm=\"%s\"", realm)` and HAProxy with `chunk_printf("Basic realm=\"%s\"")`, neither escaping quotes. A realm containing `"` would break the header, so this is config-time hygiene.
- For fail2ban/CrowdSec, a server that logs a distinct "auth failed" event (with the attempted user) is much easier to protect than one whose access log only shows `401`, which a backend can also produce. Traefik's CLF does log the attempted username, but the forum shows it is not a reliable signal on its own. Caddy logs no username on failure. HAProxy logs neither unless `log-format` includes `%[http_auth_user]` and the ACL result.

### Gaps
- I found no official fail2ban filters shipped by Caddy, Traefik, HAProxy, OLS or h2o for Basic-auth failures. Community filters exist, but none was checked.
- The exact body text of go-http-auth's default 401 (`UnauthResponse`) was not confirmed.

## Forward (delegated) authentication: forward_auth / forwardAuth with Authelia, Authentik, oauth2-proxy

### Takeaway
Forward auth makes the proxy send a sub-request (without the body by default) carrying the original method, scheme, host, URI and client IP in `X-Forwarded-*` headers to an auth service.
- A **2xx** answer lets the request continue, and selected response headers (`Remote-User`, `X-Authentik-Username`, `X-Auth-Request-User`) are copied onto the upstream request.
- **Any other answer** (302 to a login portal, 401, 403) is relayed to the client.

Caddy (`forward_auth`, since v2.5.0, 2022) and Traefik (`forwardAuth`) have it built in. HAProxy needs the Lua `haproxy-auth-request` plugin. LiteSpeed offers the FastCGI Authorizer role. h2o could do it with mruby's async `http_request`; no official recipe was found.

The recurring security issue is identity-header injection: a client sends its own `Remote-User`. Caddy had a high-severity advisory on exactly this (fixed in 2.11.2, March 2026). Authelia, Authentik and oauth2-proxy all insist on trusted-proxy configuration for `X-Forwarded-*`.

### Cited Findings
- **Caddy forward_auth**: "proxies a clone of the request to an authentication gateway". It makes a `GET` with `uri` rewritten. "If the upstream responds with a 2xx status code, then access is granted and the header fields in copy_headers are copied to the original request ... Otherwise ... the upstream's response is copied back to the client", typically a redirect to the login page. The `Before>After` syntax renames copied headers. All `reverse_proxy` subdirectives apply. — [Caddy forward_auth docs](https://caddyserver.com/docs/caddyfile/directives/forward_auth) ([source md](https://github.com/caddyserver/website/blob/master/src/docs/markdown/caddyfile/directives/forward_auth.md))
- **Caddy expanded form**: `reverse_proxy <upstreams> { method GET; rewrite <to>; header_up X-Forwarded-Method {method}; header_up X-Forwarded-Uri {uri}; @good status 2xx; handle_response @good { request_header Remote-User {rp.header.Remote-User} ... } }`, "in addition to other X-Forwarded-* headers already set by reverse_proxy". — [Caddy forward_auth docs](https://caddyserver.com/docs/caddyfile/directives/forward_auth)
- **Caddy history**: introduced by "reverseproxy: Support performing pre-check requests (#4739)" on 2022-05-06. "Skip copying missing response headers (#6608)" landed 2024-11-04, and the fix for GHSA-7r4p-vjf4-gxv4 (#7545) on 2026-03-04. — [forwardauth caddyfile.go history](https://github.com/caddyserver/caddy/commits/master/modules/caddyhttp/reverseproxy/forwardauth/caddyfile.go)
- **Caddy GHSA-7r4p-vjf4-gxv4 (high, 2026-03-06)**: "`copy_headers` generates conditional header-set operations that only fire when the upstream auth service includes the named header ... No delete ... for the original client-supplied request header". When the auth service returns 200 without one of them, "the client-supplied header passes through unchanged ... Any requester holding a valid authentication token can inject arbitrary values for trusted identity headers". It affected `>= 2.10.0, < 2.11.2`, a regression from #6608. The fix always emits a `Delete` of each `copy_headers` target before the conditional `Set`. — [GHSA-7r4p-vjf4-gxv4](https://github.com/caddyserver/caddy/security/advisories/GHSA-7r4p-vjf4-gxv4); [forwardauth caddyfile.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/reverseproxy/forwardauth/caddyfile.go)
- **Traefik forwardAuth options**: `address`; `trustForwardHeader` (deprecated, see below); `authResponseHeaders`; `authResponseHeadersRegex`; `authRequestHeaders` (if empty, *all* request headers are passed); `addAuthCookiesToResponse`; `forwardBody` ("breaks streaming"); `maxBodySize` (default -1, unlimited; a larger body gets 401); `maxResponseBodySize`; `headerField`; `preserveLocationHeader`; `preserveRequestMethod`; `authSigninURL` (redirect on a 401 from the auth server); `tls.ca/cert/key/insecureSkipVerify`. Headers sent to the auth server: `X-Forwarded-Method`, `-Proto`, `-Host`, `-Uri`, `-For`. — [Traefik forwardAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/forwardauth/) ([source md](https://github.com/traefik/traefik/blob/master/docs/content/reference/routing-configuration/http/middlewares/forwardauth.md))
- **Traefik `trustForwardHeader`**: "deprecated and will be removed in the next major version". The docs say to configure `forwardedHeaders.trustedIPs` at the entry point and set it to true. If it is unset, Traefik "will log a warning at startup and use a legacy behavior where some X-Forwarded-* headers (e.g. X-Forwarded-For, X-Forwarded-Proto) are removed but others (e.g. X-Forwarded-Prefix) are forwarded untouched". — [Traefik forwardAuth reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/forwardauth/); [forward.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/forward.go)
- **Traefik behaviour (code)**: the sub-request is GET unless `preserveRequestMethod`. On a transport error it answers 500 (499 if the client cancelled). A non-2xx answer copies the auth response's headers (minus hop-by-hop), status and body to the client, rewriting `Location` unless `preserveLocationHeader`. On 2xx, only the listed `authResponseHeaders` are deleted from the client request and replaced, with the comment "Any other header the client sends is forwarded to the backend unchanged ... trusting unlisted client headers downstream is a backend misconfiguration". — [forward.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/forward.go)
- **Authelia model**: Authelia offers the authz endpoints `/api/authz/forward-auth` (Traefik, Caddy, HAProxy via Lua, Skipper), `/api/authz/auth-request` (nginx), `/api/authz/ext-authz` (Envoy) and legacy `/api/verify`. Its authentication strategies are CookieSession (redirect on failure) and HeaderAuthorization (401 + `WWW-Authenticate`), so the same endpoint can serve Basic-auth API clients. Responses: 200 when authorized; 401 for detected XHR; 302 for GET/OPTIONS; 303 otherwise. The `X-Forwarded-*` headers are "considered required". — [Authelia proxy introduction](https://www.authelia.com/integration/proxies/introduction/); [Authelia proxy authorization guide](https://www.authelia.com/reference/guides/proxy-authorization/)
- **Authelia + Caddy**: `forward_auth authelia:9091 { uri /api/authz/forward-auth; copy_headers Remote-User Remote-Groups Remote-Email Remote-Name }`, with warnings to configure `trusted_proxies` narrowly ("should not trust entire subnets unless that subnet only has trusted proxies"). — [Authelia Caddy integration](https://www.authelia.com/integration/proxies/caddy/); [Caddy forward_auth docs](https://caddyserver.com/docs/caddyfile/directives/forward_auth)
- **Authelia + Traefik**: `forwardAuth.address: http://authelia:9091/api/authz/forward-auth`, `trustForwardHeader: true`, `authResponseHeaders: Remote-User,Remote-Groups,Remote-Email,Remote-Name`, and entry-point `forwardedHeaders.trustedIPs`. The example also protects an endpoint "with [Authorization] header for basic authentication". — [Authelia Traefik integration](https://www.authelia.com/integration/proxies/traefik/)
- **Authelia + HAProxy**: needs HAProxy 1.8.4+ (2.2.0+ recommended) with `USE_LUA=1`, `haproxy-lua-http`, a JSON library and `haproxy-auth-request`. The config sets `X-Forwarded-Method/Proto/Host/URI` with `http-request set-header`, then `http-request lua.auth-intercept be_authelia /api/authz/forward-auth HEAD * remote-user,remote-groups,remote-name,remote-email - if protected-frontends`, `http-request deny if ... { var(txn.auth_response_code) -m int 403 }` and a redirect to `var(txn.auth_response_location)`. — [Authelia HAProxy integration](https://www.authelia.com/integration/proxies/haproxy/)
- **Authentik**: "Forward auth uses your existing reverse proxy for application traffic and relies on the authentik outpost only to check authentication and authorization". The modes are single application and domain level (one cookie domain, but no per-application policies). Caddy uses `forward_auth http://outpost:9000 { uri /outpost.goauthentik.io/auth/caddy; copy_headers X-Authentik-Username X-Authentik-Groups ... ; trusted_proxies private_ranges }` with "capitalization of the headers is important". The headers set are `X-authentik-username`, `-groups`, `-entitlements`, `-email`, `-name`, `-uid`, `-jwt` and `-meta-*`. — [Authentik forward auth](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/forward_auth.mdx); [Authentik Caddy template](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/_caddy_standalone.mdx); [Authentik proxy provider headers](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/index.mdx); [Authentik Caddy docs](https://docs.goauthentik.io/add-secure-apps/providers/proxy/server_caddy)
- **Authentik and Basic auth**: Authentik can receive Basic credentials (an app password, or the reserved user `goauthentik.io/token`) and can *send* Basic credentials built from user attributes to the upstream ("Send HTTP-Basic Authentication"). This turns a legacy Basic-only application into an SSO-protected one. — [Authentik header authentication](https://github.com/goauthentik/authentik/blob/main/website/docs/add-secure-apps/providers/proxy/header_authentication.mdx)
- **oauth2-proxy**: "the `/oauth2/auth` endpoint on every request ... only returns a 202 Accepted response or a 401 Unauthorized response without proxying the whole request through". With Traefik it is paired with an errors middleware that turns 401 into a redirect to sign-in, and it requires `--reverse-proxy`. `--set-xauthrequest` adds `X-Auth-Request-User/-Groups/-Email/-Preferred-Username` response headers. `--pass-user-headers` and `--pass-basic-auth` (both default true) send `X-Forwarded-User/-Email/...` and Basic credentials upstream in proxy mode. If `--trusted-proxy-ip` is unset, "OAuth2 Proxy currently trusts all source IPs for backwards compatibility, which means a client that can reach OAuth2 Proxy directly may be able to spoof forwarded headers". `--trusted-ip` "bypasses authentication". — [oauth2-proxy Traefik integration](https://oauth2-proxy.github.io/oauth2-proxy/configuration/integrations/traefik); [oauth2-proxy configuration overview](https://oauth2-proxy.github.io/oauth2-proxy/configuration/overview)
- **LiteSpeed/OLS**: the context `Authorizer` "Specifies an external application that can be used to generate authorized/unauthorized decisions. Currently, only the FastCGI Authorizer is available". FastCGI applications on LiteSpeed "can take two roles: ... a responder role or authorizing requests (an authorizer role)". — [Static_Context help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/Static_Context.html); [ExtApp_Help](https://github.com/litespeedtech/openlitespeed/blob/master/dist/docs/ExtApp_Help.html)
- **h2o**: "Starting from version 1.7, a HTTP client API is provided. HTTP requests issued through the API will be handled asynchronously; the client does not block the event loop", via `http_request(url, {method:, header:, body:})` and `.join`, with `proxy.timeout.*` applied. — [h2o mruby](https://h2o.examp1e.net/configure/mruby.html)
- **CrowdSec bouncer**: the CrowdSec bouncer for Traefik itself uses ForwardAuth to ask CrowdSec about the client IP and returns 403 for banned IPs. That makes ForwardAuth the generic plug-in point for IP reputation too. — [CubePath: CrowdSec with Traefik and Nginx bouncers](https://cubepath.com/docs/server-tools/crowdsec-traefik-nginx-bouncers) (secondary source)

### Inferences
- Why operators like forward auth, synthesised from the docs above (no survey found):
  - One login portal with SSO, 2FA/WebAuthn and policy for many applications that know nothing about auth.
  - The proxy keeps routing, TLS and streaming, while the auth service sees only headers (`forwardBody` off by default).
  - Per-application policy and group headers.
  - A path for API clients to keep using Basic or Bearer through the same endpoint (Authelia HeaderAuthorization, Authentik app passwords).
  - Session cookies end the per-request password hashing that makes plain Basic auth expensive.
- The cost: one extra HTTP round trip per request to the auth service, with no caching in Caddy or Traefik as far as their code shows. Availability is coupled too: Traefik answers 500 when the auth service is unreachable, which is a fail-closed design.
- Security rules every implementation converged on:
  - Delete client-supplied identity headers unconditionally, underscore aliases included.
  - Trust `X-Forwarded-*` only from configured proxies.
  - Narrow `authRequestHeaders` (Traefik forwards all request headers by default, cookies and Authorization included).
  - Cap body and response sizes.
  - Always use GET/HEAD for the sub-request so the body is not consumed.

### Gaps
- No primary source was found on operator sentiment (for example a survey). The "what operators like" points are inferred from vendor docs and issues.
- I did not verify whether Caddy or Traefik cache forward-auth decisions; the code read shows none.
- h2o: no official forward-auth example or community recipe was found.
- LiteSpeed Enterprise's FastCGI Authorizer specifics (variables passed, header copying such as `Variable-*`, caching) were not researched in detail.
- HAProxy: I did not check whether recent versions (3.x) offer a native sub-request or auth-request without Lua, for example via SPOE/SPOA. Every integration guide found uses `haproxy-auth-request` (Lua).
