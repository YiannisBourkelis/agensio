# Web-server HTTP Basic authentication: what administrators need and what they complain about

Method note: Stack Overflow / Server Fault pages cannot be fetched by the research tools, so question titles, scores, view counts, creation years and answer texts were read through the public Stack Exchange API (`api.stackexchange.com/2.3`) on 2026-10-08; "score / views / year" below are those values. Source code claims were checked against the current `master` branches of nginx, Caddy and Traefik on GitHub (downloaded 2026-10-08). Items before 2018 are marked "(older)". Anything taken only from a search-engine snippet, not from the page itself, is marked "(snippet only)".

## 1. Performance: expensive password hashes re-verified on every request

### Takeaway
Basic auth carries the password on every request, so the server re-verifies it for every asset of every page; with bcrypt (or any deliberately slow hash) the hash cost is multiplied by the number of requests. This is the best-documented performance complaint across nginx, Caddy and Traefik. Caddy fixed it in 2020 with an in-memory cache of verification results. Traefik and nginx still verify every time, and nginx does it synchronously inside the event-loop worker. The usual workarounds are a low bcrypt cost, a cheaper hash (apr1/MD5, SHA-crypt), a result cache, or moving to session/cookie auth.

### Cited Findings
- **Caddy #3462 (2020-05-30), "Enabling basicauth causes CPU usage to spike"**: on a 1 vCPU / 1 GB Linode, 10-20 req/s from one browser (a netdata dashboard behind `reverse_proxy`) took 60-80 % of the CPU. A pprof profile showed more than 19 s of CPU in a 30 s window, with more than 92 % of it in `blowfish/encryptBlock` (bcrypt). Another user: "Sites with lots of thumbnails would take quite a while to load and I would see a big CPU spike", and called it an easy DoS vector — [caddyserver/caddy#3462](https://github.com/caddyserver/caddy/issues/3462)
- In that thread, maintainer Matt Holt said this is expected with bcrypt and that caching is acceptable "if we assume that the program memory is absolutely a safe place". He first leaned towards opt-in. He rejected a fast hash as the fix, and on DoS said to use "rate limiting, firewalling, and CDN rules" — [caddyserver/caddy#3462](https://github.com/caddyserver/caddy/issues/3462)
- **Caddy's fix (PR #3465, June 2020) as it stands today**: `HashCache` maps "concatenated hashed password + plaintext password" to the boolean result, holds at most 1000 entries, evicts about 1/10 at random when full, uses a `singleflight` group so concurrent identical checks hash only once, and is enabled automatically when configured from the Caddyfile (`ba.HashCache = new(Cache)`), but is opt-in in JSON. The code comment says plaintext passwords "will be stored in memory for a longer time", which is acceptable "since basicauth necessitates plaintext passwords being received over the wire anyway" — [caddy basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go), [caddy caddyfile.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/caddyfile.go)
- Caddy's `caddy hash-password` defaults to **bcrypt cost 14** ("strikes a solid balance between security, usability, and hardware performance"). The argon2id option defaults to time 1 and **46 MiB of memory per hash**. Its help calls bcrypt "legacy, slower" — [caddy bcrypt.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/bcrypt.go), [caddy argon2id.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/argon2id.go), [caddy command.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/command.go)
- Caddy PR #4720 (2022-04-22), "caddyauth: Speed up basicauth provision, deprecate `scrypt`": provisioning was also slow, because a fake hash for unknown users is now precomputed once — [caddyserver/caddy#4720](https://github.com/caddyserver/caddy/pull/4720)
- **Traefik #4791 (2019-04-17)**: the same page took ~20 ms without auth, ~25 ms with bcrypt cost 5 and ~200 ms with cost 11. The issue was closed and frozen with no fix and no caching — [traefik/traefik#4791](https://github.com/traefik/traefik/issues/4791). The current Traefik middleware still calls `goauth.CheckSecret` per request (a `singleflight` dedup was added, no result cache) — [traefik basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go)
- The Traefik CVE text gives another measure: a bcrypt comparison for an existing user took ~166 ms, against ~0.6 ms for an unknown user (CVE-2026-32595) — [NVD CVE-2026-32595](https://nvd.nist.gov/vuln/detail/cve-2026-32595) (snippet only)
- **nginx (2015, older)**: "enabling basic authentication adds between 100 and 150 ms to my otherwise 30-40 ms page load time". Maxim Dounin replied that passwords are checked on every request, that password hashes are CPU-intensive by design, and that the user should pick "something less CPU-intensive" — [nginx mailing list 2015-11](https://mailman.nginx.org/pipermail/nginx/2015-November/049322.html)
- **nginx-devel (2019-07)**: asked whether to use the highest bcrypt cost, Dounin answered that with Basic auth "hashing happens on every user request" and "with high costs you are likely make your site completely unusable" — [nginx-devel 2019-07](https://mailman.nginx.org/pipermail/nginx-devel/2019-July/012362.html)
- A 2017 nginx thread says that many bcrypt-protected requests "could block nginx causing it to slow down severely" — [nginx mailing list 2017-06](https://mailman.nginx.org/pipermail/nginx/2017-June/054129.html) (snippet only)
- **nginx source, current master**: on every request the access handler `ngx_open_file`s the `auth_basic_user_file`, reads it in buffer chunks, finds the user line and calls `ngx_crypt` → libc `crypt_r()` inline. There is no cache of the file or of results. A scheme that libc's `crypt_r()` cannot handle returns HTTP 500 — [ngx_http_auth_basic_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_auth_basic_module.c), [ngx_crypt.c](https://github.com/nginx/nginx/blob/master/src/core/ngx_crypt.c)
- An openHAB forum thread is titled "NGINX Basic Auth extremely slow with OH3 Main UI" (a single-page app making many requests) — [openHAB community](https://community.openhab.org/t/nginx-basic-auth-extremely-slow-with-oh3-main-ui/112312) (page could not be fetched; contents unverified)
- **Contradictory advice**: the second answer (score 10) on Server Fault's "How To limit Nginx Auth_Basic re-tries?" recommends `htpasswd -B -C 12` or `-C 14` as a brute-force defence ("around 1s per password attempt" at 14). That is the same cost that makes every legitimate page load slow — [SF 421046](https://serverfault.com/questions/421046/how-to-limit-nginx-auth-basic-re-tries)
- **Apache**: `htpasswd -B` defaults to cost 5 (allowed range 4-17). MD5 (apr1) has been the default format since 2.2.18 — [Apache htpasswd](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)
- **Apache's caching module `mod_authn_socache`** exists because "an HTML page contains hundreds of objects ... and a request to the page generates hundreds of effectively-immediate requests for authenticated additional contents". Its default `AuthnCacheTimeout` is 300 s. It says file and dbm providers "are unlikely to benefit, as these are fast and lightweight in their own right", and warns that caching "can be a security issue, though short-term caching is unlikely to be a problem" — [mod_authn_socache](https://httpd.apache.org/docs/2.4/mod/mod_authn_socache.html)

### Inferences
- In nginx the bcrypt call runs on the worker's event loop, so one slow verification stalls every connection on that worker, not only the request being checked. This is an inference from the source (inline `crypt_r` in the access phase), not a measured report.
- Apache's documentation assumes the file provider is cheap. With bcrypt in the file that is no longer true, and the docs do not cover that case.
- Workarounds seen in the wild, in order of frequency: lower the cost or use apr1 (the nginx, Apache and Traefik answers); a result cache (Caddy, Apache socache for databases); "use sessions, not basic auth" (Dounin's advice, mholt's DoS reply).
- What a new server could do: cache successful (user, password) verifications for a short time, keyed unambiguously (length-prefixed, or an HMAC of the plaintext under a per-process key so plaintext is not kept); verify off the event loop or limit concurrent verifications; warn at config load when a bcrypt cost (or argon2 memory) would cost more than a few ms per request.
- With Caddy's argon2id defaults, N concurrent cache-missing verifications need N × 46 MiB, which could exhaust memory under a password-spraying attack. This is an inference; no report found.

### Gaps
- No systematic benchmark across servers of requests per second against bcrypt cost was found. The available numbers are anecdotes (Caddy profile, Traefik 25/200 ms, nginx 100-150 ms).
- The openHAB thread's details could not be retrieved.
- No report was found of an nginx `auth_basic` worker stall measured directly (for example with a latency histogram).

## 2. Configuration pitfalls: inheritance, exceptions and holes

### Takeaway
The most-viewed Basic-auth questions on Server Fault are about scoping, not crypto. Typical requests: protect a whole site but exempt a path (API, media, ACME, health check, `admin-ajax.php`, OPTIONS), or exempt an IP range. In nginx a regex `\.php$` location wins over the prefix location that holds `auth_basic`, so PHP scripts can run without auth. Apache's `.htaccess`, `Satisfy` and `Require` merging, and the 2.2→2.4 change, keep surprising people. Certbot and ACME interact badly in both directions: the challenge path returns 401 and fails, and a newly generated HTTPS vhost can silently leave the site open.

### Cited Findings
- **Sitewide auth with exceptions is the top-voted SF basic-auth question**: "Enable basic auth sitewide and disabling it for subpages?" (score 40, 91,667 views, 2011, older). The trap: `location /api/ { auth_basic off; }` matched but had no `proxy_pass` (handlers are not inherited). The accepted workaround (score 44) moves the proxy directives into an include file used by both locations — [SF 330580](https://serverfault.com/questions/330580/enable-basic-auth-sitewide-and-disabling-it-for-subpages)
- The nginx docs show `auth_basic` at server level with `location /public/ { auth_basic off; }`, i.e. `off` cancels inheritance — [nginx admin guide](https://docs.nginx.com/nginx/admin-guide/security-controls/configuring-http-basic-authentication/). One tutorial claims `off` only works when auth is set at location level — [linuxcapable](https://linuxcapable.com/password-protect-nginx-with-basic-authentication/). That claim is contradicted by the nginx docs example (snippet only for linuxcapable).
- **Regex `.php` locations bypass prefix auth in nginx**: requesting `/reports/report.php` matched only the `\.php` regex location, so the `/reports/` auth was skipped. The fix is a nested PHP location inside the protected one, or `location ^~ /reports/` — [nginx mailing list 2008](https://mailman.nginx.org/pipermail/nginx/2008-June/005307.html) (older). The same question keeps recurring: "Nginx - basic http authentication on PHP-script" (score 4, 16,729 views, 2012) — [SF 375961](https://serverfault.com/questions/375961/nginx-basic-http-authentication-on-php-script); "How to use FastCGI globally and Basic Auth in sublocations in nginx?" - **IP-based exceptions**: "How to disable http basic auth in nginx for a specific ip range?" (score 36, 47,225 views, 2011). The accepted answer (72) is `satisfy any; allow ...; deny all;` plus `auth_basic` — [SF 242218](https://serverfault.com/questions/242218/how-to-disable-http-basic-auth-in-nginx-for-a-specific-ip-range). A 2018 alternative (accepted, 19) uses `geo $authentication { default "Authentication required"; 10.8.0.0/24 "off"; }` and `auth_basic $authentication;` (variables allowed since 1.3.10) — [SO 48279160](https://stackoverflow.com/questions/48279160/nginx-http-basic-authentication-with-exceptions-for-particular-ip-addresses). - **`satisfy any` confusion**: "satisfy any causing all clients to be permitted" turned out to be a third-party module returning `NGX_OK` in the access phase — [SF 493413](https://serverfault.com/questions/493413/nginx-reverse-proxy-satisfy-any-causing-all-clients-to-be-permitted). There are similar mailing-list reports of "ALL traffic was allowed in" — [nginx mailing list 2017-04](https://mailman.nginx.org/pipermail/nginx/2017-April/053524.html) (snippet only). ### Inferences
- The shape of the need is clear: "protect this site or prefix, except these paths, methods and addresses". nginx makes that error-prone because `auth_basic` lives on locations, regex locations win over prefixes, and handlers do not inherit. Apache makes it error-prone through `.htaccess` replacement semantics and two generations of directives.
- Exceptions administrators repeatedly need: `/.well-known/acme-challenge/`, health or status endpoints, OPTIONS preflight, application APIs that use their own tokens, `wp-admin/admin-ajax.php`, media or upload folders, and trusted IP ranges.
- When auth is tied to a vhost or listener instead of to the site, adding HTTPS (certbot's new vhost) can drop it silently. A server where protection belongs to the site, whatever the listener, avoids the "certbot opened my site" failure.
- A server that applies auth before location selection (or re-checks it on every internal re-entry) structurally avoids the regex-location bypass.

### Gaps
- No quantitative count across forums was obtained. Stack Exchange free-text totals came out inconsistent (for example `"auth_basic off"` returned 4 hits on SO) and were discarded. Frequency is judged from scores and views of canonical questions.
- Webhook and payment-callback exceptions (Stripe, GitHub, PayPal IPN on staging sites) came up only indirectly. No canonical thread was found within the tool budget.

## 3. Backends: the Authorization header, double prompts, PHP variables

### Takeaway
nginx forwards the client's `Authorization` header to the upstream by default. Applications that do their own auth (Jenkins, JIRA/Tomcat, Bitwarden, LibreChat, any Bearer-token SPA) then either prompt a second time, try to log in with the site password, or fail their API calls with 401. The reverse need is just as common: inject static credentials towards an upstream, or pass the authenticated user name (`X-Forwarded-User`, `REMOTE_USER`). For PHP, `PHP_AUTH_USER` missing under CGI/FastCGI on Apache is a perennial question.

### Cited Findings
- "Jenkins/Nginx - Double prompted for basic auth, why?" (score 10, 8,864 views, 2016). The accepted answer (41): add `proxy_set_header Authorization "";` because "after basic auth Nginx will additionally forward the auth headers to Jenkins" — [SO 35563508](https://stackoverflow.com/questions/35563508/jenkins-nginx-double-prompted-for-basic-auth-why-why-is-there-an-internal-je). The same fix for JIRA/Tomcat: "Don't forward auth to Tomcat" — [SF 511846](https://serverfault.com/questions/511846/basic-auth-for-a-tomcat-app-jira-with-nginx-as-reverse-proxy)
- "Nginx - Forward HTTP AUTH - User" (score 23, 83,894 views, 2013). The accepted answer (31) forwards `Authorization`. The second answer (11) shows the opposite need, for Jenkins's reverse-proxy-auth plugin: `proxy_set_header Authorization ""; proxy_set_header X-Forwarded-User $remote_user;`, because otherwise Jenkins "will try to re-authenticate the user, and fails" — [SF 511206](https://serverfault.com/questions/511206/nginx-forward-http-auth-user)
- "Proxy pass remote_user with nginx" (score 8, 16,195 views, 2017) — [SO 45423424](https://stackoverflow.com/questions/45423424/proxy-pass-remote-user-with-nginx)
- **Application with its own token auth**: LibreChat behind nginx basic auth (Sept 2023). - **Static credentials towards an upstream**: "Authorization header in Nginx for proxying to basic auth backend doesn't work" (score 13, 91,033 views, 2017). The ingress-nginx variant uses `configuration-snippet` + `more_set_input_headers "Authorization: Basic ..."` (score 7) — [SO 59824039](https://stackoverflow.com/questions/59824039/basic-authentication-via-nginx-ingress-controller)
- **PHP**: "PHP_AUTH_USER not set?" (score 53, 85,543 views, 2010, older). The top answer (83) for CGI-mode PHP is `RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]` plus base64-decoding it in PHP — [SO 3663520](https://stackoverflow.com/questions/3663520/php-auth-user-not-set). Also "Why are $_SERVER["PHP_AUTH_USER"] and $_SERVER["PHP_AUTH_PW"] not set?" (score 16, 69,797 views) — [SO 14724127](https://stackoverflow.com/questions/14724127/why-are-serverphp-auth-user-and-serverphp-auth-pw-not-set); "REMOTE_USER and PHP_AUTH_USER sometimes empty" (22,756 views) — [SO 19495552](https://stackoverflow.com/questions/19495552/remote-user-and-php-auth-user-sometimes-empty)
- Apache hides `Authorization` from CGI, FastCGI and SCGI scripts by default. `CGIPassAuth On` (2.4.13+, default Off) passes it, replacing the compile-time `SECURITY_HOLE_PASS_AUTHORIZATION`. It applies to `mod_cgi`, `mod_cgid`, `mod_proxy_fcgi` and `mod_proxy_scgi` — [Apache core: CGIPassAuth](https://httpd.apache.org/docs/2.4/mod/core.html)
- Mobile apps: openHAB thread "iOS app through Nginx Reverse Proxy using Basic Auth [kind of solved]" — [openHAB community](https://community.openhab.org/t/ios-app-through-nginx-reverse-proxy-using-basic-auth-kind-of-solved/96646) (title only; contents unverified). Docker clients: "Docker login not passing basic authentication headers to nginx" (2019) — [SO 55516317](https://stackoverflow.com/questions/55516317/docker-login-not-passing-basic-authentication-headers-to-nginx)

### Inferences
- Two opposite defaults are each wrong half the time: forwarding the site password to the upstream (nginx's default) leaks it to the application and causes double prompts, while stripping it breaks applications that rely on it (WordPress loopback, PHP scripts that read `PHP_AUTH_USER`). A per-site or per-location choice (forward / strip / replace with `X-Forwarded-User`) is what administrators keep building by hand.
- Bearer-token SPAs and native apps cannot coexist with a Basic gate on the same paths, because there is only one `Authorization` header. The workaround is always to exempt the API path, which re-opens it.

### Gaps
- No current documentation was found on whether nginx's stock `fastcgi_params` sets `REMOTE_USER`, or on how php-fpm derives `PHP_AUTH_USER` from `HTTP_AUTHORIZATION` under nginx. It was not verified within the budget.
- No r/selfhosted or Reddit thread could be retrieved directly, so the "basic auth breaks the mobile app" theme rests on forum titles and a search summary.

## 4. Browser behaviour: no logout, per-origin prompts, Safari loops

### Takeaway
Basic auth has no logout: browsers keep credentials until the browser (or tab) closes, and the old "send wrong credentials" tricks no longer work reliably. Credentials are scoped per origin and realm, so every subdomain, scheme and port prompts again, and an HTTP→HTTPS redirect after a prompt asks twice. Safari and iOS have a long tail of "prompts on every page" reports. Browsers have tightened Basic auth (no embedded `user:pass@` URLs for subresources, no cross-origin image prompts). Password managers autofill the native dialog only in narrow conditions.

### Cited Findings

- Administrators want a session-like experience (logout, expiry after N minutes, one login across `*.example.com`) that Basic auth cannot give. - Prompts on plain HTTP and the double prompt around HTTPS redirects suggest a rule: never challenge on a plain listener when the site has HTTPS; redirect first.

- 1Password, Chrome's and Safari's built-in password managers and their Basic-prompt support were not checked.

## 5. Security: brute force, enumeration, weak formats, charset

### Takeaway
None of nginx, Apache, Caddy or Traefik rate-limits failed Basic-auth attempts itself. The answer everywhere is fail2ban on the error log, or an external rate limit. Timing differences between unknown and known users became real CVEs in Traefik in 2026 (three in a row, one of them a broken patch and one introduced by a performance dedup). nginx skips the hash for unknown users and logs the two cases differently. Weak formats are still accepted (`{PLAIN}`, unsalted `{SHA}`, DES `crypt` truncating at 8 characters, apr1 MD5 as Apache's default). Non-ASCII passwords depend on RFC 7617's optional `charset="UTF-8"` and on the browser.

### Cited Findings
- "How To limit Nginx Auth_Basic re-tries?" (score 23, 24,952 views, 2012). Accepted (36): "Auth Basic module doesn't support this feature, but you can do this by using Fail2ban", with a filter on the nginx error log — [SF 421046](https://serverfault.com/questions/421046/how-to-limit-nginx-auth-basic-re-tries). "Nginx: Rate limit failed basic auth attempts" (2020, score 6). Answers: fail2ban, or a hack routing `error_page 401` to a named location under `limit_req` (score 0, its author unsure it protects) — [SF 1000941](https://serverfault.com/questions/1000941/nginx-rate-limit-failed-basic-auth-attempts). "Log invalid login attempts - htpasswd" (20,528 views, 2012) — [SF 460765](https://serverfault.com/questions/460765/log-invalid-login-attempts-htpasswd)
- **fail2ban's shipped `nginx-http-auth` filter** matches only `user "X": password mismatch` and `user "X" was not found in "..."` (plus PAM). The first credential-less request (`no user/password was provided`) is deliberately not counted. It reads `%(nginx_error_log)s` or the journal (`_SYSTEMD_UNIT=nginx.service`), on ports http,https. Its dev note admits "Extensive search of all nginx auth failures not done yet" — [nginx-http-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/nginx-http-auth.conf), [jail.conf](https://github.com/fail2ban/fail2ban/blob/master/config/jail.conf). For Apache, `apache-auth` notes that "An unauthorized response 401 is the first step for a browser to instigate authentication however apache doesn't log this as an error" — [apache-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/apache-auth.conf)
- **nginx source**: an unknown user is logged as `user "%V" was not found in "%s"` and answered with 401 *without* running the hash; a known user with a wrong password runs `crypt_r` and logs `password mismatch`. The comparison is `ngx_strcmp` of the computed against the stored hash — [ngx_http_auth_basic_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_auth_basic_module.c)
- **Traefik user enumeration**: CVE-2026-32595: an existing user takes a ~166 ms bcrypt compare, an unknown one returns in ~0.6 ms; fixed in 2.11.41 / 3.6.11 / 3.7.0-ea.2 — [NVD](https://nvd.nist.gov/vuln/detail/cve-2026-32595) (snippet only). CVE-2026-41263 (published 2026-04-24, CVSS 6.3): "The patch for CVE-2026-32595 is a no-op", because a map key/value confusion made the fallback secret empty, leaving a ~130× timing oracle (0.48 ms vs 62 ms); fixed in 2.11.43, 3.6.14 and 3.7.0-rc.2 (May 2026) — [vuln.today CVE-2026-41263](https://vuln.today/cve/CVE-2026-41263). CVE-2026-71326 (2026-08-03, GHSA-6765-c87h-8mrf): the `singleflight` dedup key concatenated password and stored secret with no delimiter, so an attacker could receive a concurrent legitimate request's success and "authenticate as an arbitrary username"; affected 3.6.11-3.6.24 and 3.7.0-3.7.9, fixed by length-prefixing — [GHSA-6765-c87h-8mrf](https://github.com/traefik/traefik/security/advisories/GHSA-6765-c87h-8mrf), [traefik basic_auth.go](https://github.com/traefik/traefik/blob/master/pkg/middlewares/auth/basic_auth.go)
- **Caddy** compares against a precomputed `fakePassword` for unknown users "so that timing side-channels can be mitigated" — [caddy basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go). Caddy #7349 (2025-11, open) asks for a timing-safe `token_auth`, because people protect APIs with header matchers that are not timing-safe — [caddyserver/caddy#7349](https://github.com/caddyserver/caddy/issues/7349)
- **Weak formats**: nginx accepts libc `crypt()` schemes, `$apr1$`, `{PLAIN}`, `{SHA}` (unsalted SHA-1, vulnerable to rainbow tables, kept for migration) and `{SSHA}` — [nginx auth_basic docs](https://nginx.org/en/docs/http/ngx_http_auth_basic_module.html), [ngx_crypt.c](https://github.com/nginx/nginx/blob/master/src/core/ngx_crypt.c). Apache `htpasswd`: MD5 is the default; `-d` crypt is "insecure" and limits passwords to 8 characters ("extra characters silently discarded"); `-s` SHA-1 is insecure and unsalted; `-p` plaintext only on Windows/Netware — [Apache htpasswd](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)
- Traefik #8870 (2022, open): "Traefik2 dashboards exposes BasicAuth credentials (salted hashes only)" — [traefik/traefik#8870](https://github.com/traefik/traefik/issues/8870)
- **Charset**: "What encoding should I use for HTTP Basic Authentication?" (score 103, 66,893 views, 2011). RFC 2617 left it undefined or ISO-8859-1. RFC 7617 (2015) lets a server send `charset="UTF-8"` in the challenge — [SO 7242316](https://stackoverflow.com/questions/7242316/what-encoding-should-i-use-for-http-basic-authentication), [RFC 7617](https://datatracker.ietf.org/doc/html/rfc7617). Firefox sent ISO-8859-1 until Firefox 59 switched to UTF-8 (bug 1419658), while Chrome, curl and nginx had settled on UTF-8 — [Mozilla bug 1419658](https://bugzilla.mozilla.org/show_bug.cgi?id=1419658) (snippet only). HCL Domino still decodes ISO-8859-1 — [nashcom blog](https://blog.nashcom.de/nashcomblog.nsf/dx/domino-http-basic-authentication-still-uses-iso-8859-1.htm). "HTTP basic authentication URL with '@' in password" (score 57, 65,484 views) — [SO 20574841](https://stackoverflow.com/questions/20574841/http-basic-authentication-url-with-in-password)
- musl's bcrypt reportedly returns null for costs above 19 (relevant for Alpine-based nginx images) — [musl list 2021-01](https://openwall.com/lists/musl/2021/01/28/2) (snippet only)
- **ingress-nginx attack surface**: CVE-2025-24514 (2025-03-25, CVSS 8.8, part of "IngressNightmare"): the `auth-url` annotation allowed nginx configuration injection, leading to code execution in the controller and Secret disclosure; fixed in 1.11.5 / 1.12.1 — [Tenable CVE-2025-24514](https://www.tenable.com/cve/CVE-2025-24514)

### Inferences
- Administrators want rate limiting of *failed* attempts per source (and per user) built in, plus a log line in a stable, documented format that fail2ban already understands. The fail2ban regex is tied to nginx's exact wording, so a new server that wants to reuse the shipped `nginx-http-auth` filter would have to emit identical lines; otherwise it ships its own filter.
- The Traefik CVE chain shows that performance work on verification (dedup, caching) is security-critical: keys must be length-prefixed and include the user, and unknown users must cost the same as known ones. nginx's current behaviour (no hash for unknown users) is the same timing oracle Traefik was given CVEs for. This is inferred from the source; no nginx advisory was found.
- Rejecting or warning on `{PLAIN}`, `{SHA}`, DES crypt (8-character truncation) and very high bcrypt costs at configuration load would address both the security and the performance complaints.

### Gaps
- No nginx or Apache advisory about Basic-auth timing enumeration was found. Whether nginx considers it in scope is unknown.
- No current data was found on brute-force volumes against Basic-auth endpoints, such as honeypot statistics.

## 6. Tooling: htpasswd availability, formats, many servers, Kubernetes

### Takeaway
Creating the file is a recurring obstacle. `htpasswd` lives in `apache2-utils` / `httpd-tools`, which nginx-only hosts and slim container images lack. `openssl passwd` cannot make bcrypt. Which formats a given server accepts is unclear (and for nginx's bcrypt it depends on libc). Each proxy has its own syntax: Caddy wants pre-hashed values, Traefik needs `$$` in compose labels, ingress-nginx needs a Secret with key `auth`.

Apache `htpasswd` warns to keep password files outside the URI space and not to use `-b` (password visible on the command line) — [Apache htpasswd](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)

### Inferences
- A server that can create and update users itself (its own CLI or control API, bcrypt or argon2id with a sane cost, no external package) removes the single most-viewed class of questions (installing and using `htpasswd`).
- Accepting existing htpasswd files (apr1, SHA-crypt, bcrypt) eases migration from nginx and Apache. Refusing `{PLAIN}`, `{SHA}` and DES, or warning about them, avoids silently weak setups.
- Edit-without-reload (nginx's per-request file read) is a feature administrators rely on. A server that caches the file should re-stat it rather than require a reload.

### Gaps
- "Editing files on many servers" (Ansible's `htpasswd` module, configuration management, shared user stores) was not researched; no source was gathered.
- The ingress-nginx `auth-secret-type` (`auth-file` vs `auth-map`) annotation was not confirmed from the docs page fetched.

### Inferences
- Most of the high-traffic SE questions date from 2009-2015, but the same themes reappear in 2018-2026 material (Traefik and ingress questions 2018-2020, Caddy 2020-2026, Traefik CVEs 2026, LE threads 2024-2026). The problems persist; the canonical Q&A is simply old.
- A new server that wants to avoid this catalogue would provide:
  - site-level protection that survives adding HTTPS;
  - path, method and address exceptions that cannot be bypassed by location precedence, with ACME, OPTIONS and health checks handled by default;
  - an explicit forward/strip/replace policy for `Authorization`;
  - built-in user management with a modern hash and a result cache keyed safely;
  - constant-cost handling of unknown users;
  - built-in failed-attempt limiting with fail2ban-compatible log lines;
  - `charset="UTF-8"` in the challenge;
  - optionally a session cookie after the first login, for logout and expiry.

### Gaps
- Stack Exchange view counts measure search traffic over 10-15 years, not current incidence. No source gives the share of today's deployments that hit each problem.
- Reddit (r/nginx, r/selfhosted, r/sysadmin) could not be fetched; that community's view is missing apart from forum and GitHub proxies.
- trac.nginx.org tickets on `auth_basic` were not surveyed (only the mailing lists and the source).
