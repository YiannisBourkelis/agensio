# Web server HTTP Basic authentication: standards and security guidance (as of 2026-10-08)

Sources: the RFC texts were downloaded from rfc-editor.org and quoted verbatim; the Fetch Standard (version "Last Updated 6 October 2026") was downloaded and grepped; libxcrypt man pages and `lib/hashes.conf` came from the `develop` branch on GitHub; the Apache, Caddy and nginx source excerpts came from their GitHub mirrors. The "local measurement" rows come from a C program written for this research, linked against libxcrypt 4.4.38 (Debian 13 `libcrypt1 1:4.4.38-1`), on one thread of an AMD Ryzen 9 9900X (the project's Linux box). They are a first-hand measurement, not a published source.

## Q1. Protocol rules: RFC 7617 and RFC 9110 (challenge, credentials, case rules, 401 / 403 / 407)

### Takeaway
A Basic challenge is `WWW-Authenticate: Basic realm="..."` with an optional `charset="UTF-8"`, and realm is mandatory. The credentials are the base64 encoding of `user-id ":" password`. The first colon splits the two, and neither part may contain control characters. Scheme and parameter names are case-insensitive. Missing or wrong credentials get a 401 with a challenge. Valid credentials that are not allowed in get a 403, or a 404 to hide the resource. A proxy uses 407 with Proxy-Authenticate / Proxy-Authorization instead.

### Cited Findings
**RFC 7617 (The 'Basic' HTTP Authentication Scheme, 2015)**
- Sec. 2: "The authentication parameter 'realm' is REQUIRED"; "The authentication parameter 'charset' is OPTIONAL"; "No other authentication parameters are defined -- unknown parameters MUST be ignored by recipients"; "Note that both scheme and parameter names are matched case-insensitively." — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2: "The realm value is a free-form string that can only be compared for equality with other realms on that server." — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2: credentials use the "token68" syntax. The client "constructs the user-pass by concatenating the user-id, a single colon (":") character, and the password", encodes it to octets, then applies "Base64 ([RFC4648], Section 4)". Example: `Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==` (Aladdin / open sesame). — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2: "The user-id and password MUST NOT contain any control characters (see "CTL" in Appendix B.1 of [RFC5234])." — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2: "a user-id containing a colon character is invalid, as the first colon in a user-pass string separates user-id and password from one another; text after the first colon is part of the password." Also: "many user agents produce user-pass strings without checking that user-ids supplied by users do not contain colons; recipients will then treat part of the username input as part of the password." — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2: the default octet encoding is left undefined "for backwards compatibility reasons ... as long as it is compatible with US-ASCII". — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 2.1: `charset` is "purely advisory". "The only allowed value is "UTF-8"; it is to be matched case-insensitively". It means the server expects NFC normalisation and UTF-8 encoding. Recipients "MUST support all characters defined in the "UsernameCasePreserved" profile ... [RFC7613], with the exception of the colon" for the user-id, and the "OpaqueString" profile for the password. Example: `WWW-Authenticate: Basic realm="foo", charset="UTF-8"`. — [RFC 7617 §2.1](https://datatracker.ietf.org/doc/html/rfc7617#section-2.1). (RFC 7613 has since been obsoleted by [RFC 8265](https://datatracker.ietf.org/doc/html/rfc8265), which keeps the same profile names.)
- Sec. 2.2: the authentication scope is the request URI with everything after the last "/" of the path removed. "A client SHOULD assume that resources identified by URIs with a prefix-match of the authentication scope are also within the protection space", and "MAY preemptively send the corresponding Authorization header field". For example, after `http://example.com/docs/index.html`, `/docs/test.doc` is inside the scope, while `/other/` and the `https://` variant are outside it. — [RFC 7617 §2.2](https://datatracker.ietf.org/doc/html/rfc7617#section-2.2)
- Sec. 2: "A proxy can respond with a similar challenge using the 407 (Proxy Authentication Required) status code ... and the Proxy-Authenticate header field". — [RFC 7617 §2](https://datatracker.ietf.org/doc/html/rfc7617#section-2)
- Sec. 4: Basic "SHOULD NOT be used (without enhancements such as HTTPS [RFC2818]) to protect sensitive or valuable information". Servers "ought to avoid storing user passwords in plaintext or as unsalted digests". It warns about password reuse across sites and about spoofing by counterfeit servers. It also says components "that can take over control over the message framing on an existing connection need to be used carefully or not at all (for instance: NPH ... scripts)". — [RFC 7617 §4](https://datatracker.ietf.org/doc/html/rfc7617#section-4)

**RFC 9110 (HTTP Semantics, 2022; obsoletes RFC 7235, which RFC 7617 cites)**
- §11.1: HTTP "uses a case-insensitive token to identify the authentication scheme". — [RFC 9110 §11.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.1)
- §11.2: `token68 = 1*( ALPHA / DIGIT / "-" / "." / "_" / "~" / "+" / "/" ) *"="`. Auth-param names are "matched case-insensitively and each parameter name MUST only occur once per challenge". Parameter values may be token or quoted-string, and recipients have to accept both. — [RFC 9110 §11.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.2)
- §11.4: "Upon receipt of a request for a protected resource that omits credentials, contains invalid credentials (e.g., a bad password) or partial credentials ..., an origin server SHOULD send a 401 (Unauthorized) response that contains a WWW-Authenticate header field with at least one (possibly new) challenge". "A server that receives valid credentials that are not adequate to gain access ought to respond with the 403 (Forbidden) status code". — [RFC 9110 §11.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.4)
- §11.5: a protection space is "the origin ... of the server being accessed, in combination with the realm value if present". "the user agent MAY reuse the same credentials for all other requests within that protection space for a period of time determined by the authentication scheme, parameters, and/or user preferences". For realm, "a sender MUST only generate the quoted-string syntax". — [RFC 9110 §11.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.5)
- §11.6.1: "A server generating a 401 (Unauthorized) response MUST send a WWW-Authenticate header field containing at least one challenge. A server MAY generate a WWW-Authenticate header field in other response messages". Several challenges on one field line "might not be interoperable". — [RFC 9110 §11.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.6.1)
- §11.6.2: "A proxy forwarding a request MUST NOT modify any Authorization header fields in that request." Caching of those responses is deferred to RFC 9111 §3.5. — [RFC 9110 §11.6.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.6.2)
- RFC 9111 §3.5: "A shared cache MUST NOT use a cached response to a request with an Authorization header field ... to satisfy any subsequent request unless the response contains a Cache-Control field with a response directive ... that allows it". Those directives are must-revalidate, public and s-maxage. — [RFC 9111 §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5)
- §11.7.1 / 11.7.2: "A proxy MUST send at least one Proxy-Authenticate header field in each 407 ... response that it generates". Proxy-Authenticate "applies only to the next outbound client on the response chain". Proxy-Authorization "applies only to the next inbound proxy that demanded authentication". — [RFC 9110 §11.7](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.7)
- §15.5.2 (401): "The server generating a 401 response MUST send a WWW-Authenticate header field". "If the request included authentication credentials, then the 401 response indicates that authorization has been refused for those credentials. The user agent MAY repeat the request with a new or replaced Authorization header field". If the same challenge comes back after a failed attempt, the UA "SHOULD present the enclosed representation to the user". — [RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2)
- §15.5.4 (403): "If authentication credentials were provided in the request, the server considers them insufficient to grant access. The client SHOULD NOT automatically repeat the request with the same credentials. The client MAY repeat the request with new or different credentials. However, a request might be forbidden for reasons unrelated to the credentials." "An origin server that wishes to "hide" the current existence of a forbidden target resource MAY instead respond with a status code of 404". — [RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)
- §15.5.8 (407): similar to 401, "The proxy MUST send a Proxy-Authenticate header field". — [RFC 9110 §15.5.8](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.8)
- §17.16.1: "HTTP depends on the security properties of the underlying transport- or session-level connection to provide confidential transmission of fields. Services that depend on individual user authentication require a secured connection prior to exchanging credentials". — [RFC 9110 §17.16.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.1)
- §17.16.2: "Existing HTTP clients and user agents typically retain authentication information indefinitely. HTTP does not provide a mechanism for the origin server to direct clients to discard these cached credentials". — [RFC 9110 §17.16.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.2)
- §17.16.3: realm-only protection spaces "expose credentials to all resources on an origin server ... This makes it possible for a different resource to harvest authentication credentials". This is "of particular concern when an origin server hosts resources for multiple parties under the same origin". The mitigations are "not making the content of the Authorization request header field available" and "using a different host name (or port number) for each party". — [RFC 9110 §17.16.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.3)
- MDN summarises the same split: invalid credentials get 401/407, and "valid credentials that are inadequate" get 403. — [MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)

### Inferences
- Parser rules that follow from the above. Match the scheme `Basic` case-insensitively. Accept one or more SP before the token68. Decode with the RFC 4648 §4 alphabet and padding. Split at the first `:`. Reject any CTL (0x00-0x1F, 0x7F) in either part.
- Rejecting NUL matters on its own: base64 can decode to a 0x00 byte, and `crypt_rn()` takes C strings. A password `secret\0junk` would otherwise be hashed as `secret`. The same applies to any C API.
- A malformed `Authorization` value should get the same 401 + challenge as wrong credentials. The RFC lists "invalid" credentials under 401, and the same answer avoids a distinguishable error path.
- Status mapping:
  - no, malformed or wrong credentials → 401 + `WWW-Authenticate: Basic realm="…", charset="UTF-8"`;
  - correct password for a user outside the location's allowed user list → 403, or 404 to hide;
  - refusals unrelated to credentials (IP access rules, rate limits) → 403 / 429 rather than 401. A 401 would make the browser re-prompt.
  - The 429 status itself is RFC 6585 and was not part of this research.
- Send one challenge per `WWW-Authenticate` field line, with the realm as a quoted-string, prebuilt per location. Don't put several challenges on one line (§11.6.1 interop note).
- Answers that the server caches or prebuilds for public use must not be reused for authenticated requests. Under RFC 9111 §3.5 a downstream shared cache will not reuse them unless the server sends `public`, `s-maxage` or `must-revalidate`. So the static handler's prebuilt `Cache-Control` blocks need care on Basic-protected locations: `immutable`/`public` blocks from presets would make authenticated content cacheable by CDNs.
- §17.16.3 maps onto multi-tenant hosting. Two parties under one host name share a protection space. The proxy handler forwards `Authorization` to the upstream as is (§11.6.2 forbids modifying it), so an upstream application sees the Basic password unless the edge strips the header when the edge consumed it. Whether to strip is a design decision, and the RFC text supports stripping only as a "restricting direct access" mitigation.

### Gaps
- RFC 7617 does not say what a recipient must answer when the decoded user-pass has no colon or contains CTLs; 401 is an inference.
- I didn't check whether major servers send `charset="UTF-8"` by default. nginx and Apache are believed not to, but that is unverified.

## Q2. How browsers handle Basic auth today

### Takeaway
Browsers keep Basic credentials per origin and realm for the session, and no header revokes them except `Clear-Site-Data: "cookies"` over HTTPS. `user:pass@host` URLs are blocked for subresources and stripped elsewhere. Cross-origin subresources such as images can no longer raise the login dialog. `fetch()` cannot carry URL credentials, and CORS preflights never carry credentials, so a Basic-protected API must answer OPTIONS preflights without demanding auth. Plain-HTTP Basic is still allowed by default. Chrome (since 88) and Firefox (since 136) let administrators turn it off, and Chrome 154 (scheduled for October 2026) warns before any public plain-HTTP site.

### Cited Findings
- Encoding: "Browsers use `utf-8` encoding for usernames and passwords. Firefox once used `ISO-8859-1`, but changed to `utf-8` for parity with other browsers" (Firefox bug 1419658). — [MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)
- Credential lifetime: UAs "typically retain authentication information indefinitely". HTTP has no mechanism to make them discard it, and UAs "are encouraged to provide a readily accessible mechanism for discarding cached credentials under user control". — [RFC 9110 §17.16.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.16.2)
- Logout: the `Clear-Site-Data` directive `"cookies"` removes cookies, and "HTTP authentication credentials are also cleared out. This affects the entire registered domain, including subdomains." It is "available only in secure contexts (HTTPS)" and "Baseline ... available across browsers since September 2023". — [MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data). The per-directive support table was not extracted (see Gaps).
- CSRF: "sites that use HTTP Basic Auth are particularly vulnerable to Cross-Site Request Forgery (CSRF) attacks because the user credentials are sent in all requests regardless of origin (this differs [from] cookie-based credential mechanisms, because cookies are commonly blocked in cross-site requests)". — [MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)
- Credentials in URLs: "`https://username:password@www.example.com/` This syntax is no longer allowed in modern browsers; the username and password are stripped from the request before it is sent." — [MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)
- Chrome deprecated embedded credentials in subresource requests in Chrome 57. The reason given: "Hard-coding credentials into subresource requests is problematic ... it's allowed hackers to brute-force credentials", especially requests "that reach into internal IP ranges (your routers, etc.)". — [Chrome 57 deprecations](https://developer.chrome.com/blog/chrome-57-deprecations/). The console message reads "Subresource requests whose URLs contain embedded credentials (e.g. `https://user:pass@host/`) are blocked", and the opt-out flag is `--disable-blink-features=BlockCredentialedSubresources`. — [FlightAware forum report](https://discussions.flightaware.com/t/requests-whose-urls-contain-embedded-credentials-blocked/20218), [Ionic forum](https://forum.ionicframework.com/t/blockcredentialedsubresources/135630); feature entry [chromestatus 5669008342777856](https://chromestatus.com/feature/5669008342777856) (page did not render for me). The blocking milestone, M59, comes from those secondary reports.
- Fetch Standard, Request constructor: "If parsedURL includes credentials, then throw a TypeError." So `fetch("https://u:p@host/")` fails outright. Redirects to a URL with credentials are a network error for CORS requests. — [Fetch Standard §5.4 / §4.4](https://fetch.spec.whatwg.org/)
- Fetch Standard, CORS: "Note that even so, a CORS-preflight request never includes credentials." The preflight is an `OPTIONS` request, and the real request proceeds only "If a CORS check for request and response returns success and response's status is an ok status". Otherwise the result is a network error. — [Fetch Standard §3.3.5, §4.8 CORS-preflight fetch](https://fetch.spec.whatwg.org/#cors-preflight-fetch)
- Fetch Standard: "A CORS non-wildcard request-header name is a header name that is a byte-case-insensitive match for `Authorization`". So `Access-Control-Allow-Headers: *` does not cover Authorization; it has to be listed by name. — [Fetch Standard](https://fetch.spec.whatwg.org/)
- Fetch Standard, 401 handling: the UA prompts for username and password only "If response's status is 401, httpRequest's response tainting is not "cors", includeCredentials is true, and request's traversable for user prompts is a traversable navigable". Cross-origin CORS fetches never show the dialog; they just get the 401. Credentials are included when the credentials mode is "include", or "same-origin" with basic tainting. — [Fetch Standard §4.6 HTTP-network-or-cache fetch](https://fetch.spec.whatwg.org/#http-network-or-cache-fetch)
- Practitioner reports agree: the preflight "never includes credentials (default browser behavior), but the server replies with a 401", and the workaround is to exempt OPTIONS from authentication. — [Baeldung, CORS preflight and Spring Security](https://www.baeldung.com/fixing-401s-with-cors-preflights-and-spring-security); [Spring Security issue 7444](https://github.com/spring-projects/spring-security/issues/7444)
- Cross-origin dialogs: "From Firefox 59 onwards, image resources loaded from different origins to the current document are no longer able to trigger HTTP authentication dialogs (Firefox bug 1423146)". — [MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication). The Firefox pref `network.auth.subresource-http-auth-allow` takes 0 (no sub-resource dialogs), 1 (same-origin only) or 2 (cross-origin allowed). — [arkenfox user.js issue 585](https://github.com/arkenfox/user.js/issues/585), [Mozilla test](https://kdab.searchfox.org/firefox-main/source/netwerk/test/unit/test_auth_dialog_permission.js). The pref's current default is reported inconsistently (see Gaps). A W3C webappsec thread notes Chrome blocked cross-origin image prompts first. — [public-webappsec 2015-09](https://lists.w3.org/Archives/Public/public-webappsec/2015Sep/0051.html)
- Basic over plain HTTP, Chrome: the enterprise policy `BasicAuthOverHttpEnabled` (since Chrome 88) allows Basic challenges over non-secure HTTP when enabled or unset, and when disabled "forbids non-secure HTTP requests from using the Basic authentication scheme". It is ignored if `AuthSchemes` excludes Basic. — [Samsung Internet policy mirror](https://developer.samsung.com/browser/policy/basic-auth-over-http-enabled.html), [Chromium commit](https://chromium.googlesource.com/chromium/src/+/a8cb48c920b87f5ad23b2e685c201e14e80274e7)
- Basic over plain HTTP, Firefox: bug 1763671 added the pref `network.http.basic_http_auth.enabled`, shipped in Firefox 136. When it is disabled the browser returns the 401 without prompting, "matching" the Chrome and Edge policies. — [Bugzilla 1763671](https://bugzilla.mozilla.org/show_bug.cgi?id=1763671). An older request for a plaintext warning in the Firefox auth dialog (bug 1185145) was closed as a duplicate of 333521. A commenter there noted that users cannot tell Digest from Basic in the prompt. — [Bugzilla 1185145](https://bugzilla.mozilla.org/show_bug.cgi?id=1185145)
- HTTPS by default: Chrome 154, scheduled for October 2026, turns "Always Use Secure Connections" on by default for public sites. Users have to approve a warning before visiting a public site that doesn't support HTTPS. Chrome 147 (April 2026) enabled it earlier for Enhanced Safe Browsing users. — [Google Security Blog, Oct 2025](https://security.googleblog.com/2025/10), [CyberInsider](https://cyberinsider.com/chrome-will-default-to-https-for-all-public-sites-starting-october-2026/)
- Password-field warnings on HTTP pages (Firefox 51/52, Chrome 56, Safari 11.1) apply to login forms, and the sources describe them only for forms. — [DigiCert on Safari 11.1](https://www.digicert.com/blog/safari-warns-about-unsecure-logins), [Graham Cluley on Firefox 52](https://grahamcluley.com/firefox-52-warns-try-enter-passwords-non-encrypted-websites/)

### Inferences
- A Basic-protected location that also serves cross-origin API clients must answer `OPTIONS` requests carrying `Access-Control-Request-Method` without a 401. The real request then carries `Authorization`, and the response needs `Access-Control-Allow-Credentials: true`, an exact origin, and `Authorization` listed explicitly in Allow-Headers.
- agensio's static locations already answer OPTIONS with 204 + Allow. Auth placed before the method policy would break preflights; the auth check placed after OPTIONS handling would not.
- Server-side "logout" options: send `Clear-Site-Data: "cookies"` over HTTPS on a logout URL, or answer one request with a 401 (the UA MAY re-prompt, §15.5.2). Neither is guaranteed across browsers.
- Since the browser sends credentials automatically on cross-site requests (MDN CSRF note), Basic auth should not protect state-changing endpoints without CSRF defences. Browsers send `Sec-Fetch-Site` / `Origin` headers that the server could check, but that is not sourced here.

### Gaps
- I could not confirm from a primary source what Chrome's or Safari's native HTTP-auth dialog shows over plain HTTP. Recollection, unverified: Chrome's dialog says "Your connection to this site is not private".
- Safari has no documented equivalent of the Chrome policy or the Firefox pref that I could find.
- The default of `network.auth.subresource-http-auth-allow`: one search summary said 2, while hardening guides set 1. Not settled.
- The chromestatus page (JS-rendered) did not load, so the exact M59 milestone rests on secondary sources.
- The per-directive Clear-Site-Data support in Safari and Firefox (the `cookies` directive clearing HTTP auth) was not extracted from MDN's compat table.

## Q3. Password hashing: algorithms, parameters, what to refuse, verification cost

### Takeaway
Current guidance (OWASP 2025/26, NIST SP 800-63B-4 of August 2025, RFC 9106) gives this order: Argon2id, then scrypt, with bcrypt for legacy only and PBKDF2 when FIPS applies. Salts are at least 32 bits (NIST) and the cost is "as high as practical". Passwords are never truncated (NIST), which rules out bcrypt for passwords over 72 bytes. libxcrypt, the system library on Debian, Ubuntu and Fedora, recommends yescrypt (`$y$`) and has no Argon2. Formats to refuse include `$1$`, `$apr1$`, `{SHA}`, DES crypt, NT, SunMD5 and bigcrypt. On one modern core, yescrypt at its default cost takes about 6.6 ms and about 16 MiB per verification, and bcrypt at cost 10 about 33 ms. Basic auth checks the password on every request, so without a cache of verified credentials this throttles a server to about 150 requests per second per core.

### Cited Findings
**OWASP Password Storage Cheat Sheet**
- Argon2id is the first choice: "a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism". Equivalent options: m=47104 (46 MiB) t=1 p=1; m=19456 (19 MiB) t=2 p=1; m=12288 t=3; m=9216 t=4; m=7168 (7 MiB) t=5, all p=1. — [OWASP Password Storage CS](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (fetched from the [GitHub source](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/Password_Storage_Cheat_Sheet.md))
- scrypt: minimum N=2^17 (128 MiB), r=8, p=1, or 2^16/r8/p2, 2^15/p3, 2^14/p5, 2^13 (8 MiB)/p10. — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- bcrypt for legacy systems: "work factor of 10 or more" and "a password limit of 72 bytes". Pre-hashing risks null-byte collisions; the safe form given is `bcrypt(base64(hmac-sha384(data:$password, key:$pepper)), $salt, $cost)`. — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- PBKDF2 when FIPS-140 applies: HMAC-SHA-256 with 600,000 iterations, HMAC-SHA-512 with 220,000, HMAC-SHA-1 with 1,400,000 (legacy). — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- A hash should "take less than one second". A pepper is defence in depth, stored apart from the hashes. Legacy hashes are upgraded by expiry plus reset, or by layering (`bcrypt(md5($password))`) until the next login. — [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

**NIST SP 800-63B-4 (final, published 2025-08-26), §3.1.1.2 and §3.2.2**
- Minimum 15 characters for single-factor passwords and 8 within MFA. "SHOULD permit a maximum password length of at least 64 characters". "SHOULD accept all printing ASCII characters and the space character" and Unicode, with NFC "applied before hashing". No composition rules and no periodic changes (SHALL NOT). Candidates are checked against a blocklist. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- "Verifiers SHALL request the password to be provided in full ... and SHALL verify the entire submitted password (e.g., not truncate it)." — [NIST SP 800-63B-4 §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html)
- "Passwords SHALL be salted and hashed using a suitable password hashing scheme ... The chosen cost factor SHOULD be as high as practical without negatively impacting verifier performance. It SHOULD be increased over time ... An approved password hashing scheme published in the latest revision of [SP800-132] or updated NIST guidelines ... SHOULD be used." "The salt SHALL be at least 32 bits". A reference to the scheme and cost "SHOULD be stored for each password to allow migration". An additional keyed hashing step with a secret key "stored separately from the hashed passwords" is a SHOULD, ideally inside an HSM, TEE or TPM. — [NIST SP 800-63B-4 §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html)

**RFC 9106 (Argon2), §4**
- "FIRST RECOMMENDED option": Argon2id t=1, p=4, m=2^21 (2 GiB), 128-bit salt, 256-bit tag. "SECOND RECOMMENDED" when memory is short: t=3, p=4, m=2^16 (64 MiB). For "Frontend server authentication", it suggests 0.5 s on a 2 GHz CPU using 2 cores, with Argon2id, 4 lanes and 1 GiB of RAM. — [RFC 9106 §4](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)

**libxcrypt crypt(5) and hashes.conf**
- yescrypt `$y$`: "Recommended for new hashes". Cost "1 to 11 (logarithmic, also affects memory usage)"; salt "up to 512 (128+ recommended)" bits; no passphrase length limit. — [libxcrypt crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)
- gost-yescrypt `$gy$` and sm3-yescrypt `$sm3y$`: "Acceptable for new hashes where required". scrypt `$7$`: cost "6 to 11". — [crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)
- bcrypt `$2b$`: maximum passphrase 72 characters, cost "4 to 31 (logarithmic)". "$2y$" is "equivalent to "$2b$""; "$2a$" and "$2x$" "provide bug-compatibility with crypt_blowfish 1.0.4 and earlier, which incorrectly processed characters with the 8th bit set." — [crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)
- sha512crypt `$6$` and sha256crypt `$5$`: "Acceptable for new hashes. The default processing cost parameter is 5000, which is too low for modern hardware." Rounds run from 1000 to 999,999,999. — [crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)
- These "should not be used for new hashes": sha1crypt `$sha1`, SunMD5 `$md5`, md5crypt `$1$` ("MD5 is so cheap on modern hardware ... Processing cost is not adjustable"), bsdicrypt `_`, bigcrypt. DES: "it is feasible to discover any passphrase hashed with this method", and it truncates to 8 characters. NT `$3$`: "so weak that almost any human-chosen passphrase hashed with this method is guessable". — [crypt(5)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.5)
- `hashes.conf` flags: STRONG = yescrypt, gost_yescrypt, sm3_yescrypt, scrypt, bcrypt ($2b$, $2y$, $2a$), sha512crypt. DEFAULT = yescrypt, bcrypt, sha512crypt. yescrypt carries the DEBIAN and FEDORA flags. There is no `$apr1$` (Apache MD5) and no Argon2 entry. — [libxcrypt lib/hashes.conf](https://github.com/besser82/libxcrypt/blob/develop/lib/hashes.conf). The README advises `--enable-hashes=strong` for "Security-conscious environments". — [libxcrypt README](https://github.com/besser82/libxcrypt/blob/develop/README.md)

**htpasswd (what users will bring)**
- Apache `htpasswd`: MD5 (`$apr1$`) "has been the default since version 2.2.18". `-B` bcrypt is "currently considered very secure", with `-C` cost default 5 and range 4-17. `-2` / `-5` select SHA-256 / SHA-512 crypt with `-r` rounds (default 5000). `-d` crypt() is "insecure", 8-character limit, "extra characters silently discarded". `-s` SHA-1 is insecure and unsalted. `-p` plaintext. Usernames are at most 255 bytes and cannot contain `:`. — [Apache htpasswd](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)

- Local test: bcrypt silently truncates. Two 73-byte passwords that differ only in byte 73 verify as equal under `$2b$`, while yescrypt tells them apart. ### Inferences
- For a server that links libxcrypt, the practical "accept" set is `$y$`, `$gy$`, `$7$`, `$2b$/$2y$` (warn about the 72-byte limit and the NIST no-truncation rule), and `$6$`/`$5$` (warn when rounds < some floor). That matches libxcrypt's STRONG set plus sha256crypt.
- The "refuse at config load" set: `$1$`, `$apr1$` (libxcrypt can't verify it anyway), `{SHA}`, `{SSHA}`, `{PLAIN}`, plaintext, DES (13-character hashes), `_` bsdicrypt, bigcrypt, `$3$`, `$md5`, `$sha1`, and `$2a$`/`$2x$` (8-bit bugs).
- Argon2id would need libargon2 or OpenSSL 3.2+'s Argon2 KDF. OpenSSL 3.2's Argon2 is from memory and unverified. Either is a new dependency or code path that the CLAUDE.md rules require to be justified. yescrypt through the system libcrypt needs no new vendored code on Linux.
- For a helper that writes new hashes: yescrypt at cost 5 (the Debian default) costs about 6.6 ms and 16 MiB. That is well under OWASP's "< 1 s" and close in memory to OWASP's Argon2id minimum of 19 MiB.

### Gaps
- OWASP does not mention yescrypt at all, so no OWASP-style parameter table exists for it; equivalence to Argon2id is not established by any source here.
- NIST approves only SP 800-132 schemes (PBKDF2). Whether yescrypt, scrypt or Argon2 are "approved" under "updated NIST guidelines" is not stated in the text read.
- RHEL 9/10 default `ENCRYPT_METHOD` is not verified. Recollection: SHA512, for FIPS reasons.

## Q4. Caching verified credentials, constant-time comparison, enumeration by timing

### Takeaway
Apache's mod_authn_socache does not cache verification results. It caches the provider's stored hash, keyed by `context:user`, for 300 s, and still runs the hash verification on every request, so it saves the backend lookup but not the CPU. Caddy's optional `hash_cache` does cache results. Its key is the stored hash concatenated with the plaintext password, so the plaintext stays in memory. The cache holds both true and false results, is capped near 1,000 entries with random eviction, and collapses concurrent identical checks with singleflight. Because the key contains the stored hash, a password change invalidates old entries automatically. Caddy and OWASP both defend against username enumeration by hashing against a fake hash for unknown users and by not exiting early.

### Cited Findings
- mod_authn_socache "maintains a cache of authentication credentials". Default `AuthnCacheTimeout 300 (5 minutes)`. `AuthnCacheContext` defaults to `directory` and can be `server` or a custom string. Sharing contexts "has potential to become a vector for cross-site or cross-application security breaches, so this directive is not permitted in .htaccess contexts". Guidance: "short-term caching is unlikely to be a problem ... cache credentials for as long as it takes to relieve the load on a backend, but no longer". Cached credentials might "'accidentally' extend a session". — [Apache mod_authn_socache](https://httpd.apache.org/docs/2.4/mod/mod_authn_socache.html)
- mod_authn_socache source: `construct_key` returns `context ":" user` for Basic (`context ":" user ":" realm` for Digest). `ap_authn_cache_store(r, module, user, realm, data)` stores the provider's `data`, which is the stored password hash. On lookup, the module calls `ap_password_validate(r, user, password, val)`, so every request still pays for the hash. Under contention the store is skipped ("not cached (mutex busy)"). — [httpd trunk modules/aaa/mod_authn_socache.c](https://github.com/apache/httpd/blob/trunk/modules/aaa/mod_authn_socache.c)
- Caddy `basic_auth` `hash_cache`: "a mapping of plaintext passwords to their hashes will be cached in memory (with random eviction) ... with the downside that plaintext passwords will be stored in memory for a longer time ... Note that a cache hit does not mean it is a valid password." In the code, `cacheKey := hex.EncodeToString(append(account.password, plaintextPassword...))`. The value is a bool (match or not). Requests for the same key share one compare through `singleflight.Group`. At 1,000 entries `makeRoom()` deletes about a tenth at random. — [Caddy caddyauth/basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)
- Caddy enumeration defence: when the user is not found, "we use a fake password to simulate realistic CPU cycles". `fakePassword` comes from `hasher.FakeHash()`, and the `Comparer` interface promises to "securely compare ... in constant-time". — [Caddy basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)
- OWASP: compare with a vetted function, or else one that "Has a maximum input length, to protect against denial of service attacks with very long inputs" and "Returns in constant time". — [OWASP Authentication CS, "Compare Password Hashes Using Safe Functions"](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- OWASP: respond "with a generic error message regardless of whether: The user ID or password was incorrect. The account does not exist. The account is locked or disabled." The "quick exit" pattern (fail fast if the user doesn't exist) creates a timing difference, and the fix is to hash in every case. — [OWASP Authentication CS, "Authentication and Error Messages"](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- The output of `crypt_rn` is "entirely printable ASCII" and contains no whitespace, `:`, `;`, `*`, `!` or `\`. On error the output is an "invalid hash" that is "shorter than 13 characters, will begin with a '*', and will not compare equal to setting", and `crypt_rn`/`crypt_ra` return NULL. — [libxcrypt crypt(3)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.3)

### Inferences
- A cache that is safe and fast for an event-loop server would use this key: `HMAC-SHA256(k_process, stored_hash_string || 0x00 || user || 0x00 || password)`, where `k_process` is random at start and never stored.
  - No plaintext stays resident, unlike Caddy.
  - Including the stored hash string makes a password change or reload a miss with no explicit invalidation, the same effect Caddy gets from its key.
  - Compare the 32-byte MAC with `CRYPTO_memcmp`.
- Recommended cache behaviour:
  - Cache only successes. Caching failures, as Caddy does, lets an attacker who sprays random passwords fill the bounded cache and evict legitimate entries, which forces CPU work.
  - Use a short TTL in the spirit of Apache's 300 s default.
  - Keep a fixed capacity per worker, so the cache-hit path takes no lock.
  - Drop the whole cache on reload.
- Apache's design, caching the hash lookup, solves a different problem (a slow DBM/SQL/LDAP backend). For a file of hashes loaded into memory it buys nothing; the cost that matters is the 6-130 ms verification measured in Q3.
- For timing parity, the dummy hash for unknown users has to match the algorithm and cost of real entries. With a file that mixes `$y$` and `$2b$10$`, the response time still reveals which algorithm a real user has, and with it that the user exists. One option is a dummy per distinct (prefix, cost) present, with unknown users mapped to the most common one.
- Enumeration through the cache: a cached hit answers in microseconds while a miss takes milliseconds. That reveals only that this exact user:password was recently valid, which the attacker would need to know already, so it is an acceptable leak.

### Gaps
- I didn't check how Squid (`credentialsttl`), HAProxy or Envoy cache Basic results.
- No standard or NIST/OWASP text was found that specifically addresses caching verified credentials. The guidance above is drawn from Apache's doc and Caddy's code plus inference.

## Q5. Running slow hash verification without blocking the event loop; bounding concurrency

### Takeaway
nginx runs `crypt()` inline in the worker: its maintainer says bcrypt-5 blocks "the event loop for 4 milliseconds" per request, capping one worker at about 250 req/s. A server built on Asio should run verifications on a small dedicated thread pool and post the result back to the connection's worker. `crypt_rn` is MT-safe with one `crypt_data` per thread. Concurrency should be bounded by both CPU and memory: about 16 MiB per yescrypt-5 hash and about 64 MiB per scrypt or yescrypt-7 hash. When the queue is full the server should refuse quickly.

### Cited Findings
- nginx's `ngx_http_auth_basic_crypt_handler` calls `ngx_crypt(r->pool, r->headers_in.passwd.data, passwd->data, ...)` synchronously (source line 292). — [nginx src/http/modules/ngx_http_auth_basic_module.c](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_auth_basic_module.c)
- Dounin: "you block the event loop for 4 milliseconds 100 times per second"; "no more than 250 requests per second on a single core / using a single nginx worker process". — [nginx mailing list 2017-06](https://mailman.nginx.org/pipermail/nginx/2017-June/054134.html). Related threads: "Basic auth is slow" — [nginx 2015-11](https://mailman.nginx.org/pipermail/nginx/2015-November/049322.html); bcrypt cost and Basic-auth login performance — [nginx 2019-07](https://mailman.nginx.org/pipermail/nginx/2019-July/058114.html)
- libxcrypt thread safety: `crypt` is "MT-Unsafe race:crypt"; `crypt_r`, `crypt_rn` and `crypt_ra` are "MT-Safe" — "It is safe to call them from multiple threads simultaneously, as long as a separate data object is used for each thread." — [libxcrypt crypt(3) ATTRIBUTES](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.3)
- `struct crypt_data` "may be quite large (32kB in this implementation ...; over 128kB in some other implementations). This is large enough that it may be unwise to allocate it on the stack." "Some recently designed hashing methods need even more scratch memory" than the struct holds. — [crypt(3) BUGS](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.3)
- Caddy deduplicates concurrent checks of the same credentials with `singleflight` so that "the expensive op" runs once. — [Caddy basicauth.go](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/caddyauth/basicauth.go)
- Peak memory of one verification (local measurement, Q3 table): yescrypt cost 5 ≈ 16 MiB scratch, cost 7 ≈ 64 MiB, cost 9 ≈ 256 MiB; scrypt default ≈ 64 MiB; bcrypt and sha-crypt under 1 MB.

### Inferences
- Suggested design for an Asio server:
  - A fixed pool of N verifier threads (N small, e.g. 1-2 or cores/4), each with its own heap-allocated, zeroed `crypt_data`, fed by a bounded MPSC queue.
  - The worker posts the job (stored hash string plus password bytes in a fixed buffer) and suspends the request. The verifier posts the boolean back to the worker's `io_context`.
  - The worker then fills its own per-worker cache, so no state is shared on the hit path.
- Bounding the work:
  - Cap the queue (e.g. 2-4× N) and answer 503 + Retry-After, or 429, when it is full, instead of queueing unbounded work.
  - Cap jobs per client address in flight.
  - Collapse identical (hash, password) jobs, as Caddy's singleflight does.
- Peak memory is N × the per-hash scratch. yescrypt-5 with N=4 is about 64 MiB; scrypt default with N=4 is about 256 MiB. Admitting a high cost setting at config load therefore needs an operator-visible warning.
- With a cache of successful verifications, legitimate traffic pays one verification per (worker, user, password, TTL). Only guessing and first requests reach the pool, so the bound on the pool is effectively the bound on brute-force CPU.
- The client-abort machinery already in agensio (E9) applies: a request whose client disappears while its verification is queued should drop the job.
- In `crypt_rn`, zero the whole `crypt_data` before first use. The man page says this "is not just a recommendation, as it is for crypt_r". Wipe the password copy (`explicit_bzero`) after the job.

### Gaps
- No authoritative source (OWASP, NIST) prescribes thread-pool sizing or queue limits for password verification; the above is design inference.
- HAProxy's handling of `crypt()` in `userlist` (global lock, main thread) was not researched.

## Q6. Brute-force defences, lockout trade-offs, fail2ban, logging

### Takeaway
NIST caps consecutive failures per account at 100 or fewer. Instead of hard lockouts it suggests growing delays ("30 seconds up to an hour") and risk signals such as the IP address. OWASP keys the failure counter to the account, not the IP, to stop distributed guessing, and warns that lockouts can be abused for denial of service. fail2ban ships filters for Apache's and nginx's Basic-auth error-log lines; those lines carry the user and client address but never the password. Every failure and every lockout should be logged.

### Cited Findings
- NIST SP 800-63B-4 §3.2.2: "the verifier SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100 by disabling that authenticator". "The limit of 100 attempts is an upper bound, and agencies MAY impose lower limits." Techniques to avoid locking out the legitimate user: bot-detection challenges; "Requiring the claimant to wait after a failed attempt for a period of time that increases as the subscriber account approaches its maximum allowance for consecutive failed attempts (e.g., 30 seconds up to an hour)"; risk-based signals such as "the claimant's IP address, geolocation, timing of request patterns". — [NIST SP 800-63B-4 §3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html)
- OWASP: "The counter of failed logins should be associated with the account itself, rather than the source IP address, in order to prevent an attacker from making login attempts from a large number of different IP addresses". The parameters are lockout threshold, observation window and lockout duration, or an "exponential lockout" that starts "very short ... (e.g., one second), but doubles after each failed login attempt". The design must "prevent it from being used to cause a denial of service by locking out other users' accounts". It names brute force, credential stuffing and password spraying as the attack types. — [OWASP Authentication CS, "Protect Against Automated Attacks"](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- OWASP logging: "Ensure that all failures are logged and reviewed", "all password failures", and "all account lockouts". — [OWASP Authentication CS, "Logging and Monitoring"](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- fail2ban `nginx-http-auth` filter: `user "(?:[^"]+|.*?)":? (?:password mismatch|was not found in "[^\"]*"), client: <HOST>, server: \S*, request: "\S+ \S+ HTTP/\d+\.\d+", host: "\S+"`, at error level, with `journalmatch = _SYSTEMD_UNIT=nginx.service + _COMM=nginx`. — [fail2ban filter.d/nginx-http-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/nginx-http-auth.conf) (local copy: `docs/fail2ban-ref/config/filter.d/nginx-http-auth.conf`)
- fail2ban `apache-auth` filter: matches `user <F-USER>…</F-USER> (?:auth(?:oriz|entic)ation failure|not found|denied by provider)`, `user …: password mismatch`, `Authorization of user … to access … failed`, and `client used wrong authentication scheme`, in Apache's error log with optional `AH\d+:` codes. — [fail2ban filter.d/apache-auth.conf](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/apache-auth.conf) (local copy: `docs/fail2ban-ref/config/filter.d/apache-auth.conf`)
- Typical jail settings in practitioner guides: `maxretry = 5`, `bantime = 1h`, with a warning that `maxretry = 1` causes false positives. — [OneUptime fail2ban guide, 2026](https://oneuptime.com/blog/post/2026-03-02-how-to-configure-fail2ban-jails-for-ssh-apache-and-nginx-on-ubuntu/markdown) (secondary)

### Inferences
- For a web server, an "account lockout" on Basic auth is a self-inflicted denial of service, because anyone can lock out a known user name. NIST's growing delay is the better fit, and so is OWASP's exponential back-off with a per-(user) counter, capped at 100 consecutive failures.
  - Implemented as a short, cheap refusal (429 or 401 with no verification) while a user's delay is active, the delay also saves the hash CPU.
  - A per-address counter adds a second axis. It can live in the server for the hot path, with fail2ban/nftables above it for bans (agensio's design already puts per-address limits in the firewall).
- Add a per-address and per-user token bucket in front of the verifier queue (Q5). Each worker owns its own counters, keeping with the one-worker-state rule. A per-user limit enforced per worker is weaker by a factor of the worker count; that is acceptable, or the counter can be sharded by a hash of the user.
- Log lines for failures should follow the shape that existing fail2ban filters (or an agensio filter) can match: event, user (escaped, length-capped), client address after `trusted_proxies`, site, request line, and reason. Reasons: `password mismatch`, `user not found`, `malformed`, `scheme`, `rate-limited`. Never log the password or the raw `Authorization` value. In the access log, the combined format's `%u` field is the conventional place for the authenticated user.
- Logging "user not found" separately from "password mismatch" contradicts nothing in OWASP, since the generic message rule is about responses, not logs. But the log is then sensitive data, because it records typed user names, which can be passwords typed into the wrong field.

### Gaps
- The OWASP Logging Cheat Sheet's text on excluding passwords and session tokens from logs was not fetched. The "never log the password" rule above is standard practice but uncited here.
- No source gives a quantified recommended threshold for per-IP Basic-auth rate limits.

## Q7. libxcrypt: API, prefixes, thread safety, platform availability

### Takeaway
libxcrypt (LGPL-2.1+) is the system `libcrypt.so.1` on Debian, Ubuntu and Fedora. Its MT-safe API is `crypt_rn(phrase, setting, struct crypt_data*, int size)`. The man page also documents `crypt_r`, `crypt_ra`, `crypt_gensalt_rn` and `crypt_checksalt`. It supports `$y$`, `$gy$`, `$sm3y$`, `$7$`, `$2b$/$2y$/$2a$/$2x$`, `$6$`, `$5$` and the legacy formats, with phrases up to 512 bytes. macOS's own libc `crypt()` only supports DES and BSDI extended DES, so on macOS a build would need libxcrypt itself (which builds there) or an alternative. Alpine's support is unverified.

### Cited Findings
- Interfaces: "the traditional Unix `crypt` and `crypt_r` interfaces, as well as a set of extended interfaces pioneered by Openwall Linux, `crypt_rn`, `crypt_ra`, `crypt_gensalt`, `crypt_gensalt_rn`, and `crypt_gensalt_ra`". It is meant to be "fast and lightweight enough for use in servers that must field thousands of login attempts per minute". It is licensed "GNU Lesser General Public License (version 2.1, or at your option, any later version)". — [libxcrypt README](https://github.com/besser82/libxcrypt/blob/develop/README.md)
- Signatures (crypt(3)): `char *crypt_r(const char *phrase, const char *setting, struct crypt_data *data)`, `char *crypt_rn(..., struct crypt_data *data, int size)`, `char *crypt_ra(..., void **data, int *size)`. "When used with crypt_rn, the entire data object (except for the input and setting fields) must be zeroed before its first use". `crypt_ra` mallocs the object. Errors are EINVAL (bad or unsupported setting), ERANGE (phrase longer than `CRYPT_MAX_PASSPHRASE_SIZE`), and ENOMEM. "Upon error, crypt_rn and crypt_ra return a null pointer"; crypt and crypt_r may return NULL or an invalid hash, depending on build configuration. — [libxcrypt crypt(3)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.3)
- Thread safety: `crypt` is MT-Unsafe; `crypt_r`, `crypt_rn` and `crypt_ra` are MT-Safe with a separate data object per thread. — [crypt(3)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt.3)
- Header constants on Debian 13 (libxcrypt 4.4.38): `CRYPT_OUTPUT_SIZE 384`, `CRYPT_MAX_PASSPHRASE_SIZE 512`, `CRYPT_GENSALT_OUTPUT_SIZE 192`, `CRYPT_GENSALT_IMPLEMENTS_DEFAULT_PREFIX 1`. — local `/usr/include/crypt.h`
- `crypt_gensalt`: "If prefix is a null pointer, the best available hashing method will be selected. (CAUTION: if prefix is an empty string, the "traditional" DES-based hashing method will be selected ...) If count is 0, a low default cost will be selected." — [libxcrypt crypt_gensalt(3)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt_gensalt.3). Local check: count 0 gives `$y$j9T$` (yescrypt cost 5) and `$2b$05$`.
- `crypt_checksalt(setting)` returns CRYPT_SALT_OK, CRYPT_SALT_INVALID, CRYPT_SALT_METHOD_DISABLED, CRYPT_SALT_METHOD_LEGACY or CRYPT_SALT_TOO_CHEAP, "intended ... to determine whether the user's passphrase should be re-hashed", and was added in 4.3.0. Its man page BUGS says it only ever returns OK or INVALID. — [crypt_checksalt(3)](https://github.com/besser82/libxcrypt/blob/develop/doc/crypt_checksalt.3). NEWS for 4.4.21 contradicts that: it "will now return the value 'CRYPT_SALT_METHOD_LEGACY' in case the setting ... uses a hashing method, which is considered to be too weak". — [libxcrypt NEWS](https://github.com/besser82/libxcrypt/blob/develop/NEWS). The man page appears outdated.
- Prefixes and native-system flags (`hashes.conf`): `$y$` (DEBIAN, FEDORA, DEFAULT), `$gy$`, `$sm3y$` (EULER, KYLIN), `$7$`, `$2b$` (FreeBSD, NetBSD, OpenBSD, Owl, Solaris, SUSE), `$2y$`, `$2a$`, `$2x$`, `$sm3$`, `$6$` and `$5$` (GLIBC, FREEBSD, SOLARIS), `$sha1`, `$md5`, `$1$`, `$3$`, `_` (FREEBSD, NETBSD, OPENBSD, OSX), bigcrypt, and descrypt (… OSX). OSX appears only on bsdicrypt and descrypt. — [hashes.conf](https://github.com/besser82/libxcrypt/blob/develop/lib/hashes.conf)
- Compatibility: on Linux libxcrypt is "binary backward compatible with the libcrypt.so.1 shipped as part of the GNU C Library". With `--disable-obsolete-api` it installs libcrypt.so.2, and that configuration "is always used on all operating systems other than Linux". — [libxcrypt README](https://github.com/besser82/libxcrypt/blob/develop/README.md). NEWS 4.5.1 records "Fix build with clang-20+ on macOS (issue #216)", so macOS builds are maintained. — [NEWS](https://github.com/besser82/libxcrypt/blob/develop/NEWS)
- Debian: Debian 13 ships `libcrypt1 1:4.4.38-1` / `libcrypt-dev`, `ENCRYPT_METHOD YESCRYPT` in `/etc/login.defs`, and `pam_unix.so obscure yescrypt`. — local system. Ubuntu: yescrypt has been supported by libxcrypt since 20.04 and has been the default since 22.04. — [Openwall yescrypt list, 2022-10](https://www.openwall.com/lists/yescrypt/2022/10/28/3). Fedora: yescrypt is the default per the FEDORA flag in hashes.conf. — [hashes.conf](https://github.com/besser82/libxcrypt/blob/develop/lib/hashes.conf)

### Inferences
- Linking `-lcrypt` on Linux is effectively free: it is in every Debian/Ubuntu/Fedora base system, and the `libcrypt-dev`/`libxcrypt-devel` headers are build-only. It would still be a new row in the CLAUDE.md dependency table: "system libcrypt (libxcrypt) for verifying crypt(5) hashes".
- Use `crypt_rn` with a heap `crypt_data` per verifier thread, check for NULL, compare the result against the stored string in constant time, and treat any result starting with `*` as failure.
- Use `crypt_gensalt_rn(NULL or "$y$", count, NULL, 0, …)` for an `agensio passwd`-style helper. Pass an explicit count (5 or higher), because count 0 means a "low default cost".
- macOS (a first-class target in this project): the system `crypt()` cannot verify any modern format, per hashes.conf's OSX flags. The options are to require libxcrypt (Homebrew availability unverified), to vendor a single algorithm (e.g. yescrypt's reference code, BSD-licensed per Openwall, unverified), or to disable Basic auth there with a clear config error.

### Gaps
- Alpine/musl: whether Alpine packages libxcrypt, and which formats musl's own `crypt()` supports, is not confirmed. Search results suggested that musl's crypt covers DES, MD5, SHA-256/512 and bcrypt, but not yescrypt, from an unreliable snippet.
- RHEL 9/10 ship libxcrypt (believed) with SHA-512 as the default method (believed); neither was confirmed.
- Homebrew `libxcrypt` formula availability and the yescrypt reference-code license were not checked.
