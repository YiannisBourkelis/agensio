# Password protection in hosting panels and managed hosts, and what site owners need beyond it

Research date: 2026-10-08. Markers: **[older]** = item dated before 2024 (still useful as history or as a still-open pattern); **[snippet]** = the page itself could not be fetched (HTTP 403 or empty), so the claim rests on the search engine's summary of that page and should be re-checked before it is quoted; **[unverified]** = plausible but not confirmed from a primary source.

## Per panel: what the user can do, what is written, hash, nginx, limits, reported problems

### Takeaway
Every panel offers the same thing: one HTTP Basic realm on a directory (or the whole site), a list of username/password pairs, and nothing else. None of the panels documents expiry, per-path exceptions inside the protected tree, logout, audit or 2FA. Only CloudPanel (and SpinupWP, by hand-editing nginx) offers "trusted IP or password". The problems people report are of two kinds. The first is the panel's Apache-to-nginx translation leaking: static files or PHP files served without the challenge, or files downloaded instead of executed (Plesk 2016, 2023, 2024; DirectAdmin 2013-14). The second is the realm blocking machine traffic the site needs: certificate validation, `admin-ajax.php`, loopback/cron, API clients.

### Cited Findings

**cPanel: "Directory Privacy"** (docs valid for cPanel 88 through current, page modified 2026-07-08)
- The user ticks a checkbox to enable protection, enters a name that "**only** functions as a label for the directory in its `.htaccess` file", then adds authorized users (username plus password, with a 100-point strength meter), and can delete users from the list — [cPanel Docs: Directory Privacy](https://docs.cpanel.net/cpanel/files/directory-privacy/)
- It "modifies `htaccess` and `htpasswd` configurations"; "A protected directory's subdirectories inherit their parent directory's password protection"; it "does **not** protect directories that users access via FTP, SFTP, Web Disk, or other services"; the directory must be `0700` for user creation to succeed (as the docs state it) — [cPanel Docs: Directory Privacy](https://docs.cpanel.net/cpanel/files/directory-privacy/)
- The password file is kept outside the web root at `/home/$USER/.htpasswds/<path>/passwd` (third-party hosting tutorial) — [GreenGeeks tutorial](https://www.greengeeks.com/tutorials/to-set-up-directory-privacy-in-cpanel/)
- Hash used: not stated in cPanel's current docs (see Gaps). Historical **[older]**: an old cPanel advisory involved passwords truncated to eight characters (the classic `crypt()` DES limit), fixed in cPanel 9.9.8 build 29 (mid-2000s) — [cPanel news (search result)](https://news.cpanel.com/?p=909); the Apache `htpasswd` manual confirms that with `crypt()` "only the first 8 characters of the password are used" — [Apache htpasswd manual](https://httpd.apache.org/docs/2.4/programs/htpasswd.html)
- Reported problem, AutoSSL renewal **[snippet]**: when a domain or directory is password-protected, AutoSSL's DCV file request gets a 401 and validation fails. The fixes given are an `.htaccess` exemption in `.well-known` (`Satisfy Any`), excluding `.cpaneldcv`/`.txt`, or WHM's "Use a Global DCV Passthrough instead of .htaccess modification". Webdisk subdomains are password-protected by default and fail the same way — [cPanel community: AutoSSL and password protected domains](https://support.cpanel.net/hc/en-us/community/posts/19662800267927-AutoSSL-and-password-protected-domains); [cPanel community: Auto SSL and Password Protected Directory](https://support.cpanel.net/hc/en-us/community/posts/19675257722391-Auto-SSL-and-Password-Protected-Directory)

**Plesk: "Password-Protected Directories"** (Obsidian docs)
- Websites & Domains > Password-Protected Directories > Add Protected Directory. The path is relative to the document root, with an optional title "displayed to visitors" that can be changed later under Directory Settings. On Linux, Plesk creates a missing directory; on Windows only an existing one can be protected — [Plesk Obsidian: Restricting Access to Content](https://docs.plesk.com/en-US/obsidian/customer-guide/websites-and-domains/restricting-access-to-content.65152/)
- Users are per directory: "This user will only have access to this specific directory, and not all of the domain's protected directories". "Unless there is at least one user associated with a password-protected directory, no one can browse that directory"; protection extends to everything inside — [Plesk Obsidian: Restricting Access to Content](https://docs.plesk.com/en-US/obsidian/customer-guide/websites-and-domains/restricting-access-to-content.65152/)
- **[older][snippet]** The Plesk 12.5 docs limited these passwords to "5 to 14 symbols in length" — [Plesk 12.5 reseller guide](https://docs.plesk.com/en-US/12.5/reseller-guide/65152/). Whether Obsidian keeps this limit is not confirmed.
- There is an XML API (ADD/SET/DELETE directory, ADD-USER/SET-USER/DELETE-USER) for protected directories "under either a standard HTTP virtual host or an SSL/TLS HTTPs virtual host", plus a `protdir` CLI — [Plesk XML API: Managing Protected Directories](https://docs.plesk.com/en-US/obsidian/api-rpc/about-xml-api/reference/managing-protected-directories.49346/); [Plesk CLI protdir](https://docs.plesk.com/en-US/obsidian/cli-linux/using-command-line-utilities/protdir-site-directories-protection.39417/)
- Bug PPPM-13942 **[snippet]**: static files (JS, images, CSS) in a protected directory return 404 or 500 when both Proxy Mode and "Smart static files processing" are on. Fixed in Obsidian 18.0.52 (25 April 2023), but only for default templates: custom nginx templates needed `^~` added by hand — [Plesk KB 13499309025687](https://support.plesk.com/hc/en-us/articles/13499309025687-Static-files-in-Plesk-protected-directory-are-inaccessible-ERROR-404-not-found)
- Bugs PPS-15620 and PPPM-14334, February 2024: PHP files in a protected directory were served **without** a login on 18.0.57.3 and 18.0.58.2 ("missing auth_basic directives"); 18.0.59 then produced "wrong location directives", so PHP files were downloaded instead of executed after login. No permanent fix appears in the thread — [Plesk forum: Protected directory not working for PHP files](https://talk.plesk.com/threads/protected-directory-not-working-for-php-files.373318/)
- **[older]** March 2016, Plesk 12.x: clicking "abort" at the prompt still let a visitor fetch protected files directly under PHP-FPM (ticket PPPM-3839, Dec 2015). The workaround was to switch the handler to Apache FastCGI or write nginx auth rules by hand — [Plesk forum: Security password protected directories](https://talk.plesk.com/threads/security-password-protected-directories.337344/post-798347)

**DirectAdmin: "Password Protected Directories"**
- Advanced Features (or Account Management) > Password Protected Directories > Add Protected Directory: pick the folder, set a username and password, Protect. Later the user can un-protect, change the username or password, or add another pair — [AZDIGI tutorial](https://azdigi.com/en/blog/directadmin/how-to-set-up-password-protected-directories-on-directadmin)
- With nginx, DirectAdmin renders a template (`nginx_protected_directory.conf`) into `location /dir/ { auth_basic ...; auth_basic_user_file ...; include .../nginx_php.conf; }` **[snippet]** — [DirectAdmin forum: Protect directory via DA with Nginx setup](https://forum.directadmin.com/threads/protect-directory-via-da-with-nginx-setup.47415)
- **[older]** 2013-2014: protection "Can turn ON, but not OFF", PHP files were served as downloads, and turning protection off gave 500s. Staff explained that "locations cannot overlap with nginx, but can be one within the other", so the PHP location had to be nested inside each protected location, and fixed it with a per-user `nginx_php.conf` (July 2014 pre-release) — [DirectAdmin forum thread 47415](https://forum.directadmin.com/threads/protect-directory-via-da-with-nginx-setup.47415)
- **[snippet]** A separate thread reports that images in protected directories stayed public and direct links bypassed authentication — [DirectAdmin forum: Protecting directory](https://forum.directadmin.com/threads/protecting-directory.56343/latest)

**ISPConfig: "Protected Folders" + "Protected Folder Users"**
- The feature is split into two records that "work together", and the folder stays public until at least one user exists — [Noiz docs: How to password protect a folder in ISPConfig](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/)
- Apache: ISPConfig writes a block between `### ISPConfig folder protection begin ###` and `### ISPConfig folder protection end ###` in `.htaccess` and "rewrites everything between them whenever the record changes". nginx: "nginx does not read `.htaccess` files, so ISPConfig writes the protection into the site's server configuration instead; the only file it keeps in the folder is `.htpasswd`" — [Noiz docs](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/)
- The password "is stored as a one-way hash and ISPConfig cannot show it to you again"; the guide warns to use HTTPS because Basic sends credentials "in a lightly encoded, easily reversed form" — [Noiz docs](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/)
- **[snippet]** The `.htpasswd` sits in the same directory as the `.htaccess`, and Apache blocks downloading it by default. A forum answer says the feature "is designed to protect new empty subfolders", so overriding an existing `.htaccess` is intended — [HowtoForge: How does a client password protect a directory?](https://forum.howtoforge.com/threads/how-does-a-client-password-protect-a-directory.54431); [HowtoForge: Folder Protection acts weird](https://forum.howtoforge.com/threads/ispconfig-3-folder-protection-acts-weird.56859)
- A 2025-26 thread titled "ISPConfig: .htaccess Basic Auth Not Working Despite Everything Being Correct" exists, but its content could not be fetched — [HowtoForge thread 94099](https://forum.howtoforge.com/threads/ispconfig-htaccess-basic-auth-not-working-despite-everything-being-correct.94099)

**HestiaCP: nothing built in**
- On 2024-10-27 a user asked for a Directory Privacy option to protect WordPress `wp-admin` ("attackers bypass CAPTCHA and two-factor"). Answers: no panel feature. The suggested workarounds were a custom nginx/Apache site template, `.htpasswd` under `/home/<user>/web/<domain>/private/`, fail2ban WordPress jails, a WordPress htpasswd plugin, or IP restriction. One user (2024-11-15) asked for a built-in feature letting "users defined in the WP panel or the control panel" into wp-admin — [HestiaCP forum: Directory privacy feature](https://forum.hestiacp.com/t/directory-privacy-feature/16360)

**CloudPanel: "Basic Auth" (nginx)**
- Per site: Settings/Security > Basic Auth > Enabled, then **multiple users** (Add User) and a **Whitelisted IPs** list whose addresses skip the prompt (article of 2020-12-09, updated 2026-01-13) — [AZDIGI: Set up Basic Authentication on CloudPanel](https://azdigi.com/en/blog/cloudpanel/set-up-basic-authentication-on-cloudpanel)
- **[snippet]** CloudPanel's own tutorial: "turn on the switch to enable Basic Authentication for the desired site or path", with users and IPs that bypass it — [CloudPanel tutorial: NGINX access control](https://www.cloudpanel.io/tutorial/nginx-access-control/)

**RunCloud: "Site Authentication"**
- Web app > Tools > Site Authentication > "Set Password Authentication" (one username and password) > "Enable HTTP Authentication". Wrong credentials or Cancel give "401 Unauthorized". It is pitched as "ideal for teams who wish to publish their website on the live internet for testing and development purposes", for "your clients or your team members". The docs mention no exceptions, extra users or paths — [RunCloud docs: Password protection](https://runcloud.io/docs/password-protection-website)

**SpinupWP: "Basic Auth" (nginx)**
- A dashboard toggle with one username and password; SpinupWP redeploys the nginx config. The generated `/etc/nginx/sites-available/{DOMAIN}/server/basic-auth.conf` holds `auth_basic "Basic Authentication"`, `auth_basic_user_file` and a built-in exception `location /.well-known/ { auth_basic off; }`. An IP bypass is possible, but only by SSH-editing that file (`allow <ip>; deny all;`) and running `sudo nginx -t` — [SpinupWP doc: Enable Basic Authentication](https://spinupwp.com/doc/enable-basic-authentication-for-your-spinupwp-site/)

**Hash summary across panels**
- None of the panel docs fetched states the hash algorithm; ISPConfig says only "one-way hash" — [Noiz docs](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/); Kinsta says "encrypted" — [Kinsta htpasswd doc](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)
- What an nginx front end can verify: `crypt()`, Apache `apr1` MD5, and RFC 2307 `{PLAIN}`, `{SHA}` (unsalted, "should not be used") and `{SSHA}` — [nginx ngx_http_auth_basic_module](https://nginx.org/en/docs/http/ngx_http_auth_basic_module.html). Whether bcrypt works through nginx's `crypt()` path is **contested**: one guide lists `$2y$` among supported formats, another says nginx does not support bcrypt — [GetPageSpeed: nginx basic auth htpasswd](https://www.getpagespeed.com/server-setup/nginx/nginx-basic-auth-htpasswd) (search summary shows both claims). (It most likely depends on the system's libc `crypt()`; **[unverified]**.)

### Inferences
- The panel model is "directory = realm, users belong to that directory" (Plesk says so explicitly; cPanel and ISPConfig work the same way in practice). Nobody exposes realm sharing, so a user who protects two folders types the password twice and manages two user lists.
- Panels that translate `.htaccess` semantics into nginx `location` blocks keep producing the same bug: nginx location matching picks the PHP or static location instead of the protected one, so the challenge is skipped (Plesk 2016, 2023, 2024; DirectAdmin 2013-14). A server where protection is a property of the path, checked before location selection, avoids this whole class. agensio's `Dispatcher::admit` already runs access rules before `Router::location` and on `try_files` targets (CLAUDE.md "Access by client address"), so Basic auth placed at the same step would inherit that property.
- Exempting `/.well-known/acme-challenge/` is something users must learn: cPanel needs a WHM switch, and SpinupWP builds the exemption in. agensio answers ACME challenges in the dispatcher before routing (CLAUDE.md, H3), so a realm placed after that point would not break renewal.

### Gaps
- The hash cPanel, Plesk, DirectAdmin, CloudPanel, RunCloud and SpinupWP write today (apr1, bcrypt, SHA-512 crypt?) is not documented in anything I could fetch. Verifying it needs a test install or the panel source (ISPConfig is open source).
- Whether Plesk Obsidian still limits these passwords to 5-14 characters is not confirmed.
- No current (2025-26) cPanel forum thread on Directory Privacy bugs was found beyond the AutoSSL ones; cPanel's support pages returned 403.
- The content of the 2025-26 ISPConfig basic-auth thread could not be read.

## Managed WordPress hosts: how staging and private sites are protected, and how access is shared with clients

### Takeaway
Every managed host fetched uses plain HTTP Basic auth with a single shared credential per environment. Some prefill it (Flywheel's default username "flywheel", WP Engine's username fixed to the environment name). Most turn off page caching or the CDN while it is on, and some add noindex as a second layer (Kinsta's `X-Robots-Tag`, WP Engine's virtual `robots.txt`). Clients get access by being sent the shared username and password. None of these hosts offers per-client credentials, expiry, magic links or audit for staging. The JAMstack platforms (Vercel, Netlify) are the ones that offer revocable shareable links and team/SSO logins.

### Cited Findings

**Kinsta: "htpasswd" tool**
- One username/password protects "the entire WordPress site", on live sites and staging. It "creates a hidden file in the Nginx configuration of your site, which stores your encrypted username and password" — [Kinsta docs: htpasswd](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)
- "You cannot enable password protection if you have enabled Kinsta's CDN or edge caching"; "Password protection can also result in MISS responses in the server cache" — [Kinsta docs: htpasswd](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)
- "While there isn't a way for the server to log a user out, you can change the credentials to remove access"; closing the dialog gives "401 Authorization Required", and the prompt looks different in Chrome, Firefox and Safari — [Kinsta docs: htpasswd](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)
- Staging: "By default, indexing is turned off for Staging sites". Staging URLs carry `X-Robots-Tag: noindex, nofollow, nosnippet, noarchive`, which cannot be removed even with a custom domain on staging. Standard staging has caching off by default and cannot use Kinsta's CDN — [Kinsta docs: Staging environment](https://kinsta.com/docs/wordpress-hosting/staging-environment/)

**WP Engine: "Password Protection"**
- Basic auth toggled per environment in the User Portal. "The username for password protection is always your environment name and cannot be changed"; the password can be shown and edited; there is a single pair per environment — [WP Engine support: Block/Unblock Traffic to a Website](https://wpengine.com/support/password-protecting-wp-engine-site/)
- "WP Engine's Varnish html page caching will not apply to pages when password protection is enabled"; "Do not use a CDN with password protection enabled"; external services and APIs must be given the credentials. Assets loaded from more than one domain cause repeated prompts (the fix is a single domain or relative paths). WordPress admin login is separate. IP or country blocking lives in a different tool (Web Rules Engine) — [WP Engine support](https://wpengine.com/support/password-protecting-wp-engine-site/)
- Crawlers: WP Engine serves a virtual `robots.txt` disallowing bots on `*.wpengine.com` environment domains, and custom robots.txt changes show only on environments with a custom domain (which shared plans allow on Production only) — [WP Engine support: Robots.txt and WordPress](https://wpengine.com/support/?p=7270) (search summary)
- **[older]** WP Engine announced "Password Protection for Sites in Development" as a blog feature — [WP Engine blog](https://wpengine.com/resources/announcing-password-protection-sites-development/)

**Flywheel (WP Engine): "Privacy Mode"**
- Basic auth pop-up. On by default on demo (trial) sites, and "You won't be able to turn off Privacy Mode until the site is paid for"; "The password for the site is shown in plain text. We suggest that you refrain from using your personal password here"; it "prevents Google from crawling the site before it goes live" — [Flywheel: Why are my sites password protected?](https://getflywheel.com/wordpress-support/why-are-my-sites-password-protected/)
- The default username is "flywheel" and the password a random two-word combination. Staging has its own Privacy Mode credentials. For client review Flywheel points to sharing the password, Local's "Live Links", or a demo/staging site **[snippet]** — [Flywheel (search result)](https://getflywheel.com/?p=18101)

**SiteGround: "Protected URLs" (Site Tools > Security)**
- Protection per path (domain plus path). Users are created once and then attached to URLs ("Manage Access" per user adds or removes URLs), so one user can cover several URLs and several users can share one. The KB lists `wp-admin` (WordPress) and `/administrator` (Joomla) as typical paths. The article (2025-11-28) mentions no IP allowlist or expiry — [SiteGround KB: Password protect URL](https://www.siteground.com/kb/password-protect-url)

**Cloudways**
- **[snippet]** "By default, staging applications on Cloudways are password protected (.htpasswd)"; credentials are set in Access Details and toggled with Enable. Manual `.htaccess` protection reportedly causes internal server errors for some users, and `.htpasswd` is "not supported for custom PHP stack on some configurations" — [Cloudways: Create staging environment](https://support.cloudways.com/create-staging-environment-site)
- **[snippet]** Feedback-board requests exist titled "Add password protection to main applications, not [only staging]", "Password protecting apps from console (via htpasswd)" and "Enable less strong *staging site* passwords". The titles show demand for live-site protection and for a password a client can type; vote counts could not be read (403) — [Cloudways feedback 45282610](https://feedback.cloudways.com/forums/203824-service-improvement/suggestions/45282610-add-password-protection-to-main-applications-not); [Cloudways feedback 7859454](https://feedback.cloudways.com/forums/203824-service-improvement/suggestions/7859454-password-protecting-apps-from-console-via-htpassw); [Cloudways feedback 38938630](https://feedback.cloudways.com/forums/203824-product-improvements-flexible/suggestions/38938630-enable-less-strong-staging-site-passwords)

**Smaller managed hosts** (for the pattern)
- Web60 (Irish managed WP, KB updated 2026-03-16): staging sites are "always protected by Basic Auth" and it "cannot be turned off for staging environments". Clients get the credentials and the owner resets the password afterwards. For a live site needing a temporary block, Web60 recommends maintenance mode rather than Basic auth "to keep search engines informed" — [Web60 KB: Password protecting your site](https://web60.ie/kb/security/password-protecting-your-site)

**For contrast: JAMstack platforms**
- Vercel: "Shareable links allow external users to securely access your deployments through a query string parameter". They are revoked by switching back to "Only people with access", listed centrally under Deployment Protection > Access, and Hobby accounts get "one shareable link in total per account" (docs updated 2026-08-28) — [Vercel docs: Sharable Links](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)
- Vercel Password Protection (a single shared password) is Enterprise or a Pro add-on, with a $20/month per project charge on project-level pricing. It is compatible with Vercel Authentication, Trusted IPs, Shareable Links and "Protection bypass for Automation" — [Vercel docs: Password Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/password-protection) (search summary)
- Netlify: "basic password protection" (a shared password, a "generic password prompt", Pro plans) or "team login protection" (visitor must be a team member; "Supports SSO through an identity provider"; Enterprise). Either can cover all deploys or only non-production ones, and with team login, functions see the user via `context.user` — [Netlify docs: Password protection](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)

### Inferences
- The managed-WordPress pattern is "Basic auth, one shared credential, off when you launch". Everything above that (who the client is, when access ends, who looked) is left out. The platforms that did build more (Vercel, Netlify) built revocable links and identity-based login, not more Basic users.
- Hosts tie the realm to cache bypass (WP Engine, Kinsta) because a shared cache must never serve a protected page to an unauthenticated visitor. A server with a built-in cache needs the same rule: either check the realm before the cache lookup, or never cache responses to authenticated requests.
- Belt and braces against indexing (Basic auth plus `X-Robots-Tag: noindex` on staging host names) is the established practice (Kinsta, WP Engine), and it matters because staging protection is often switched off for a client demo and forgotten.

### Gaps
- SiteGround's and Cloudways' mechanism underneath (Apache `.htaccess` vs nginx) is not documented in the pages read.
- Kinsta's and WP Engine's treatment of `wp-cron`, loopback and the REST API behind their realm is not documented.
- No managed WordPress host was found offering per-client credentials, expiring credentials or magic links for staging; this is absence of evidence from the docs read, not proof.

## Needs that plain Basic auth and the panels do not serve well

### Takeaway
The unmet needs cluster into five areas:
- **temporary, revocable, per-person access** (served today by WordPress plugins, Vercel links, Cloudflare Access email PINs and signed URLs, never by panels);
- **protecting an admin path without breaking the public endpoints that live under it** (`admin-ajax.php`, `admin-post.php`);
- **"office IP or password"** (only CloudPanel exposes it);
- **coexistence with machine traffic** (ACME, loopback/cron, REST/App Passwords, webhooks, CDNs);
- **identity features** (logout, 2FA/SSO, audit), which push people to forward-auth proxies or Zero Trust services.

### Cited Findings

**Temporary and revocable access, magic links, signed URLs**
- Demand inside WordPress: "Temporary Login Without Password" (100,000+ active installs, updated within the last week as of 2026-10) creates self-expiring login links with a role and an expiry, which can be deactivated early and track "last login time and number of times accessed". Usage limits and activity history are paid — [WordPress.org plugin page](https://wordpress.org/plugins/temporary-login-without-password/)
- Demand for a cookie-based site gate instead of the browser prompt: the "Password Protected" plugin (over 300,000 active installs per the search summary) sets a cookie after a single password. It offers IP whitelisting and blocks the REST API unless the password was entered (with an option to allow it) **[snippet]** — [InstaWP plugin listing](https://instawp.com/plugin/password-protected/); [WordPress.org (archived 2021)](https://webcf.waybackmachine.org/web/20210921125008/https://wordpress.org/plugins/password-protected)
- nginx `secure_link`: "check authenticity of requested links, protect resources from unauthorized access, and limit link lifetime". Its `$secure_link` is `""` (bad), `"0"` (expired) or `"1"`; it is MD5-based and "Not built by default" (`--with-http_secure_link_module`) — [nginx secure_link module](https://nginx.org/en/docs/http/ngx_http_secure_link_module.html)
- CloudFront signed URLs: a canned policy sets an expiry; a custom policy adds an optional start time, an IP range and wildcard resources. Validity can range from minutes to years, and the expiry is checked at request time, so a started download completes — [AWS CloudFront: Use signed URLs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)
- Cloudflare Access one-time PIN: an emailed code, sent only "if the user is allowed by an Access policy". The PIN "expires 10 minutes after the initial request"; useful for guests outside the organisation's IdP — [Cloudflare docs: One-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/). Free for "up to 50 users" **[older]** (Oct 2020 announcement; current pricing page did not render) — [Cloudflare blog: Teams plans](https://blog.cloudflare.com/teams-plans)
- Vercel's shareable links (query-string bypass, revocable, listed centrally) are the closest product to "send the client a link, kill it later" — [Vercel docs: Sharable Links](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)

**Protecting only an admin path (WordPress)**
- **[older]** Wordfence (May 2014), "Please stop password protecting your wp-admin folder because it breaks public AJAX": `admin-ajax.php` lives in `/wp-admin/`, so protecting the folder breaks all front-end AJAX for visitors. The fix is a `<Files admin-ajax.php>` exemption (`Satisfy any`) — [Wordfence blog](https://www.wordfence.com/blog/2014/05/please-stop-password-protecting-your-wp-admin-folder-because-it-breaks-public-ajax-for-wordpress/) (search summary; page body did not load)
- **[older]** SecuPress (2016-06-09): the same breaks "all your `admin-ajax.php` and `admin-post.php` requests"; exempt those plus static assets (CSS, JS, images) — [SecuPress blog](https://secupress.me/blog/dont-use-password-protection-wp-admin-folder)
- SiteGround's own KB names `wp-admin` as the path to protect without mentioning the exemption — [SiteGround KB](https://www.siteground.com/kb/password-protect-url); HestiaCP users ask for exactly this (wp-admin only) — [HestiaCP forum](https://forum.hestiacp.com/t/directory-privacy-feature/16360)

**"Office IP or password" (either one admits)**
- Apache: "By default all `Require` directives are handled as though contained within a `<RequireAny>` container", and `Require ip` can be combined with password providers — [Apache 2.4 Authentication howto](https://httpd.apache.org/docs/2.4/howto/auth.html); nginx: "Simultaneous limitation of access by address and by password is controlled by the satisfy directive" — [nginx auth_basic module](https://nginx.org/en/docs/http/ngx_http_auth_basic_module.html)
- Panel exposure: CloudPanel "Whitelisted IPs" skip the prompt — [AZDIGI CloudPanel](https://azdigi.com/en/blog/cloudpanel/set-up-basic-authentication-on-cloudpanel); SpinupWP only by SSH-editing nginx — [SpinupWP doc](https://spinupwp.com/doc/enable-basic-authentication-for-your-spinupwp-site/); the "Password Protected" plugin's IP whitelist — [InstaWP listing](https://instawp.com/plugin/password-protected/); cPanel AutoSSL workaround threads suggest IP-allowing the CA's validation addresses **[snippet]** — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/19675257722391-Auto-SSL-and-Password-Protected-Directory)

**One password for many areas or sites**
- Apache's realm is reused by the browser: "once a client has authenticated in the 'Restricted Files' area, it will automatically retry the same password for any area on the same server that is marked with the 'Restricted Files' Realm"; but "the client will always need to ask again for the password whenever the hostname of the server changes" — [Apache 2.4 Authentication howto](https://httpd.apache.org/docs/2.4/howto/auth.html)
- Plesk users are bound to one directory, so the same person needs one account per protected directory — [Plesk Obsidian docs](https://docs.plesk.com/en-US/obsidian/customer-guide/websites-and-domains/restricting-access-to-content.65152/); SiteGround is the exception, with users attachable to several URLs — [SiteGround KB](https://www.siteground.com/kb/password-protect-url)

**Logout**
- Kinsta: "there isn't a way for the server to log a user out"; change the credentials to cut access — [Kinsta docs](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)
- The browser keeps Basic credentials for the session, Cancel keeps the cached pair, and the folk workaround is a deliberate wrong login (a forum post and blog) — [tuhrig.de: Basic auth log out with JavaScript](https://tuhrig.de/basic-auth-log-out-with-javascript) (search summary; secondary source)

**Two-factor, SSO and identity (forward auth)**
- Authelia works "in collaboration with several reverse proxies" (nginx, NGINX Proxy Manager, Traefik, Caddy, HAProxy, Envoy, SWAG, Skipper) through authz endpoints. It returns 200, a redirect or 401 to the portal, or 403, applies per-domain and per-path policies, and passes the user on via "Trusted Header SSO". It depends on `X-Forwarded-Proto/Host/URI/For` — [Authelia: Proxy integration](https://www.authelia.com/integration/proxies/introduction/)
- oauth2-proxy with nginx `auth_request`: a `/oauth2/auth` endpoint checks the session, `-set-xauthrequest` returns `X-Auth-Request-User/Email`, and it puts Google or GitHub login in front of a site without code changes — [Render blog: Password protect with oauth2-proxy](https://render.com/blog/password-protect-with-oauth2-proxy) (search summary)
- Tailscale Serve keeps a service inside the tailnet and "adds a few Tailscale identity headers" (`Tailscale-User-Login`, `-Name`, `-Profile-Pic`); Funnel is public and "does not include identity headers" — [Tailscale KB: Serve](https://tailscale.com/kb/1312/serve)
- Netlify team login supports SSO and gives functions `context.user` — [Netlify docs](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)
- Demand signal: the HestiaCP user wanted wp-admin protection precisely because "attackers bypass CAPTCHA and two-factor" at the application layer — [HestiaCP forum](https://forum.hestiacp.com/t/directory-privacy-feature/16360)

**Audit of who accessed**
- Only the plugin and platform layer records this. The Temporary Login plugin shows last login time and access count — [WordPress.org](https://wordpress.org/plugins/temporary-login-without-password/); Netlify team login identifies each visitor — [Netlify docs](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/). None of the panel docs read mentions an access record for protected directories.

**Coexistence with machine traffic**
- ACME/AutoSSL validation breaks behind a realm unless `/.well-known/` is exempted: cPanel's 401 on DCV **[snippet]** — [cPanel community](https://support.cpanel.net/hc/en-us/community/posts/19662800267927-AutoSSL-and-password-protected-domains); SpinupWP ships the exemption — [SpinupWP doc](https://spinupwp.com/doc/enable-basic-authentication-for-your-spinupwp-site/)
- WordPress loopbacks: since 5.2.0, Site Health's loopback copies `PHP_AUTH_USER`/`PHP_AUTH_PW` into an `Authorization: Basic` header. That only works when PHP actually receives the credentials, which it does not when the web server consumes them — [WordPress developer reference: can_perform_loopback](https://developer.wordpress.org/reference/classes/wp_site_health/can_perform_loopback/). A 401 on loopback "may affect tools such as WP_Cron, template editors, and plugins" — [WPFixIt: Fix loopback failures](https://www.wpfixit.com/fix-wordpress-loopback-failures/) (secondary)
- WordPress Application Passwords use `Authorization: Basic` too, so a site behind a Basic realm sends the realm's credentials to the REST API as a login attempt. Trac #51939 ("Basic Auth staging protections conflicts with App Passwords", milestone 5.6, fixed) — [WordPress Trac #51939](https://core.trac.wordpress.org/ticket/51939). **[snippet]** The fix makes App Password authentication run only once an App Password exists, and "creating an Application Password will be prevented if the site appears to already be using Basic Authentication" — [Changeset 49752](https://core.trac.wordpress.org/changeset/49752). A May 2022 comment shows the header clash still hurting OAuth 2.0 client-credential flows — [wp-trac list, May 2022](https://lists.wordpress.org/pipermail/wp-trac/2022-May/472023.html)
- Third-party services must be given the credentials while protection is on, and CDNs and page caches are disabled — [WP Engine support](https://wpengine.com/support/password-protecting-wp-engine-site/); [Kinsta docs](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/)

**Search engines and accidental indexing of staging**
- Google: password-protect confidential content to "ensure only authorized users can access it. This will also prevent that content from appearing in Google Search"; `noindex` is the rule for content that may be crawled but must not be indexed — [Google Search Central: Control what you share](https://developers.google.com/search/docs/crawling-indexing/control-what-you-share)
- Host practice: Kinsta adds `X-Robots-Tag: noindex, nofollow, nosnippet, noarchive` to staging — [Kinsta staging docs](https://kinsta.com/docs/wordpress-hosting/staging-environment/); WP Engine disallows bots on environment domains via virtual `robots.txt` — [WP Engine robots.txt](https://wpengine.com/support/?p=7270); Flywheel's Privacy Mode "prevents Google from crawling the site before it goes live" — [Flywheel](https://getflywheel.com/wordpress-support/why-are-my-sites-password-protected/)
- **[snippet]** Known failure mode: a `noindex` set on staging is carried to production at launch and de-indexes the live site — [Search Engine Land: Keep staging out of the index](https://searchengineland.com/?p=286987); Moz Q&A "staging website got indexed by Google" threads show the opposite failure — [Moz Q&A](https://mozprod.nodebb.com/community/q/topic/71816/staging-website-got-indexed-by-google/10)

### Inferences
- **Temporary access** is the clearest gap: owners want "send this client a link that works until Friday" and "revoke that one person". Basic auth has neither expiry nor per-recipient revocation short of deleting the user, and panels expose neither. A server-level design could offer per-user `expires`, or a signed, expiring link that sets a cookie (Vercel-style) instead of the browser prompt.
- **Admin-path protection** needs built-in exceptions per application. agensio already does this for access rules (WordPress keeps `/wp-admin/admin-ajax.php` open under a `/wp-admin` rule, CLAUDE.md "Access by client address"). A password realm on the same paths would need the same table, plus `admin-post.php` and the static assets SecuPress lists.
- **"IP or password"** is a combinator over two checks agensio already has one half of (`[[site.access]]` allow lists). CloudPanel's "Whitelisted IPs" is the user-facing shape.
- **App Passwords/REST**: a server realm that strips or consumes `Authorization` before PHP would break WordPress loopbacks (which re-send PHP's copy). One that passes it through would collide with App Passwords. Either way the behaviour should be stated, and a cookie-based realm avoids the header clash entirely.
- **Audit** is cheap at the server: the realm user is known per request, and the combined log format already has a user field, so "who accessed staging and when" is a log query. No panel surfaces it.
- **Indexing**: emitting `X-Robots-Tag: noindex` automatically on any realm-protected response, and on non-production host names, is established host practice. It costs one prebuilt header.

## What non-technical users find confusing

### Takeaway
The browser's native dialog is the weak point. It looks different in every browser, Cancel shows a bare 401 page, password managers cannot fill it reliably, iOS Safari and in-app browsers (links opened from Slack, Instagram, mail apps) mishandle it, there is no logout, and assets on a second host name prompt again. Credentials are often fixed, generated or shown in plain text by the host, and they cannot be recovered once forgotten.

### Cited Findings
- The prompt "appearance varies across browsers (Chrome, Firefox, Safari)", and closing it returns "401 Authorization Required" — [Kinsta docs](https://kinsta.com/docs/wordpress-hosting/mykinsta-tools/htpasswd/); RunCloud: wrong credentials or Cancel give "401 Unauthorized" — [RunCloud docs](https://runcloud.io/docs/password-protection-website)
- Repeated prompts when assets load from more than one domain — [WP Engine support](https://wpengine.com/support/password-protecting-wp-engine-site/); the browser must ask again "whenever the hostname of the server changes" — [Apache Authentication howto](https://httpd.apache.org/docs/2.4/howto/auth.html)
- Password managers: there "isn't any way for 1Password in the browser to see and manipulate the HTTP authentication dialog"; the workaround is "Go & Fill" from the extension menu; Firefox's modal dialog blocks extensions entirely; long-running feature requests exist — [1Password community: HTTP Basic Auth](https://1password.community/discussion/82091/http-basic-auth); [1Password community: Allow autofill of HTTP authentication popups](https://www.1password.community/discussions/1password/allow-1password-to-autofill-http-authentication-popups/112198) (search summaries)
- **[older]** iOS Safari repeatedly re-prompting for Basic credentials (iOS 11 era; Safari sometimes not sending the header) — [Apple Developer Forums 113883](https://developer.apple.com/forums/thread/113883); a related WebKit bug — [WebKit Bugzilla 216236](https://auto-bugs.webkit.org/show_bug.cgi?id=216236) (search summaries; current iOS status unknown)
- In-app browsers and WebViews: Cordova's InAppBrowser could not show the Basic popup — [Apache Cordova CB-13554](https://issues.apache.org/jira/browse/CB-13554); a WKWebView sheet stopped sending requests after Cancel or Log in — [WebKit Bugzilla 138843](https://bugs.webkit.org/show_bug.cgi?id=138843) (search summaries; developer-oriented evidence, **[older]**)
- Embedding credentials in a link is not a workaround: Chrome blocks subresource requests whose URLs carry `user:pass@` (citing brute-forcing, session fixation and leakage of test-server credentials) — [Chromium code review 2651943002](https://codereview.chromium.org/2651943002); [W3C webapps list, Jan 2017](https://lists.w3.org/Archives/Public/public-webapps-github/2017Jan/1579.html) (search summaries, **[older]** 2017)
- Forgotten or awkward passwords: ISPConfig "cannot show it to you again" — [Noiz docs](https://docs.noiz.ie/ispconfig/how-to-password-protect-a-folder-in-ispconfig/); Flywheel shows it "in plain text" and advises not to reuse a personal password — [Flywheel](https://getflywheel.com/wordpress-support/why-are-my-sites-password-protected/); WP Engine's username cannot be changed (it is the environment name) — [WP Engine support](https://wpengine.com/support/password-protecting-wp-engine-site/); cPanel enforces a strength meter — [cPanel docs](https://docs.cpanel.net/cpanel/files/directory-privacy/); a Cloudways request asks for *weaker* staging passwords so clients can type them **[snippet]** — [Cloudways feedback 38938630](https://feedback.cloudways.com/forums/203824-product-improvements-flexible/suggestions/38938630-enable-less-strong-staging-site-passwords)
- Two logins confuse: WP Engine notes the Basic login is separate from the WordPress admin login — [WP Engine support](https://wpengine.com/support/password-protecting-wp-engine-site/)
- **[snippet]** A third-party Netlify guide sells the paid tier on showing "a styled password page instead of the browser's basic auth popup" — [netli.fyi](https://netli.fyi/blog/restrict-access-netlify-site-with-passwords) (secondary, vendor-adjacent)

### Inferences
- For the "client preview" case, a styled login page that sets a cookie works better than the native prompt: it is fillable by password managers, works in in-app browsers, can carry the site's name and a "forgot? ask <owner>" line, and supports logout. Basic auth remains the right tool for machine clients (curl, CI, monitoring).
- Credentials should be chosen by the owner, re-settable, and never shown again in plain text. Hosts that display them (Flywheel) trade security for the "send it to the client" workflow; a revocable link avoids the trade.
- Same-host asset loading matters: a realm on `staging.example.com` with assets on the production host or a CDN triggers repeated prompts, so a server feature should warn when a protected site references other host names it serves.

### Gaps
- Current (2025-26) behaviour of iOS Safari and the major in-app browsers (Instagram, Facebook, Slack, Gmail) with Basic prompts was not verified; the sources are older developer reports.
- Whether Chrome still shows the realm text (AuthName) in its dialog is not verified here; panels (cPanel, Plesk) still present the realm as a user-visible "title" or "label".
- No usability study of Basic auth prompts was found.
