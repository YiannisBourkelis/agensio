# What popular web applications and frameworks require from the web server in front of them (November 2026)

Research date: 2026-11-13. Method: official documentation pages and shipped configuration files were fetched and summarised; where a page could not be fetched, a search snippet was used and is marked "(search snippet)". Versions named are the ones the pages showed on that date. No fetched page contained text addressed to an automated reader asking it to do something; the only instruction-like text seen was the search tool's own reminder to list sources, which is tool output, not page content.

## Key question 1: Which requirements recur across applications, so that a web server needs a general feature for them?

### Takeaway
Eleven requirements recur across almost every application examined: trusted forwarded headers, a front controller with a PHP entry-point whitelist, "no script execution in upload directories", PATH_INFO, dot-file denial with a `/.well-known/` exception, WebSocket upgrade, unbuffered streaming (with `X-Accel-Buffering: no` as the de-facto signal), internal redirect for protected downloads (X-Accel-Redirect / X-Sendfile), large and long uploads, pre-compressed and immutable assets, and raw (un-normalised) request targets for proxied applications. Per-application detail follows as the evidence; the applications given most depth are WordPress, Laravel, Drupal, Symfony, Nextcloud, Rails, Django and Next.js.

### Cited Findings

#### The recurring requirements, each with the applications that state it

- **Forwarded headers and a trusted-proxy list.** Symfony ignores `X-Forwarded-*` unless `framework.trusted_proxies` and `trusted_headers` are set, and says the nginx realip module "breaks trusted proxies" — [Symfony proxies](https://symfony.com/doc/current/deployment/proxies.html). Express `trust proxy` takes a boolean, addresses, a hop count or a function, and warns the last trusted proxy must remove or overwrite `X-Forwarded-For/Host/Proto` — [Express behind proxies](https://expressjs.com/en/guide/behind-proxies.html). Rails warns "Make sure your proxies strip or overwrite any of these headers they do not manage themselves" (`config.action_dispatch.trusted_proxies`) and has `config.assume_ssl` for TLS-terminating proxies — [Rails configuring guide, v8.1.4.1](https://guides.rubyonrails.org/configuring.html). FastAPI/Uvicorn ignore the headers until `--forwarded-allow-ips` names the proxy — [FastAPI behind a proxy](https://fastapi.tiangolo.com/advanced/behind-a-proxy/), [Uvicorn deployment](https://uvicorn.dev/deployment/). Nextcloud has `trusted_proxies`, `forwarded_for_headers`, `overwritehost`, `overwriteprotocol`, `overwritewebroot` — [Nextcloud reverse proxy](https://docs.nextcloud.com/server/latest/admin_manual/configuration_server/reverse_proxy_configuration.html). The same is stated by Gitea/Forgejo (`REVERSE_PROXY_TRUSTED_PROXIES`, default `127.0.0.0/8,::1/128`) — [Forgejo reverse proxy, v17.0](https://forgejo.org/docs/latest/admin/setup/reverse-proxy/); Home Assistant ("Requests from reverse proxies are blocked if these options are not set") — [Home Assistant http](https://www.home-assistant.io/integrations/http/); n8n (`N8N_PROXY_HOPS=1`, and `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto` on the last proxy) — [n8n webhook URL](https://docs.n8n.io/hosting/configuration/configuration-examples/webhook-url/); Immich ("All reverse proxies between Immich and the user must forward all headers and set the Host, X-Real-IP, X-Forwarded-Proto and X-Forwarded-For headers") — [Immich reverse proxy](https://docs.immich.app/administration/reverse-proxy/) (search snippet); Strapi 5 (`proxy.koa`, and `X-Forwarded-Proto: https`, `X-Forwarded-Host`, `X-Forwarded-For`) — [Strapi support article](https://support.strapi.io/articles/1276365193-how-to-fix-admin-panel-login-issues-in-strapi-v5-behind-reverse-proxies) (search snippet).
- **`X-Forwarded-Host` specifically.** Next.js Server Actions compare the browser's Origin with the host read from `X-Forwarded-Host` or `Host`; a proxy that rewrites Host and adds no `X-Forwarded-Host` breaks them — [guardlayer blog](https://www.guardlayer.io/blog/nextjs-invalid-server-actions-request) (third-party, search snippet). Flask's official nginx example sets `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Prefix` — [Flask nginx, 3.1.x](https://flask.palletsprojects.com/en/stable/deploying/nginx/). Jellyfin's example sets `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Protocol`, `X-Forwarded-Host` — [Jellyfin nginx](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/nginx).
- **Front controller plus a whitelist of PHP entry points.** Symfony: only `location ~ ^/index\.php(/|$)` runs, `location ~ \.php$ { return 404; }` for the rest, and "verify that `http://example.com/index.php` is not accessible" (`internal`) — [Symfony web server configuration, 8.1](https://symfony.com/doc/current/setup/web_server_configuration.html). Laravel 13 ships the same pair of locations — [Laravel deployment](https://laravel.com/docs/deployment). Magento: `location ~ ^/(index|get|static|errors/report|errors/404|errors/503|health_check)\.php$` and a final deny of `\.php$|\.phtml$|\.htaccess$|\.htpasswd$|\.git` — [Magento nginx.conf.sample](https://raw.githubusercontent.com/magento/magento2/2.4-develop/nginx.conf.sample). Matomo: `^/(index|matomo|piwik|js/index|plugins/HeatmapSessionRecording/configs)\.php$`, every other `.php` 403 — [matomo-nginx](https://raw.githubusercontent.com/matomo-org/matomo-nginx/master/sites-available/matomo.conf). MediaWiki: `^/w/(mw-config/)?(index|load|api|thumb|opensearch_desc|rest|img_auth)\.php$` and `location / { return 404; }` — [MediaWiki Manual:Short URL/Nginx](https://www.mediawiki.org/wiki/Manual:Short_URL/Nginx). Drupal: PHP runs only directly in the root or in `/core/` (`RewriteCond %{REQUEST_URI} !/core/[^/]*\.php$` then `RewriteRule "^(.+/.*|autoload)\.php($|/)" - [F]`) — [Drupal 11.x .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess). Winter CMS: only `/index.php` is passed to FastCGI and the docs warn against widening it — [Winter CMS configuration, v1.2](https://wintercms.com/docs/v1.2/docs/setup/configuration).
- **No script execution in directories users can write to.** WordPress: `location ~* /(?:uploads|files)/.*\.php$ { deny all; }`, with the advice to upload a test PHP file and confirm it cannot run — [WordPress nginx page, updated 2026-10-14](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/). Drupal writes into the public files directory `Options -Indexes -ExecCGI -Includes -MultiViews`, `SetHandler Drupal_Security_Do_Not_Remove_See_SA_2006_006`, `php_flag engine off`; the private directory also gets `Require all denied` — [Drupal FileSecurity.php](https://raw.githubusercontent.com/drupal/drupal/11.x/core/lib/Drupal/Component/FileSecurity/FileSecurity.php). Django: "Media files are uploaded by your users. They're untrusted! Make sure your web server never attempts to interpret them" — [Django 6.1 deployment checklist](https://docs.djangoproject.com/en/stable/howto/deployment/checklist/). PrestaShop 9 blocks PHP in `/img` and `/upload` — [PrestaShop 9 nginx](https://devdocs.prestashop-project.org/9/basics/installation/advanced/nginx/). Yii 2: `location ~ ^/assets/.*\.php$ { deny all; }` — [Yii 2 installation](https://www.yiiframework.com/doc/guide/2.0/en/start-installation). Mastodon serves `/system/` (user media) with `X-Content-Type-Options nosniff` and a strict CSP — [Mastodon dist/nginx.conf](https://raw.githubusercontent.com/mastodon/mastodon/main/dist/nginx.conf). MediaWiki serves `/w/images` with `nosniff` and HTML-type uploads as plain text, `/w/images/deleted` denied — [MediaWiki Short URL/Nginx](https://www.mediawiki.org/wiki/Manual:Short_URL/Nginx).
- **PATH_INFO.** Nextcloud: `fastcgi_split_path_info ^(.+?\.php)(/.*)$`, `PATH_INFO $path_info`, fallback `try_files $uri $uri/ /index.php$request_uri` — [Nextcloud 36 nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html). Moodle: slash arguments and the routing engine need the split; misconfiguration shows as "missing images and CSS" — [Moodle 5.3 Nginx page](https://docs.moodle.org/en/Nginx). phpBB: `rewrite ^(.*)$ /index.php/$1 last;` with PATH_INFO passed — [phpBB nginx.sample.conf](https://raw.githubusercontent.com/phpbb/phpbb/master/phpBB/docs/nginx.sample.conf). Drupal: `update.php/selection` must reach `update.php`; a `try_files` existence check on the whole path breaks the updater — [Pantheon blog (2016, still the documented cause)](https://pantheon.io/blog/update-your-nginx-config-drupal-8), [Drupal nginx recipe: `fastcgi_split_path_info ^(.+?\.php)(|/.*)$`](https://nginx-wiki.getpagespeed.com/config/recipes/drupal). MediaWiki: `location /w/rest.php/` — [MediaWiki Short URL/Nginx](https://www.mediawiki.org/wiki/Manual:Short_URL/Nginx). Joomla without mod_rewrite falls back to `/index.php/` — [Joomla htaccess.txt](https://raw.githubusercontent.com/joomla/joomla-cms/5.4-dev/htaccess.txt).
- **Dot files denied, `/.well-known/` open.** The same negative-lookahead rule `location ~ /\.(?!well-known).*` appears in Laravel — [Laravel deployment](https://laravel.com/docs/deployment); Moodle — [Moodle Nginx](https://docs.moodle.org/en/Nginx); October CMS — [October CMS 4.x](https://docs.octobercms.com/4.x/setup/web-server-config.html); PrestaShop — [PrestaShop 9 nginx](https://devdocs.prestashop-project.org/9/basics/installation/advanced/nginx/); Drupal (`RewriteRule "/\.|^\.(?!well-known/)" - [F]`) — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess). Nextcloud warns a global `location ~ /\.` breaks uploads above 10 MiB to `/.file` and suggests `location ~ /\.(?!file).*` — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html).
- **Well-known URLs that are redirects or JSON with CORS.** Nextcloud: `/.well-known/carddav` and `/caldav` → 301 `/remote.php/dav/`, every other `/.well-known` → `/index.php$request_uri`, `acme-challenge` and `pki-validation` served as files; behind a reverse proxy the proxy must do the redirects (examples for Apache, Traefik 1/2, HAProxy, NGINX, Caddy, Pomerium, NGINX Proxy Manager) — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html), [Nextcloud reverse proxy](https://docs.nextcloud.com/server/latest/admin_manual/configuration_server/reverse_proxy_configuration.html). Synapse: `/.well-known/matrix/server` and `/client` with `Access-Control-Allow-Origin: *` — [Synapse reverse proxy](https://element-hq.github.io/synapse/latest/reverse_proxy.html).
- **WebSocket upgrade.** Laravel Reverb (`/app` WebSocket, `/apps` API, default `0.0.0.0:8080`) — [Laravel Reverb](https://laravel.com/docs/reverb); Laravel Octane's nginx example maps `$http_upgrade` — [Laravel Octane](https://laravel.com/docs/octane); Rails Action Cable at `/cable` — [Action Cable overview](https://guides.rubyonrails.org/action_cable_overview.html); Nextcloud notify_push at `/push/` → port 7867 — [notify_push README](https://github.com/nextcloud/notify_push); Uptime Kuma ("relies on WebSocket") — [Uptime Kuma wiki](https://github.com/louislam/uptime-kuma/wiki/Reverse-Proxy); Grafana Live at `/api/live/` — [Grafana behind a proxy](https://grafana.com/tutorials/run-grafana-behind-a-proxy/); Jellyfin `/socket` — [Jellyfin nginx](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/nginx); Gitea `/-/ws` (falls back to polling) — [Gitea reverse proxies](https://docs.gitea.com/administration/reverse-proxies); Plausible `/live/websocket` — [Plausible CE wiki](https://github.com/plausible/community-edition/wiki/reverse-proxy); Mastodon `/api/v1/streaming` to a separate upstream on port 4000 — [Mastodon nginx.conf](https://raw.githubusercontent.com/mastodon/mastodon/main/dist/nginx.conf); Vaultwarden examples pass Upgrade/Connection — [Vaultwarden proxy examples](https://github.com/dani-garcia/vaultwarden/wiki/Proxy-examples).
- **Unbuffered streaming, signalled by `X-Accel-Buffering: no`.** Next.js: "If you are using nginx or a similar proxy, you will need to configure it to disable buffering", example sets `X-Accel-Buffering: no` on every route; Partial Prerendering requires streaming — [Next.js self-hosting, updated 2026-10-15](https://nextjs.org/docs/app/guides/self-hosting). Drupal BigPipe sends `X-Accel-Buffering: no` and `Surrogate-Control: no-store, content="BigPipe/1.0"`; a buffering proxy still works but loses the benefit — [BigPipe environment requirements (2019; the header behaviour is unchanged in principle, not re-verified for Drupal 11)](https://www.drupal.org/docs/8/core/modules/big-pipe/bigpipe-environment-requirements). Nextcloud: behind an nginx front, downloads are capped at 1 GB by proxy buffering unless buffering is off or the backend sends `X-Accel-Buffering no` — [Nextcloud big file upload](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/big_file_upload_configuration.html). Mercure: "Disable response buffering and keep the idle timeout longer than the hub's heartbeat interval (40 seconds by default)" — [Mercure nginx docs](https://mercure.rocks/docs/hub/nginx) (search snippet). Discourse `/message-bus/` uses `proxy_buffering off` — [Discourse nginx.sample.conf](https://raw.githubusercontent.com/discourse/discourse/main/config/nginx.sample.conf). Uvicorn's nginx example turns `proxy_buffering` off — [Uvicorn deployment](https://uvicorn.dev/deployment/). Jellyfin sets `proxy_buffering off` for streaming load — [Jellyfin nginx](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/nginx).
- **Internal redirect for protected downloads.** Moodle: `$CFG->xsendfile = 'X-Accel-Redirect'` with `xsendfilealiases`, and an `internal` `location /dataroot/` ("The definition of 'internal' here is critical") — [Moodle Nginx](https://docs.moodle.org/en/Nginx). Discourse: request headers `X-Sendfile-Type: X-Accel-Redirect` and `X-Accel-Mapping` on `/uploads/`, an `internal` `/downloads/` alias, and `^~ /backups/` internal — [Discourse nginx.sample.conf](https://raw.githubusercontent.com/discourse/discourse/main/config/nginx.sample.conf). WooCommerce: the "X-Accel-Redirect/X-Sendfile" download method, with `location ~* /wp-content/uploads/woocommerce_uploads/ { if ( $upstream_http_x_accel_redirect = "" ) { return 403; } internal; }` — [WooCommerce developer docs](https://developer.woocommerce.com/docs/code-snippets/using_nginx_server_to_protect_your_uploads_directory/) (search snippet), [WooCommerce digital product guide](https://woocommerce.com/document/digital-downloadable-product-handling/). Rails: `config.action_dispatch.x_sendfile_header` (Rack::Sendfile) — [Rails configuring](https://guides.rubyonrails.org/configuring.html); Thruster implements X-Sendfile (`X_SENDFILE_ENABLED`, on by default) — [Thruster README](https://github.com/basecamp/thruster). Symfony `BinaryFileResponse::trustXSendfileTypeHeader()` reads the proxy's `X-Sendfile-Type` and `X-Accel-Mapping` request headers and throws when the mapping is missing — [Symfony commit](https://github-redirect.dependabot.com/symfony/symfony/pull/31604) (search snippet); FrankenPHP documents the Caddy equivalent — [FrankenPHP X-Sendfile](https://frankenphp.dev/docs/x-sendfile/) (search snippet). Drupal has a contributed module — [nginx_accel_redirect](https://drupal.org/project/nginx_accel_redirect) (search snippet). WordPress multisite before 3.5 used an `internal` `/blogs.dir` alias "to avoid PHP readfile()" (historic, pre-2013; current multisite does not need it) — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- **Large request bodies and long timeouts.** Values the official examples set: Nextcloud `client_max_body_size 512M`, `client_body_timeout 300s`, chunk size default 100 MiB, PHP `max_execution_time 3600` in the 16 G example — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html), [big file upload](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/big_file_upload_configuration.html); Immich `client_max_body_size 50000M`, request buffering off, proxy timeout "at least 10 minutes" — [Immich reverse proxy](https://docs.immich.app/administration/reverse-proxy/) (search snippet); Vaultwarden 525M — [Vaultwarden wiki](https://github.com/dani-garcia/vaultwarden/wiki/Proxy-examples); Gitea and Forgejo 512M — [Gitea](https://docs.gitea.com/administration/reverse-proxies), [Forgejo](https://forgejo.org/docs/latest/admin/setup/reverse-proxy/); Mastodon 99m and `proxy_read_timeout 120` — [Mastodon nginx.conf](https://raw.githubusercontent.com/mastodon/mastodon/main/dist/nginx.conf); Synapse 50M to match `max_upload_size` — [Synapse](https://element-hq.github.io/synapse/latest/reverse_proxy.html); Jellyfin 20M — [Jellyfin](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/nginx); Discourse 10m — [Discourse](https://raw.githubusercontent.com/discourse/discourse/main/config/nginx.sample.conf); PrestaShop 16M — [PrestaShop](https://devdocs.prestashop-project.org/9/basics/installation/advanced/nginx/); Magento `fastcgi_read_timeout 600s` and `max_execution_time=18000` — [Magento](https://raw.githubusercontent.com/magento/magento2/2.4-develop/nginx.conf.sample); kamal-proxy `response_timeout` 30 s and `max_request_body` 1 GB — [Kamal proxy, 2.12.0](https://kamal-deploy.org/docs/configuration/proxy/); Thruster read and write timeouts 30 s, no body limit — [Thruster](https://github.com/basecamp/thruster).
- **Request buffering is wanted both ways.** Nextcloud sets `fastcgi_request_buffering on` because PHP-FPM needs Content-Length — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html); Immich turns request buffering off so uploads do not fill the proxy — [Immich](https://docs.immich.app/administration/reverse-proxy/) (search snippet); kamal-proxy buffers requests and responses by default — [Kamal proxy](https://kamal-deploy.org/docs/configuration/proxy/).
- **Raw request target, never normalised.** Synapse: the proxy "must not `canonicalise` or `normalise` the requested URI in any way"; Apache needs `nocanon` and `AllowEncodedSlashes NoDecode` — [Synapse reverse proxy](https://element-hq.github.io/synapse/latest/reverse_proxy.html). Gitea: forward without decoding so `%2F` passes intact — [Gitea](https://docs.gitea.com/administration/reverse-proxies). Forgejo: nginx additionally needs `merge_slashes off` — [Forgejo](https://forgejo.org/docs/latest/admin/setup/reverse-proxy/).
- **Pre-compressed assets and immutable caching.** Drupal core rewrites `css_*.css` / `js_*.js` to `.br` or `.gz` siblings when they exist, with `Content-Encoding` and `Vary` — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess). Joomla does the same for `.css.gz`/`.js.gz` — [Joomla htaccess.txt](https://raw.githubusercontent.com/joomla/joomla-cms/5.4-dev/htaccess.txt). Discourse uses `brotli_static on` with `expires 1y` and `immutable` on `/assets/` — [Discourse](https://raw.githubusercontent.com/discourse/discourse/main/config/nginx.sample.conf). Mastodon uses `gzip_static on` — [Mastodon](https://raw.githubusercontent.com/mastodon/mastodon/main/dist/nginx.conf). Nextcloud adds `, immutable` only when the request carries a `v` query argument (`map $arg_v $asset_immutable`) — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html). Next.js sets `public, max-age=31536000, immutable` itself for hashed assets and "It cannot be overridden" — [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting).
- **Host validation at the edge.** Django: "You should also configure the web server that sits in front of Django to validate the host. It should respond with a static error page or ignore requests for incorrect hosts" — [Django checklist](https://docs.djangoproject.com/en/stable/howto/deployment/checklist/). Rails: outside development `config.hosts` is empty and no Host check is done — [Rails configuring](https://guides.rubyonrails.org/configuring.html).
- **A health URL.** Laravel `/up` — [Laravel deployment](https://laravel.com/docs/deployment); Rails `/up`, polled by kamal-proxy every second — [Kamal proxy](https://kamal-deploy.org/docs/configuration/proxy/); Synapse `/health` — [Synapse](https://element-hq.github.io/synapse/latest/reverse_proxy.html); Magento `health_check.php` — [Magento](https://raw.githubusercontent.com/magento/magento2/2.4-develop/nginx.conf.sample).
- **Long-running processes beside the site.** Laravel: "you should manually configure a process monitor" for queue workers, Reverb and Octane, and `php artisan reload` after a deploy — [Laravel deployment](https://laravel.com/docs/deployment); Octane and Reverb show Supervisor examples (`stopwaitsecs=3600`, `minfds=10000`) — [Octane](https://laravel.com/docs/octane), [Reverb](https://laravel.com/docs/reverb). Forge runs `schedule:run` every minute and monitors workers with Supervisor — [Forge docs](https://forge.laravel.com/docs/sites/laravel) (search snippet). Craft CMS's default web-based queue runner needs `ignore_user_abort` — [Craft 5 requirements](https://craftcms.com/docs/5.x/requirements.html). Redmine recommends Sidekiq for production queues — [RedmineInstall](https://www.redmine.org/projects/redmine/wiki/RedmineInstall).
- **Early Hints.** FrankenPHP "supports modern web features like early hints, Brotli, and Zstandard compression" — [Laravel Octane](https://laravel.com/docs/octane); Symfony has `sendEarlyHints()` since 6.3 (2023, still current) — [Symfony blog](https://symfony.com/blog/new-in-symfony-6-3-early-hints) (search snippet).
- **Headers a proxy must not filter.** Drupal 11.3+ HTMX support needs `HX-Request`, `HX-Trigger` and related headers passed through — [Drupal web server requirements, updated 2026-09-13](https://www.drupal.org/docs/getting-started/system-requirements/web-server-requirements).

#### WordPress (7.1; multisite, WooCommerce)

- Versions: WordPress 7.1 requires PHP 7.4+, "PHP 8.4 or later is recommended"; required extensions json, hash, mysqli; highly recommended curl, dom, exif, fileinfo, igbinary, imagick, intl, mbstring, openssl, xml, zip; servers listed: Apache 2.4, nginx 1.30/1.31, Angie 1.12, LiteSpeed 6.3, OpenLiteSpeed 1.8/1.9 (Caddy not listed) — [Hosting handbook, server environment, updated 2026-11-04](https://make.wordpress.org/hosting/handbook/server-environment/).
- Permalinks: `try_files $uri $uri/ /index.php?$args;`; restrictions: `location ~ /\. { deny all; }`, the uploads PHP rule above; multisite subdirectory (3.5+): `rewrite /wp-admin$ $scheme://$host$request_uri/ permanent;`, `rewrite ^(/[^/]+)?(/wp-.*) $2 last;`, `rewrite ^(/[^/]+)?(/.*\.php) $2 last;`; multisite subdomain: wildcard `server_name`, same `try_files` — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- The same page is internally inconsistent about `cgi.fix_pathinfo` (0 in one section, a config that "works with `cgi.fix_pathinfo = 1`" in another) — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- Hardening the documentation asks for: block `wp-admin/includes/`, `wp-includes/[^/]+\.php`, `wp-includes/js/tinymce/langs/.+\.php`, `wp-includes/theme-compat/` (the second line breaks multisite's `ms-files.php`); deny `wp-config.php`; server-side password on `/wp-admin/` "may break `wp-admin/admin-ajax.php`"; the page gives no rule for xmlrpc.php or for PHP in uploads and no nginx equivalents — [WordPress hardening, updated 2026-10-14](https://developer.wordpress.org/advanced-administration/security/hardening/).
- Full-page cache plugins: WP Super Cache serves `try_files /wp-content/cache/supercache/$http_host/$cache_uri/index.html $uri $uri/ /index.php?$args;` after clearing `$cache_uri` for POST, query strings, admin/login/feed/sitemap URLs and the cookies `comment_author|wordpress_[a-f0-9]+|wp-postpass|wordpress_logged_in`; W3 Total Cache serves `/wp-content/w3tc/pgcache/$cache_uri/_index.html` (multisite variants include `$host` and a captured blog segment); nginx `fastcgi_cache` with a `/purge(/.*)` location and the Nginx Helper plugin — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- WP Rocket "will work out of the box on NGINX servers"; its nginx configuration is optional and supplies what `.htaccess` gives on Apache/LiteSpeed — [WP Rocket docs](https://docs.wp-rocket.me/article/37-nginx-configuration-for-wp-rocket) (search snippet). Rocket-Nginx is a separate community project; one host calls it "use at your own risk" — [GridPane KB](https://gridpane.com/kb/wp-rocket-and-rocket-nginx-caching-on-gridpane/) (search snippet).
- LiteSpeed Cache's page cache needs LiteSpeed Enterprise (5.0.10+), OpenLiteSpeed (1.4.17+), WebADC (2.0+) or QUIC.cloud CDN; its general optimisation features run on any server — [LiteSpeed Cache FAQ](https://wordpress.org/plugins/litespeed-cache/faq/) (search snippet).

- **Strapi 5**: `proxy.koa` replaced v4's `proxy: true`; admin login breaks behind HTTPS proxies on 5.24+ without it — [Strapi support](https://support.strapi.io/articles/1276365193-how-to-fix-admin-panel-login-issues-in-strapi-v5-behind-reverse-proxies) (search snippet).
- **Uptime Kuma**: WebSocket required, sub-paths unsupported — [Uptime Kuma wiki](https://github.com/louislam/uptime-kuma/wiki/Reverse-Proxy).
- **n8n**: `N8N_WEBHOOK_URL` (replaces `WEBHOOK_URL`), `N8N_PROXY_HOPS` — [n8n docs](https://docs.n8n.io/hosting/configuration/configuration-examples/webhook-url/).
- **Vaultwarden**: `IP_HEADER`; optional restriction of `/admin` — [Vaultwarden wiki](https://github.com/dani-garcia/vaultwarden/wiki/Proxy-examples).
- **Grafana**: `root_url`, `serve_from_sub_path`, `proxy_set_header Host $host` — [Grafana tutorial](https://grafana.com/tutorials/run-grafana-behind-a-proxy/).
- **Gitea / Forgejo**: container registry always at `/v2`; sub-paths discouraged (Forgejo: they "weaken browser same-origin protections"); the proxy may serve `public/` assets directly; unix socket and FastCGI listeners exist — [Gitea](https://docs.gitea.com/administration/reverse-proxies), [Forgejo](https://forgejo.org/docs/latest/admin/setup/reverse-proxy/).
- **Jellyfin**: security headers suggested with a warning that `Permissions-Policy` may break clients — [Jellyfin nginx](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/nginx).
- **Home Assistant**: "Don't cache 404 responses, HTML pages, service worker files, or `/api/` and `/auth/` responses"; default port 80 on HAOS from 2026.8, 8123 in the container — [Home Assistant http](https://www.home-assistant.io/integrations/http/).
- **Mastodon**: `proxy_cache` for the app (200 for 7 d, 410 for 24 h, stale on errors), `error_page 404 500 501 502 503 504 /500.html`, HSTS — [Mastodon nginx.conf](https://raw.githubusercontent.com/mastodon/mastodon/main/dist/nginx.conf).
- **Synapse**: proxy `/_matrix` and `/_synapse/client`; `/_synapse/admin` not to be exposed without reason; incompatible with `mod_security2` — [Synapse](https://element-hq.github.io/synapse/latest/reverse_proxy.html).
- **Plausible CE / Umami**: Plausible needs no proxy since v2.1.2 (built-in Let's Encrypt); its nginx and Apache examples are "community-contributed and untested by maintainers" — [Plausible CE wiki](https://github.com/plausible/community-edition/wiki/reverse-proxy). Umami: `CLIENT_IP_HEADER`, `BASE_PATH` (needs a rebuild) — [Umami environment variables](https://umami.is/docs/environment-variables) (search snippet).

### Inferences
- A server that implements these eleven general features covers the stated needs of nearly every application above; what remains is application-specific URL rewriting (key question 2).
- `X-Accel-Buffering: no` is the one response header several unrelated projects (Next.js, Drupal BigPipe, Nextcloud) emit to steer a proxy; honouring it for proxied and FastCGI answers gives those applications streaming without configuration.
- Internal redirect has two dialects a server must both speak to be drop-in: the response header (`X-Accel-Redirect: /internal/path`, Moodle, WooCommerce) and the negotiated form where the proxy announces `X-Sendfile-Type` and `X-Accel-Mapping` in the request (Rack::Sendfile for Rails and Discourse, Symfony's BinaryFileResponse).
- "Raw target pass-through" and "merge duplicate slashes" pull in opposite directions: filesystem-backed applications want normalisation, proxied Git forges and Matrix want none. The setting has to be per location kind.
- Nextcloud's `^/(?:\.|autotest|occ|issue|indie|db_|console)` and Matomo's `^/(config|tmp|core|lang)` are string prefixes, not path-segment prefixes; a segment-bounded prefix matcher expresses a slightly narrower rule, which is still safe because the unmatched remainder falls through to the front controller or a 404.
- The applications disagree on request buffering (Nextcloud on, Immich off), so it must be a per-location choice, with "on" the safe default for FastCGI.

Read the page before quoting either wording.

## Key question 2: Which applications need something a server without regular-expression rewrites or .htaccess support cannot express with prefix/exact/suffix locations and try_files, and what exactly?

### Takeaway
Most applications need no regular expression once a server has a front-controller fallback, a PHP entry-point whitelist, path-info, and glob-style refusals. The real exceptions are few and specific: WordPress multisite in subdirectory mode, the file-based page caches (WP Super Cache, W3 Total Cache, Statamic full measure), PrestaShop's image URLs and web-service path, Magento's versioned static path and its `static.php`/`get.php` fallbacks, and (optionally) TYPO3 and Joomla hardening rules.

### Cited Findings
- **WordPress multisite, subdirectory mode**: needs the first path segment removed before `wp-*` paths and before any `.php`: `rewrite ^(/[^/]+)?(/wp-.*) $2 last;` and `rewrite ^(/[^/]+)?(/.*\.php) $2 last;`, plus `rewrite /wp-admin$ $scheme://$host$request_uri/ permanent;`. Subdomain mode needs only a wildcard server name — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- **WP Super Cache / W3 Total Cache served without PHP**: a `try_files` target built from the host and the request path (`/wp-content/cache/supercache/$http_host/$cache_uri/index.html`), skipped for POST, any query string, a list of URL patterns and four cookie-name patterns — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/). Both plugins also work with PHP serving the cached file; WP Rocket states the same for itself — [WP Rocket docs](https://docs.wp-rocket.me/article/37-nginx-configuration-for-wp-rocket) (search snippet).
- **Statamic full-measure static caching**: a `try_files` target composed of path, an underscore, the query string and `.html` (`/static${uri}_$args.html`), optionally the host, for GET only, with a query-argument test for background recaching; the half measure needs nothing from the server — [Statamic static caching](https://statamic.dev/static-caching).
- **PrestaShop 9**: product image URLs carry the image id as digits and are rewritten to nested directories (`/img/p/$1/$1$2.$3` and seven longer variants), category images (`/img/c/$1.$2`), `^/api/?(.*)$` → `/webservice/dispatcher.php?url=$1`; all need capture groups — [PrestaShop 9 nginx](https://devdocs.prestashop-project.org/9/basics/installation/advanced/nginx/).
- **Magento 2.4**: `rewrite ^/static/version\d*/(.*)$ /static/$1 last;` (a variable-length version segment removed), missing static files rewritten to `/static.php?resource=<captured path>`, missing media to `/get.php`; negative lookahead `^/setup/(?!pub/).` — [Magento nginx.conf.sample](https://raw.githubusercontent.com/magento/magento2/2.4-develop/nginx.conf.sample).
- **October CMS / Winter CMS**: the catch-all is an unconditional rewrite to `/index.php` (existing files are *not* served unless whitelisted) and the whitelist has wildcards in the middle of paths (`^/plugins/.*/.*/(assets|resources)`); the documented alternative is the mirrored `public/` docroot, which needs neither — [October CMS 4.x](https://docs.octobercms.com/4.x/setup/web-server-config.html), [Winter CMS](https://wintercms.com/docs/v1.2/docs/setup/configuration).
- **Drupal**: the rules that look like regex are globs in substance — PHP refused in any subdirectory but `core/`, `sites/*/files/**/*.php`, `sites/*/private/`, endings and file names anywhere; the image-style and `/system/files/` rules are ordinary fallbacks to `index.php`. The one true rewrite is optional: the redirect from `…/index.php/path` to the clean URL — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess), [Drupal nginx recipe](https://nginx-wiki.getpagespeed.com/config/recipes/drupal).
- **Nextcloud**: no captures are needed, but three forms beyond plain `try_files`: a fallback that appends the original request URI as path info (`/index.php$request_uri`), a PHP whitelist where every *other* `.php` request is also sent to that fallback rather than refused, and a header that depends on a query argument (`immutable` only with `?v=`) — [Nextcloud nginx](https://docs.nextcloud.com/server/latest/admin_manual/installation/nginx.html).
- **phpBB**: fallback to `/index.php/$1` (path info) and a deny with a lookbehind so `ext/phpbb…` stays reachable — [phpBB nginx.sample.conf](https://raw.githubusercontent.com/phpbb/phpbb/master/phpBB/docs/nginx.sample.conf).
- **MediaWiki**: `/wiki/…` is sent to `/w/index.php` with no capture used (MediaWiki reads the request URI), so a prefix location with a fixed fallback script expresses it — [MediaWiki Short URL/Nginx](https://www.mediawiki.org/wiki/Manual:Short_URL/Nginx).
- **Joomla**: the exploit filters are regular expressions over the query string, one case-insensitive; routing itself is a plain front controller plus a second one for `/api/` — [Joomla htaccess.txt](https://raw.githubusercontent.com/joomla/joomla-cms/5.4-dev/htaccess.txt).
- **TYPO3**: community rules have a wildcard segment in the middle (`(?:typo3conf/ext|typo3/sysext|typo3/ext)/[^/]+/(?:Configuration|Resources/Private|Tests?|Documentation|docs?)/`) — [TYPO3 forum pattern via search](https://docs.typo3.org/m/typo3/reference-coreapi/14.3/en-us/Security/GuidelinesAdministrators/RestrictAccessToFiles.html) (search snippet, community-derived).
- **Laravel, Symfony, CodeIgniter, CakePHP, Yii, Matomo, Moodle, Kanboard, Grav**: their official nginx configurations use regex syntax only for things a prefix, an exact match, a suffix or a name pattern states equally: `^/index\.php(/|$)`, `\.php$`, `/\.(?!well-known)`, lists of entry scripts, lists of directories — [Laravel](https://laravel.com/docs/deployment), [Symfony](https://symfony.com/doc/current/setup/web_server_configuration.html), [CodeIgniter](https://codeigniter.com/user_guide/installation/running.html), [CakePHP](https://book.cakephp.org/5/en/installation.html), [Yii](https://www.yiiframework.com/doc/guide/2.0/en/start-installation), [Matomo](https://raw.githubusercontent.com/matomo-org/matomo-nginx/master/sites-available/matomo.conf), [Moodle](https://docs.moodle.org/en/Nginx).
- **Case-insensitive matching** appears in WordPress (`~* /(?:uploads|files)/.*\.php$`), Magento (`~* ^/setup($|/)`, extension lists), Matomo (`~* ^.+\.php$`) and Grav's asset rules — [WordPress](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/), [Magento](https://raw.githubusercontent.com/magento/magento2/2.4-develop/nginx.conf.sample), [Matomo](https://raw.githubusercontent.com/matomo-org/matomo-nginx/master/sites-available/matomo.conf), [Grav](https://learn.getgrav.org/17/webservers-hosting/servers/nginx).
- **Proxied applications** need no rewriting at all; their sub-path variants use prefix stripping (`rewrite ^/grafana/(.*) /$1 break;`, kamal-proxy `strip_path_prefix`, Caddy `handle_path`) — [Grafana](https://grafana.com/tutorials/run-grafana-behind-a-proxy/), [Kamal proxy](https://kamal-deploy.org/docs/configuration/proxy/), [notify_push](https://github.com/nextcloud/notify_push).

### Inferences
- Five typed primitives would close almost all of the gap without a regex engine: (1) "strip one leading path segment" for WordPress multisite; (2) a `try_files` target assembled from host, path and query string with method and cookie conditions, for the file-based page caches; (3) a fallback that carries the request path as path info or as one query parameter (`/index.php$request_uri`, `/static.php?resource=…`, `dispatcher.php?url=…`); (4) removal of a variable segment matching a simple class (`version\d*`); (5) prefix stripping for proxies.
- PrestaShop's image URLs are the one case that genuinely needs capture-and-substitute (digit explosion into nested directories). Without it the shop's product images 404 on friendly URLs; it would need either a regex rewrite or a PrestaShop-specific rule in a preset.
- Magento and PrestaShop are therefore the two mainstream applications a server limited to prefix/exact/suffix locations and `try_files` cannot host from their official configuration; WordPress multisite in subdirectory mode and the "no PHP" modes of the page-cache plugins are the WordPress cases; everything else on the list is expressible.
- Regex lookarounds in the official files (`(?!well-known)`, `(?<!ext/)phpbb`, `(?!pub/)`) are all "deny X except Y"; an allow-exception on a refusal rule states them.
- Query-string exploit filters (Joomla) are optional hardening from the Apache era; no other application examined ships them.

### Gaps
- Not verified by running any of these applications; the classification is from reading the official configurations.
- Whether current PrestaShop 9 still emits the digit-style image URLs by default (rather than routing them through PHP) was not checked beyond the presence of the rules in the 9 documentation.
- TYPO3's static-file versioning rewrite (file name with an embedded timestamp) is believed to need a capture, but the official rule text was not retrieved.
- Shopware, Mautic, Contao, Flarum and other applications that panels ship templates for were outside the list and not examined.

## Key question 4: For WordPress, Laravel and Drupal, what would maintainers or documentation teams check when reviewing a new web server's preset?

### Takeaway
Each project's own documentation implies a checklist: WordPress reviewers would look for permalinks, no PHP in uploads, protected include-only files and `wp-config.php`, multisite, an `admin-ajax.php` exception under any `/wp-admin` protection, upload size, and page-cache compatibility; Laravel's for a `public/` docroot where only `index.php` runs, dot files refused except `.well-known`, the two security headers, and proxying for Octane and Reverb; Drupal's for everything its `.htaccess` does, since the project states the administrator is responsible for recreating it elsewhere. The places to ask are the WordPress Hosting Team (`#hosting` Slack, hosting-handbook GitHub), Laravel's Discord and GitHub Discussions, and Drupal Slack (`#support`, `#documentation`) plus the core issue queue.

### Cited Findings

#### WordPress
- Permalinks through `try_files $uri $uri/ /index.php?$args;`, with `$args` kept — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- PHP refused under any `uploads` or `files` directory, verified by uploading a test file; hidden files refused — [same page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- Include-only files refused: `wp-admin/includes/`, `wp-includes/*.php` (top level), `wp-includes/js/tinymce/langs/*.php`, `wp-includes/theme-compat/`; `wp-config.php` denied; an exception for `ms-files.php` on multisite — [WordPress hardening](https://developer.wordpress.org/advanced-administration/security/hardening/).
- A password or address rule on `/wp-admin/` must leave `wp-admin/admin-ajax.php` reachable — [WordPress hardening](https://developer.wordpress.org/advanced-administration/security/hardening/).
- Multisite: the subdirectory rewrites and the `/wp-admin` trailing-slash redirect; wildcard names for subdomain mode — [WordPress nginx page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- Page caches: either the plugin's file layout is served directly with its bypass conditions (POST, query string, the four cookie patterns, admin/login/feed/sitemap URLs) or the plugin runs through PHP; a server-side cache needs a purge the plugin can call (Nginx Helper for `fastcgi_cache`), and only 200 responses cached so redirects of multilingual sites are not — [same page](https://developer.wordpress.org/advanced-administration/server/web-server/nginx/).
- LiteSpeed Cache will not page-cache on another server — [LiteSpeed Cache FAQ](https://wordpress.org/plugins/litespeed-cache/faq/) (search snippet).
- WooCommerce: `woocommerce_uploads` refused to direct requests and served only through the internal redirect — [WooCommerce developer docs](https://developer.woocommerce.com/docs/code-snippets/using_nginx_server_to_protect_your_uploads_directory/) (search snippet).
- Environment: PHP 8.4+ recommended, the extension list, ImageMagick 7.1+, Ghostscript 10+ — [Hosting handbook](https://make.wordpress.org/hosting/handbook/server-environment/).
- Upload size at the server as well as in PHP (413) — [Kinsta](https://kinsta.com/blog/413-request-entity-too-large-error/) (third-party, search snippet).

#### Laravel
- Document root `public/`, every request to `public/index.php`, and nothing else executed: `location ~ ^/index\.php(/|$)` then `location ~ \.php$ { return 404; }` — [Laravel deployment](https://laravel.com/docs/deployment).
- `.env` and other dot files refused, `.well-known` open: `location ~ /\.(?!well-known).* { deny all; }` — [Laravel deployment](https://laravel.com/docs/deployment).

- Process supervision for queue workers, Reverb and Octane, and `php artisan reload` on deploy — [Laravel deployment](https://laravel.com/docs/deployment).

#### Drupal
- "Some security features exist only for Apache through `.htaccess`. You are responsible for recreating these features when not using Apache" — [Drupal web server requirements](https://www.drupal.org/docs/getting-started/system-requirements/web-server-requirements).
- The protected endings and names of the `FilesMatch` (twig, yml, module, inc, install, sql, composer files, `web.config`, editor backups) — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess).
- PHP only in the root and directly in `core/`; `autoload.php` refused; `core/install.php` and `core/rebuild.php` reachable, `update.php` with path info — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess), [Drupal nginx recipe](https://nginx-wiki.getpagespeed.com/config/recipes/drupal).
- Public files (`sites/*/files`): served, never executed, no listings; private files: no direct access; `/system/files/` and image-style derivatives fall back to Drupal — [FileSecurity.php](https://raw.githubusercontent.com/drupal/drupal/11.x/core/lib/Drupal/Component/FileSecurity/FileSecurity.php), [Drupal nginx recipe](https://nginx-wiki.getpagespeed.com/config/recipes/drupal).
- Dot paths refused except `.well-known`; `X-Content-Type-Options nosniff`; the `Proxy` request header removed; `Authorization` passed to PHP — [Drupal .htaccess](https://raw.githubusercontent.com/drupal/drupal/11.x/.htaccess).

The long-running core issue for an nginx example is the existing place where a server configuration for Drupal is discussed — [#2937161](https://www.drupal.org/node/2937161) (search snippet).

### Inferences
- For all three projects, the review is easiest to pass when the preset is presented as a line-by-line mapping of the project's own file (WordPress's nginx page and hardening page, Laravel's nginx block, Drupal's `.htaccess`), since those are what reviewers know.
- WordPress has the only documentation with a team (Hosting) whose remit is server environments and a handbook open to pull requests; it is the most realistic place to get a new server listed. Laravel's page lists only nginx and FrankenPHP and promotes its own platforms, so a listing there is unlikely; a review is more realistic through Discord or GitHub Discussions. Drupal has no official nginx file at all, so a new server would be reviewed against `.htaccess`, most likely in Slack or the core issue.
- xmlrpc.php, `wp-config.php` backups and `readme.html` are not covered by WordPress's official pages; they come from host practice (HestiaCP ships "disable-xmlrpc" WordPress templates). A preset that refuses them goes beyond the documentation and should say so.
- Drupal's `update.php/selection` and Nextcloud-style path info are the items most likely to fail in a first review of a server whose PHP handling checks that the full path is a file.

### Gaps
- No maintainer or documentation-team statement was found that describes a review procedure for third-party server presets in any of the three projects; the checklists are derived from their published configurations.
- WordPress's official position on `xmlrpc.php` blocking and on `wp-cron` versus system cron was not found on the pages read.
- The Drupal Slack page does not list a hosting or web-server channel; whether one exists was not established.
- The current Laravel Discord invite and the state of the Laracasts and Laravel.io forums were not verified directly.
- The current status of Drupal issue #2937161 (whether an example nginx file has landed in core) was not opened and should be checked before citing it as open.
